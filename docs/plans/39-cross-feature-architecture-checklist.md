# T03~T08 남은 공통 아키텍처 선택

2026-11-13 설계 검토안. 오늘은 아키텍처 설계만 진행하고 구현·실제 검증은 내일 한다. T02 체크리스트 10항목과 기존 ADR의 기능 정책은 재질문하지 않는다. 사용자 선택은 R1A·R2A·R3A·R4A·R5A로 5묶음 모두 선택했다. 세부 기술 계약·검증 계획은 후속 구체화하며 앱 형태와 운영 서비스 선택을 자동 확정하지 않는다.

연결 문서: [설계 마무리 계획](39-design-completion-plan.md), [T02 아키텍처](39-t02-personal-data-architecture.md), [방/전환 경계 검토안](39-account-transition-contract.md).

## 유지하는 기존 정책

- 방은 마지막 연결 종료 후 60초 유예, 일반 참여자 퇴장·방장 종료, 복수 연결이 남으면 참여 유지. 참여 요청 진행·응답 불명·유예 중 계정 전환 금지.
- 닉네임은 공백 정리 후 2~20자·한글/영문/숫자/공백·활성 사용자 간 중복 방지. 프로필 편집 여부와 원본 생성 시점 보존.
- 사진은 개발용 로컬 저장, JPG/PNG/WebP·5MB·실제 내용 검증, 안전한 파일명과 참조 확인, 실패 시 이전 이미지 유지.
- UUID 이관은 원본·카카오 인증을 함께 확인하고 계정별로 기록을 무손실 병합한다. 원본 ID·일시·평가 순서와 가장 오래된 UUID의 프로필 출처를 보존하며 기존/직접 편집 카카오 프로필을 우선한다.
- 로그아웃은 해당 브라우저 인증을 종료하고 새 UUID로 시작한다. 카카오 기록은 보존한다. 작업 키나 공개 UUID만으로 다른 사용자 기록·인증을 가져오지 않는다.

## R1. 방 실시간 연결을 관리할 서버 구조

- [x] **R1A — 단일 API 프로세스부터 설계(추천).** 현재처럼 연결 객체는 그 프로세스 메모리에 두고 참여·만료·유예 상태는 DB에 저장한다. 장점: 기존 구조와 로컬 개발 환경에 맞고 추가 메시지 시스템이 없다. 비용: 여러 API 프로세스/인스턴스를 동시에 띄우는 구조는 지원하지 않으며 재시작 시 연결 복구 설계가 필요하다.
- [ ] **R1B — 여러 API 프로세스의 연결·이벤트를 공유하도록 설계.** 장점: 프로세스를 나눠 부하 분산과 독립 재시작을 할 수 있다. 비용: 프로세스 간 이벤트 전달, 연결 생존 확인, 정리 작업 소유권·중복 처리가 필요하다. Redis 등은 가능한 구현 후보일 뿐 특정 외부 서비스를 이 선택만으로 생성하지 않는다.

현재 `RoomConnectionManager`는 단일 worker의 메모리 구조다. [FastAPI WebSocket 예제](https://fastapi.tiangolo.com/advanced/websockets/)도 메모리 연결 목록의 단일 프로세스 한계를 명시한다. R1A 선택을 전체 운영 배포 승인으로 해석하지 않는다.

### R1 추가 설명 — R1A 선택

- 사용자 확인: 현재 서버 RAM은 1GB이며 백엔드와 MySQL을 같은 서버에서 실행한다. 사용자가 R1A 단일 API 프로세스를 선택했다. 실제 운영 메모리·CPU·worker 수는 측정하지 않았고 운영 설정을 변경하지 않았다.
- 같은 1GB 안에서 B를 실행하면 API 프로세스마다 앱·모델·연결 풀 등이 추가될 수 있고 메시지 시스템도 함께 두면 추가 자원이 필요하다. RAM 증설이나 별도 서버 없이 프로세스 수만 늘리는 것은 자원 용량을 늘리는 일이 아니다. 메모리 압박에 따른 지연·프로세스 종료 가능성이 있으나 실제 발생 여부와 처리 인원은 미검증이다. [FastAPI 메모리 설명](https://fastapi.tiangolo.com/deployment/concepts/#memory-per-process)을 참고한다.
- DB가 같은 RAM을 사용하므로 OS·MySQL·백엔드·연결 수·이미지 처리·모델 추론의 최대 사용량을 함께 측정해야 한다. 앞서 승인한 주기적 모델 학습을 HTTP 요청 밖에서 한다는 정책만으로 같은 서버의 별도 학습 프로세스가 안전해지는 것은 아니다. 학습 실행 위치·자원 한도는 후속 기술 계약에서 구체화하고 별도 유료 자원을 자동 도입하지 않는다.
- 프로세스는 실행 중인 서버 프로그램 하나다. 물리 서버 한 대에서도 여러 프로세스를 실행할 수 있다. A에서도 한 프로그램이 여러 사용자의 연결을 동시에 관리한다. 지원 인원은 부하 측정 전 확정할 수 없다.
- A의 흐름: 철수와 영희가 같은 프로그램에 연결 → 철수 선택을 DB에 저장 → 그 프로그램이 가진 영희 연결로 변경 소식을 전송한다. 연결 객체는 메모리, 방 참여·선택·유예 같은 지속 상태는 DB가 맡는다.
- B의 흐름: 철수는 프로그램 1, 영희는 프로그램 2에 연결 → 선택은 공유 DB에 저장 → 프로그램 사이에 변경 이벤트 전달 → 각 프로그램이 자신이 가진 연결로 전송한다. 실제 소켓 자체를 Redis나 DB로 옮기는 방식은 아니다. DB 공유나 사용자별 고정 라우팅만으로 다른 프로세스의 방 참여자에게 실시간 이벤트가 전달되지는 않는다.
- A의 비용은 재시작 시 모든 연결이 끊기고 한 프로세스 한계에서 부하를 나눌 수 없다는 점이다. B는 장애 난 프로세스의 연결도 재접속해야 하지만 다른 프로세스 연결을 유지할 여지가 있다. 공유 DB·메시지 시스템이 실패하면 B도 영향을 받는다.
- B에서는 마지막 연결 여부를 전체 프로세스 기준으로 확인해야 한다. 프로세스 사망 시 정상 종료 알림이 없으므로 생존 확인·만료 기준이 필요하고, 60초 유예 정리 중복 실행도 막아야 한다. 재시작 복구의 정확한 상태·시각 계약은 두 방식 모두 후속 기술 설계 대상이다.
- Redis Pub/Sub은 가능한 이벤트 전달 수단이지만 [공식 문서](https://redis.io/docs/latest/develop/pubsub/)상 연결 단절 등으로 메시지를 놓칠 수 있다. DB 상태 재조회와 이벤트 유실/재접속 처리가 별도로 필요하다. B가 자동으로 더 빠르거나 무중단이 되는 것은 아니다.
- A는 추가 시스템·관측 지점이 적고 B는 분산 부하·다중 CPU 활용 여지가 크지만 메시지 시스템·생존 확인·중복/순서·장애 테스트 비용이 늘어난다. A에서 B로 바꿀 때 방 비즈니스 규칙은 유지하고 연결 관리·이벤트 전달·생존 확인을 확장하도록 책임을 분리하는 것을 추천한다. 이는 B 구현 승인이나 추상화 프레임워크 도입을 뜻하지 않는다.

## R2. 카카오 연결·로그아웃 성공 응답이 유실될 때의 복구

- [x] **R2A — 준비와 확정의 두 단계 전환(추천).** 기존 인증을 종료하기 전에 다음 인증용 비밀값을 별도 보호 쿠키로 받아 두고, 확정 요청에서 받은 사실을 증명한다. 이관·인증 교체는 한 DB 트랜잭션으로 확정하고 같은 작업·비밀값으로 결과를 복원한다. 장점: 서버에 비밀 원문을 보관하지 않아도 응답 유실 복구 근거를 만들 수 있다. 비용: 추가 요청·쿠키·전환 작업 상태와 정리가 필요하다.
- [ ] **R2B — 한 요청으로 전환하고 복원 불가 시 카카오 재인증.** 장점: 정상 경로의 요청 수·전환 준비 상태가 줄어든다. 비용: 서버는 성공했는데 새 쿠키를 받지 못한 경우 다시 카카오 인증이 필요할 수 있다. 기록은 한 번만 옮기고 작업 번호만으로 새 인증을 발급하지 않는다. 복구용 재인증 경로는 별도로 설계해야 한다.

R2는 브라우저가 공유하는 기존 보호 쿠키 경로의 설계다. 모든 미래 앱의 쿠키 사용을 확정하지 않는다. [Stripe의 멱등 요청](https://docs.stripe.com/api/idempotent_requests)은 중복 실행 방지의 참고 사례이며 Stripe가 위 두 단계 쿠키 전환을 사용한다는 뜻은 아니다. 세부 비교는 [전환 경계 §5](39-account-transition-contract.md)를 따른다.

## R3. 이관한 원본 UUID를 DB에서 어떻게 폐기할까

- [x] **R3A — 기록·참조·인증 정리 후 원본 사용자 행 삭제.** 장점: 활동할 수 없는 사용자 행을 계속 보관하지 않고 폐기 의미가 명확하다. 비용: 인증·방·작업 결과 등의 FK를 모두 안전하게 정리하고 재시도 복구용 최소 문맥을 별도로 보존해야 한다. 관련 참조가 남았으면 부분 삭제하지 않고 롤백한다.
- [ ] **R3B — 인증과 사용을 막은 이관 완료 표식으로 보관.** 원본은 활성 사용자가 아니며 기록은 카카오 사용자에게 이동한다. 장점: 이관·이전 요청 추적과 남은 참조를 다루기 쉽다. 비용: 모든 활성 사용자 조회·인증·닉네임 유일성에서 비활성 원본을 구분하고 이후 정리 정책을 관리해야 한다.

둘 다 원본 UUID로 로그인·복원·쓰기 또는 방 이용을 허용하지 않는다. R3B는 원본 UUID를 대표 사용자로 남기는 방식이 아니다. 기존 ADR의 '폐기'를 물리 삭제로 할지 비활성화로 할지 명확히 하는 결정이며 아직 필드·마이그레이션을 추가하지 않았다.

2026-11-13 사용자 선택: **R3A 원본 사용자 행 삭제**. 기록·프로필 출처를 대상에 보존하고 원본 인증 및 FK를 정리한 뒤 같은 이관 트랜잭션에서 사용자 행을 삭제한다. R2A 복구 작업은 원본 사용자 행의 존속에 의존하지 않아야 하며 최소 작업 문맥·대상 인증 연결을 별도로 보존한다. 비활성 사용자 보관은 채택하지 않는다. 실제 마이그레이션·DB 삭제는 아직 수행하지 않았다.

## R4. 현재 웹에서 다른 탭의 계정 전환을 알게 된 경우

- [x] **R4A — 탭 알림과 인증 문맥 재확인을 함께 사용(추천).** 다른 탭에 변경 힌트를 보내고 이전 사용자의 새 쓰기를 보류하며 서버에서 현재 인증을 확인한 뒤 화면을 교체한다. 늦게 도착한 이전 사용자 응답은 새 화면에 적용하지 않는다. 장점: 다른 탭이 빨리 상태를 정리할 수 있다. 비용: 탭별 상태·진행 요청·알림 누락 처리가 추가된다.
- [ ] **R4B — 탭 알림 없이 복귀·요청 시 서버 인증을 재확인.** 장점: 프론트의 탭 통신을 줄일 수 있다. 비용: 다음 확인 전까지 이전 화면이 남을 수 있고 확인 지점·안내 처리가 필요하다. 늦은 응답 검사와 잘못된 사용자로 이전 요청을 재실행하지 않는 규칙은 그대로 필요하다.

어느 쪽이든 서버 인가·현재 인증 비교가 필요하며 알림을 인증 증거로 쓰지 않는다. 다른 탭 전환 후 이전 식사/피드백 요청을 새 사용자로 자동 재생하지 않는다. 이 선택만으로 모든 탭이 처음부터 같은 사용자를 가져야 한다거나 자동 병합된다고 정하지 않는다. 탭이 없는 앱에 탭 통신을 요구하지 않는다.

## R5. 새로 업로드한 프로필 사진을 조회할 방식

- [x] **R5A — 주소를 알면 조회 가능한 URL.** 장점: 일반 이미지 태그로 표시하고 캐시하기 쉽다. 비용: 링크가 전달되면 방 밖이나 인증 없는 사람도 조회할 수 있다. 긴 임의 파일명은 추측을 어렵게 하지만 접근 권한 검사를 대신하지 않는다.
- [ ] **R5B — 허용된 조회 응답에서 짧게 유효한 서명 URL 발급(추천).** 서버가 본인/허용된 방 조회에서 이미지 링크를 만들고 이미지 요청의 서명·만료를 검증한다. 장점: 로그인 헤더를 붙이기 어려운 이미지 표시에서도 링크의 유효기간을 제한할 수 있다. 비용: 서명·만료·갱신·캐시 설계가 늘고 링크를 가진 사람은 유효기간 동안 볼 수 있다. 정적 공개 디렉터리로 우회 접근하지 못하게 해야 한다.
- [ ] **R5C — 사진 요청마다 현재 인증과 본인/같은 방 참여 권한 확인(추가 제안).** 공개 정적 파일이나 전달 가능한 서명 링크 대신 보호 API가 이미지 바이트를 응답한다. 주소만 알아서는 사진을 받지 못한다. 장점: 현재 조회자의 권한으로 접근을 결정한다. 비용: 이미지별 인증·권한 조회, 프론트의 인증 헤더 포함 요청과 이미지 표시·메모리 정리, 비공개 캐시 처리가 필요하다. 승인·구현 전 제안이며 기존 A/B의 유일한 대안 제시를 보완한다.

현재 기본 SVG와 기존 카카오 외부 이미지의 공개 여부까지 바꾸는 선택은 아니다. 어느 방식이든 업로드 소유권·실제 이미지 검증·안전한 경로·파일 참조 보존은 유지한다. 운영 클라우드 저장소 도입은 범위 밖이다.

### R5 추가 설명 — R5A 선택

최신 사용자 선택: **R5A**. 업로드 사진의 조회 URL에는 JWT·방 참여 권한 검사·서명 만료를 적용하지 않는다. 앱 화면은 본인 프로필·방 참여자 표시로 한정하고 클릭·확대·공유 기능은 만들지 않는다. 업로드·교체·삭제의 본인 인증과 소유권 검사는 유지한다. 임의 파일명·안전한 저장 경로·실제 이미지 검증과 실패 시 이전 파일 보존도 유지한다. 주소 비노출이나 주소를 아는 외부인의 조회 차단을 보장한다고 표현하지 않는다. 아래 B/C는 비교 이력이며 채택하지 않았다.

사용자 명확화: 프로필 사진은 본인 화면과 방 참여 시 참여자 표시 용도로 사용한다. 사진 클릭·확대·상세 보기 기능은 만들지 않는다. 이 UI 범위는 확정된 요구이며 R5A/B의 링크 접근 정책 선택과 구분한다. 클릭 기능이 없어도 브라우저는 사진 표시를 위해 이미지 주소로 자동 요청하므로 URL 접근 제어는 별도로 필요하다. [MDN 이미지 요소](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img)를 참고한다. A/B 모두 동일한 비클릭 UI를 제공할 수 있고 B도 사용자가 사진을 클릭하거나 별도 인증 버튼을 누르는 과정은 없다.

R5는 업로드 후 사진을 내려받아 화면에 표시하는 권한이다. 둘 다 본인과 허용된 방 참여자의 화면에 같은 사진을 표시할 수 있다. A에서는 전달받은 고정 URL을 나중에도 열 수 있고, B에서는 서버가 조회 권한을 확인한 후 발급한 URL에 서명과 만료 시각을 붙인다. 예를 들어 10분짜리 링크라면 10분 이후 새 다운로드 요청은 거부하고 정상 화면은 권한 확인 후 새 링크를 받는다. 10분은 설명용이며 채택된 만료 시간이 아니다.

B의 만료는 새 접근을 제한하는 장치다. 이미 받은 이미지·저장한 파일·스크린샷을 지우거나 유효기간 안의 링크 전달을 막지는 못한다. [AWS 서명 URL](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html)도 권한 확인 후 서명 링크를 발급하고 만료를 검사한다. 이 원칙은 로컬 파일 응답에도 적용할 수 있으며 AWS 도입을 확정하지 않는다.

사용자 후속 명확화: 사진 주소를 외부에 배포하는 기능을 의도하지 않는다. 공유·클릭 기능을 전제로 설명하지 않는다. 브라우저가 사진을 받으려면 요청 위치를 알아야 하므로 주소 자체를 절대 알아낼 수 없다는 보장과 서버가 외부에 공개·공유하지 않는 요구를 구분한다. 주소만으로 외부 조회가 되지 않게 하려면 C처럼 실제 조회자의 권한을 검증할 수 있다. 웹 구현은 [Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)로 JWT를 헤더에 넣어 바이트를 받은 뒤 [Blob URL](https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static)로 표시하는 방식이 가능하다. 원본 저장 경로와 JWT는 URL에 넣지 않으며 계정/방 변경 시 이전 응답·이미지 상태를 정리한다. 이미 받은 사진의 재배포 방지는 보장하지 않는다. 사용자의 목적을 반영한 권장 제안은 R5C이며 아직 선택하지 않았다.

## 2026-11-13 사용자 선택 기록

- R1A: RAM 1GB·백엔드/MySQL 동시 실행 조건에서 단일 API 프로세스 채택. 실제 운영 설정·용량 검증은 미실행이다.
- R2A: 준비와 확정의 두 단계 전환 채택. 요청 경로·작업 수명·쿠키 경합 등 기술 계약은 후속 구체화한다.
- R3A: 이관 완료 후 원본 사용자 행 물리 삭제 채택. 데이터 무손실 보존·참조 정리·별도 복구 근거를 함께 설계한다.
- R4A: 탭 알림과 서버 인증 문맥 재확인 채택. 탭 메시지는 인증 증거로 쓰지 않는다.
- R5A: 주소를 알면 조회 가능한 URL 채택. 사진 클릭·확대·공유 UI는 만들지 않으며 업로드·교체·삭제의 본인 인증은 유지한다. R5B·R5C는 채택하지 않았다.

## 이 선택 후 묶어서 완성할 기술 설계

아래 범위의 초안을 [통합 구현 아키텍처](39-implementation-architecture.md)와 [T09 검증 계획](39-validation-and-handoff.md)에 작성했다. 추가 제품/자원 선택도 [M1A·M2A·M3A·M4A](39-final-design-choices.md)로 마쳤다. 실행 코드 적용이나 검증 완료로 해석하지 않는다.

- T02: 기존 값 대응의 check/apply/verify, 요청 DTO·오류, 재료 코드 매핑, 시점별 학습 특징·유효 라벨, 학습 데이터 분리·모델 검증·버전/복구·스케일 연결. 모델 성능을 실제 사용자 데이터 없이 검증됐다고 표시하지 않는다.
- T03: 사용자→인증→방→참여/작업 행의 일관된 잠금, 마지막 연결 판단·재시작 복구·정리 작업, 참여 요청의 멱등 키·상태 조회·취소 표식과 늦은 성공 방지. 단순 미참여 조회로 진행 중 요청이 실패했다고 단정하지 않는다.
- T04~T05: 프로필 출처와 필드별 직접 편집 상태, 유일 키 충돌·파일 저장/DB 커밋/참조 정리의 실패 경계.
- T06~T08: 이관 트랜잭션·중복 계정 생성 방지·원본/대상 잠금, 제외 합집합·100개 초과 보존·질문 순환 병합·프로필 우선순위, 인증 폐기와 원본 처리, 로그아웃 왕복.
- T09: 기존 카카오 DB 전환·재실행·충돌 중단, 전체 사용자 여정·경계·실패/동시성·REST/WS·MySQL·브라우저 검증의 설계와 내일 실행 순서.

최종 선택: `R1A, R2A, R3A, R4A, R5A`. 이 문서는 정책 선택과 설계 검토안이며 코드·DB·테스트 실행 변경은 없다.

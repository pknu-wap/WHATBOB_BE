### 최근에 먹은 메뉴

- 본인의 식사 기록을 최신순으로 보고, 음식 종류별로 가장 최근 기록을 골라 최대 6개를 표시한다. 치즈버거를 먹은 다음 불고기버거를 먹었다면 햄버거 종류는 불고기버거를 먹은 기록으로 한 번 표시한다. 최신 기록이 한 종류에 몰려 있으면 다른 종류가 있는 이전 기록까지 확인한다.
- 연결된 메뉴가 삭제된 식사 기록은 최근 메뉴 카드에서 제외한다. 개인 식사 기록 목록에는 저장된 `menu_name`으로 남는다. 현재 `GET /api/users/me/meals`는 개별 식사 기록을 `eaten_at` 내림차순과 같은 시각의 `id` 내림차순으로 반환한다. 홈의 최근 메뉴 목록은 별도 API로 제공한다. [식사 기록 API](../../app/users/router.py) · [식사 기록 조회](../../app/users/repository.py)
- 홈의 최근 메뉴는 식사 시각(`eaten_at`)이 조회 시각과 같거나 앞선 기록만 사용한다. 이 조건은 음식 종류별로 최신 기록을 고르고 6개로 제한하기 전에 적용한다. 같은 종류에 오늘 먹은 기록과 내일로 저장된 기록이 있다면 오늘 카드를 보여주며, 내일의 식사 시각부터는 그 기록이 표시 대상에 들어간다.
- 현재 식사 등록은 클라이언트가 보낸 `eaten_at`을 UTC로 저장하며, 값을 생략하면 서버의 현재 시각을 사용한다. 미래 시각도 기존 요청 모델의 검증을 통과하므로 홈에서는 조회 시각으로 표시 대상을 고른다. [식사 등록 요청 모델](../../app/users/schemas.py) · [식사 등록 처리](../../app/users/service.py)

### 요즘 인기 메뉴

- 인기 순위는 매일 한국시간 자정에 전날 하루치 식사 기록으로 계산한다. 실제 식사 시각(`eaten_at`)이 전날 자정 이상, 집계일 자정 미만인 기록을 사용한다. 예를 들어 11월 20일 자정에는 한국시간 11월 19일의 기록을 집계한다. `버거`와 `햄버거`는 한 음식 종류로 합산한다.
- 서버가 집계 시각을 놓치면 재시작 후 가장 최근에 놓친 집계 한 번만 실행한다. 해당 집계일의 전날 기록으로 계산한다. 인기 메뉴 API는 저장된 결과를 조회한다.
- 한 음식 종류를 먹은 사용자 수로 순위를 정한다. 같은 사용자가 같은 종류를 여러 번 먹어도 한 번만 센다. 사용자 수가 같으면 두 종류 중 가장 최근에 먹은 기록이 있는 쪽이 앞선다. 식사 시각까지 같으면 음식 종류의 고유 키 순으로 정렬하는 방식을 제안한다.
- 아직 실제 집계 순위를 보여준 적이 없고 기록 사용자가 5명 미만이면 #54 댓글의 음식 8종을 댓글 순서대로 보여준다. 집계 대상인 전날의 기록 사용자가 5명 이상이면 실제 집계 순위대로 최대 8종을 보여준다. 이후 집계에서 5명 미만이면 마지막으로 표시한 실제 인기 순위를 유지한다. 예를 들어 일요일 기록을 바탕으로 월요일에 실제 순위를 보여주고 월요일에 기록한 사용자가 4명이라면, 화요일 자정 집계 후에도 월요일에 표시한 순위를 계속 보여준다.
- 마지막 실제 인기 순위 한 벌은 MySQL에 저장한다. 5명을 채우지 못한 집계는 저장된 순위를 교체하지 않는다. 서버가 재시작한 뒤에도 같은 순위를 조회할 수 있어야 한다. [마지막 실제 인기 순위 보관 결정](../adr/0004-persist-last-popular-menu-ranking.md)
- 연결된 메뉴가 삭제된 식사 기록은 인기 순위와 전환 기준인 5명의 사용자 수 집계에서 제외한다.
- 저장된 실제 인기 순위를 보여줄 때 어떤 음식 종류에 속하는 메뉴가 모두 삭제됐으면 그 종류의 카드만 제외한다. 다른 카드의 상대 순서와 저장된 집계 기준 시각은 유지한다.

### 대표 일러스트

- 같은 음식 종류의 메뉴는 대표 일러스트 한 장을 공유한다. 사용할 그림이 없거나 대표 그림이 실제 메뉴와 크게 다르면 공통 이미지를 표시한다. 예를 들어 토마토 소스가 뚜렷한 파스타 그림을 크림 파스타에 쓰기 어렵다면 크림 파스타 카드에는 공통 이미지를 표시한다.
- 공통 이미지가 표시되는 메뉴도 원래 음식 종류로 묶는다. 예를 들어 크림 파스타 카드에 공통 이미지를 써도 크림 파스타와 토마토 파스타는 모두 파스타 집계에 들어간다.

## 구현 설계 제안

### #62 음식 종류 연결과 최근 메뉴 첫 카드

식사 기록은 ‘누가 언제 무엇을 먹었는지’ 적은 일기다. 메뉴는 ‘치즈버거’처럼 주문할 수 있는 항목이고, 음식 종류는 ‘햄버거’처럼 비슷한 메뉴를 모으는 이름표다. 치즈버거와 불고기버거는 서로 다른 메뉴이며 같은 햄버거 종류를 가리킨다. 이름표를 가리키는 번호를 저장하면 이름을 고쳐도 어느 종류에 속하는지 알 수 있다. 예시 번호와 이름은 구조를 설명하기 위한 값이다. [구현 티켓 #62](https://github.com/pknu-wap/WHATBOB_BE/issues/62)

| 데이터 | 예시 | 어디에 쓰는가 |
| --- | --- | --- |
| 식사 기록 `user_meals` | 사용자 5번이 오후 6시에 메뉴 101번을 먹음. 당시 이름은 치즈버거 | 본인이 먹은 시각과 당시 이름을 조회한다. |
| 메뉴 `menus` | 메뉴 101번은 치즈버거이고 원본 코드가 따로 있음. 메뉴 102번은 불고기버거 | 고유한 원본 코드 `food_code`로 기존 메뉴를 찾아 음식 종류를 연결한다. |
| 음식 종류 `food_kinds` | 종류 12번의 표시명은 햄버거. 메뉴 101번과 102번이 모두 12번을 가리킴 | 두 홈 목록이 같은 기준으로 메뉴를 묶는다. |

#### 기존 데이터에 종류를 연결하는 순서

1. 현재 DB에서 메뉴 코드와 `base_name`을 확인한다. `base_name`은 시드가 원본 이름의 첫 밑줄 앞부분을 떼어 만든 값이다. 예를 들어 `버거_치즈버거`에서는 `버거`가 남는다.
2. 음식 종류를 저장할 공간과 메뉴가 그 종류를 가리킬 칸을 만든다. 작업 중에는 이 칸이 비어 있을 수 있다. 종류 식별자를 정할 때는 표시명과 구분한다.
3. 정해 둔 별칭을 먼저 적용한다. `버거`와 `햄버거`를 하나의 햄버거 종류로 연결한다. 별칭이 없는 메뉴는 `base_name`으로 종류를 찾거나 새로 만든다. 운영 DB의 기존 메뉴는 `food_code`로 찾아 연결한다.
4. 기존 메뉴에서 종류가 비어 있는 칸을 채운다. 이 작업을 백필이라고 한다. 같은 방식으로 다시 실행해도 이미 연결된 메뉴와 수동 분류를 보존한다. 앞으로 CSV를 다시 읽는 시드도 동일한 분류 규칙을 사용해 새 메뉴나 미분류 메뉴를 연결한다.
5. 연결이 비었거나 존재하지 않는 종류를 가리키는 행이 없는지 확인한다. 대표 별칭이 합쳐졌는지, 같은 스크립트를 다시 실행해도 기존 ID와 식사 기록이 보존되는지 검증한다. 이후 `NOT NULL`은 빈 연결을 막고, 외래 키는 실제로 존재하는 음식 종류만 가리키도록 검사한다. 운영에서는 같은 점검 시간에 새 저장 경로를 배포하고 검증을 마친 뒤 관련 쓰기를 재개한다.

현재 시드는 이미 `food_code`로 기존 행을 찾고, 기존 메뉴의 원본 필드를 갱신한다. 종류 연결을 자동으로 덮어쓰면 수동 분류가 사라질 수 있으므로, 기존 원본 필드 갱신과 종류의 최초 연결을 별도 조건으로 다룬다. 기존 MySQL 마이그레이션처럼 재실행과 데이터 보존을 검증한다. [메뉴 시드](../../scripts/seed_menus.py) · [기존 MySQL 데이터 보존 검사](../../scripts/migrate_issue39.py)

현재 작업 트리의 식사용 CSV에는 서로 다른 `food_code` 7,503개가 있다. 그중 `base_name`이 정확히 `버거`인 280개와 `햄버거`인 105개에 별칭 규칙을 적용하면 385개 메뉴가 한 종류에 연결된다. 운영 DB에는 다른 메뉴가 있을 수 있으므로 배포 전 실제 입력과 별칭을 대조한다. [현재 식사용 CSV](../../data/menus_meals_only.csv)

백필 도중 멈추면 완료한 메뉴 연결을 남겨두고 빈 칸부터 다시 채운다. 종류가 비었거나 잘못 연결된 메뉴가 남아 있으면 제약 적용과 홈 카드 공개를 보류하고 원인을 수정한다. 기존 메뉴와 식사 기록은 ID와 저장된 이름을 비교해 보존을 확인한다.

#### 홈 요청이 첫 카드가 되는 순서

1. 프론트가 기존 Bearer 토큰을 붙여 `GET /api/users/me/home-card-recently-eaten-food-max-6`를 호출한다. 백엔드는 토큰으로 사용자 ID를 확인하고 기존 인증 실패 응답을 사용한다.
2. 백엔드는 조회 기준 시각을 한 번 정한다. 본인의 식사 기록에서 현재 카탈로그 메뉴와 연결되고 식사 시각이 조회 시각 이하인 기록만 고른다. 메뉴를 삭제하면 현재 DB는 식사 기록의 메뉴 연결을 비우고 당시 메뉴 이름은 보존한다.
3. 식사 시각이 최신인 순서로 비교하고, 같은 시각에는 식사 기록 ID가 큰 쪽을 먼저 잡는다. #62는 가장 앞의 한 건만 고른다.
4. 그 메뉴가 가리키는 음식 종류 ID와 식사 기록의 당시 이름·시각, 조회 가능한 공통 이미지 경로를 기존 `ApiResponse`로 반환한다. `Cache-Control: no-store`로 개인 카드의 응답을 캐시에 보관하지 않도록 한다. 보여줄 기록이 없으면 `items: []`를 반환한다.
5. 홈이 백엔드 기준 상대 경로의 공통 이미지를 읽고 첫 카드 또는 빈 상태를 표시한다. #63은 같은 요청과 응답 형식으로 종류별 최대 6개를 표시한다.

오후 8시에 조회할 때 본인 기록이 ‘오후 6시 치즈버거’, ‘오후 7시 삭제된 메뉴’, ‘내일 국밥’이면 오후 6시 치즈버거 카드가 뜬다. 같은 치즈버거 식사 기록을 저장한 다른 사용자가 있어도 토큰의 사용자에 속한 기록만 조회한다. [현재 메뉴 및 식사 기록 모델](../../app/menus/models.py) · [현재 인증 식사 기록 API](../../app/users/router.py)

#### 확정한 음식 종류 ID와 별칭 규칙

- 음식 종류에는 **숫자 ID**, **고유 문자열 키**, **표시명**을 둔다. 예를 들어 ID는 `12`, 키는 `burger`, 표시명은 `햄버거`다. 메뉴는 숫자 ID를 외래 키로 저장하고, 두 홈 API도 숫자 `food_kind_id`를 반환한다. 시드와 초기 인기 목록은 문자열 키로 해당 환경의 숫자 ID를 찾는다. 표시명을 변경해도 같은 ID와 키를 유지한다.
- **별칭은 저장소의 공용 규칙 파일**에서 관리하고, 백필과 메뉴 시드는 같은 파일을 읽는다. 예를 들어 원본 `base_name`이 `버거` 또는 `햄버거`이면 `burger` 키로 같은 종류를 찾는다. 규칙 변경은 리뷰와 배포를 거쳐 새 메뉴와 미분류 메뉴에 적용한다. 이미 분류된 메뉴를 옮길 때는 대상 메뉴를 확인한 뒤 별도 작업으로 연결을 변경한다.

#### 검토한 선택지와 비용

| 결정 | 선택지 | 얻는 점 | 부담과 검증할 점 |
| --- | --- | --- | --- |
| 음식 종류 식별자 | DB 숫자 ID와 고유한 문자열 키를 각각 둔다 | 메뉴에는 작은 숫자를 저장하고 초기 데이터는 읽기 쉬운 키로 찾는다. 표시명은 별도로 수정한다. | 번호와 키 두 값을 관리한다. 개발 DB와 운영 DB에서 숫자가 다를 수 있어 초기 데이터에는 문자열 키를 사용한다. |

#### 확정한 운영 DB 전환 방식

운영 DB는 한 번의 점검 시간에 관련 쓰기를 멈춘 뒤 전환한다. 메뉴 등록·수정·삭제와 CSV 시드를 멈추고, 구조 추가 → 백필 → 연결 검증 → 제약 적용 → 새 저장 경로 검증 순으로 진행한다. 검증을 마친 다음 쓰기를 재개한다. 운영과 비슷한 격리 DB에서 소요 시간과 잠금 범위를 확인하고, 그 영향에 맞춰 점검 시간을 잡는다.

MySQL은 온라인 구조 변경에서도 잠금이 필요한 단계가 있다고 문서화한다. ### #63 최근에 먹은 메뉴를 종류별 최대 6개로 표시

#62에서 연결한 숫자 `food_kind_id`를 기준으로 같은 음식 종류를 알아본다. 기존 최근 메뉴 API의 항목 구조를 사용하고, 최신 한 장을 고르는 동작을 최대 여섯 장으로 확장한다. [구현 티켓 #63](https://github.com/pknu-wap/WHATBOB_BE/issues/63)

#### 식사 기록을 카드로 바꾸는 순서

1. 기존 인증으로 본인 ID를 확인하고 조회 기준 시각을 한 번 정한다.
2. 본인이 기록한 식사 중 현재 카탈로그 메뉴가 있고 `eaten_at`이 기준 시각 이하인 기록을 찾는다. 미래 기록과 삭제된 메뉴 기록을 먼저 걸러내야 같은 종류의 유효한 옛 기록을 가리지 않는다.
3. 각 음식 종류에서 식사 시각이 가장 최근인 기록을 고른다. 두 기록의 식사 시각이 같으면 식사 기록 ID가 큰 쪽을 고른다.
4. 고른 기록을 최신순으로 최대 여섯 건 반환한다. 여섯 종류를 채울 때까지 더 오래된 기록도 대상에 포함된다.
5. 홈은 서버가 정한 순서대로 저장 당시 이름과 시각, 이미지가 들어간 카드를 그린다. 종류가 둘이면 두 장, 대상이 없으면 빈 상태를 표시한다. 개인 식사 기록 조회에서는 삭제된 메뉴의 저장 당시 이름도 계속 보인다. [기존 개인 식사 기록 조회](../../app/users/repository.py)

저녁 8시에 조회한다면 오후 7시의 불고기버거와 치즈버거가 같은 시각에 있어도 ID가 큰 한 장만 햄버거 종류를 대표한다. 밤 9시 햄버거 기록과 오후 7시 30분에 먹었으나 카탈로그에서 삭제된 메뉴의 기록은 후보에서 빠진다. 가장 최근 여섯 끼가 모두 햄버거여도 이전의 국밥, 떡볶이 등 다른 종류를 찾아 남은 자리를 채운다.

#### 확정한 조회 방식

홈은 최근 메뉴 API를 한 번 호출한다. 백엔드는 본인의 유효한 식사 기록을 `eaten_at` 내림차순과 식사 기록 ID 내림차순으로 DB에서 한 묶음씩 읽는다. 처음 본 음식 종류만 담으므로 담은 순서가 곧 카드 순서다.

여섯 종류를 채우기 전에 다음 묶음이 필요하면 마지막으로 읽은 식사 기록의 시각과 ID를 함께 기준으로 삼아 그 뒤부터 읽는다. 한 요청의 묶음들은 같은 조회 기준 시각과 일관된 DB 읽기 범위를 사용한다. 여섯 종류를 찾거나 기록을 다 읽으면 목록을 한 번 반환한다. 묶음 크기는 내부 설정이며, 읽을 전체 기록 수에 별도의 상한을 두지 않는다.

#### 검토한 조회 방식과 비용

| 선택지 | 처리 과정 | 얻는 점 | 부담과 검증할 점 |
| --- | --- | --- | --- |
| A. DB에서 종류별로 번호 매기기 | MySQL의 `ROW_NUMBER()`로 음식 종류마다 최신 기록에 1번을 매긴다. 1번끼리 다시 최신순으로 정렬해 최대 여섯 행을 받아온다. | 카드 데이터 조회 한 번에 끝나고 앱에 결과 행만 전달돼, 요청 중 앱과 DB가 여러 번 왕복할 필요가 없다. | 이력이 길면 DB가 대상 행을 묶고 정렬하는 비용이 생긴다. 운영과 비슷한 MySQL 데이터에서 조회 범위와 정렬 비용을 확인한다. |
| B. 앱이 최신 기록을 조금씩 읽으면서 고르기 | DB가 시간·ID 순서로 한 묶음씩 보내고 앱은 처음 본 종류만 모은다. 마지막 기록의 시간과 ID를 책갈피로 삼아 다음 묶음을 읽는다. 여섯 종류를 찾거나 이력이 끝나면 멈춘다. | 최근 기록에서 다양한 종류를 빨리 찾으면 오래된 기록까지 읽을 필요가 줄어든다. | 같은 종류가 오래 이어지면 DB에 여러 번 요청한다. 같은 시각의 행이 묶음 경계에서 빠지지 않도록 시간과 ID를 모두 사용한다. 한 요청이 여러 묶음을 읽는 동안 같은 DB 상태를 보도록 조회 범위를 잡는다. |

Google Cloud BigQuery 문서는 종류별로 행에 번호를 매겨 첫 행만 남기는 SQL을 설명한다. Shopify는 상품을 페이지 단위로 읽을 때 마지막 정렬 값과 ID를 함께 기억하는 커서를 운영 API에 적용했다. 같은 이름을 가진 상품도 다음 페이지에서 빠지지 않게 하는 방식이며, #63의 같은 식사 시각 처리에도 적용할 수 있다. [Google Cloud BigQuery의 그룹별 첫 행 예시](https://docs.cloud.google.com/bigquery/docs/migration/teradata-sql#qualify_rows_clauses) · [MySQL 윈도 함수](https://dev.mysql.com/doc/refman/8.0/en/window-functions-usage.html) · [Shopify 커서 페이지 조회](https://shopify.engineering/pagination-relative-cursors)

격리 SQLite 예제로 두 방식의 결과 순서가 같은지 확인했다. 검증에는 삭제, 미래 시각 직전과 도달, 같은 시각의 기록, 다른 사용자 격리, 최대 여섯 종류, 빈 목록, 같은 종류가 100건 연속인 사례를 사용했다. 구현 후에는 최근 기록이 다양한 사용자와 같은 종류를 연속으로 기록한 사용자의 DB 조회 횟수와 처리 시간을 운영에 가까운 MySQL에서 확인한다. 현재 식사 기록에는 사용자와 식사 시각을 묶은 인덱스가 있으므로 실행 계획을 확인하고 묶음 크기와 추가 인덱스의 필요성을 판단한다. [식사 기록 인덱스](../../app/menus/models.py)

### #64 초기 인기 메뉴 8종 공개

실제 인기 순위가 처음 발행되기 전에는 홈에 합의한 음식 종류 여덟 개를 정해진 순서대로 표시한다. #62에서 등록한 음식 종류와 숫자 ID를 사용한다. [구현 티켓 #64](https://github.com/pknu-wap/WHATBOB_BE/issues/64) · [초기 목록을 정한 #54 댓글](https://github.com/pknu-wap/WHATBOB_BE/issues/54#issuecomment-7006671972)

#### 홈에 초기 카드가 표시되는 순서

1. 초기 등록 작업이 떡볶이 → 돈까스 → 햄버거 → 마라탕 → 파스타 → 국밥 → 짜장면 → 제육볶음 순서로 DB에 초기 목록을 저장한다. 등록할 때 #62에서 정한 고유 문자열 키로 해당 DB의 음식 종류 ID를 찾는다.
2. 프론트가 `GET /api/menus/popular`를 호출한다. 이 API는 로그인 없이 조회할 수 있고, 최근 메뉴는 본인 인증을 사용하는 별도 요청으로 조회한다.
3. 백엔드가 목록의 각 음식 종류에서 숫자 ID와 표시명을 읽어 정해진 순서로 카드를 만든다. #64에서는 조회 가능한 공통 이미지 경로를 제공하고 #67에서 대표 일러스트를 연결한다.
4. 서버는 기존 공통 응답 형식으로 `source: "initial"`, `as_of: null`과 카드 여덟 개를 보낸다. `source`는 카드가 어디에서 왔는지를 뜻하고, `as_of`는 실제 순위에 사용하는 집계 기준 시각으로 초기 목록에서는 비어 있다.
5. 홈은 API가 보낸 순서대로 카드를 그린다. #65에서 실제 순위가 생기면 서버가 같은 API에서 저장된 순위와 기준 시각을 반환한다. [실제 인기 순위 보관 결정](../adr/0004-persist-last-popular-menu-ranking.md)

#### 확정한 초기 목록 저장 방식

- MySQL에 초기 목록의 **위치 1~8과 음식 종류 ID**를 저장한다. 위치와 음식 종류는 각각 한 번씩만 나오며, 음식 종류 ID는 #62에서 등록한 종류를 참조한다. 백엔드는 위치순으로 읽어서 카드를 반환한다.
- 초기 등록 전에 여덟 종류와 위치를 확인하고 목록 전체를 한 작업으로 반영한다. 운영에서 합의한 순서를 바꿀 때도 초기 목록의 위치만 한 트랜잭션으로 변경할 수 있다.
- 초기 목록과 마지막 실제 인기 순위는 별도 데이터로 둔다. #65의 자정 집계는 실제 순위를 발행하고 초기 목록은 그대로 둔다. 공개 API는 발행된 실제 순위가 생기기 전까지 초기 목록을 읽는다.

#### 검토한 초기 목록 저장 방식

| 선택지 | 동작 방식 | 얻는 점 | 감수할 점 |
| --- | --- | --- | --- |
| A. 백엔드 저장소에 순서 있는 목록을 둔다 | 음식 종류 키 여덟 개를 순서대로 적는다. 백엔드는 일치하는 음식 종류를 묶어서 조회하고 파일의 순서에 맞춰 응답을 만든다. | 개발, 테스트, 운영이 같은 배포 버전을 사용하면 같은 순서를 재현할 수 있다. 변경을 코드 리뷰와 테스트에서 확인할 수 있다. | 순서를 바꿀 때 파일을 수정해 배포한다. 배포 전에 파일의 키가 DB에 모두 등록돼 있는지 확인해야 한다. |
| B. DB에 음식 종류와 위치를 저장한다 | 초기 등록 작업이 문자열 키를 숫자 ID로 바꿔 위치 1~8과 함께 기록한다. 백엔드는 위치 순서로 조회한다. | 데이터 변경으로 순서를 바꿀 수 있어 앱 배포 주기와 분리할 수 있다. | 테이블과 초기 등록이 필요하다. 같은 위치나 음식 종류가 중복되지 않도록 하고, 여러 위치를 변경할 때 목록 전체가 함께 반영되도록 한다. |

Shopify는 표준 상품 분류를 버전이 붙은 파일로 배포하므로 어떤 버전의 데이터를 쓰는지 고정할 수 있다. YouTube의 공개 API는 재생목록 항목에 위치를 저장하고, 수동 정렬 목록에서 항목의 위치를 수정할 수 있게 한다. 공개된 사용 방식에서 각각 A의 버전 관리와 B의 위치 데이터 관리에 해당하는 원리를 볼 수 있다. 메모리 SQLite 예제에서 음식 종류의 숫자 ID와 등록 순서를 섞어도 두 방식이 합의한 여덟 개를 올바른 순서로 반환하는 것을 확인했다. 배포 검증에서는 음식 종류 여덟 개가 중복 없이 연결되는지, 토큰 없이 호출하면 정확한 순서와 `initial`·`null`이 나오는지, 카드 그림 경로가 실제로 열리는지 확인한다.

### #65 자정에 전날 인기 순위 집계 및 공개

매일 한국시간 자정에 전날 하루를 대상으로 실제 인기 순위를 계산한다. 홈의 공개 인기 메뉴 API가 읽을 수 있게 순위를 MySQL에 저장한다. #64의 초기 8종 목록은 별도로 보관한다. [구현 티켓 #65](https://github.com/pknu-wap/WHATBOB_BE/issues/65) · [마지막 실제 순위 보관 결정](../adr/0004-persist-last-popular-menu-ranking.md)

#### 전날 식사 기록이 실제 순위가 되는 순서

1. FastAPI 서버 안의 예약 작업이 집계일의 한국시간 자정을 집계 함수에 넘긴다. 예를 들어 한국시간 11월 20일 자정 작업의 대상은 11월 19일 하루다. 실제 작업 시작이 몇 분 늦어져도 같은 기준 시각을 사용한다.
2. 전날 자정부터 집계일 자정 직전까지를 UTC로 바꿔 MySQL에서 찾는다. 11월 19일 00:00 한국시간에 먹은 기록은 포함되고 11월 20일 00:00에 먹은 기록은 다음 집계에 포함된다. 카탈로그에서 삭제된 메뉴의 기록을 제외한다.
3. 이 범위의 서로 다른 사용자 수를 센다. 한 사람이 여러 메뉴를 먹어도 5명 기준에서는 한 명이다. 5명 미만이면 실제 순위를 새로 저장하지 않는다. 최초라면 초기 목록을 사용하고, 이전 실제 순위가 있으면 그 순위를 유지한다.
4. 같은 대상 기록을 음식 종류별로 묶는다. DB에서 해당 종류를 먹은 서로 다른 사람 수와 가장 나중의 식사 시각을 구한다. 예를 들어 한 사람이 치즈버거와 불고기버거를 먹으면 햄버거를 먹은 사람 한 명으로 센다.
5. 인원 수 내림차순, 그 종류의 가장 최근 식사 시각 내림차순, 숫자 음식 종류 ID 오름차순으로 정렬한다. 앞에서 최대 여덟 종류를 고른다.
6. 새 순위와 그 자정의 기준 시각을 MySQL에 한 트랜잭션으로 저장한다. API는 저장된 순위를 `source: "aggregated"`와 `as_of`로 반환한다. 5명 미만인 날도 검사가 정상적으로 끝나면 마지막 성공 집계일을 기록하고, 공개 중인 순위의 `as_of`는 유지한다. 재시작 보충과 중복 실행은 #66에서 이 집계 함수를 재사용한다.

다섯 사람이 전날 유효한 식사 기록을 남겼다고 가정한다. 두 사람은 햄버거를, 다른 두 사람은 국밥을, 한 사람은 파스타를 먹었다. 햄버거와 국밥은 각각 두 명으로 동률이므로, 국밥을 먹은 마지막 시각이 더 늦었다면 국밥 → 햄버거 → 파스타 순으로 공개한다. 식사 기록의 사용자 정보는 공개 응답에 포함하지 않는다.

#### 확정한 자정 실행 방식

A안으로 확정했다. FastAPI가 시작되면 기존 방 정리 작업과 같은 앱 수명주기에서 인기 메뉴 예약 작업을 시작한다. 작업은 `Asia/Seoul` 기준 다음 자정을 계산해 기다린 뒤 집계 함수를 부른다. 동기 MySQL 집계는 API 이벤트 루프 밖에서 실행한다. 서버를 종료할 때는 다음 자정을 기다리는 예약 작업도 종료한다. 자정을 놓쳤으면 재시작 시 #66의 복구 절차가 가장 최근에 놓친 집계 한 번을 같은 함수로 실행한다.

두 실행 방식의 운영 비용을 아래와 같이 비교했다.

| 선택지 | 시작 방식 | 얻는 점 | 감수할 점 |
| --- | --- | --- | --- |
| A. FastAPI 서버 안의 예약 작업 | 백엔드가 기동하면서 자정 예약 작업을 등록하고, 매일 한국시간 자정에 집계 함수를 부른다. 동기 DB 집계는 API 이벤트 루프 밖에서 실행한다. | 기존 방 정리 작업과 같이 앱의 실행·배포 과정에서 관리할 수 있다. 작업 전용 프로세스를 따로 띄우지 않는다. | 자정에 백엔드가 꺼져 있으면 집계가 늦어진다. 기동 시 놓친 날짜를 확인하는 작업이 필요하다. 집계와 응답이 같은 서버의 자원을 사용한다. |
| B. 호스트의 별도 예약 실행기 | 서버의 예약 실행기가 자정에 명령행 집계 프로그램을 한 번 실행한다. 프로그램은 같은 집계 함수를 불러 MySQL에 저장하고 종료한다. | 예약 실행기와 MySQL이 살아 있으면 API가 재배포 중에도 집계할 수 있다. 작업의 실행·종료 기록을 API와 별도로 확인할 수 있다. | 운영 환경에 예약 설정과 실행 로그 관리가 추가된다. 같은 호스트에서 별도 프로세스가 잠시 메모리를 쓰고 MySQL 부하는 API 조회와 공유한다. 호스트나 DB가 꺼져 놓친 날에는 복구가 필요하다. |

Google은 내부 분산 cron에서 작업을 실행하는 예약 시각으로 각 실행을 식별한다. WhatBap에서도 집계 함수에 그날의 한국시간 자정을 넘기면 지연이나 재시작 시 같은 기준으로 집계할 수 있다. Google Cloud Scheduler는 예외적으로 같은 예약 작업을 다시 전달할 수 있어 반복 실행이 저장 결과를 망치지 않도록 처리해야 한다고 설명한다. 현재 WhatBap는 API와 MySQL을 한 서버에서 실행하는 설계를 따르며, A의 기존 실행 예시는 FastAPI 시작 시 켜는 방 정리 작업이다. [Google SRE의 예약 작업](https://sre.google/sre-book/distributed-periodic-scheduling/) · [Google Cloud Scheduler 실행 방식](https://docs.cloud.google.com/scheduler/docs/overview) · [왓밥 앱 수명주기](../../app/main.py)

메모리 SQLite로 4명에서 5명으로 바뀌는 경우, 같은 사람의 반복 식사, 다른 세부 메뉴 합산, 삭제된 메뉴의 제외, 자정 경계, 두 동률 기준과 최대 여덟 종을 확인했다. 로컬 Python에 IANA 시간대 데이터가 없어 날짜 예제의 서울 시각 변환은 UTC+9로 확인했다. 구현에서는 실행 환경에서 `Asia/Seoul`을 읽을 수 있는지와 운영에 가까운 MySQL에서 자정 집계의 영향을 확인한다. [Python 시간대 데이터](https://docs.python.org/3/library/zoneinfo.html#data-sources)

### #66 마지막 인기 순위 유지와 놓친 자정 집계 복구

#65에서 정한 FastAPI 내부 예약 작업을 사용한다. 자정 예약 작업과 서버 시작 시 복구 작업은 같은 집계 함수에 처리할 한국 날짜를 넘긴다. DB에는 마지막 성공 집계일과 현재 공개 중인 실제 순위의 기준 시각(`as_of`)을 구별해 저장한다. [구현 티켓 #66](https://github.com/pknu-wap/WHATBOB_BE/issues/66)

#### 재시작부터 홈 표시까지

1. 예를 들어 월요일 자정에 실제 순위를 공개한 뒤 서버가 꺼져 화요일과 수요일 자정을 놓쳤다고 하자. 수요일 오전 9시에 FastAPI가 다시 켜지면 가장 최근 자정인 수요일 00:00을 복구 대상으로 잡는다. 이 집계가 읽는 기록은 화요일 00:00부터 수요일 00:00 직전까지다. 화요일 자정에 예정됐던 집계는 건너뛴다.
2. 서버는 MySQL에서 집계 상태 한 행에 쓰기 잠금을 건 뒤 마지막 성공 집계일을 확인한다. 이미 수요일이나 그 이후 날짜를 성공 처리했다면 종료한다. 완료 기록이 없는 첫 실행에도 가장 최근 자정을 후보로 삼는다. 자정 실행과 재시작 복구가 겹치면 하나가 먼저 상태 행을 잠그고, 다른 하나는 앞 작업이 끝난 뒤 날짜를 다시 확인한다. [InnoDB 쓰기 잠금](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)
3. 화요일에 유효한 식사를 기록한 사용자가 네 명 이하면 성공 집계일만 수요일로 적는다. 홈은 가장 최근에 공개한 순위를 계속 받는다. 이 예시에서는 월요일 자정에 공개한 일요일 식사 기록 기준 순위다. 실제 순위가 한 번도 없었다면 초기 여덟 종을 받는다. 사용자가 다섯 명 이상이면 화요일 식사 기록으로 새 순위를 만들고 수요일 자정을 `as_of`로 저장한다.
4. 저장 도중 실패하면 DB가 확정 전 변경을 취소한다. 기존 순위와 성공 집계일이 남으므로 같은 기준 날짜를 다시 시도할 수 있다. DB에서 확정한 직후 서버가 꺼졌다면 다음 실행은 이미 저장된 성공 집계일을 보고 중복 게시를 건너뛴다. 복구 중에는 홈이 DB에 저장된 기존 결과를 읽을 수 있다. [InnoDB 일관된 조회](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)
5. 공개 API는 순위 항목과 `as_of`를 같은 조회 시점에서 읽는다. 저장된 순위가 햄버거 → 국밥 → 파스타이고 국밥에 속한 메뉴가 DB에서 모두 삭제되었다면 햄버거 → 파스타만 보낸다. 나머지 순서와 원래 `as_of`를 유지한다. 실제 순위의 카드가 전부 숨겨지면 `source: "aggregated"`와 같은 `as_of`를 담은 빈 목록을 보낸다.

#### 확정한 순위 저장 방식

A안으로 확정했다. MySQL에 현재 공개 순위 최대 여덟 항목과 집계 상태 한 행을 둔다. 유효한 기록 사용자가 5명 이상이면 기존 항목을 새 순위로 교체하고, `as_of`와 마지막 성공 집계일을 같은 트랜잭션에서 갱신한다. 확정 전 실패하면 기존 순위와 두 날짜를 보존한다. 유효한 기록 사용자가 4명 이하인 날에는 성공 집계일만 갱신한다. 홈은 현재 공개 순위 항목을 순서대로 읽는다.

#### 순위 저장 방식 비교

| 선택지 | DB가 새 순위를 공개하는 순서 | 얻는 점 | 감수할 점 |
| --- | --- | --- | --- |
| A. 기존 순위 한 벌을 교체 | DB에 현재 순위 최대 여덟 줄과 집계 상태 한 줄을 둔다. 수요일 순위가 준비되면 한 트랜잭션에서 월요일 항목을 수요일 항목으로 교체하고 날짜를 갱신한다. | 홈이 현재 순위를 바로 읽는다. 버전 번호와 지난 버전 정리 절차가 필요 없다. | 새 항목과 두 날짜를 언제나 같은 트랜잭션으로 저장해야 한다. 교체가 확정된 뒤 과거 순위가 필요하면 별도 보관 설계가 필요하다. |
| B. 새 순위에 번호를 붙여 공개할 번호를 전환 | 월요일 순위를 17번이라 하면, 수요일 항목을 18번으로 넣고 상태가 가리키는 번호를 17에서 18로 바꾼다. 새 항목 저장, 번호와 날짜 갱신, 이전 버전 정리를 한 트랜잭션으로 확정한다. | 각 항목이 어느 집계에서 만들어졌는지 번호로 바로 알 수 있다. 나중에 보관 정책을 추가할 때 버전 단위를 재사용할 수 있다. | 현재 번호를 통해 읽는 조회와 버전 제약이 추가된다. 마지막 한 벌만 보관한다는 명세를 지키려면 이전 버전 정리도 처리해야 한다. |

두 방식 모두 DB에 기록을 확정하기 전에는 홈에 이전 순위가 보이고, 확정 후에는 새 순위가 보인다. 둘 다 전날 식사 기록을 같은 방법으로 집계하고, 동시에 실행된 다른 집계 작업은 상태 행의 잠금이 풀리기를 기다린다. 실제 실행 시간은 MySQL에서 측정한다.

Google은 내부 예약 실행 시스템에서 예정 시각을 실행 식별에 사용해 재시작 뒤 중복 여부를 확인한다. Netflix가 사용하는 Apache Iceberg는 새 데이터 버전을 만들고 현재 버전을 가리키는 참조를 한 번에 바꾼다. WhatBap에서는 첫 원리를 자정 작업을 식별하는 데, 두 번째 원리를 B안의 순위 공개에 적용할 수 있다. [Google SRE의 예약 작업](https://sre.google/sre-book/distributed-periodic-scheduling/) · [Netflix의 Iceberg 사용 사례](https://netflixtechblog.com/incremental-processing-using-netflix-maestro-and-apache-iceberg-b8ba072ddeeb) · [Apache Iceberg의 참조 교체](https://iceberg.apache.org/spec/#optimistic-concurrency)

### #67 기존 일러스트와 공통 이미지 연결

#64 설계에서 공통 이미지로 시작하는 인기 카드에 확인된 대표 일러스트를 연결한다. 최근 메뉴도 음식 종류의 대표 일러스트를 공유한다. 최근 카드의 세부 메뉴와 대표 그림이 크게 다르면 그 카드에 공통 이미지를 사용한다. [구현 티켓 #67](https://github.com/pknu-wap/WHATBOB_BE/issues/67)

#### Figma 원본에서 홈 카드까지

1. Figma에서 그림을 음식 종류와 대조하고 원본 레이어 이름을 기록한다. 마라탕·국밥·짜장면·제육볶음부터 확인한다. 재사용할 그림은 개별 파일로 내보내고, 확인 결과 그림이 없는 음식 종류는 #68 제작 목록에 넘긴다. 확인 대기와 원본 누락을 구분한다. [Figma 개별 레이어 내보내기](https://help.figma.com/hc/en-us/articles/360040028114-Export-static-designs-from-Figma)
2. 대표 그림과 공통 그림을 `app/static/menu-illustrations/`에 함께 배포한다. 예를 들어 햄버거의 DB에는 `/static/menu-illustrations/burger.png` 같은 상대 경로를 둔다. 제목이나 숫자 ID가 바뀌어도 파일 연결이 유지되도록 음식 종류의 고유 문자열 키로 파일과 초기 매핑을 찾는다. 그림을 교체할 때는 새 파일을 먼저 배포하고 접근을 확인한 후 DB 경로를 바꾼다. [현재 정적 파일 경로](../../app/main.py)
3. 프론트엔드가 최근 메뉴를 요청하면 백엔드는 선택된 식사의 메뉴 예외 여부를 확인한다. 예를 들어 토마토 그림이 파스타 대표 일러스트면 최근 토마토 파스타에는 그 그림을, 그림과 크게 다른 최근 크림 파스타에는 공통 이미지를 보낸다. 인기 메뉴는 음식 종류 카드이므로 대표 파스타 그림을 사용한다. 두 파스타 모두 같은 종류에 속한다.
4. 대표 경로가 비어 있거나 배포 파일에 없으면 두 API 모두 공통 이미지의 경로를 `image_url`로 보낸다. 백엔드에서 그림 선택 규칙을 공유하고, 브라우저는 받은 경로로 실제 그림 파일을 요청한다. 확인 단계에서는 대표 이미지와 공통 이미지의 HTTP 응답, 그리고 예외 전후의 카드 순서와 음식 종류 ID를 확인한다.

#### 확정한 메뉴별 예외 저장 방식

B안으로 확정했다. 공통 그림을 써야 하는 메뉴의 `menu_id`만 `menu_illustration_exceptions`에 한 줄씩 등록한다. `menu_id`는 기본 키이자 `menus.id`를 참조하는 외래 키로 둔다. 해당 메뉴를 삭제하면 예외 행도 함께 삭제한다(`ON DELETE CASCADE`). 초기 등록은 고유 `food_code`로 실제 메뉴를 찾는다.

최근 메뉴 API는 메뉴를 조회하는 쿼리에서 `LEFT JOIN`으로 예외 행을 함께 읽는다. 예외 행이 있으면 공통 그림을 사용하고, 예외 행이 없으면 음식 종류의 대표 그림을 사용한다. 사용할 대표 그림이 없으면 공통 그림을 사용한다. 인기 메뉴는 음식 종류의 대표 그림과 공통 그림을 사용한다.

#### 메뉴별 예외 저장 방식 비교

| 선택지 | 크림 파스타 한 메뉴를 예외로 표시하는 법 | 얻는 점 | 감수할 점 |
| --- | --- | --- | --- |
| A. 메뉴 행에 체크 칸 추가 | `menus`의 해당 행에 `use_default_illustration` 값을 켠다. 기존 메뉴와 새 메뉴의 기본값은 꺼짐이다. | 최근 카드가 메뉴를 읽는 조회에서 값도 함께 가져온다. 메뉴 한 행에서 예외 여부를 확인할 수 있다. | 메뉴 테이블에 홈 그림용 컬럼이 추가된다. 기존 메뉴에 기본값을 적용하는 마이그레이션이 필요하다. |
| B. 예외 메뉴만 별도 표에 등록 | 예외 표에 크림 파스타의 `menu_id`를 한 줄 넣는다. 메뉴 하나당 최대 한 줄을 허용하고 메뉴 삭제 시 그 줄도 정리한다. | 예외가 있는 메뉴만 별도 표에 모여 있다. 그림 예외 관리가 메뉴의 기본 데이터와 분리된다. | 예외 표와 외래 키를 관리한다. 최근 카드 조회에서 이 표를 한 번에 함께 읽어야 한다. |

두 방식 모두 초기 예외를 등록할 때 고유 `food_code`로 실제 메뉴를 찾는다. 예외 여부는 최근 카드의 메뉴를 읽는 쿼리에서 함께 읽는다. 인기 집계와 인기 카드 조회는 음식 종류를 기준으로 처리한다.

Shopify는 테마와 함께 고정 크기 이미지를 배포하고, URL에 자산 버전을 붙여 파일이 바뀌면 브라우저가 새 파일을 받게 한다. WhatBap에서도 교체용 파일에 새 경로를 부여하는 데 같은 원리를 적용할 수 있다. Shopify의 사용자 정의 필드는 상품처럼 이미 정해진 데이터에 필요한 추가 속성을 붙이는 사례이며, #67의 B안은 메뉴에 별도 예외 기록을 붙이는 형태로 이 원리를 적용한다. [Shopify 정적 파일 배포와 버전 관리](https://shopify.dev/docs/storefronts/themes/best-practices/performance/use-shopify-cdn) · [Shopify 사용자 정의 필드](https://shopify.dev/docs/apps/build/metafields)

### DB와 집계 작업

- `food_kinds`는 음식 종류의 숫자 ID, 고유 문자열 키, 카드 표시명, 대표 일러스트 경로를 가진다. `menus.food_kind_id`는 음식 종류의 숫자 ID를 참조한다. 대표 그림이 세부 메뉴와 크게 다를 때의 예외는 해당 메뉴 단위로 기록한다.
- 기존 메뉴는 정해진 별칭을 먼저 적용하고, 나머지는 원본 `base_name`별로 종류를 만들어 연결한다. `food_code`는 기존 메뉴를 식별하는 데 사용한다. MySQL 전환은 종류를 등록하고 기존 메뉴를 연결한 뒤, 연결 누락을 확인하고 외래 키와 필수 제약을 적용한다. 이후 시드는 같은 분류 규칙을 사용하며 이미 분류된 메뉴의 수동 수정은 보존한다. [기존 메뉴 시드](../../scripts/seed_menus.py) · [MySQL 마이그레이션 예시](../../scripts/migrate_issue39.py)
- 일일 작업은 서버의 시각대와 관계없이 `Asia/Seoul` 자정을 계산하고, DB에서는 집계 창을 UTC로 비교한다. 성공한 마지막 집계 날짜와 현재 표시 중인 실제 순위의 기준 시각을 구별한다. 사용자가 5명 미만인 집계도 완료로 기록하지만 표시 순위는 교체하지 않는다.
- 같은 기준 시각의 작업은 유효한 순위 한 벌만 반영한다. 집계에 실패하면 기존 순위와 성공 날짜를 보존해 재시도할 수 있게 한다. 갱신 시에는 순위와 기준 시각을 한 트랜잭션에서 함께 저장한다. [앱 내 작업의 기존 수명주기](../../app/main.py) · [UTC 시간 검증](../../app/users/schemas.py)

### API 계약 초안

| 메서드와 경로 제안 | 인증 | `data` 필드 제안 |
| --- | --- | --- |
| `GET /api/users/me/home-card-recently-eaten-food-max-6` | 기존 Bearer 토큰 필수 | `items[]`에 `food_kind_id`, `menu_name`, `eaten_at`, `image_url`. 최근 먹은 음식 종류의 홈 카드 데이터를 최대 6개 반환하고 종류별 최신 식사 기록을 대표로 사용한다. |
| `GET /api/menus/popular` | 공개 조회 | `source`, `as_of`, `items[]`. 항목은 `food_kind_id`, `name`, `image_url`을 포함한다. 초기 목록은 8종, 실제 순위는 최대 8종이다. |

두 API는 기존 `ApiResponse` 형식을 사용하고 `food_kind_id`를 JSON 숫자로 반환한다. 최근 메뉴 응답은 사용자 본인 범위로 제한하고 `Cache-Control: no-store`를 적용한다. 표시할 식사 기록이 없으면 빈 `items`를 반환한다. 인기 메뉴는 사용자 이름이나 개별 식사 기록을 제공하지 않는다. 공개 응답은 `source`가 `initial`일 때 `as_of`를 `null`로, `aggregated`일 때 게시된 실제 순위의 집계 기준 시각으로 제공한다. 날짜·시각은 UTC ISO 8601을 사용하고 `image_url`은 백엔드 기준 상대 경로다. [공통 응답](../../app/recommend/schemas.py) · [기존 인증 조회](../../app/users/router.py) · [기존 공개 카탈로그](../../app/recommend/router.py)

홈 조회 함수명은 경로와 맞춰 `get_my_home_card_recently_eaten_food_max_6`으로 둔다. 기존 `GET /api/users/me/meals`는 개별 식사 기록을 페이지 단위로 반환한다.

## #68 빠진 음식 일러스트 추가

현재 대조에서 원본으로 확실히 식별되지 않은 국밥과 짜장면은 디자이너의 PNG를 받으면 등록한다. #67의 개별 원본 확인에서 사용할 그림이 나오면 재사용한다. 대표 그림을 연결하기 전에도 두 홈 목록의 해당 카드에는 먼저 배포한 공통 그림을 표시한다. ### PNG 수령 후 등록 절차

1. 디자이너에게 PNG를 받으면 실제 홈 카드 크기에서 음식 식별, 여백, 잘림, 배경 투명도, 기존 일러스트와의 색·외곽선·구도를 확인한다.
2. PNG를 `app/static/menu-illustrations/`에 넣고 백엔드와 함께 배포한다. 예를 들어 국밥의 `/static/menu-illustrations/gukbap.png`가 HTTP 200으로 열리는지 확인한다.
3. MySQL의 `food_kinds`에서 해당 음식 종류를 찾아 대표 일러스트 경로에 그 주소를 등록한다. 다음 홈 API 조회에서 대표 그림을 적용하는 카드가 새 주소를 받는지 확인한다. 이 주소는 조회 시 읽으므로 자정 집계와 무관하게 적용된다.
4. 대표 그림이 아직 등록되지 않았거나 배포 파일이 없는 음식은 두 홈 API에서 공통 그림 주소를 반환한다. 첫 배포부터 공통 이미지 파일이 실제로 조회되는지 확인한다.

나중에 제공된 일러스트를 참조한 이미지 생성이 별도로 요청되면, 생성 직전에 요청자가 모델을 변경하고 명시적으로 허락한 뒤에 진행한다.

## 일러스트 보관과 제공

| 방식 | 그림과 DB에 저장하는 값 | 배포와 복구 |
| --- | --- | --- |
| 백엔드 정적 파일 | 백엔드와 함께 그림을 파일로 배포하고 DB에 파일 경로를 저장한다. 브라우저는 기존 `/static` 경로에서 그림을 읽는다. | 파일과 참조 경로가 맞아야 한다. 그림은 백엔드 배포에서 버전 관리하고, DB 백업은 참조 경로를 담는다. |
| DB에 파일 저장 | 그림의 바이트를 MySQL의 `BLOB` 컬럼에 저장한다. 백엔드는 DB에서 그림을 읽어 브라우저에 응답한다. | DB 백업에 그림이 포함된다. DB에 그림 용량이 더해지고 파일을 읽을 때 DB를 사용한다. |

메뉴 일러스트는 백엔드 정적 파일로 배포하고 DB에는 파일 경로를 저장한다. 현재 백엔드는 `app/static`을 `/static`으로 제공하며, 기본 프로필 이미지도 이 경로에서 제공한다. 메뉴 일러스트를 추가하거나 교체할 때 파일과 DB의 경로를 함께 확인한다. [정적 파일 설정](../../app/main.py) · [기본 프로필 이미지](../../app/static/default-profile.svg)

## 구현과 출시 전 확인

- Figma의 개별 원본 파일을 확인하고 재사용, 추가 제작, 공통 이미지가 필요한 대상을 확정한다.
- 운영 DB의 실제 `base_name` 대조표로 종류 연결과 대표 일러스트 예외를 확인한다. `자장면`과 `짜장면`의 합산, 토마토와 크림 파스타의 이미지 표시를 검증한다.
- 두 홈 API의 실제 응답과 파일 URL을 프론트엔드에서 확인하고, MySQL에서 최초 등록·재실행 및 자정 집계·복구 시나리오를 검증한다.

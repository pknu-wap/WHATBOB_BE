# #39 오늘 설계 정리와 다음 구현 기준

2026-11-13 정리. 사용자가 주요 아키텍처를 선택하고 평가·학습·이관·방·검증의 처리 설명을 이해했음을 확인했다. **T02~T09의 주요 정책 선택과 통합 설계 문서·검증 계획 작성을 마쳤다. 구현·실제 검증·운영 적용은 별개다.** 모든 기술 필드/경로를 사용자가 개별 승인했다는 의미로 기록하지 않는다.

## 확정된 설계

| 범위 | 구현할 사용자 동작 |
| --- | --- |
| T02 | UUID/Kakao 모두 JWT 확인 후 개인 질문·추천·평가 이용. 유형별 제외 전체 교체·마지막 저장 우선. 수정 이력 보관, 같은 추천·메뉴의 최신 평가 한 표, 다른 추천의 평가 누적 |

## 구현 때 해소할 확인 항목

아래는 설계 선택 미응답이 아니라 실제 데이터·환경·동작 검증 항목이다. 확인 결과 정책을 바꿔야 한다면 영향과 대안을 사용자에게 설명하며, 기존 정책을 임의로 완화하지 않는다.

- 운영 기존 제외 값의 정확 대응표, 8재료군의 실제 메뉴 연결·누락/미확인 분류. 로컬 7,503행 스키마 확인을 운영 데이터 검증으로 대체하지 않는다.
- 학습 데이터의 양·명시 라벨 분포·추천 당시 입력 재현 가능성, 시점 분리·수렴·예측 품질. 검증할 모델이 없으면 기본 추천을 유지한다.
- 개발 PC의 실제 학습 실행 환경·허용된 자료 경로·작은 모델 전달 방법. 새 유료 자원·공개 업로드를 도입하지 않는다.
- 실제 MySQL에서의 유일 제약·잠금/교착·FK·원본 삭제 후 복구와 단계별 마이그레이션 재실행.
- 사진 디코딩·업로드 크기 경계·고아 파일/공유 참조 보존, 브라우저 쿠키·탭·WS 연동.
- 백엔드+MySQL 같은 1GB 환경의 메모리·CPU·연결 풀·동시 연결/요청 지연. 용량을 측정하지 않고 지원 인원이나 안정성을 약속하지 않는다.

통합 문서의 테이블/경로·작업 수명·재시작 복구 등의 세부는 구현 기준 초안이다. 제품 요구를 유지하면서 실제 코드·테스트로 정밀화한다. 재시작 때 이전 online 연결의 정확한 단절 시각을 모르는 한계와 파일/DB의 비원자성도 숨기지 않는다.

# T01 준비 기록·인증 세션 전환 구조 조사

조사일: 2026-11-11. 설계 검토 자료이며 구현 완료나 최종 채택을 의미하지 않는다.
내부 기준: [현재 인증 합의](39-t01-auth-architecture.md), [UUID 사용자 ADR](../adr/0001-uuid-users-with-optional-kakao-linking.md).

## 1. 공개 1차 자료에서 확인한 사실

### Stripe: 응답 재생 계약

- API v1은 실행이 시작된 요청의 최초 상태 코드와 응답 본문을 키별로 저장하고, 같은 키의 재요청에 저장된 결과를 반환한다. `500`도 포함한다.
- 입력 검증 실패나 실행 중인 요청과의 충돌로 실행이 시작되지 않았다면 결과를 저장하지 않는다. 같은 키의 매개변수가 달라지면 오류이며, 키는 최소 24시간이 지난 뒤 제거할 수 있다.
- API v2는 성공한 작업을 반복하지 않고 실패·부분 실패 작업을 가능한 경우 완료하여 갱신된 응답을 반환한다. v1의 응답 고정 설명을 Stripe 전체의 공통 계약으로 일반화하면 안 된다.
- 이 자료는 상태 코드·본문 저장을 설명한다. 인증 쿠키나 `Set-Cookie`까지 저장·재생한다고 확인한 것은 아니다.

출처: [Stripe 공식 Idempotent requests 문서](https://docs.stripe.com/api/idempotent_requests).

### Shopify: 별도 요청 기록과 복구 지점

- 2019년 Payment Service 사례는 클라이언트와 멱등 키 조합으로 API 호출을 잠그고 동시 요청에 `409`를 반환한다.
- 별도 `IncomingRequest` DB 모델로 신규·재시도·완료를 구분하며, 완료된 요청은 이전 응답을 반환할 수 있다.
- 기록에 단계별 진행 지점인 recovery point를 저장한다. 로컬 DB 변경 단계는 트랜잭션으로 처리하고, 실패한 요청은 완료 단계를 복구한 뒤 이어간다. 외부 부작용을 별도 유형으로 다룬다.
- 추가 DB 쓰기와 단계 관리 비용이 있으며 배포 후에도 기존 복구 지점을 처리할 수 있어야 한다.

출처: [Shopify Engineering — Building Resilient GraphQL APIs Using Idempotency](https://shopify.engineering/building-resilient-graphql-apis-using-idempotency).

### AWS: 토큰 기록과 변경의 원자성

- AWS Builders’ Library는 호출자가 제공한 요청 식별자로 의도를 나타내고 동일 호출자의 재시도를 구분하는 방식을 설명한다.
- 멱등 토큰 기록과 관련 변경은 ACID의 전부 성공 또는 전부 실패 조건을 만족해야 한다. 토큰만 남거나 리소스만 생기는 상태를 피하기 위해서다.
- 재응답은 의미상 동등할 수 있으며 바이트 단위 동일할 필요는 없다. 키 보관 기간·늦은 요청을 별도로 다루고, 동일 키에 다른 매개변수는 오류로 처리한다.

출처: [AWS Builders’ Library — Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

세 자료는 결제·리소스 생성의 멱등성 사례다. 세 회사가 WhatBap의 익명 사용자·준비 쿠키·SHA-256 인증 세션과 동일한 구조를 사용한다는 근거는 없다.

## 2. WhatBap 적용 비교: 아래는 조사에 따른 설계 판단

현재 합의는 서버 생성 32바이트 비밀값, DB에는 SHA-256만 저장, UUID 생성 전에 HttpOnly 쿠키 선전달, DB에서 준비 5분 검증, 생성 성공부터 정식 세션 14일, JWT 1시간과 요청별 DB 세션 확인이다. 기존 SQL DB를 사용하며 Redis는 추가하지 않는다. 메모리 1GB·적은 트래픽은 제약일 뿐 성능 측정 결과가 아니다. [내부 합의](39-t01-auth-architecture.md)

| 구조 | DB 변경과 재시도 | 장점 | 비용·제약 |
| --- | --- | --- | --- |
| 하나의 세션 행 `pending → active` | 준비 행을 잠그고 사용자 생성·사용자 FK 연결·상태 전환을 한 트랜잭션에서 수행. 재요청은 active 행의 같은 사용자로 복원 | 비밀값 해시와 상태 조회가 단순하고 별도 완료 연결이 필요 없음 | pending의 사용자 FK는 비어 있어야 함. 상태별 제약·만료 의미를 명확히 하고 모든 인증 경로에서 active만 허용해야 함 |
| 준비 기록과 정식 세션 분리 | 준비 행 잠금 후 사용자·세션 생성과 준비 완료·세션 FK 연결을 한 SQL 트랜잭션에서 커밋 | 준비 수명과 정식 인증 수명을 별도 모델로 표현 | 연결·고유 제약과 정리 정책 필요. 완료 준비 기록을 삭제하면 재시도 경로가 끊기는지 검토 |
| 별도 작업 기록과 다단계 복구 | 요청 레코드에 진행 지점을 남기고 단계별 실행·복구 | 외부 호출 등 한 SQL 트랜잭션으로 끝낼 수 없는 작업을 재개할 수 있음 | 진행 상태·복구 함수·배포 호환성·추가 쓰기 관리. 현재 DB 내부 생성에는 필요성이 약함 |

두 번째는 **분리된 두 모델을 원자적으로 커밋**하는 구조다. 세 번째의 **여러 단계 사이에서 재개하는 작업 기록**과 같은 설계가 아니다. Shopify에서 차용할 것은 요청 추적·복구 원칙이며 테이블 분리 자체만으로 Shopify의 다단계 모델을 구현했다고 볼 수 없다.

Stripe에서 참고할 **저장한 HTTP 응답 재생**은 위 세 구조와 함께 사용할 수 있는 별도 응답 전략이다. 현재 합의에서는 JWT·비밀값 원문을 DB에 저장하지 않으므로 그대로 복제하기 어렵다. 유효 세션을 다시 확인하고 같은 사용자에 새 JWT를 발급하는 의미상 동등한 재응답이 대안이다. 세션이 폐기되었다면 이전 성공 응답을 그대로 반환해 인증을 되살리지 않아야 한다.

## 3. 구조 선택과 별개로 해결할 실패 조건

1. **브라우저 보관 기간과 준비 허용 기간은 다르다.** 준비 쿠키의 브라우저 수명까지 5분이면, 서버 생성 커밋 후 정식 쿠키 갱신 응답을 받지 못한 브라우저는 5분이 지나 쿠키를 잃는다. DB에 active 세션이 남아도 요청에 비밀값이 없으므로 같은 사용자로 복원할 수 없다. 쿠키가 남아 있는 재시도에서만 active 상태 우선 확인이 효과가 있다.
2. **해시에서는 원본을 복원할 수 없다.** 같은 비밀값을 유지한다면 브라우저가 이미 가진 값을 재전송하여 검증할 수 있다. 생성 시 새 비밀값으로 회전하면 그 응답 유실에 대비해 이전 값으로 안전하게 복구하는 연결·허용 기간이 필요하다. 유지와 회전은 아직 미결정이다.
3. **공개 멱등 키는 인증 자격 증명이 아니다.** 키만 아는 요청에 JWT나 복원 쿠키를 반환해서는 안 된다. WhatBap은 준비 비밀값을 가진 요청을 DB 기록과 대조한다. 요청 추적 식별자와 사용자 인증 권한을 구분해야 한다.
4. **같은 키의 잠금은 다른 키의 경합을 해결하지 않는다.** 두 탭이 준비 쿠키 없이 각각 준비 요청을 보내 서로 다른 비밀값을 받으면, 해시별 잠금·고유 제약은 두 사용자의 생성을 막지 못한다. 응답 순서에 따른 쿠키 덮어쓰기와 탭 간 초기화 조정은 별도 계약이다.
5. **원자성은 HTTP 전달 성공을 보장하지 않는다.** 사용자·세션·준비 완료 연결을 함께 커밋해도 브라우저가 응답을 받는다는 보장은 없다. 잠금만 추가하거나 응답만 저장하는 것으로 자격 증명 분실 문제를 해결했다고 볼 수 없다.

권고 초안: 현재 DB 내부 작업에는 첫 번째와 두 번째를 우선 비교하고, 모델의 상태 불변식과 정리 정책에 따라 선택한다. 외부 부작용이 도입되기 전에는 Shopify식 다단계 복구를 필수로 추가할 근거가 없다. 먼저 비밀값 유지·회전 및 쿠키 보관·응답 유실 복구 계약을 확정해야 어느 구조에서도 안전한 재시도가 성립한다.

## 4. 확인 범위

- 위 세 1차 자료를 직접 열어 사실을 확인했다. 표와 실패 조건은 WhatBap의 내부 합의에 적용한 추론이며 각 회사의 비공개 구현에 관한 주장이 아니다.
- 애플리케이션 코드·API·DB는 변경하지 않았다. 문서 검증은 `git diff --check`로 수행하며 애플리케이션 테스트는 실행하지 않는다.

# #39 T02~T09 통합 구현 아키텍처

작성: 2026-11-13. 오늘은 설계, 내일(2026-11-14)은 구현·실제 검증이다. **사용자가 선택한 정책과 아래 기술 초안을 구분한다.** M1A·M2A·M3A·M4A도 선택 완료이며 명시한 제품/자원 정책에 반영한다. 테이블·경로·상태 등 기술 초안은 아직 실행 코드에 적용하지 않았다. [마지막 설계 선택](39-final-design-choices.md)은 선택 이력이고 검증·인계는 [T09 계획](39-validation-and-handoff.md)에 모은다.

최신 확정값: 개인 보정 최대 ±0.05(100점 환산 ±5점)·90일 반감기·k=5·근접 개인화 추첨 beta=0.5, 섭취 불가 8재료군, 별도 기존 환경에서 주 1회 점검/수동 학습, 사진 5MB·1,200만 픽셀 이하를 긴 변 512px 정지 이미지로 정규화. 실제 학습·파일 처리·운영 데이터 변경은 미실행이다.

근거: [T02 D01~D14](39-t02-personal-data-architecture.md), [공통 선택](39-cross-feature-architecture-checklist.md), [계정 전환 계약](39-account-transition-contract.md), [명세](../specs/39-uuid-users-and-kakao-migration.md), [ADR-0001](../adr/0001-uuid-users-with-optional-kakao-linking.md), [ADR-0002](../adr/0002-room-reconnect-and-account-switching.md), [ADR-0003](../adr/0003-account-transition-and-runtime-decisions.md).

## 1. 구현 기준선과 책임

- 확인한 스택은 FastAPI·SQLAlchemy·PyMySQL·PyJWT이며 기본 계층 Controller → Service → Repository → DB를 유지한다. 내부 정수 사용자 PK·기존 FK를 UUID로 일괄 교체하지 않는다.
- T01의 UUID·보호 쿠키·JWT/DB 세션 확인은 기존 구현이다. T02의 추천/질문/피드백 인증 필수, 새 제외 목록 관리, 누적 평가·학습, T03 자동 퇴장, T04~T08은 후속 작업이다. 현재 코드의 선택적 인증을 이미 제거했다고 표현하지 않는다.
- API 프로세스는 하나다. MySQL과 같은 1GB 서버를 쓰며 실제 메모리·CPU·동시 연결 한도는 측정 전이다. Redis·별도 추천 서버·클라우드 저장소·새 외부 유료 서비스는 이 설계로 도입하지 않는다.
- HTTP/WS Controller는 요청·DTO·응답만 담당한다. 추천 Module은 `recommend(authenticated_actor, answers, exclusions)` 결과와 저장을, 계정 전환 Module은 `prepare/commit/recover`의 원자성을, 프로필 Module은 `update_nickname/replace_photo/delete_photo`의 소유권과 실패 복구를 맡는다. 호출부에 여러 Repository의 실행 순서를 요구하지 않는다.
- DB·시각·난수·카카오 응답·파일 저장은 테스트에서 통제 가능한 의존성으로 전달한다. 파일 저장은 실제로 사용하는 로컬 방식부터 구현하고 가상의 클라우드 Adapter를 미리 추가하지 않는다.

## 2. 변경할 DB 구조 초안

시각은 UTC, 순서 비교는 `(created_at, id)`로 한다. MySQL DATETIME의 timezone 미포함을 기존 T01 변환 방식과 맞춘다. 기존 행·ID·일시를 새로 발급해 옮기지 않는다.

| 대상 | 확장 초안 | 제약·인덱스와 이유 |
| --- | --- | --- |
| `users` | `nickname_edited`, `profile_image_edited` 및 필드별 프로필 출처 시각/원본 UUID 스냅샷 | 닉네임과 사진을 독립적으로 비교한다. 출처는 삭제될 원본 User FK에 의존하지 않는다. 기존 uuid·kakao_id·nickname_key 유일성 유지 |
| `user_food_exclusions` | nullable `catalog_code`, `catalog_version`; 기존 `keyword`, 타입·ID·생성 시각 보존 | 같은 사용자·타입의 코드 중복은 잠금과 정규화로 막는다. 기존 중복 점검 후 필요한 유일 인덱스를 추가한다. 미대응 키워드에 억지 코드를 넣지 않는다 |

| `recommendation_feedback_states` 신규 | 사용자·추천·원본 메뉴 키별 현재 유효 피드백 ID | 이력과 별개인 재구축 가능한 현재 상태. 유일 `(user_id,recommendation_id,menu_key)`; 같은 평가 수정은 한 표만 집계 |

| `request_operations` 신규 | 사용자·원본 인증 ID 스냅샷·작업 종류·키·요청 지문·상태·비민감 결과 | 원본 인증 namespace와 종류·키 유일. 현재 소유자 FK는 이관 시 이동하고 원본 인증 스냅샷은 FK로 묶지 않는다. 키만으로 인증하지 않는다 |
| `account_transitions` 신규 | 작업 ID·종류·원본 사용자/인증 스냅샷·대상 사용자/인증 연결·준비 비밀 해시·제공자 검증 문맥·상태·만료 | 비밀 원문·카카오 토큰 저장 금지. 원본 User/AuthSession 삭제에도 복구 가능. 준비 해시는 일반 익명 생성 API에서 사용 불가 |
| `kakao_link_guards` 신규 제안 | 카카오 subject별 잠금용 행 | 기존 대상 계정이 없는 첫 동시 연결도 같은 DB 행으로 직렬화한다. 일반 사용자 작업은 이 행을 잡지 않으며 외부 인증 후에만 사용 |
| `rooms`, `room_members` | 기존 만료·연결 종료 시각 활용; 참여 시작 후 최초 WS 연결 대기 시각 표현 | 타이머 대신 DB의 마감 시각으로 유효 상태 판단. 호스트 중복 종료 시각도 일관되게 유지 |
| 프로필 파일 | 메타데이터/현재 참조로 활성 파일 식별 | 파일은 DB BLOB에 넣지 않는다. 다른 사용자가 참조 중이면 삭제하지 않는다 |

`feedback_states`·통계는 원본 이력에서 재구축하는 파생 데이터다. 파생 자료 재계산으로 원본 평가를 삭제하지 않는다. 원본 사용자에 `retired_at`을 추가해 남겨두는 방식은 R3A와 맞지 않아 채택하지 않는다.

## 3. 공통 저장·잠금 규칙

1. JWT와 DB 세션으로 actor를 확인한다. 쓰기 Service 안에서 다시 최신 사용자·세션을 검증한다. Controller의 이전 조회만 믿지 않는다.
2. 카카오 연결만 subject guard를 먼저 잠근다. 그 뒤 관련 기존 User를 ID 오름차순 → AuthSession을 ID 오름차순 → Room을 ID 오름차순 → 참여/업무 행 → 작업 결과 행 순으로 잠근다. 일반 쓰기는 guard 단계를 생략한다.
3. 방에서 사용자를 발견한 뒤 역순으로 User를 잠그지 않는다. 정리 작업은 후보를 잠금 없이 찾고 필요한 ID를 수집한 다음 정해진 순서로 잠금·재검사한다. 새로운 관련 사용자를 발견하면 트랜잭션을 다시 시작한다.
4. 잠금 아래에서 상태·제외 조건·참조를 재확인하고 변경을 모아 **Service 최상위에서 한 번 commit**한다. 하위 이관 함수·질문 통계 함수는 flush만 하며 중간 commit하지 않는다.
5. 카카오 HTTP 통신·사진 디코딩·모델 학습 동안 DB 잠금을 보유하지 않는다. 추천 계산이 오래 걸리면 버전 스냅샷으로 계산 후 저장 시 제외 조건/인증 버전을 재확인해 변경 시 다시 계산하거나 충돌로 중단한다. 첫 구현은 같은 사용자 잠금 아래 짧은 계산을 허용하되 지연을 측정한다.
6. DB commit 뒤 WS 이벤트와 파일 정리를 수행한다. WS 전송 실패로 이미 확정한 DB를 성공 전 상태처럼 되돌리지 않는다. 클라이언트 재접속은 REST 최신 상태를 확인한다.
7. 교착·연결 장애는 같은 키로 제한 재시도한다. 외부 인가 코드를 재소비하지 않으며 commit 결과 불명은 새로운 작업 실행 대신 기존 작업 결과를 확인한다. MySQL 검증 전 교착 없음·직렬성 보장을 주장하지 않는다.

T01 토큰 갱신은 현재 AuthSession을 잠그고 User를 일반 조회한다. 이관에서는 User를 잠근 후 해당 세션의 갱신/폐기가 끝날 때까지 기다리고 최신 상태를 재검사한다. 이후 T01을 수정할 때 Session→User 쓰기 잠금 역순을 도입하지 않는 회귀 검증이 필요하다.

## 4. T02 개인 기능과 제외 조건

### HTTP 계약 초안

기존 공통 응답을 재사용하고 기존 bare 응답인 `/users/me`, 방·인증 응답까지 일괄 포맷 변경하지 않는다. 새 DTO는 Entity를 직접 반환하지 않는다.

| 요청 | 계약 |
| --- | --- |
| `GET /api/recommendations/order-sheet/questions` | JWT 필수. 사용자 질문 순환 상태만 읽고 갱신. 기존 상위 7+탐색 2·주제 중복 방지 유지 |
| `POST /api/recommendations/random` | JWT 필수. 현재 제외 목록+추가 제외 적용 후 기존 종류 단위 무작위 선택 유지. ML 점수 적용 대상 아님 |
| `POST /api/recommendations/order-sheet` | JWT 필수, 본문 `user_id`는 422. 현재 `answers`, `exclusions`, `top_k` 유지. 중복 질문/잘못된 선택지 거절 |
| `POST /api/recommendations/{id}/feedback` | JWT 필수, 본문 `user_id`는 422. 현재 소유자·추천 포함 메뉴 확인. 선택 메뉴 생략 시 기존 첫 메뉴 규칙을 유지하되 응답/작업 지문에 실제 메뉴를 확정 |
| `GET/PUT /api/users/me/allergies` | 신규 제안. `codes` 전체 목록 교체; 알려지지 않은 코드 하나라도 있으면 전부 거절 |
| `GET/PUT /api/users/me/unables` | 신규 제안. 별도 섭취 불가 재료 catalog의 `codes` 전체 교체 |
| `GET /api/recommendations/unable-ingredients` | 신규 제안. 코드·표시명·범위·catalog_version. 기존 `/allergens` 목록과 구분 |
| `GET/PUT/DELETE /api/users/me/dislikes...` | 기존 본인 비선호 자유 입력 유지. 병합 후 100개 초과 보존/편집 계약 확장 필요 |
| `GET/POST /api/users/me/meals` | 기존 계약·메뉴 이름 스냅샷·식사 시각 보존. POST에 작업 키를 붙여 재전송과 실제 반복 식사를 구분 |

기존 `/allergens` 목록은 메뉴 추천 요청이 아니므로 공개 조회를 유지하는 기술 초안이다. repository 상수 19개 코드의 재사용이며 법령 최신성·메뉴 재료 정확성을 검증했다는 뜻은 아니다. JWT 미제공 질문/추천/평가를 guest 쿠키로 우회하지 않는다.

### 목록 교체와 기존 값 대응

- 유형별 전체 교체·마지막 성공 저장 우선은 유지한다. 동일 사용자 쓰기를 잠금으로 줄 세우며 버전 불일치를 이유로 저장 거절하는 정책은 추가하지 않는다.
- 새 ALLERGY/UNABLE는 고정 코드만 받는다. 조회는 `items[{id,code,name,mapping_status}]`, `legacy_items`, `total_count`, `editable`, `catalog_version` 형태로 구분하는 초안이다. 미대응 원본이 있으면 해당 유형 전체 편집은 `409 EXCLUSION_MAPPING_REQUIRED`; 조회·원래 제외 효과는 유지한다. 새 DISLIKE 자유 입력은 유지한다.
- 9B 대응 도구는 check → 검증된 정확 대응표 apply → 원본/효과 verify. 추측 대응·자동 삭제는 하지 않는다. 기존 원문과 변환 문맥은 보존한다. 메뉴/사용자 스키마 전환과 별개로 재실행 가능해야 한다.
- 병합으로 DISLIKE가 100개를 넘으면 조회에서 모두 반환한다. PUT은 `max(100,현재 보유 개수)`까지 허용해 기존 전체를 보존·수정·줄일 수 있게 하는 기술 초안이다. 합치기에서 100개로 자르지 않는다. 미대응 값이 있으면 정식 대응 전 편집 제한을 적용한다.
- 메뉴와 catalog는 명시적 코드 매핑으로 연결한다. 원래 키워드 기반 제외를 유지하면서 확인된 코드 매핑의 제외를 합친다. 새 매핑 때문에 이전에 제외되던 음식이 다시 후보가 되지 않아야 한다.
- 로컬 `menus_meals_only.json`/CSV는 7,503행, 대표 재료 분류 7종이고 전체 원재료표가 없다. 대표 재료 `egg_dairy`만으로 달걀/유제품을 정확히 구분할 수 없고 `veggie_tofu`는 모든 채소를 대두로 간주할 근거가 아니다. `other` 2,166행과 빈 태그 736행은 매핑 점검 대상이며 안전한 음식이라는 뜻이 아니다. 운영 DB 상태는 미확인이다.
- 매핑에는 버전·근거·미확인 상태를 기록한다. 미확인 재료의 완전 제외를 보장하는 문구를 사용하지 않는다. 새로운 미확인 메뉴의 추천 허용/거절 정책을 임의로 추가하지 않으며, 실제 매핑 커버리지 검증을 구현 완료 조건으로 남긴다.

### 평가·중복·저장 흐름

1. 추천·식사·피드백의 재전송을 구분할 UUIDv4 `Idempotency-Key`를 신규 호출 계약으로 제안한다. key namespace는 원본 서비스 인증 세션·종류이며 payload 지문에는 실제 평가 메뉴와 값이 들어간다. 새로 식사한 경우는 새 키다.
2. 인증·User 잠금 → 원본 세션 검증 → 추천의 현재 소유자·메뉴 확인 → 같은 키의 결과/지문 확인 순으로 처리한다. 같은 키·다른 payload는 `409 IDEMPOTENCY_KEY_REUSED`.
3. 새로운 실제 평가 요청은 이력 한 행을 append하고 `(현재 사용자,추천,메뉴)`의 유효 상태를 새 ID로 바꾼다. 같은 값의 새 요청도 이력은 남길 수 있지만 유효 표는 한 건이다. 같은 키의 재전송은 이력을 만들지 않는다.
4. 사용자별 누적 수/비율은 서로 다른 추천의 유효 상태를 합쳐 산출한다. 같은 메뉴가 서로 다른 추천에 등장한 평가는 별개의 표다. 이관 후에도 추천 ID와 피드백 ID의 순서를 보존한다.
5. 기존 질문 통계도 append 횟수를 그대로 더해 수정·재전송이 중복 기여하지 않게 유효 상태에서 계산한다. 질문 선택의 상위/탐색 알고리즘은 유지한다. 소유자 없는 기존 피드백의 보관·기존 통계 기여는 별도 legacy 기준선으로 분리해 의도치 않게 지우지 않는다.
6. 평가·유효 상태·파생 통계·작업 성공을 한 트랜잭션으로 commit한다. 이관 완료 후 원본 JWT 요청은 거절하며 피드백을 자동으로 대상 계정에 재실행하지 않는다.
7. 미인증 401, 타인/소유자 없는 추천 404, 추천 외 메뉴·잘못된 질문 400, 본문 금지 필드 422, 현재 상태 충돌 409, DB 장애는 기존 오류 계층의 5xx다. 거절된 쓰기는 통계도 변경하지 않는다. 제외 후 후보 없음은 기존 404 도메인 오류 유지.

## 5. 학습 추천의 입력·학습·예측 초안

### 추천 요청 경로

`JWT/세션 → 본인 제외 조건 → 강제 제외 → 오늘 답변 점수 → 누적 이력 특징 → 로지스틱 예측 → 제한 보정 → 기존 종류 다양성/추첨 → 추천·반환 메뉴 스냅샷 저장`

인증·제외 조건 조회 실패는 중단한다. 모델 불가만 기본 추천으로 대체한다. 제외된 메뉴를 모델이 복구하지 않는다. 랜덤 추천과 방 공동 후보 계산은 이 모델을 자동 적용하지 않는다.

- 오늘 점수 `b=답변 일치 가중치 합/유효 답변 가중치 합`으로 0~1 정규화한다. 상관없음뿐이면 분모 0을 처리하고 `b=0`으로 둔다. 원래 응답 `match_score`는 원래 단위를 유지하고 내부 모델 점수와 구분해 스냅샷에 기록한다.
- 기존 다양성 함수에 연결할 때는 개인 보정을 유효 답변 가중치 합 W와 곱해 원래 점수 단위로 되돌린다(W=0일 때 기술 스케일은 1). `ranking_score=기존 답변 점수+c*스케일`과 화면 `match_score`를 별도 값으로 유지한다. 기존 최근 노출 감점의 스케일·종류별 중복 방지·근접 후보 범위는 보존한다. 근접 후보 균등 추첨의 제한 가중 추첨 전환과 이전 불만족 감점의 교체는 M1의 추가 선택에 따른다.
- 초기 결합식은 `c=alpha*r*(2*p-1)`, `r=n_eff/(n_eff+k)`다. `p`는 명시적 만족의 예측값, `n_eff`는 해당 사용자의 후보 관련 유효 평가 증거량이다. 최종 개인 보정 `c`의 절댓값은 alpha 이하다. [M1A](39-final-design-choices.md) 선택으로 alpha=0.05·k=5·90일 반감기를 초기값으로 한다. 업계 표준값이나 성능 검증 결과가 아니다.
- 오늘 점수 0.80/0.60의 차이 0.20은 alpha 0.05의 두 후보 최대 보정 차이 0.10으로 뒤집지 못한다. 0.80/0.77처럼 가까우면 바뀔 수 있다. 이는 개인 보정만 비교한 것이며 기존 반복 노출 감점·종류 추첨 이후 최종 순서까지 같은 보장을 주장하지 않는다.
- 현재 메뉴별 최신 불만족 0.35 감점과 새 누적 학습 보정을 동시에 무제한 더하지 않는다. 교체·대체 경로의 제안은 M1에 명시한다. 근거 없는 고정 가중치로 먼저 구현하지 않는다.
- 현재 10% 근접 후보 균등 추첨은 alpha=0.05 보정을 적용해도 동일 기본 점수 후보들의 확률을 그대로 둘 수 있다. M1은 근접 후보에서 `w=1+beta*r*p`의 제한 가중 추첨을 제안한다. 종류 대표는 해당 종류의 최상위 ranking_score 메뉴로 정하고 동점은 안정된 ID 순으로 선택한다. 종류별 가중치는 대표 하나에서 계산하며 전체 상품 가중치를 합치지 않는다. 선택한 종류 안에서도 같은 제한 가중치를 쓴다. M1A 선택으로 beta=0.5와 이 추첨 변경을 채택했다. 점수 값만 달라지는 테스트뿐 아니라 선택 분포가 의도대로 바뀌는 검증을 계획한다.

### 입력과 정답

- 첫 입력: 오늘 답변 조건 일치 벡터, 정규화 기본 점수, 메뉴의 기존 분류·조리·온도·무게감·영양 결측 표시, 사용자 메뉴/분류별 유효 만족·불만족 수/비율·최근 시각. 원시 user_id/JWT/카카오 ID/이메일/닉네임은 학습 특징에서 제외한다.
- 로지스틱 회귀는 자동으로 복잡한 상호작용을 학습하는 모델이 아니므로 필요한 답변×메뉴 일치와 이력 특징을 명시적으로 만든다. 전처리와 특징 순서·결측 처리·인코딩을 학습/예측에서 같은 버전으로 사용한다.
- 정답은 추천별·메뉴별 유효 명시 평가의 만족=1/불만족=0이다. 미평가·미선택·식사 기록을 자동 불만족으로 만들지 않는다. 여러 번 수정한 이력은 학습 기준 시점의 최신 상태 한 건만 사용한다.
- 특징은 추천 시점 스냅샷이다. 평가 수정은 정답을 바꾸며 이미 저장한 과거 입력을 현재 누적 이력으로 다시 계산하지 않는다. 계정 이관 후 현재 소유자 조회는 바뀌어도 과거 시점에 없던 타 UUID 이력을 과거 특징에 주입하지 않는다.
- 과거 추천은 시점별 특징/메뉴/규칙을 정확히 재현할 수 있는 경우만 학습 데이터에 포함한다. 재현 불가 행은 원본 이력을 보존하고 학습 제외 사유를 남긴다. 현재 값으로 가짜 과거를 만들지 않는다.

### 학습·검증·배포

1. 일관된 읽기 시점의 데이터 기준 시각과 유효 라벨을 확정한다. 내보내기는 페이지 단위로 하고 전체 DB 이력을 API 메모리에 올리지 않는다.
2. 추천 시각 기준으로 오래된 학습/그 다음 검증/가장 최근 테스트를 나눈다. 같은 추천의 메뉴·수정 이력은 서로 다른 분할에 흩어지지 않는다. 학습 기준 뒤 생긴 평가로 학습하지 않는다. 전처리도 학습 분할에만 fit한다.
3. 양쪽 라벨·기간별 표본이 충분한지 확인한다. 일률적인 최소 1,000건 같은 수치를 다른 서비스에서 가져와 보장하지 않는다. 클래스 누락·데이터 부족·수렴 실패면 새 모델을 승인하지 않는다.
4. log loss·Brier score·분류별 표본/편향, 개인 보정 상한·제외 위반·추론 지연을 검증한다. 미평가 메뉴의 만족 여부를 모르는 상태에서 전체 순위 개선률을 계산했다고 주장하지 않는다. 오프라인 지표는 실제 서비스 만족도 향상의 증명이 아니다.
5. 학습 모델은 특징 스키마·계수·절편·인코더·최근성/강도 설정·라벨 기준·학습 기간·코드 버전·검증 결과·체크섬을 하나의 immutable 버전으로 묶는다. 첫 선형 모델은 API에서 필요한 계수 기반 예측을 제공해 학습 라이브러리 전체를 서빙에 반드시 로드하지 않는 초안이다. 라이브러리 `predict_proba`와 수치 동등성을 테스트한다.
   계수 artifact에는 양성 클래스가 만족=1이라는 클래스 순서를 명시한다. 샘플 가중·정규화·특징 순서·결측 처리와 함께 검증하고 확률 방향을 임의로 뒤집지 않는다.
6. 신뢰한 로컬 artifact만 로드한다. 활성 버전 포인터를 원자 교체하고 직전 정상 버전으로 돌아갈 수 있게 한다. 요청 중에는 같은 버전을 사용한다. 특징 불일치·NaN·손상·로딩 실패면 해당 모델을 사용하지 않는다.
7. M3A 선택에 따라 개발 PC 등 별도 기존 환경에서 주 1회 점검/수동 학습한다. 실제 PC 가용성·허용된 자료 경로와 모델 전달은 구현 단계에서 확인한다. 첫 모델이 없거나 검증을 통과하지 못하면 기본 추천을 유지하고 누적 이력은 계속 보존한다. 실제 사용자 만족도·반영 강도는 이후 피드백으로 조정한다.

## 6. T03 방과 재접속

| 상태/사건 | 처리 초안 |
| --- | --- |
| REST 참여 성공·WS 연결 전 | 참여를 바로 유효하게 저장하고 연결 대기 마감 시각을 둔다. 연결을 한 번도 안 한 유령 참여도 무한 보존하지 않는다. 초안은 기존 60초와 일치시키되 기술 검토 시 확인 |
| 같은 사용자 연결 여러 개 | 하나라도 살아 있으면 참여 유지, 마지막 연결이 끊길 때만 DB disconnected_at 설정 |
| 마지막 연결 끊김 | DB에 유예 시작·마감 저장, 메모리 타이머는 빠른 실행 보조 |
| 마감 전 재연결 | 사용자/방 잠금 아래 인증·방 유효성 확인, disconnected_at 해제·완료 상태 유지 |
| `now >= deadline` | 일반 참여자와 주문서 삭제·참여/완료 수 재계산, 호스트는 방 종료·연결 종료·물리 정리 |
| 타이머/정리 작업 지연 | 조회/변경 시에도 DB 마감을 확인한다. 스케줄러가 늦었다고 만료 참여를 유효하게 취급하지 않는다 |
| 서버 재시작 | 기존 저장된 유예 마감은 연장하지 않는다. 이전 online 참여는 실제 단절 시각을 알 수 없어 재시작 복구 시각부터 60초 복귀 기회를 주는 기술 초안. 기동 복구 완료 전 WS/방 쓰기를 받지 않는다 |

정확한 장애 단절 시각은 인메모리 연결만으로 복원할 수 없다. 재시작 초안은 중단 시간만큼 복귀 판단이 늦어질 수 있다는 비용이 있다. 평상시 60초 유예를 자동으로 바꾸는 것으로 표현하지 않는다.

방 생성·참여는 키별 `PENDING → SUCCEEDED/FAILED/CANCELLED` 작업으로 구분한다. `GET /api/room-operations/{key}?kind=JOIN&room_id=...` 조회와 `POST /api/room-operations/{key}/cancellation`을 제안한다. 모두 JWT·원본 세션 namespace·자기 작업 확인이 필요하다. 기록 없음은 `UNKNOWN`이며 취소는 같은 namespace에 선행 종결 표식을 만들 수 있다. 늦은 원래 요청은 그 표식을 확인해 성공하지 못한다. 이미 성공한 참여는 취소로 숨기지 않고 정상 퇴장 경로를 사용한다.

작업 성공은 현재 참여가 계속 살아 있다는 뜻이 아니다. 방이 물리 삭제됐으면 성공 당시 방 ID와 현재 종료/없음 상태를 구분해 응답한다. 방 이벤트 유실은 REST 재조회로 복구한다. 별도 메시지 시스템·내구성 이벤트 전송 보장은 추가하지 않는다.

## 7. T04 닉네임·T05 사진

- `PATCH /api/users/me/nickname` 본문 `{nickname}` → 검증 후 User DTO. 주변 공백 제거, 한글/영문/숫자/공백 2~20자. 내부 공백·대소문자·Unicode 동등성은 T01의 UTF-8 binary 키 방식과 일치시키고 임의 casefold 중복 정책을 추가하지 않는다. 자기 이름 저장은 성공, 타인 중복은 409.
- 닉네임 성공 저장은 해당 필드의 직접 편집 표시를 남긴다. 기존 legacy 프로필은 별도 보호하며 과거 편집 여부를 추측해 기존 사용자를 덮어쓰지 않는다.
- UUID 단계의 편집 출처와 카카오 계정에서 직접 편집한 보호 표시는 구분한다. UUID의 편집 표시를 그대로 대상의 카카오 직접 편집 표시로 승격하면 나중에 더 오래된 UUID 프로필을 적용하는 정책을 잘못 막을 수 있다. 대상에서 직접 편집했는지와 선택된 원본 출처를 필드별로 따로 보존한다.
- `PUT /api/users/me/profile-image` multipart `file`, `DELETE /api/users/me/profile-image`로 기본 SVG 복원. 양쪽 JWT·본인 세션 확인. 조회는 R5A이며 임의 이름 기반 공개 파일 URL만 응답한다. 다른 사용자의 업로드 파일을 경로 문자열만 바꿔 삭제하지 못한다.
- 5MB(바이트 기준 제안은 5×1024×1024) 입력을 스트리밍 제한하고 파일명/Content-Type뿐 아니라 실제 JPG/PNG/WebP 디코딩을 검사한다. 깨진 파일·경로 조작·잘못된 형식은 이전 프로필을 유지한다. M4A 선택에 따라 1,200만 픽셀 상한, 긴 변 512px·비율 유지 정지 이미지 저장, 메타데이터 제거를 적용하고 초과·애니메이션은 거절한다.
- 새 파일은 버전 관리 밖 임시 경로에 저장·검증 → 임의 이름의 최종 파일로 원자 이동 → User 잠금·세션 재검증 → DB 참조 교체 commit → 참조 없는 이전 파일 삭제 순서다. DB 실패면 새 파일을 제거하고 기존 참조는 그대로 둔다.
- 파일시스템과 DB는 한 트랜잭션이 아니다. 프로세스가 중간에 죽으면 고아 파일이 남을 수 있으므로 유예 후 참조를 재확인하는 정리 작업을 둔다. 아직 commit되지 않은 파일을 지우지 않게 최근 임시/최종 파일은 보호한다. 사진 저장·이관·정리는 같은 파일 참조 규칙을 따른다.
- DB commit 결과가 불명확하면 새 파일을 즉시 지우지 않고 참조 확인 뒤 정리한다. 이관은 파일을 복사/삭제하기 전에 최종 프로필 소유자와 전체 참조를 확인한다. 파일명이 바뀌면 새 URL을 주어 이전 캐시와 구분한다.

## 8. T06~T08 카카오 전환·무손실 병합

### API·작업 상태 초안

- `POST /api/auth/transitions`에서 종류 `KAKAO_LINK|LOGOUT`, 현재 JWT·복원 쿠키·기대 sid·Origin/기존 보호 헤더·작업 키를 확인한다. 카카오 연결은 서버가 검증할 인가 코드와 state 바인딩이 필요하다.
- `POST /api/auth/transitions/{id}/commit`은 준비 비밀 쿠키로 준비 수신을 확인한다. `GET /api/auth/transitions/{id}`는 원본 인증 또는 준비 비밀을 확인해 자기 작업 상태만 반환한다. `POST /api/auth/transitions/{id}/recovery`는 성공 작업+준비 비밀+유효 대상 인증으로 복원한다.
- `PREPARED → COMMITTED` 또는 `EXPIRED/CANCELLED/FAILED`. commit 중 변경은 DB 트랜잭션 밖에 보이지 않는다. 응답 유실은 별도 실패 상태가 아니라 같은 COMMITTED 결과 복구다. 번호/UUID만 아는 요청에는 정보·토큰을 주지 않는다.
- 준비 유효 5분·성공 복구 24시간은 **운영 기술 초안**이다. 준비 쿠키의 브라우저 수명은 복구 기간까지 두고 PREPARED 단계는 서버에서 5분 검사해야 확정 응답 유실을 복구할 수 있다. 대상 세션이 폐기·만료되면 복구도 거절한다. 원래 T01의 정식 인증 30일·JWT 1시간과 구분한다.
- 병렬 전환·다른 탭의 늦은 Set-Cookie를 클라이언트 세대 번호만으로 막는다고 보장하지 않는다. 기대 원본 sid·작업·현재 쿠키가 다르면 충돌로 중단하고 최신 인증을 다시 확인한다. R4A 메시지는 비밀값을 담지 않는다.
- 준비 응답이 완전히 유실돼 브라우저에 준비 비밀이 없으면 서버의 해시에서 원문을 복원하지 않는다. 유효 원본 인증과 아직 PREPARED인 자기 작업을 잠금 아래 확인한 뒤 새 준비 세대·해시를 발급하는 복구 초안이다. 이미 검증해 저장한 provider 문맥을 재사용하고 일회용 인가 코드를 다시 소비하지 않는다. 이전 준비 세대는 무효화하며 COMMITTED/결과 불명 작업을 PREPARED로 되돌리지 않는다. 늦은 쿠키는 문맥 확인에서 거절한다.

### 처리 순서

1. 현재 사용자가 방 참여/유예/결과 불명인지 검사한다. 카카오 외부 인증은 잠금 밖에서 수행하고 성공한 제공자 문맥을 작업에 바인딩한다. 원본 인증과 provider 인증 모두 증명돼야 한다.
2. 별도 HttpOnly 준비 쿠키를 전달한다. 이때 기존 사용자·인증·기록은 변경하지 않는다. 준비 전용 해시는 일반 T01 사용자 생성/토큰 API로 사용할 수 없다.
3. commit에서 subject guard → 원본/대상 User → AuthSession → 방/참여·작업을 잠그고 현재 상태를 다시 확인한다. 대상 카카오 계정의 다른 기기 참여도 검사한다. 진행 중 방 작업이 있거나 결과가 불명확하면 전환을 막는다.
4. 대상 계정이 없으면 유일 kakao_id 제약 아래 새 대상을 만들고, 이미 있으면 그 계정을 사용한다. T06 단독 배포 상태에서는 기존 대상 이관은 원본 보존 후 거절하고 T07에서 완성한다. 중복 대상 생성 경쟁은 guard·유일 제약·롤백 검증으로 처리한다.
5. 원본/대상 제외 목록은 타입별 합집합, 정확히 같은 항목만 중복 제거한다. 별개 식사 기록은 같은 메뉴·같은 시간이라도 합치지 않는다. 식사·추천·피드백의 user_id만 이동해 원본 ID·시각·순서를 유지한다. 스냅샷은 그대로 둔다.
6. 유효 피드백 파생 상태는 이동한 추천별 원본 이력에서 재구축한다. 질문 상태는 주제별 횟수 합산, last_clusters는 더 최근 `(updated_at,source_id)` 상태를 사용한다. `guest:` 이력은 본인 소유 증거가 없으므로 자동 귀속·삭제하지 않는다.
   대상 상태 저장 후 원본 `user:{id}` scope 행은 제거한다. 이 행은 User FK가 아니므로 자동 CASCADE에 맡기지 않는다. 원본 상태의 필요한 감사 문맥은 이관 작업 기록에 보존한다.
7. 프로필은 필드별로 legacy 대상·대상에서 직접 편집한 값 우선, 아니면 가장 오래된 UUID 출처 값을 선택한다. 프로필 출처 시각은 대상 계정 생성 시각과 다르다. 닉네임을 원본에서 대상에 옮길 때 유일 키는 같은 트랜잭션 안에서 원본에서 해제한 뒤 대상에 설정한다.
8. 원본 UUID의 모든 인증을 무효화한다. RESTRICT FK인 auth_sessions는 복구 문맥을 작업 스냅샷으로 옮긴 뒤 제거해야 원본 User를 삭제할 수 있다. 방 host RESTRICT/참여 CASCADE가 남지 않았는지 확인한다. 이관되지 않은 자식 행이 있으면 원본을 삭제하지 않고 전부 롤백한다.
9. 대상 인증을 준비 해시에 연결하고 작업 COMMITTED와 함께 한 번 commit한다. 이후 쿠키·JWT·User DTO 응답. 준비 비밀로 같은 결과를 복구하되 다시 이관하지 않는다. 대상 인증 재폐기 후에는 복구할 수 없다.
10. 로그아웃은 기록 이관/대상 삭제를 하지 않는다. 현재 브라우저 인증만 종료하고 새 UUID·랜덤 닉네임·기본 사진·인증을 만든다. 카카오 다른 기기의 인증·기록은 유지한다. 재로그인 시 새 UUID 활동을 같은 대상에 다시 합친다.

정상 처리 중 외부 인증이 실패하면 원본 유지, DB 변경 실패면 전체 롤백, commit 뒤 응답만 실패하면 성공 복구다. 삭제된 원본 행을 다시 만들어 복구하는 방식은 쓰지 않는다.

### 작업 보존과 정리

- 원본 서비스 세션이 살아 있는 동안의 작업 키/취소 표식은 무조건 지우고 같은 키를 새 작업으로 받지 않는다. 키 namespace가 원본 sid여서 새 sid의 요청과 구분된다. 원본 인증이 영구 종료된 뒤에만 일반 작업 정리가 안전하다.
- 전환 복구는 별도 기한·준비 해시·대상 세션 연결을 가지므로 원본 User/AuthSession 정리와 독립이다. 복구 기한 경과는 새 사용자 생성/재이관 허용이 아니며 provider 재인증을 통한 정상 새 전환으로 처리한다.
- 정리는 작은 배치로 수행하고 작업 ID·오류 코드·지연만 남긴다. JWT·원문 쿠키·사진 내용·카카오 토큰·개인 프로필은 로그에 남기지 않는다.

## 9. 1GB 운영 자원·마이그레이션

- DB 풀 크기·동시 이미지 디코딩·후보 처리 배치·모델 파일 크기·API 요청 시간 한도를 설정으로 둔다. 초안은 작은 풀과 이미지 동시 처리 1개부터 측정한다. 추천마다 전체 과거 이력을 ORM 객체로 로드하지 않고 유효 상태/집계를 조회한다.
- 모델 특징은 고정 소규모 차원으로 제한하고 거대한 사용자/메뉴 one-hot 행렬·딥러닝 런타임을 첫 모델에 추가하지 않는다. 이 설계만으로 1GB에서 충분하다는 보장은 하지 않는다.
- DB 마이그레이션은 기존 T01 방식의 check/apply/verify와 유지보수 모드·명시적 적용을 따른다. 신규 nullable 필드/표 확장 → 기존 데이터 검사/안전한 backfill → 검증 후 제약 적용 순서다. 기존 틀린 데이터는 보고하고 자동 삭제하지 않는다.
- `Base.metadata.create_all`만으로 기존 테이블 컬럼이 바뀐 것으로 간주하지 않는다. 변경 단계별 manifest·원본 행/참조 대조·부분 실패 후 재실행을 설계한다. MySQL DDL 전체가 애플리케이션 트랜잭션처럼 되돌아간다고 가정하지 않는다.
- 운영 DB·배포·패키지 설치는 이번 설계 작업에서 실행하지 않았다. 라이브러리 버전은 내일 Python 호환성과 필요한 기능을 확인해 고정한다.

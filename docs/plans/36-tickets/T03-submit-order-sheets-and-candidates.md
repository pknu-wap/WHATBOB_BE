# T03: 개인 주문서 제출부터 공동 후보 확정까지

## Parent

[개발 명세 #43](https://github.com/pknu-wap/WHATBOB_BE/issues/43), 원본 요청 #36.

## What to build

참여자가 주문서를 제출하면 해당 라운드의 답변과 추천을 연결하고 각자의 첫 메뉴를 후보로 제공한다. 모두 제출하면 정확히 같은 메뉴를 합쳐 투표 가능한 후보를 확정한다. 후보가 하나면 투표 없이 결과를 보여주고 후보가 없으면 대기실로 복귀한다.

## Acceptance criteria

- [ ] 현재 라운드 참여자만 본인 주문서를 제출하고 제출 후 답변을 바꿀 수 없다. 동일 제출 재전송은 중복 추천·완료를 만들지 않는다.
- [ ] 고정된 공통 제외 조건을 실제 추천에 적용하고 기존 개인 질문·추천의 점수·추첨·다양성 로직을 활용한다.
- [ ] 라운드 제출 답변과 그 답변에서 생성된 추천을 연결한다. 다른 화면에서 받은 최신 개인 추천을 임의로 후보로 사용하지 않는다.
- [ ] 추천 응답 첫 메뉴 하나씩을 후보로 삼고 동일 메뉴는 병합하되 제안한 참여자 정보를 보존한다. 차순위로 후보를 채우지 않는다.
- [ ] 전원 제출 후 자동으로 후보를 확정하고 복수 후보이면 투표 단계와 첫 투표 회차를 시작한다.
- [ ] 후보 하나이면 무투표 결과임을 구분해 표시하고 실제 없는 득표수를 만들지 않는다.
- [ ] 추천 가능한 메뉴가 없으면 이유와 취소 상태를 조회할 수 있고 대기실로 돌아간다. 일시 DB 장애를 후보 없음으로 잘못 처리하지 않는다.
- [ ] 본문 없는 기존 완료 표시로 실제 답변 제출이나 신규 라운드 권한·단계 검증을 우회하지 못한다.
- [ ] 새로운 저장 구조·마이그레이션·후보/진행 상태 응답·알림·프론트 연동 계약과 REST·WebSocket 검증을 함께 제공한다.
- [ ] D20에서 사용자가 확정한 추가 제외 조건 지원·적용 방식을 명세와 검증 기대값에 반영한다. 결정 전 임의 지원·미지원 구현으로 차단을 해제하지 않는다.

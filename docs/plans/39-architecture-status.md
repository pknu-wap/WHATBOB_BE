# #39 아키텍처 설계 진행표

기준일: 2026-11-13. 사용자 요청에 따라 남은 설계를 아래 **고정된 5묶음**으로 관리한다. 완료는 설계 계약 정리 완료이며 실행 코드·테스트·배포 완료를 뜻하지 않는다. 승인된 정책과 에이전트가 구체화한 기술 세부는 각 계약 문서에서 구분한다.

## 현재 진행

2026-11-13 구현 갱신: 사용자의 “T01부터 시작” 지시에 따라 승인된 T01 서버 계약의 구현과 격리 검증을 진행했다. [구현·연동 문서](../UUID_AUTH_API.md)를 기준으로 HTTP 세 API·세션 JWT·WebSocket 재인증·MySQL 전환 스크립트를 확인한다. 아래 3~5번의 정책·운영·배포는 이 구현 지시만으로 승인·완료하지 않았다.

| 번호 | 묶음 | 상태 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 인증 통신 | 설계 정리 완료·서버 구현·격리 검증 | HTTP·WebSocket 서버 구현. 프론트 갱신 예약·복구 한도 구현과 실제 브라우저 검증은 남음 |
| 2 | DB 구조·기존 데이터 전환 | 설계 정리 완료·스크립트 구현·격리 MySQL 검증 | 기존 기록 보존·재실행·충돌 중단 검증. 운영 DB 적용은 수행하지 않음 |
| 3 | 여러 탭·계정 전환 | 검토안 작성·정책 검토 중 | 탭별 이전 인증·진행 요청·응답 유실·참여 결과 확인·로그아웃과 카카오 전환의 경계 정리 |
| 4 | 설정·서버 운영 | 남음 | 쿠키·JWT 실제 설정, 요청 제한, DB 대기, 인증 정리 실행 주체·프로세스 운영·예외적 폐기 범위 정리 |
| 5 | 배포·복구 절차 | 남음 | 점검 진입, 작업 정리, 백업·DB 변경·코드 배포·검증·복구·재개 기준 정리 |

**남은 설계: 3묶음.** 수치나 메시지 이름마다 새 묶음을 만들지 않는다. 관련 기술 세부는 담당 묶음 안에서 정리하며 사용자 경험·보안·데이터 보존 정책을 바꾸는 선택만 묶어서 설명한다. 발견된 구현 문제는 검증 항목으로 기록하고 정책을 바꿔야 할 근거가 있을 때만 기존 결정을 다시 연다.

2026-11-13 진행: 3번은 [여러 탭·계정 전환 검토안](39-account-transition-contract.md)을 작성했다. 따라서 3묶음 중 **구체안 검토 1개, 미정리 2개**다. 다른 탭 전환 시 보호 요청 보류·사용자 확인, 전환 준비·확정 두 단계의 사용자 경험을 설명하고 검토한다. 새 전환 인터페이스·작업 결과 경로는 최종 승인된 API로 기록하지 않는다.

최신 검토 방식(2026-11-13 사용자 변경 요청): 선택지·trade-off·현업 근거를 체크리스트로 한 번에 제시하고 사용자가 아는 항목부터 선택한다. 모르는 항목은 건너뛰기·보류 후 질의응답으로 검토한다. 기존 한 번에 하나 질문 규칙은 이 최신 요청으로 대체한다. 미응답·보류·에이전트 추천은 승인이 아니다. T02는 [현재 체크리스트](39-t02-architecture-checklist.md)를 따른다. 앱 형태 미정은 플랫폼 선택 유보·웹 우선·공통 서버 우선 진행의 승인이 아니며 새 탭·실행 환경·인증 보관 정책은 여전히 미결정이다. 이 문서의 T01 남은 설계 3묶음을 T02 선택이나 검토 방식 변경만으로 완료하지 않는다.

## 완료한 1번의 산출물

- [HTTP 인증 계약](39-t01-http-contract-proposal.md): 준비·생성·발급의 성공·오류와 쿠키 상태별 동작.
- [WebSocket 재인증 계약](39-t01-websocket-auth-contract.md): 만료 2분 전 갱신, 같은 연결의 교체·성공 확인, 중복·늦은 응답, 동일 화면의 HTTP 갱신 합치기, 오류·종료·Origin 경계.
- 갱신은 토큰 발급부터 WebSocket 성공 확인까지 공유 최대 10초. 자동 재연결은 별도로 최초 포함 최대 3회·전체 최대 10초. 각 대기 최대 3초와 남은 시간 중 작은 값을 사용한다.
- 방 재접속 유예는 60초. 참여 요청 시작·대기·참여·유예 중 계정 전환 금지. 서버 참여·전환 직렬화와 불명확한 참여 결과 확인은 2번·3번의 정해진 범위다.
- 메시지·오류 코드·날짜 형식 등은 에이전트가 기존 정책에 맞춰 구체화한 기술 세부다. 모든 필드를 사용자에게 개별 승인받았다고 기록하지 않는다.

## 전체 구현과의 관계

- T01 사용자 생성·복원·인증의 백엔드 구현과 격리 검증을 수행했다. T01 작업 시작은 미결정 플랫폼·새 탭 정책·전환 준비 방식의 채택을 뜻하지 않는다.
- 남은 3묶음과 프론트 연동·실제 브라우저 검증은 유지한다. 배포는 별도 승인·준비된 운영 절차에 따른다.
- T02 개인 기록, T03 방, T04 닉네임, T05 사진, T06 최초 이관, T07 다중 기록 병합, T08 로그아웃·재로그인, T09 전체 회귀는 [기존 작업 계획](39-uuid-user-tickets.md)의 범위를 유지한다. 후속 기능의 구현 상세를 전부 T01 설계 완료 조건에 추가하지 않는다.

## 완료한 2번의 산출물

- [DB 구조·전환 계약](39-t01-database-contract.md): 기존 정수 PK·FK를 유지하면서 문자형 UUID, nullable 카카오 ID, 닉네임 중복 키·레거시 구분과 `auth_sessions` 표를 추가한다.
- FK `RESTRICT`, 준비 생성·정식 연결의 원자성, 갱신·종료·정리 경합과 정리 대상 정렬을 구체화했다. 프로필 편집·이관 전용 컬럼은 담당 T04~T07에서 추가한다.
- 사전 점검·적용·사후 검증·중간 재실행 단계를 정리했다. 기존 이름·프로필·기록 충돌은 자동 보정하지 않고 적용 전에 중단한다.
- 운영 DB 버전·운영 데이터 충돌은 미확인이다. 스크립트와 격리 MySQL 검증은 완료했지만 운영 전환 성공을 보장하지 않으며 운영 DB 변경은 수행하지 않았다.

## 검토할 3번 여러 탭·계정 전환

1. 같은 화면의 동시 갱신은 완료된 통신 계약을 재사용한다. 여러 탭·쿠키 전환으로 다른 사용자 자격이 섞이지 않는 경계를 정리한다.
2. 참여 요청·전환의 서버 직렬화와 응답 유실 시 처리 결과 확인을 DB 계약에 연결한다.
3. 종료된 쿠키의 명시적 재시작과 진행 중 요청·응답을 정리한다. 기존 기록 무손실·방 참여 중 전환 금지·브라우저별 자동 사용자 병합 금지는 유지한다.

검토안은 탭 알림·응답 세대 검사·서버 문맥 확인·사용자 행 잠금·같은 작업 번호의 결과 복구를 함께 제시한다. 정책 검토 뒤 완료 표시하고 4번 운영 설정으로 이동한다. T03/T06~T08의 실제 API·작업 표·마이그레이션 구현은 담당 기능 범위를 유지한다.

## 검증 현황

- T01 구현 후 실제 앱 API·WebSocket·격리 MySQL 테스트를 실행했다. 상세 명령·결과는 LOG 최신 기록을 따른다. 운영 DB·배포 환경·실제 브라우저 검증은 미실행이다.
- 설계 완료를 기능 구현이나 외부 서비스 배포 완료로 기록하지 않는다. 코드와 충돌이 발견되면 계약과 구현 간 차이를 명시하고 구현 단계에서 검증한다.

# #36 T02 최종 설계 확인안

- 상태: 2026-11-17 사용자 확인 완료 (`T02-D01`, `T02-D02`, `T02-D03` 전체 확정).
- 범위: 방장 시작(`POST /rooms/{code}/start` 또는 대응 시작 엔드포인트) 시 최소 2명 검증, 라운드 전용 테이블(`room_rounds`) 생성, 참여자 전원의 저장된 제외 조건 스냅샷 고정 및 생존 메뉴 사전 검증, 참여자 전원 개인별 9개 주문서 질문 사전 일괄 생성(`Eager Generation`), 개인 주문서 질문 및 방 상태 조회(`GET`).
- 선행 조건: `T01` (퇴장 정리), `T01N` (상태 버전 및 내구 알림).
- 관련 티켓: [T02 티켓](36-tickets/T02-start-round-and-questions.md).

## 1. 확정된 핵심 아키텍처 결정 요약 (`T02-D01` ~ `T02-D03`)

| 결정 ID | 주제 | 사용자 확정 선택 | 핵심 설계 계약 |
| :--- | :--- | :--- | :--- |
| **T02-D01** | 라운드 상태 저장 구조 | **1번 확정 (`room_rounds` 테이블 분리)** | `rooms` 테이블에 컬럼을 덮어쓰지 않고, 별도의 `room_rounds` 및 `room_round_members` 테이블을 두어 라운드마다 고유 식별자(`round_id`, `round_no`)를 부여한다. 취소된 이전 판의 지연 요청이 새 판을 오염시키는 현상을 원천 차단한다. |
| **T02-D02** | 참여자 공통 제외 조건 처리와 메뉴 고갈 검증 시점 | **1번 확정 (시작 시점 공통 제외 스냅샷 고정 + 즉시 검증 `Fail-Fast`)** | 방장이 시작을 누르는 순간 현재 참여자 전원의 프로필 제외 조건(`ALLERGY`, `UNABLE`, `DISLIKE`)을 수집·병합하여 `room_rounds.exclusion_snapshot_json`(DB 내부 전용, 외부 응답/WS 비공개)에 고정하고, 즉시 `filter_available_menus`로 생존 메뉴가 1개 이상인지 검증한다. 0개이면 시작을 거절(방은 대기 상태 `WAITING` 유지)하고 사유를 반환한다. |
| **T02-D03** | 개인별 주문서 질문(9개) 생성 시점 | **2번 확정 (시작 시점 전원 질문지 사전 일괄 생성 `Eager Generation / CQRS`)** | 방장이 시작(`POST`)을 누르는 트랜잭션 안에서 현재 참여자 전원의 개인별 9개 질문(기존 `select_order_sheet_questions`의 7개 활용 + 2개 탐색 규칙 재사용)을 미리 뽑아 `room_round_members.assigned_question_ids`에 확정 저장한다. 이후 각 참여자가 질문지를 조회(`GET`)할 때는 DB 쓰기나 행 잠금 없이 100% 읽기 전용(`Pure Read`)으로 즉시 반환한다. |

## 2. 확정된 상세 처리 흐름 및 잠금 규칙

1. **방장 시작 요청 (`POST`) 트랜잭션 경계**:
   - 인증·세션 잠금 확인 후 대상 `Room` 행을 잠근다(`with_for_update()`).
   - 현재 방장 여부, 방 활성 상태, 대기 단계(`WAITING`) 여부를 검증한다.
   - 이미 진행 중인 라운드(`ORDER_SHEET` 등)에서 **같은 방장이 중복 시작 요청**을 보낸 경우: 새 라운드를 중복 생성하거나 질문을 다시 뽑지 않고, 현재 진행 중인 라운드의 시작 결과를 멱등(`Idempotent`)하게 그대로 반환한다.
   - 현재 유효한 참여자(`RoomMember`) 목록을 `user_id` 오름차순으로 정렬해 잠금/조회한다.
   - 참여 인원이 **최소 2명 미만**이면 시작을 거절하고 대기 상태를 유지한다.
2. **공통 제외 조건 스냅샷 및 생존 메뉴 검증 (`T02-D02`)**:
   - 확정된 참여자 전원의 저장된 제외 조건(`collect_user_exclusion_keywords`)을 합산한다.
   - 전체 메뉴(`Menu`)에 대해 `filter_available_menus`를 실행하여 생존 메뉴가 0개이면 라운드를 생성하지 않고 도메인 오류 응답을 반환한다(방은 `WAITING` 유지).
   - **개인정보/민감정보 보호**: 합산된 제외 조건 스냅샷은 `room_rounds` 내부 컬럼에만 저장하며, 어떤 REST 응답이나 WebSocket 브로드캐스트에도 다른 참여자의 알레르기·제외 조건 목록을 노출하지 않는다.
3. **전원 질문지 사전 일괄 생성 (`T02-D03`)**:
   - 참여자 `user_id` 오름차순으로 각 참여자의 `QuestionSelectionState`를 잠그고(`with_for_update()`), 생존 메뉴 풀과 기존 질문 선택 규칙(7개 활용 + 2개 탐색, 총 9개)에 따라 개인별 질문지를 선정한다.
   - 주의: 기존 `select_order_sheet_questions` 내부의 단독 `db.commit()`이 바깥 시작 트랜잭션을 중간에 끊지 않도록, commit 여부는 상위 시작 트랜잭션이 일괄 소유한다.
   - 생성된 `room_rounds` 행(상태: `ORDER_SHEET`)과 각 참여자별 `room_round_members` 행(배정된 9개 질문 ID 순서 포함)을 저장한다.
   - `T01N` 계약에 따라 `rooms.state_version`을 증가시키고 발송 대기(Outbox)에 주문서 작성 단계 전환 스냅샷을 기록한 뒤 한 번에 `commit`한다.
   - 시작 시점 이후에는 새 참여자 입장을 차단한다.
4. **개인 질문 조회 (`GET`) 및 재조회 계약**:
   - 현재 라운드에 속한 참여자가 자신의 주문서 질문을 조회하면, `room_round_members.assigned_question_ids`에 저장된 9개 질문을 순서대로 읽어 반환한다 (`GET`에서 상태를 변경하거나 질문을 새로 뽑지 않음).
   - 새로고침이나 재접속으로 여러 번 조회해도 동일한 라운드에서는 항상 같은 9개 질문과 순서가 반환된다.
   - 라운드 시작 후 들어오지 못한 비참여자나 다른 방 참여자의 조회는 거절한다.

## 진행 순서와 각 티켓의 범위

1. T01 구조 정리를 먼저 완료하고 T01N에서 기존 방 경로의 내구 알림·버전 관리를 검증한다. T02는 이 계약에 시작·질문 흐름을 연결하고 T05는 공통 퇴장 경계를 사용한다. T01N의 테스트를 T07로 미루지 않는다.
2. T02는 Q19·Q20 지원 여부를 결정하지 않고 착수할 수 있다.
3. T03은 T02와 D20이 모두 해결되기 전까지 착수하지 않는다. 사용자 보류를 무시하고 추가 조건 미지원으로 구현하는 우회는 없다.
4. T03 이후 T04와 T05는 기능적으로 서로 독립적이다. 두 티켓이 완료되면 T06에서 투표 중 퇴장 흐름을 통합한다. 공통 파일 변경이 있으면 구현 담당자가 조정한다.
5. 각 구현 티켓은 필요한 데이터 변경·명시적 마이그레이션·REST·WebSocket 계약·검증·프론트 연동 문서를 포함한다. DB, API, 테스트만 따로 떼는 수평 분할은 하지 않는다. 프론트 화면 코드 전체는 본 백엔드 명세 범위에 포함하지 않는다.
6. T07은 앞선 작업의 테스트를 뒤로 미루는 티켓이 아니다. 각 티켓을 검증하면서 완성하고, 마지막에는 실제 복구·경합·운영 DB 전환 경계의 통합 동작을 마무리한다.
7. D19는 결과 이전 핵심 흐름을 차단하지 않는다. 다만 보류 중인 결과 이후 계약까지 승인·구현됐다고 전체 완료 처리하지 않는다.

## 게시 계획 — 분할안 확인 후 실행

- T01·T01N·T02~T07은 분할안 확인 후 명세 #43의 하위 이슈로 게시한다. 티켓별 아키텍처·검증 경계가 사용자와 확정된 뒤 `ready-for-agent`로 전환하고, 미확정 항목은 설계 대기 상태와 직접 선행 티켓의 GitHub 차단 관계로 구분한다.
- D19·D20은 보류를 표현하는 결정 대기 하위 이슈로 게시하고 `needs-info` 라벨을 사용한다. `ready-for-agent`를 붙이거나 사용자에게 결정을 재촉하지 않는다.
- 생성 순서는 필요한 차단 번호가 먼저 생기도록 D20 → T01 → T01N → T02 → T03 → T04/T05 → T06 → T07이며, D19는 독립적으로 게시할 수 있다.
- 하위 이슈 연결과 차단 관계는 GitHub의 네이티브 관계를 우선 사용한다. 지원되지 않으면 본문의 Parent/Blocked by 참조로 명확히 남긴다.
- 원본 요청 #36과 명세 #43의 본문·상태를 수정하거나 닫지 않는다. 하위 관계 설정 외에 부모 이슈를 변경하지 않는다.
- 실제 새 이슈 번호·주소·게시 상태는 분할안 승인 후 이 문서에 기록한다. 현재의 T/D 식별자는 GitHub 이슈 번호가 아니다.

## 확인 요청

T01과 T01N 분리는 승인되었다. 구현 8개와 보류 결정 2개의 나머지 범위·직접 차단 관계 및 티켓별 설계를 계속 확인한다. 분리 승인을 미정 아키텍처나 전체 구현의 포괄 승인으로 보지 않는다.

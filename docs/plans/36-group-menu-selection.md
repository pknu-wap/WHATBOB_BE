## 사용자 결정

1. 각 참여자는 주문서 질문에 답하고 개인 메뉴 추천을 받는다.
2. 각 참여자의 추천 응답에서 첫 번째 메뉴 하나씩을 모아 같이 고르기 후보를 만든다. 현재 응답의 추첨·다양성 순서를 그대로 사용하며 최고 점수 메뉴를 별도로 고르지 않는다. 주문서 로직 변경 가능성과 별개로 이번 구현의 기준은 응답 첫 메뉴다(Q3).
3. 참여자는 후보 메뉴를 복수 선택하는 방식으로 투표한다.
4. 득표를 집계해 1등을 보여준다. 모든 사람의 개인 추천 목록을 교집합하는 방식은 아니다.
5. 참여자별 메뉴를 모으므로 투표 후보는 여러 개가 될 수 있다. 정확히 같은 메뉴가 여러 사람에게 추천되면 후보 하나로 합친다. 중복을 이유로 다른 순위의 메뉴를 추가하지 않으므로 참여 인원보다 후보 수가 적을 수 있다(Q5). 서로 다른 메뉴 행의 음식 종류까지 합치는 것은 이번 결정에 포함하지 않는다.
6. 개인별 후보를 추천하기 전에 참여자 전원의 저장된 알레르기·섭취 불가·비선호 조건을 합쳐 제외한다(Q4). 각자의 답변으로 추천하되 다른 참여자가 제외한 메뉴를 공동 후보에 넣지 않는다. 개인 모드에서 받은 첫 메뉴와 달라질 수 있으며, 제외 조건은 후보 부족을 이유로 임의 해제하지 않는다.
7. 대기실에서 방장이 시작하면 해당 라운드의 참여 인원을 확정하고 주문서를 작성한다. 시작 후 신규 참여는 거절하고 기존 참여자의 재접속은 허용한다(Q6).
8. 각 참여자는 후보 중 최소 하나부터 전체 후보까지 복수 선택할 수 있다. 자신에게서 나온 후보도 선택 가능하며 선택한 후보마다 한 표씩 반영한다(Q7). 같은 후보를 한 사람이 여러 표로 중복 집계하지 않는다.
9. 최다 득표가 동률이면 해당 메뉴를 모두 공동 1위로 표시한다. 동률 해소를 위한 무작위 선택이나 추가 투표를 자동으로 수행하지 않는다(Q8).
10. 모든 참여자가 주문서를 제출하면 자동으로 투표를 시작하고, 모든 참여자가 투표를 제출하면 자동으로 결과를 확정·표시한다(Q9).
11. 주문서와 투표는 제출 전에는 편집할 수 있지만 제출 후에는 해당 라운드에서 수정할 수 없다(Q10). 동일 요청 재전송으로 중복 제출·중복 득표를 만들지 않는 계약은 유지한다.
12. 결과 확정 전 일반 참여자가 명시적으로 퇴장하거나 기존 60초 재접속 유예가 만료되면, 방장에게 퇴장자를 알리고 '나간 사용자를 제외하고 진행할까요?'를 묻는다(Q11). '예'면 퇴장자를 제외한 참여자로 계속 진행하고, '아니요'면 라운드를 취소하고 대기실로 돌아간다. '아니요'가 퇴장자를 복원한다는 의미는 아니다. 방장의 퇴장·유예 만료에 따른 기존 방 종료 정책은 유지한다.
13. 방장이 '예'를 선택하면 남은 참여자의 제출한 주문서를 유지한다(Q13). 후보가 생성된 상태라면 퇴장자만 제안한 후보는 제거하고, 남은 참여자도 같은 메뉴를 제안했다면 해당 후보는 유지한다. 이미 투표 중이었다면 기존 표를 초기화하고 새 투표 회차에서 남은 참여자 전원이 다시 투표한다. 투표 회차 재시작은 기존 제출 투표의 편집과 구분한다.
14. 라운드 시작·계속 진행에는 최소 두 명이 필요하다(Q14). 결과 확정 전 퇴장으로 두 명 미만이 되면 계속 진행 선택 대신 인원 부족을 안내하고 라운드를 취소해 대기실로 돌아간다.
15. 일반 참여자 퇴장 후 방장이 결정하는 동안 라운드를 일시 정지한다(Q12). 작성·제출된 내용은 보존하며 주문서·투표 추가 제출과 자동 단계 전환을 차단한다. 방장에게 제외 후 계속 진행 여부를 묻고 다른 참여자에게 결정 대기 상태를 표시한다. 단순 연결 단절에는 먼저 기존 60초 유예를 적용하고 실제 퇴장이 확정된 뒤 이 절차를 시작한다. 두 명 미만이 된 경우에는 Q14의 인원 부족 취소가 우선한다.
16. 각 참여자는 기존 개인 주문서 로직으로 질문을 받는다(Q15). 개인 질문 선택 이력을 반영하므로 참여자마다 질문이 다를 수 있고, 방 공통 질문지를 새로 만들지 않는다.
17. 공통 제외 조건은 방장이 시작한 시점의 참여자별 저장된 알레르기·섭취 불가·비선호 조건을 모아 라운드 동안 고정한다(Q16). 진행 중 개인 설정 변경은 다음 라운드부터 적용하며 프론트에 이를 안내한다. 퇴장 후 계속 진행하는 것은 같은 라운드이므로 남은 사람의 기존 후보는 이 조건으로 생성된 결과를 유지한다.
18. 투표 중에는 전체/제출 인원만 공개하고 메뉴별 중간 득표수와 개인별 선택 내용은 공개하지 않는다(Q17). 투표 종료 후 메뉴별 득표수와 최다 득표 메뉴 전체를 공동 1위로 표시한다. 결과에도 누가 무엇을 골랐는지는 공개하지 않는다.
19. 중복 병합 후 후보가 하나면 투표를 생략하고 그 메뉴를 결과로 표시한다(Q18). 실제 투표가 없으므로 득표수를 만들어 표시하지 않으며, 투표 없이 확정된 결과임을 응답에서 구분한다.
20. 공통 제외 조건을 적용한 후 추천 가능한 메뉴가 없으면 사유를 안내하고 라운드를 취소해 대기실로 돌아간다(Q21). 제외 조건을 임의로 완화하지 않는다.
21. 주문서 작성과 투표에는 별도 제한 시간을 두지 않는다(Q22). 미제출자는 기다리며, 실제 퇴장은 방장 확인·최소 인원 정책을 적용한다. 기존 방 유효기간·만료 정책은 유지한다.

## 사용자 보류 항목

- 사용자는 Q21·Q22 결정 이후에도 Q19·Q20을 둘 다 보류한다고 재확인했다. 두 항목을 다시 묻거나 구현 편의상 포함·제외로 바꾸지 않는다. 확정된 핵심 흐름과 독립적인 설계·검증 준비만 진행하고, 이 항목에 의존하는 계약은 결정 전 구현 완료로 선언하지 않는다.
- Q19: 결과 이후 같은 방에서 '다시 고르기'를 제공할지 미정. 추천안을 승인·거절한 것으로 간주하지 않으며, 결과 보존·새 라운드 시작 계약을 임의로 확정하지 않는다.
- Q20: 주문서 제출의 추가 제외 조건을 참여자 전체에 합쳐 적용할지 미정. Q16에서 확정한 시작 시점의 저장된 제외 조건 고정은 유지하며, 추가 제외 조건의 지원·적용 방식은 임의로 확정하지 않는다.

## 확인한 현재 구현

- 방 생성·참여·완료 집계·퇴장·재접속 유예는 구현되어 있다. 방 주문서는 완료 여부만 보관하고 개인 추천 답변·결과와 연결되지 않는다.
- 개인 주문서 추천은 본인의 저장된 제외 조건과 요청의 추가 제외 조건을 적용한다. 다른 방 참여자의 제외 조건을 자동으로 적용하는 경로는 없다.
- 현재 개인 추천 응답의 순서는 단순한 점수 내림차순이 아니다. 최근 노출·개인화 보정 및 근접 점수 후보의 가중 추첨을 반영한다. 따라서 응답 첫 메뉴를 가져오는 것과 최고 점수 메뉴를 고르는 것은 서로 다른 계약이다.
- 방의 메뉴 후보·투표·결과 저장과 API는 아직 없다.
- 기존 60초 재접속 유예 및 방 참여 중 계정 전환 제한은 이번 답변으로 변경하지 않았다.

## 다음 결정

- 방장 결정 대기 중 연속 퇴장과 중복 결정 요청 처리.
- 중복 병합의 범위는 정확히 같은 메뉴로 확정했다. 같은 음식 종류이지만 다른 메뉴 행인 변형 메뉴까지 병합할지는 별도 범위로 남긴다.
- 개인 주문서 요청의 추가 제외 조건 전달 및 방 전체 적용 여부(Q20 보류), 일시적인 추천·DB 장애의 재시도와 확정된 후보 없음의 구분.
- 최소 한 개를 선택하므로 빈 투표·기권은 허용하지 않는다. 라운드/투표 재시작과 재전송의 구분을 API 계약에 반영한다.
- 결과 이후 다시 고르기 및 기존 개인 추천·평가·식사 기록과의 관계.
- API·DB·WebSocket 계약, 프론트 연동 영향 및 검증 경계.

## API와 데이터 구조 초안 — 구현 전 검토용

아래는 합의된 동작을 제공하기 위한 기술 제안이다. 사용자 보류 항목을 확정하거나 실행 코드 구현이 완료됐다는 의미가 아니다.

### 상태와 데이터

- 방의 기존 `WAITING / IN_PROGRESS / CLOSED` 상태는 유지하고, 진행 중인 라운드에 주문서 작성·투표·결과·취소 단계를 둔다. 기존 방 상태 제약에 새 단계 이름을 무작정 추가하지 않는다.
- 라운드에 시작 시점의 참여자와 공통 제외 조건, 현재 단계, 투표 회차, 퇴장 결정 대기 상태를 보관한다. 서버 재시작 후에도 진행 상태를 복원할 수 있도록 DB에 저장한다.
- 참여자별 제출 답변·그 라운드에서 생성된 개인 추천·첫 메뉴를 연결한다. 사용자의 '최신 개인 추천'을 찾아 대신 쓰지 않으며, 다른 화면의 개인 추천 호출과 섞이지 않게 한다.
- 후보마다 원본 메뉴와 후보를 제안한 참여자들을 연결한다. 같은 메뉴 후보가 여러 사람에게서 왔는지 보존해야 퇴장 시 후보 유지 여부를 판정할 수 있다.
- 투표는 라운드·투표 회차·사용자 단위로 한 번만 제출되며, 선택 메뉴 목록을 저장한다. 전원 제출 시 메뉴별 득표와 공동 1위를 한 번 확정해 저장한다. 단일 후보의 무투표 결과는 실제 득표 결과와 구분한다.
- 퇴장 결정 대기 중 추가 퇴장이 발생하면 대기 목록과 결정 버전을 갱신한다. 오래된 목록에 대한 방장 결정·이전 라운드 제출·이전 투표 회차 제출은 현재 상태를 변경하지 못하게 한다.
- 기존 사용자 인증·방 권한 확인·잠금 순서를 존중하고, 상태 변경과 후보·투표 갱신을 하나의 트랜잭션으로 처리한다. 인메모리 WebSocket 연결 정보만을 라운드 상태의 저장소로 사용하지 않는다.

### 외부 인터페이스 제안

모든 신규 REST 요청에는 현재 서비스 Bearer 토큰이 필요하다. 경로·필드는 초안이며 구현 계획 확정 시 API 문서로 구체화한다.

| 기능 | 요청 초안 | 권한·주요 동작 |
| --- | --- | --- |
| 시작 | `POST /api/rooms/{room_id}/rounds` | 방장만, 대기실·최소 2명 확인 및 참여자·제외 조건 고정 |
| 상태 복원 | `GET /api/rooms/{room_id}/rounds/current` | 참여자만, 단계·본인 제출 여부·공개 가능한 진행 상황 조회 |
| 개인 질문 | `GET /api/rooms/{room_id}/rounds/{round_id}/questions` | 해당 라운드 참여자만, 기존 개인 질문 로직 활용 |
| 주문서 제출 | `POST /api/rooms/{room_id}/rounds/{round_id}/order-sheets` | 본인 답변 확정, 전원 제출 시 후보 생성 및 자동 진행 |
| 투표 제출 | `POST /api/rooms/{room_id}/rounds/{round_id}/votes` | 본인만, 현재 투표 회차와 후보 검증, 전원 제출 시 결과 확정 |
| 퇴장 후 결정 | `POST /api/rooms/{room_id}/rounds/{round_id}/departure-decisions` | 방장만, 현재 결정 버전과 예/아니요를 검증 |
| 결과 | 위 상태 조회의 결과 필드 | 종료 후에만 메뉴별 득표·공동 1위, 무투표 확정 여부 제공 |

- `round_id`, 투표 회차, 결정 버전으로 늦게 도착한 요청을 구분한다. 같은 제출의 재시도는 결과를 복원하고 다른 답변·다른 표로 바꿔 제출하는 요청은 거절한다.
- 기존 본문 없는 `/order-sheet/complete`가 신규 라운드에서 실제 답변 제출을 대신하지 못하게 해야 한다. 기존 호출과의 호환 방식은 구현 계약에 명시한다.
- WebSocket은 상태 변경 알림을 제공하고, 클라이언트는 REST 상태 조회로 복구한다. 알림 누락·재접속 시에도 새 사용자나 새 라운드를 임의로 만들지 않는다.
- 상태 응답과 WebSocket 알림 모두에서 중간 득표·타인의 선택·개인별 제외 조건이 노출되지 않게 한다. 대기실 정보의 기존 공개 범위와 신규 라운드 정보의 참여자 전용 범위를 구분한다.
- DB 변경은 명시적인 마이그레이션을 제공한다. 로컬 테스트의 새 테이블 생성만으로 기존 운영 DB도 변경된 것으로 간주하지 않는다. 운영 DB 변경·배포는 이 설계 단계에서 수행하지 않는다.

### 프론트 변경 예상

- 방장 시작 버튼과 라운드 단계별 화면, 개인 질문/주문서 제출, 복수 선택 투표, 제출 후 수정 불가 처리.
- 시작 이후 신규 참여 거절 안내, 시작 시점 제외 조건 고정 안내, 후보가 없을 때 취소 안내.
- 퇴장자 표시와 방장 예/아니요 확인, 다른 참여자의 결정 대기 화면, 남은 인원 부족 안내.
- 새 투표 회차가 시작되면 기존 표의 선택 상태를 초기화하고, 후보 하나면 투표 화면을 생략한다.
- 투표 중 제출 인원만 표시하고 결과에서 득표·공동 1위 또는 무투표 결과를 표시한다.
- 인증·WebSocket 재연결 뒤 현재 라운드 상태를 조회해 화면을 복원한다. Q19/Q20에 따른 화면·요청은 결정 후 추가한다.

### 검증 경계 제안 — 사용자 확인 전

1. **인증된 REST API의 전체 흐름:** 방 생성·참여·시작·개인 질문·제출·중복 후보·복수 투표·공동 1위까지 실제 요청으로 검증한다. 내부 함수 호출만으로 성공했다고 판단하지 않는다.
2. **REST와 WebSocket의 퇴장·재접속 흐름:** 60초 유예·확정 퇴장·방장 결정 대기·계속/취소·재투표·최소 인원을 검증한다. 서버 재시작 시 DB 상태에서 복구되는지도 확인한다.
3. **동일 API의 거절·재전송 경계:** 비참여자·일반 참여자의 방장 명령·제출 수정·중복 전송·이전 라운드/투표 회차·중간 표 노출·후보 없음·단일 후보를 검증한다.
4. SQLite 테스트는 실제 MySQL 행 잠금 경합을 증명하지 못한다. 사용할 수 있는 격리 MySQL 테스트 환경에서는 마지막 제출·퇴장·방장 결정의 경합과 마이그레이션을 별도로 검증한다. 환경이 없으면 미검증 범위를 명시한다.

## 설계 기록 원칙

사용자가 답한 결정만 확정으로 기록한다. 제안·권장값·현재 구현을 사용자 승인으로 간주하지 않는다. 구현 전에 합의한 동작과 검증 경계를 다시 확인한다.

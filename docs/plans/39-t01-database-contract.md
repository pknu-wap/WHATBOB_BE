# T01 DB 구조·기존 데이터 전환 계약

작성: 2026-11-13. 상태: 기존 사용자·기록 보존 정책 안에서 에이전트가 정리한 기술 설계다. T01 전환 스크립트를 구현하고 격리 MySQL 8.4.13에서 보존·재실행·충돌 중단을 검증했다. 운영 DB는 변경하지 않았다. 현재 명령·설정·남은 검증은 [연동 문서](../UUID_AUTH_API.md)와 LOG 최신 기록을 따르며 아래 미구현 서술은 초기 설계 시점이다. [설계 진행표](39-architecture-status.md), [인증 아키텍처](39-t01-auth-architecture.md), [UUID 이관 ADR](../adr/0001-uuid-users-with-optional-kakao-linking.md)을 따른다.

## 확인한 코드와 보존 범위

- 현재 `users.id`는 자동 증가 `Integer` PK, `kakao_id`는 유일·필수 `BigInteger`다. `nickname`은 nullable `String(100)`이며 유일 제약은 없다. `email`·`profile_image`·생성/수정 시각도 기존 값을 유지한다.
- 음식 제외·식사 기록·추천·피드백·방장·방 참여는 정수 `users.id`를 참조한다. UUID를 추가해도 기존 PK·FK를 UUID로 바꾸지 않고 ID 재부여·기록 재생성을 하지 않는다.
- 기존 스키마 변경은 `scripts/migrate_room_lifecycle.py`가 `inspect`로 상태를 확인하고 명시적 SQL을 실행한다. T01도 별도 스크립트를 쓰며 `create_all()`로 기존 표가 변경된다고 가정하지 않는다.

## 사용자 표 확장

| 컬럼 | 설계 | 역할과 전환 |
| --- | --- | --- |
| `id` | 기존 `INTEGER` PK 그대로 | 내부 사용자 번호와 모든 기존 기록의 연결 보존 |
| `uuid` | `CHAR(36)` ASCII, 최종 NOT NULL·유일 인덱스 `uq_users_uuid` | Python `uuid.uuid4()`의 소문자 하이픈 문자열. 기존 카카오 사용자도 미설정 값만 채워 사용자 DTO에서 일관되게 식별 |
| `kakao_id` | 기존 `BIGINT`·유일성 유지, NULL 허용 | 카카오 미연결 사용자는 NULL. 기존 카카오 ID는 수정하지 않음 |
| `nickname` | 기존 nullable `VARCHAR(100)` 보존 | 기존 이름을 임의 축약·수정하지 않음. 새 UUID 이름과 이후 편집은 명세의 2~20자 검증 적용 |
| `nickname_key` | nullable `VARBINARY(400)`, 유일 인덱스 `uq_users_nickname_key` | 앞뒤 공백을 제거한 표시 닉네임의 UTF-8 바이트. 신규 생성·편집의 중복 방지용이며 응답에 노출하지 않음 |
| `is_legacy_kakao` | NOT NULL BOOLEAN, 기본 false | 전환 전에 이미 존재한 카카오 사용자만 true로 채움. 이후 이관에서 기존 프로필 보존 정책을 구분하는 사실 기록 |

- UUID는 사용자 식별자이며 비밀 인증 수단이 아니다. 카카오 사용자의 UUID가 있다는 이유로 익명 사용자로 판정하지 않는다. 카카오 연결 여부는 `kakao_id`로 판정한다.
- 문자형 UUID는 방의 기존 `String(36)` UUID 관례와 읽기 쉬운 운영을 우선한 선택이다. 16바이트 표현보다 공간·인덱스가 크지만 기존 정수 PK를 유지하므로 모든 FK와 JOIN 비용을 UUID로 바꾸지 않는다. UUIDv4는 [Python 공식 문서](https://docs.python.org/3/library/uuid.html#uuid.uuid4)의 무작위 UUID 생성 함수를 사용한다.
- 닉네임 키는 대소문자·내부 공백을 자동 변경하지 않고, 명세대로 앞뒤 공백만 제거한 정확한 텍스트의 중복을 막는다. 별도 대소문자 무시·문자 정규화 정책을 추가하지 않는다. 키의 바이트 유일성은 DB 전체 collation에 우연히 의존하지 않게 한다.
- 기존 NULL·빈 이름은 표시 값을 바꾸거나 자동 이름을 부여하지 않고 `nickname_key=NULL`로 보존한다. 새 UUID 생성과 이후 편집에서는 빈 이름을 허용하지 않는다. 기존 누락 프로필의 표현은 기존 호환을 유지하고 사용자 임의 데이터 보정과 분리한다.
- 기존 유효한 이름은 키를 채워 예약한다. 앞뒤 공백 제거 후 충돌이 있으면 제약 추가 전에 보고하고 중단한다. 사용자를 삭제·병합하거나 이름에 번호를 붙여 자동 해결하지 않는다. 충돌 해결이 필요한 실제 데이터는 사용자 결정 후 별도 작업한다.
- 새 이름 생성은 DB 유일 제약까지 확인하고 충돌 시 후보를 다시 만든다. 무한 반복하지 않으며 운영 설정의 생성 시도 상한을 적용한다. UUID 중복도 유일 제약으로 차단한다.
- UUID 사용자의 기본 사진은 배포물에 포함하는 정적 기본 이미지 URL을 DTO로 제공한다. 기존 카카오 `profile_image`를 덮어쓰지 않는다. 이미지 파일·경로 설정은 구현·운영 설정에서 연결하며 외부 저장소를 새로 만들지 않는다.
- 닉네임·사진의 직접 수정 여부와 가장 오래된 UUID 프로필 출처 메타데이터는 이를 쓰는 T04~T07에서 필요한 마이그레이션과 함께 추가한다. T01의 레거시 구분 값과 생성 시각을 유지하며 후속 작업 전에 카카오 이관을 먼저 허용하지 않는다.

## 별도 인증 표 `auth_sessions`

| 컬럼 | MySQL 설계 | 제약·의미 |
| --- | --- | --- |
| `id` | `BIGINT` 자동 증가 | PK. JWT `sid`에는 십진 문자열로 넣음 |
| `user_id` | nullable `INTEGER` | 기존 `users.id`와 같은 부호·자료형 FK, `ON DELETE RESTRICT` |
| `secret_hash` | `BINARY(32)` NOT NULL | SHA-256 `digest()` 결과, 유일 인덱스 `uq_auth_sessions_secret_hash` |
| `created_at` | `DATETIME(6)` NOT NULL | UTC 생성 시각 |
| `expires_at` | `DATETIME(6)` NOT NULL | 준비 5분 또는 정식 30일의 현재 서버 만료 |
| `revoked_at` | nullable `DATETIME(6)` | 명시적 종료 시각. 있으면 만료보다 먼저 종료로 판정 |

인덱스는 `ix_auth_sessions_user_id(user_id)`, `ix_auth_sessions_expires_id(expires_at,id)`, `ix_auth_sessions_revoked_id(revoked_at,id)`를 둔다. FK 이름은 `fk_auth_sessions_user`다. 인증 기록의 FK를 `SET NULL`로 만들지 않아 정식 기록이 준비 기록으로 바뀌는 사고를 막는다.

- 준비 여부는 `user_id IS NULL`, 정식 여부는 FK 존재로 구분한다. 준비·정식 상태 컬럼, 원문 비밀값·JWT 컬럼, 매 요청 접속 시각 갱신은 추가하지 않는다.
- MySQL에는 UTC로 정규화한 timezone 없는 `DATETIME(6)`을 저장하고 애플리케이션 경계에서 UTC 의미를 명시한다. 세션별 서버 로컬 시간에 따라 해석하지 않는다. 기존 사용자 생성 시각을 일괄 변환하지 않으며 원래 시간 의미가 불명확하면 사전 점검에서 보고한다.
- 유효 정식 인증과 사용자는 `sid` PK와 `user_id` FK JOIN으로 함께 확인한다. `sub`와 사용자 일치도 검증한다. 별도 사용자 UUID 조회로 인증하지 않는다.
- 종료·만료 인증 정리는 이 표의 행만 삭제한다. FK 방향상 인증 행 삭제는 사용자·식사·추천·방 데이터를 삭제하지 않는다.
- 후속 UUID 이관에서 원본 사용자 삭제가 필요하다면 관련 기록을 이관하고 원본 인증을 종료·정리한 뒤 명시적으로 수행한다. T01은 사용자 삭제 API를 추가하지 않는다.

## 생성·복원·종료와 잠금

1. 준비 API는 비밀값과 해시를 만들고 `user_id=NULL`, 5분 만료 인증 행을 저장한 뒤 쿠키를 설정한다. 실패한 저장의 쿠키는 발급하지 않는다.
2. 생성 API는 해시로 찾은 인증 행을 `SELECT ... FOR UPDATE`로 잠그고 DB의 최신 종료·만료·FK 상태를 다시 확인한다.
3. 유효한 준비이면 사용자·UUID·중복 없는 이름과 같은 인증 행의 FK 연결·30일 만료 변경을 한 트랜잭션으로 처리한다. 실패하면 사용자와 연결 변경을 함께 롤백한다.
4. 다른 동시 요청은 잠금 후 최신 FK를 보고 같은 사용자로 복구한다. 같은 쿠키로 사용자를 중복 생성하지 않는다. 서로 다른 쿠키의 별도 생성 허용은 유지한다.
5. 정식 인증 갱신·종료도 해당 인증 행을 잠그고 최신 상태를 재검증한다. 종료가 반영된 인증을 갱신으로 되살리지 않는다. 서버 저장 성공 후 응답을 보내며 응답 유실이 커밋 취소를 뜻하지 않는다.
6. 기존 사용자에 대한 잠금이 함께 필요한 후속 전환은 사용자 ID 오름차순 → 인증 ID 오름차순 순서로 통일한다. 준비 생성은 기존 사용자를 참조하지 않는 단일 인증 행 잠금이다. 모든 경로의 실제 잠금 순서는 구현 테스트에서 대조한다.
7. 방 생성·참여와 계정 전환이 같은 사용자 경계를 사용하는 구체적 상태·잠금은 3번 여러 탭·계정 전환 묶음에서 정리한다. 이번 표 설계가 그 기능 구현 완료를 의미하지 않는다.

## 만료·종료 정리 쿼리

- 이미 합의한 600초 주기·실행당 총 100건 상한을 유지한다. 조회 후보만으로 삭제하지 않고 잠금 후 종료·만료를 다시 확인한다.
- 종료 행 후보는 `revoked_at,id`, 종료되지 않은 만료 후보는 `expires_at,id` 순으로 각각 최대 100건 조회한 뒤, 유효 종료 시각(`revoked_at`, 그 외 `expires_at`)·`id` 순으로 합쳐 최종 최대 100개만 선택한다. 종류별로 각각 100개를 삭제하지 않는다.
- 최종 선택 ID는 ID 오름차순으로 잠그고 조건을 재확인해 삭제한다. 직전 연장·정식 생성 전환으로 유효해진 행은 건너뛰며, 상한을 채우려고 같은 실행에서 무제한 반복 조회하지 않는다.
- 주기 실행 주체·DB 시간 제한·중복 실행 방지는 운영 설정 4번에서 담당한다. 실제 실행 계획·잠금 동작은 대상 MySQL 버전에서 검증한다.

## 기존 데이터 전환 절차

아래 명령은 **구현 예정 인터페이스**이며 파일이 존재하거나 실행 가능하다고 보고하지 않는다.

- `python -m scripts.migrate_uuid_auth --check`: 스키마·참조·닉네임 키 충돌·누락·시간 의미의 읽기 전용 사전 점검.
- `python -m scripts.migrate_uuid_auth --apply`: 점검·백업·쓰기 차단 후 명시적 전환.
- `python -m scripts.migrate_uuid_auth --verify`: 구조·유일성·FK·기존 기록 보존 사후 점검.

적용 순서:

1. 실제 MySQL 버전·엔진·부호·collation·기존 FK·행 수·마이그레이션 흔적을 확인한다. 지원되지 않는 구조나 미해결 닉네임 충돌은 변경 전 중단한다. 검증 보고서에 비밀값·JWT·프로필 원문을 출력하지 않는다.
2. 운영 5번 절차에 따라 요청·WebSocket·주기 쓰기를 차단하고 일관된 백업·복구 가능성을 확보한다.
3. 필요한 새 컬럼을 우선 nullable로 추가하고 레거시 카카오 구분을 기존 행에만 채운다. 이미 채워진 UUID를 재실행으로 바꾸지 않는다.
4. 기존 사용자에게 누락 UUID·닉네임 키만 채운다. `users.id`, 카카오 ID, 표시 프로필, 생성/수정 시각·관련 기록을 바꾸지 않는다. 기존 수정 시각 자동 갱신이 있는 실제 스키마라면 이를 보존할 수 있는 적용 명령을 확인한다.
5. UUID 유일성·누락 0건·참조 보존을 확인한 뒤 UUID NOT NULL과 유일 인덱스·닉네임 키 유일 제약을 적용한다. `kakao_id` NULL 허용을 적용한다.
6. 인증 표·FK·인덱스를 생성한다. 기존 JWT를 새 인증으로 자동 교환하거나 사용자의 비밀 쿠키를 임의 생성하지 않는다. 기존 사용자는 합의대로 한 번 재로그인한다.
7. 전후 사용자 ID·카카오 ID·프로필·관련 기록 스냅샷과 행 수·FK를 비교하고 새 발급·검증 코드의 준비 상태를 확인한다. 서비스 재개와 최종 배포는 5번 담당이다.

- 중간 실패 시 적용된 컬럼·제약·자료형을 검사하고 정확히 일치하는 단계만 건너뛴다. 이름만 같고 정의가 다르면 멈춘다. 이미 채운 값을 재생성하거나 무조건 DROP·재생성하지 않는다.
- MySQL 구조 변경은 암묵적 커밋이 발생할 수 있으므로 전체가 일반 트랜잭션처럼 한 번에 롤백된다고 가정하지 않는다. [MySQL 공식 설명](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)
- `kakao_id`의 NULL 허용과 유일 인덱스는 미연결 사용자 여러 명을 허용하면서 실제 카카오 ID 중복을 막는다. MySQL 유일 인덱스는 nullable 컬럼의 여러 NULL을 허용한다. [MySQL CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)

## 검증과 완료 경계

- 격리 MySQL에서 기존 카카오 사용자·NULL/긴 닉네임·식사·추천·방 참조를 갖춘 fixture로 check/apply/verify·재실행·중단 후 재개를 검증한다. SQLite로 MySQL FK·바이트·행 잠금·DDL 호환을 증명하지 않는다.
- 같은 쿠키 동시 생성의 한 사용자 수렴, 닉네임/UUID 충돌, 갱신·종료·정리의 경합, 서로 다른 쿠키의 독립 생성과 응답 유실 복구를 실제 앱 API로 검증한다.
- `UserResponse.kakao_id`는 nullable로 확장하고 UUID를 추가하되 기존 카카오 사용자의 필드 값·정수 ID를 유지한다. 기존 서비스가 카카오 재로그인 때 프로필을 덮어쓰는 동작은 이관·프로필 출처 정책에 맞춰 T01 발급과 후속 T04~T07에서 조정해야 한다.
- 이 계약으로 2번 DB 설계 묶음은 구조·전환·검증 기준 정리 완료다. 실제 운영 데이터 충돌 유무·DB 버전은 미확인이고 실행 전 점검 관문으로 남는다. 자료형 호환·성능·잠금은 구현 시 검증하며 결과 없이 통과로 기록하지 않는다.
- 예외 데이터가 발견되면 현재 보존 정책대로 적용을 멈춘다. 그 사실을 숨기거나 이 계약만으로 기존 닉네임 변경·사용자 병합을 승인받았다고 해석하지 않는다.

# #39 설계 작업 인계 — 2026-11-13

최신 시작점: [최종 설계 기준](39-design-baseline.md). 주요 선택과 통합 설계·검증 계획 작성은 마쳤고, 구현·실제 데이터/환경 검증은 내일 작업으로 구분한다. 아래는 의사결정 이력이며 과거 미선택 표현을 현재 미결정으로 해석하지 않는다.

## 2026-11-13 M1A·M2A·M3A·M4A 선택 갱신

- 초기 개인 보정 최대 ±5점(100점 환산)·90일 반감기·k=5·근접 추첨 개인 가중치 최대 1.5:1, 섭취 불가 8재료군, 별도 기존 환경 학습, 사진 1,200만 픽셀 이하·긴 변 512px 정지 이미지 정규화를 사용자가 선택했다.
- 기존 최신 불만족 0.35 감점은 새 보정으로 교체하며 모델이 없거나 검증을 못 통과하면 개인 보정 없이 기본 추천을 제공하고 평가를 계속 저장한다. 모델 전체 재학습과 새 개인 이력 입력의 즉시 갱신은 구분한다.
- [최신 선택](39-final-design-choices.md)과 [통합 설계](39-implementation-architecture.md)가 아래 과거 미선택 표현보다 우선한다. 설계 선택과 코드/학습/검증 완료를 구분한다.

## 2026-11-13 통합 기술 초안·검증 계획 갱신

- 최신 공통 선택은 R1A·R2A·R3A·R4A·R5A다. RAM 1GB·백엔드/MySQL 동시 운영, 두 단계 전환, 이관 후 원본 사용자 물리 삭제, 탭 알림·재확인, 인증/만료 없는 사진 URL을 기준으로 한다. 사진 클릭·확대·공유 UI는 만들지 않는다.
- [통합 구현 아키텍처](39-implementation-architecture.md)와 [T09 검증·인계](39-validation-and-handoff.md)를 작성했다. [M1~M4](39-final-design-choices.md)는 모두 미선택이다. 반영 강도/최근성·첫 재료 범위·학습 실행 자원·사진 해상도 정책을 한 번에 검토한다.
- [ADR-0003](../adr/0003-account-transition-and-runtime-decisions.md)은 승인 정책만 기록한다. 통합 문서의 테이블·API·운영값 초안과 구분한다. 오늘 설계·내일 구현 일정을 유지하며 코드·DB·모델 학습·브라우저 테스트는 새로 수행하지 않았다.
- 로컬 메뉴 JSON/CSV 7,503행의 스키마를 확인했고 전체 원재료표는 없다. 실제 운영 데이터 대응·메뉴 매핑·모델 품질·1GB 처리 용량은 아직 검증하지 않았다. 아래 과거 보류/초기 상태보다 이 갱신이 우선한다.

## 2026-11-13 T02 최신 설계·검토 방식 갱신

- 최신 일정은 오늘 2시간 내 T02~T09 설계, 내일(2026-11-14) 구현·검증이다. 9B·10A까지 체크리스트 선택을 마쳤다. [설계 마무리 계획](39-design-completion-plan.md)을 따르고 오늘 코드 구현을 재개하지 않는다. 일정 오해로 시작한 추가 코드 변경은 해당 부분만 제거했으며 기존 T01은 유지했다.
- T01 서버 구현 이후 T02 설계를 진행 중이며 T02의 실행 코드 변경·통합 검증은 아직 시작하지 않았다. [T02 아키텍처](39-t02-personal-data-architecture.md)의 승인·미결정 상태를 따른다.
- 사용자는 여러 신호를 학습하는 추천 모델과 실제 피드백에 따른 조정을 선택했다(D11). 이후 D13에서 체크리스트 1A·2A·3A·4A·5B·6A·7A·8B를 승인했고 9·10번은 설명 요청으로 보류했다. 구체적인 학습·계수·저장·검증 계약과 실행 코드 적용은 남아 있다.
- 검토 방식은 한 번에 하나 질문하기에서 [체크리스트](39-t02-architecture-checklist.md) 일괄 비교·선택·보류·질의응답으로 변경했다(D12). 미응답과 추천 표시는 승인이 아니다. 아래 초기 작업 범위 서술보다 이 갱신이 우선한다.

## 2026-11-13 T01 구현 갱신

- 사용자의 T01 시작 지시에 따라 사용자 생성·복원 HTTP API, 별도 인증 세션·JWT 검증, WebSocket 재인증·만료, 기존 MySQL 전환과 제한된 인증 정리 명령을 구현했다. 현재 구현은 [UUID 인증 연동 문서](../UUID_AUTH_API.md)와 LOG 최신 기록을 따른다.
- T01·관련 MySQL 묶음 80개 통과. 전체 회귀는 305개 통과·기존 메뉴 표시명 불일치 2개 실패다. 격리 MySQL 8.4.13을 사용했으며 운영 DB·배포·실제 브라우저는 검증하지 않았다.
- 아래의 ‘구현 전·코드 변경 없음’ 서술은 이전 설계 인계 당시의 상태다. 현재 구현 상태는 이 갱신이 우선한다. 미결정 플랫폼·새 실행 환경·여러 탭 정책·운영·배포 설계가 자동 승인된 것은 아니다.
- JWT_SECRET은 기본값 없이 최소 32자를 요구한다. 기존 JWT 재로그인, 단독 카카오 로그인과 UUID 기록 이관의 구분, DB 전환·쿠키 연동을 배포 전에 확인한다. T02 기록과 실제 코드의 차이도 별도 확인 대상으로 남는다.

## 최신 사용자 확인과 설명 방식

- 앱 형태는 아직 정하지 않았다. 공통 서버 우선 진행·앱별 보관과 전달 분리·플랫폼 선택 유보는 에이전트 제안이며 사용자가 선택하지 않았다. 현재 웹 쿠키·탭 검토를 모든 앱에 일반화하지 않는다. 앱 전용 인증 경로는 미승인·미구현이다.
- 최신 D12에 따라 선택지·trade-off·근거를 체크리스트로 함께 제시하고 사용자가 항목별로 선택·보류·질문한다. 한 번에 하나 질문하도록 했던 이전 지시는 대체됐다. 추천·미응답·건너뛰기를 승인으로 처리하지 않고 설명이 필요한 항목은 질의응답으로 검토한다.
- 아키텍처 채택·변경·유보는 사용자 결정이다. 응답 전 제안을 확정·구현하지 않는다. 앞서 에이전트가 새 UUID 생성 방향으로 바꾸지 않겠다고 한 설명은 승인된 선택이 아니다. 기존 승인된 동일 인증 복원과 새 실행 환경의 사용자 정책을 구분한다.
- 탭마다 새 사용자 생성, 모든 탭의 사용자 일치 보장, 다른 탭의 보호 요청 보류·사용자 확인, 전환 준비·확정 두 요청은 이번 대화에서 승인되지 않았다. 기존 동일 인증 복원·데이터 보존·방 참여 중 전환 금지는 유지한다.

## 핵심 합의

- 서버에서 32바이트 무작위 비밀값을 발급하고 브라우저 HttpOnly 쿠키에 저장한다. 서버에는 SHA-256 해시만 `BINARY(32)`로 저장하며 해시에 유일 인덱스를 둔다. UUID 자체는 인증 수단이 아니다.
- 기존 `users` 표와 정수 PK·이용 기록을 보존하며 UUID를 추가하고 `kakao_id` NULL을 허용한다. 인증 기록은 별도 표에 둔다. 실제 나머지 자료형·인덱스·기존 데이터 채움은 미확정이다.
- 준비 API에서 인증 기록을 만들고, 5분 안의 생성 요청에서 사용자 생성과 같은 인증 기록의 FK 연결을 원자적으로 수행한다. 사용자 FK가 없으면 준비, 있으면 정식이며 별도 단계 상태 컬럼은 추가하지 않는다.
- 생성이 완료됐는데 응답이 유실된 경우 같은 쿠키로 기존 사용자를 복구한다. 초기 쿠키 보관은 30일 + 5분이며 서버 준비 유효 시간은 5분이다.
- 정식 인증은 30일. 만료 전 유효 쿠키로 JWT 발급·재발급에 성공할 때 현재부터 30일 연장한다. 일반 API 요청이나 준비 요청만으로 연장하지 않는다.
- JWT는 1시간이며 `sub`, `sid`, `iat`, `exp`, `iss`, `aud`를 담는다. 비밀값·해시·프로필은 넣지 않는다. JWT 재발급 시 인증 기록 번호는 그대로 유지한다.
- 일반 API는 JWT와 DB 인증 기록·연결 사용자 일치를 검증한다. DB 장애는 인증 부재로 바꾸지 않는다. 종료된 인증은 JWT 시간이 남아 있어도 거절한다.
- 프론트 JWT는 메모리에만 보관한다. 새로고침·새 탭에서는 비밀 쿠키로 같은 사용자 JWT를 복원하며 JWT 부재만으로 새 사용자를 만들지 않는다.
- HTTP는 JWT 만료 응답 후 재발급·원래 요청 1회 재시도를 사용하고 동시 갱신은 합친다. 활성 WebSocket은 만료 전 새 JWT를 발급받아 연결 안에서 재인증하기로 2026-11-13 합의했다. 모든 401을 재발급하지 않는다.
- 안전한 일시 장애 재시도는 최초 포함 총 3회, 대기 1초·2초의 ±50% 지터, 시도당 최대 3초, 전체 최대 10초다. 클라이언트 타임아웃은 DB 롤백을 뜻하지 않는다.
- 세 API: 준비 `POST /api/auth/preparations`, 생성 `POST /api/auth/anonymous-users`, 복원·재발급 `POST /api/auth/tokens`. 첫 방문은 준비·생성 두 요청이다.
- 준비 응답은 `next_action`으로 `CREATE_USER`/`ISSUE_TOKEN`을 안내한다. JWT 성공 응답은 JWT와 사용자 DTO를 함께 반환한다. 세부 상태·오류 분기는 승인된 HTTP 문서를 따른다.
- 같은 쿠키의 중복 생성은 한 사용자에 수렴시킨다. 서로 다른 쿠키의 여러 탭이 별도 사용자를 만드는 것은 허용한다. 브라우저별 사용자 자동 병합은 하지 않는다.
- 종료·만료 기록은 10분마다 실행당 총 최대 100건 정리한다. 사용자와 이용 기록은 삭제하지 않는다. 실행 주체·정렬·DB 제한 상세는 남아 있다.
- 카카오 로그아웃은 이전 인증 종료 후 새 UUID 이용이다. UUID에서 카카오로 이관 성공 후 이전 UUID 인증을 종료한다. 방 참여 및 60초 재접속 유예 중에는 전환을 제한한다.
- 신규 구조 배포 시 기존 세션 번호 없는 카카오 JWT는 한 번 재로그인하도록 한다. 기존 계정·프로필·기록은 보존한다.
- 현재 Vercel 프론트와 `whatbob.kro.kr`의 서로 다른 사이트 구성을 유지한다. 쿠키는 HttpOnly·Secure·SameSite=None, Domain 생략, Path=/api/auth다. 정확한 Origin과 필수 `X-Whatbob-Request: 1` 헤더로 웹 쿠키 명령을 보호한다. OPTIONS와 실제 요청은 별도로 처리한다.
- 별도 테스트 서버·DB는 만들지 않고 구현 후 현재 HTTPS 배포 환경에서 실제 브라우저 인증·쿠키를 검증한다. 자동 테스트는 격리 DB를 유지한다. 타사 쿠키 차단 한계와 쿠키 미전달 시 무한 재시도 금지를 유지한다. 운영 쿠키 이름은 아직 미확정이다.
- DB 변경·배포는 점검 중 잠시 서비스를 중단하는 방식이다. 사전 점검 → 요청·진행 작업 정리 → 백업·복구 준비 → 스키마 변경 → 백엔드·프론트 배포 → 검증 → 재개 순서다. 실제 운영 작업은 아직 하지 않았다.

인계 후 사용자가 아래 2번을 선택했다. 기존 1번 추천안 대신 연결 유지 중 재인증을 채택한다.

1. JWT 만료 시 연결 종료 → 비밀 쿠키로 JWT 재발급 → 같은 사용자·인증 기록으로 재연결 → 방 상태 다시 조회. 이전 추천안이며 미채택이다.
2. 연결을 유지하면서 새 JWT로 재인증하는 메시지를 추가한다. **사용자 선택.**
3. 처음 연결할 때만 검증한다. 이후 만료·인증 종료 반영에는 별도 장치가 필요하다.

만료 전에 토큰 API로 갱신한 뒤 같은 사용자·인증 기록의 새 JWT를 현재 연결에서 검증하고, 성공 확인 후 연결의 인증 정보를 교체한다. 기존 JWT 만료까지 완료하지 못하면 종료한다. 연결 유지가 실패한 실제 단절에는 기존 재접속 정책이 적용된다. 명시적 인증 종료는 재발급 반복 대상이 아니며 방 참여 중 로그아웃 금지 정책은 유지한다.

추가 사용자 결정: 활성 WebSocket이 있는 브라우저가 JWT 만료 2분(120초) 전에 갱신을 시작한다. JWT 수명 1시간은 유지하며 2분마다 갱신하는 뜻이 아니다. 새 JWT 만료 시각을 기준으로 다음 갱신을 예약한다. 백그라운드 지연에 의한 실패 가능성과 서버의 만료 시 종료는 유지한다.

추가 사용자 확인: 방 참여 요청을 시작한 순간부터 응답 대기 중에도 로그인·로그아웃·계정 전환이 불가능하다. 성공하면 참여·유예 중 제한을 유지하고, 실패가 확정되면 요청 중 차단을 해제한다. 응답 유실·시간 초과 시 서버의 참여 여부와 처리 결과를 확인한 뒤 판단하며, 아직 처리 중인 요청의 지연 성공을 배제하지 않은 채 해제하지 않는다. 프론트 차단과 서버 검증을 함께 적용한다. 방 이용 중 계정 전환을 허용하는 별도 흐름은 추가하지 않는다.

추가 사용자 승인: `auth.refresh`로 새 JWT·요청 번호를 전달하고 서버가 JWT·DB 인증 기록·동일 사용자와 인증 기록을 검증한 뒤 교체한다. `auth.refreshed`의 같은 요청 번호와 적용된 만료 시각으로 성공을 확인한다. 확인 유실 시 같은 JWT·번호로 제한적 재전송, 중복 성공 확인, 이전 상태로 되돌리지 않기, 끝내 확인 실패 시 연결 정리·유효 JWT로 재연결·방 상태 재조회를 채택했다. 상세는 WebSocket 재인증 계약을 따른다.

추가 사용자 승인: 토큰 API 최초 요청부터 WebSocket 성공 확인까지 하나의 최대 10초 한도를 공유한다. 토큰 API와 WebSocket은 각각 최초 포함 최대 3회이며 각 대기는 최대 3초와 전체 남은 시간 중 작은 값이다. WebSocket 재전송 전에는 1초·2초 기준 ±50% 지터를 적용하고 대기 중 성공하면 취소한다. 전체 시간이 먼저 끝나면 남은 시도를 하지 않는다.

추가 사용자 결정: 방 재접속 유예를 60초로 변경했다. 자동 재연결은 최초 포함 최대 3회·각 시도 최대 3초·전체 최대 10초이며 기존 지터를 적용한다. 최초 인증과 `connection.ready`까지 확인한 뒤 방 상태를 조회한다. 한도 내 실패 시 자동 반복을 멈추고 수동 재시도를 제공하며 복구 불가 오류는 즉시 중단한다. 재연결은 유예 기한을 새로 주거나 갱신 10초부터 자동 순환을 반복하는 수단이 아니다. 현재 코드 기본 유예도 60초지만 일반 참여자 자동 퇴장은 아직 새 정책의 미구현 부분이다.

인증 통신 마무리: 에이전트가 기존 정책 안에서 요청 번호·UTC 날짜, 오류·종료 코드, 동일 화면의 토큰 발급 공유, 연결별 성공 확인, 늦은 응답·만료 경합과 Origin 경계를 계약으로 구체화했다. 이를 별도 사용자 정책 승인으로 기록하지 않는다. 모든 보호 데이터 전송 전 DB 조회·정기 조회·Redis 도입은 여전히 미채택이다. 참여 결과 확인과 여러 탭 계정 전환은 진행표의 3번 범위다.

현재 인증 통신과 DB 묶음은 설계 정리 완료이며 남은 설계는 고정된 3묶음이다. 여러 탭·계정 전환은 검토안을 작성했고 정책 검토 1개와 미정리 운영·배포 2개가 남는다. DB 계약은 기존 사용자 ID·FK·프로필·기록을 보존하고 UUID·인증 표를 추가하며 실제 닉네임 충돌은 적용 전 중단한다. 기술 세부마다 대화를 멈추지 않고 정책 안에서 정리하며, 사용자 경험·보안·데이터 보존 정책 변경은 trade-off와 현업 근거를 포함해 묶어서 설명한다.

현재 `app/rooms/websocket.py`는 첫 인증 메시지에서 JWT를 확인하고 이후 ping/pong과 브로드캐스트 연결을 유지한다. 만료 타이머·진행 중 DB 인증 확인·인증 종료 시 연결 해제의 상세 설계 및 구현은 아직 없다. 일반 HTTP 요청과 다른 WebSocket의 Origin 검사와 보호 데이터 전송도 함께 검토해야 한다.

## 남은 설계와 구현

- DB: 설계 정리는 DB 계약을 따른다. 마이그레이션 명령의 구현·실제 버전과 충돌 점검·구조 적용·보존 검증은 미실행이다. 후속 프로필 편집·이관 전용 메타데이터는 담당 T04~T07에서 추가한다.
- 계정 전환·동시성: 여러 탭·계정 전환 시 진행 중 요청·응답, 쿠키 덮어쓰기, 종료 쿠키 재시작, 참여 결과 확인. 같은 화면의 JWT 갱신 합치기와 WebSocket 만료·오류 처리는 통신 계약에 정리됐다.
- 운영: 요청 제한 위치·임계값, DB 시간 제한, 정리 실행 주체, 점검 진입·백업·복구·재개 기준과 배포 순서.
- 쿠키 설정: 운영 쿠키 이름과 실제 설정 연결. 로컬 HTTP 전용 쿠키나 별도 테스트 환경 도입은 확정하지 않았다.
- T01 구현·격리 테스트·프론트 연동 이후 T02~T09를 진행한다. 현재 인증 설계는 실행 코드에 반영되지 않았다.

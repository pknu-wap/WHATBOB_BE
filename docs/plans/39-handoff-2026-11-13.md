## 핵심 합의

- 서버에서 32바이트 무작위 비밀값을 발급하고 브라우저 HttpOnly 쿠키에 저장한다. 서버에는 SHA-256 해시만 `BINARY(32)`로 저장하며 해시에 유일 인덱스를 둔다. UUID 자체는 인증 수단이 아니다.
- 기존 `users` 표와 정수 PK·이용 기록을 보존하며 UUID를 추가하고 `kakao_id` NULL을 허용한다. 인증 기록은 별도 표에 둔다. 실제 나머지 자료형·인덱스·기존 데이터 채움은 미확정이다.
- 준비 API에서 인증 기록을 만들고, 5분 안의 생성 요청에서 사용자 생성과 같은 인증 기록의 FK 연결을 원자적으로 수행한다. 사용자 FK가 없으면 준비, 있으면 정식이며 별도 단계 상태 컬럼은 추가하지 않는다.
- 생성이 완료됐는데 응답이 유실된 경우 같은 쿠키로 기존 사용자를 복구한다. 초기 쿠키 보관은 30일 + 5분이며 서버 준비 유효 시간은 5분이다.
- 정식 인증은 30일. 만료 전 유효 쿠키로 JWT 발급·재발급에 성공할 때 현재부터 30일 연장한다. 일반 API 요청이나 준비 요청만으로 연장하지 않는다.
- JWT는 1시간이며 `sub`, `sid`, `iat`, `exp`, `iss`, `aud`를 담는다. 비밀값·해시·프로필은 넣지 않는다. JWT 재발급 시 인증 기록 번호는 그대로 유지한다.
- 일반 API는 JWT와 DB 인증 기록·연결 사용자 일치를 검증한다. DB 장애는 인증 부재로 바꾸지 않는다. 종료된 인증은 JWT 시간이 남아 있어도 거절한다.
- 프론트 JWT는 메모리에만 보관한다. 새로고침·새 탭에서는 비밀 쿠키로 같은 사용자 JWT를 복원하며 JWT 부재만으로 새 사용자를 만들지 않는다.
- JWT 만료 응답 후 재발급·원래 요청 1회 재시도를 사용하고 동시 갱신은 합친다. 모든 401을 재발급하지 않는다.
- 안전한 일시 장애 재시도는 최초 포함 총 3회, 대기 1초·2초의 ±50% 지터, 시도당 최대 3초, 전체 최대 10초다. 클라이언트 타임아웃은 DB 롤백을 뜻하지 않는다.
- 세 API: 준비 `POST /api/auth/preparations`, 생성 `POST /api/auth/anonymous-users`, 복원·재발급 `POST /api/auth/tokens`. 첫 방문은 준비·생성 두 요청이다.
- 준비 응답은 `next_action`으로 `CREATE_USER`/`ISSUE_TOKEN`을 안내한다. JWT 성공 응답은 JWT와 사용자 DTO를 함께 반환한다. 세부 상태·오류 분기는 승인된 HTTP 문서를 따른다.
- 같은 쿠키의 중복 생성은 한 사용자에 수렴시킨다. 서로 다른 쿠키의 여러 탭이 별도 사용자를 만드는 것은 허용한다. 브라우저별 사용자 자동 병합은 하지 않는다.
- 종료·만료 기록은 10분마다 실행당 총 최대 100건 정리한다. 사용자와 이용 기록은 삭제하지 않는다. 실행 주체·정렬·DB 제한 상세는 남아 있다.
- 카카오 로그아웃은 이전 인증 종료 후 새 UUID 이용이다. UUID에서 카카오로 이관 성공 후 이전 UUID 인증을 종료한다. 방 참여 및 30초 재접속 유예 중에는 전환을 제한한다.
- 신규 구조 배포 시 기존 세션 번호 없는 카카오 JWT는 한 번 재로그인하도록 한다. 기존 계정·프로필·기록은 보존한다.
- 현재 Vercel 프론트와 `whatbob.kro.kr`의 서로 다른 사이트 구성을 유지한다. 쿠키는 HttpOnly·Secure·SameSite=None, Domain 생략, Path=/api/auth다. 정확한 Origin과 필수 `X-Whatbob-Request: 1` 헤더로 웹 쿠키 명령을 보호한다. OPTIONS와 실제 요청은 별도로 처리한다.
- 별도 테스트 서버·DB는 만들지 않고 구현 후 현재 HTTPS 배포 환경에서 실제 브라우저 인증·쿠키를 검증한다. 자동 테스트는 격리 DB를 유지한다. 타사 쿠키 차단 한계와 쿠키 미전달 시 무한 재시도 금지를 유지한다. 운영 쿠키 이름은 아직 미확정이다.
- DB 변경·배포는 점검 중 잠시 서비스를 중단하는 방식이다. 사전 점검 → 요청·진행 작업 정리 → 백업·복구 준비 → 스키마 변경 → 백엔드·프론트 배포 → 검증 → 재개 순서다. 실제 운영 작업은 아직 하지 않았다.

## 다음 논의: WebSocket JWT 만료 처리 — 아직 미승인

마지막으로 제안한 내용이며 사용자가 아직 선택하지 않았다. 중단 전 대화는 아래 선택지 설명까지 진행됐다.

1. JWT 만료 시 연결 종료 → 비밀 쿠키로 JWT 재발급 → 같은 사용자·인증 기록으로 재연결 → 방 상태 다시 조회. 현재 추천안이다.
2. 연결을 유지하면서 새 JWT로 재인증하는 메시지를 추가한다.
3. 처음 연결할 때만 검증한다. 이후 만료·인증 종료 반영에는 별도 장치가 필요하다.

추천안 1의 재연결이 30초 유예를 넘으면 기존 퇴장·방 종료 정책이 적용될 수 있음을 설명했다. JWT 만료는 재발급 대상이지만 명시적 종료는 재발급 반복 대상이 아니다. 방 참여 중 로그아웃 금지 정책은 그대로 유지한다.

현재 `app/rooms/websocket.py`는 첫 인증 메시지에서 JWT를 확인하고 이후 ping/pong과 브로드캐스트 연결을 유지한다. 만료 타이머·진행 중 DB 인증 확인·인증 종료 시 연결 해제의 상세 설계 및 구현은 아직 없다. 일반 HTTP 요청과 다른 WebSocket의 Origin 검사와 보호 데이터 전송도 함께 검토해야 한다.

## 남은 설계와 구현

- DB: UUID 형식·채움 대상, 인증 표 이름·자료형·FK 삭제 정책·인덱스, 기존 닉네임 충돌·기본 사진·프로필 출처 및 마이그레이션 명령.
- 계정 전환·동시성: 진행 중 요청·응답, 여러 탭, 쿠키 덮어쓰기, 종료 쿠키 재시작, WebSocket 만료·폐기 반영.
- 운영: 요청 제한 위치·임계값, DB 시간 제한, 정리 실행 주체, 점검 진입·백업·복구·재개 기준과 배포 순서.
- 쿠키 설정: 운영 쿠키 이름과 실제 설정 연결. 로컬 HTTP 전용 쿠키나 별도 테스트 환경 도입은 확정하지 않았다.
- T01 구현·격리 테스트·프론트 연동 이후 T02~T09를 진행한다. 현재 인증 설계는 실행 코드에 반영되지 않았다.

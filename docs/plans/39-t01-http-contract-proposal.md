# T01 인증 API 상세 계약

작성·합의: 2026-11-12. 상태: 사용자 승인된 설계 계약. 2026-11-13 T01 서버 구현·격리 검증을 수행했다. 현재 구현·설정·미실행 검증은 [연동 문서](../UUID_AUTH_API.md)와 LOG 최신 기록을 따른다. 아래 기존 코드 관찰과 미실행 서술은 설계 작성 시점의 기록이다. 기존 합의는 [인증 아키텍처](39-t01-auth-architecture.md)를 따르며 아래 상태 코드·오류 코드·응답 필드는 구현 기준으로 사용한다. 파일명은 기존 문서 링크를 유지하기 위해 보존했다.

## 범위와 기존 코드

- 새 세 POST API와 새 JWT 검증 경계의 계약이다. 기존 일반 API 오류 형식을 일괄 교체하지 않는다.
- 현재 `app/auth/router.py`는 카카오 경로만 제공하고 `TokenResponse`는 JWT와 사용자 정보를 함께 반환한다. 현재 인증 의존성은 문자열 `detail`을 사용한다. 새 구조에 맞는 발급·검증·프론트 배포와 카카오 응답 호환은 별도 작업이다.
- 새 쿠키 API는 JSON 본문 없이 호출할 수 있게 한다. 사용자 번호·UUID·비밀값을 JSON 입력으로 받지 않는다. 임의 본문은 인증 근거로 사용하지 않는다. 쿠키와 기존 Origin·`X-Whatbob-Request: 1` 검사를 사용한다.
- 일반 보호 API는 Bearer JWT만 사용하며 쿠키를 JWT의 대체 인증 수단으로 사용하지 않는다.

## 성공 응답과 HTTP 상태

| API | 성공 상태 | 응답 |
| --- | --- | --- |
| `POST /api/auth/preparations` | 신규·재사용 모두 200 | `next_action`과 선택적 `notice` |
| `POST /api/auth/anonymous-users` | 이번 요청에서 사용자 신규 생성 시 201, 이미 생성된 유효 사용자 복구 시 200 | 공통 JWT·사용자 응답 |
| `POST /api/auth/tokens` | 200 | 공통 JWT·사용자 응답 |

- 프론트는 성공 여부를 2xx로 판단하며 최초 생성과 재요청의 상태·JWT·만료 시각·`is_new_user`가 달라도 같은 사용자로 수렴하는 것을 보장 대상으로 한다. 응답 바이트가 동일하다는 보장이 아니다.
- 준비 응답의 `next_action`은 `CREATE_USER` 또는 `ISSUE_TOKEN`이다. `notice`는 기본 `null`, DB 조회 성공·기록 부재 또는 정식 인증 만료로 새 준비로 교체했다면 `PREVIOUS_SESSION_UNAVAILABLE`로 한다. 프론트는 이전 인증으로 복원할 수 없고 새 사용자로 시작한다는 안내를 표시한다. 별도 확인 클릭은 요구하지 않는다.
- 유효한 기존 쿠키 재사용은 `Set-Cookie`를 내보내지 않고 새 준비는 DB 저장 성공 후 새 쿠키를 설정한다. 공통 JWT 성공 응답은 기존 합의에 따라 정식 쿠키 만료를 갱신한다.
- 인증 API 성공·오류 응답에 `Cache-Control: no-store`를 적용하고 공통 JWT 성공 응답에는 `Pragma: no-cache`도 적용한다. 쿠키·JWT·해시를 로그나 오류 메시지에 기록하지 않는다.

## 쿠키 상태별 분기

이 표는 CSRF 검사 통과 후 동작이다. DB 오류는 아래 상태 중 하나로 바꾸지 않고 별도 503 또는 500을 반환한다. 만료 경계는 `now >= expires_at`, 종료 여부는 만료보다 먼저 판정한다.

| 쿠키·인증 상태 | 준비 API | 사용자 생성 API | 토큰 API |
| --- | --- | --- | --- |
| 쿠키 없음 | 새 준비 + `CREATE_USER` | 401 `AUTH_COOKIE_MISSING` | 401 `AUTH_COOKIE_MISSING` |
| 쿠키 형식 잘못됨 | 400 `INVALID_AUTH_COOKIE` | 400 `INVALID_AUTH_COOKIE` | 400 `INVALID_AUTH_COOKIE` |
| 형식 정상, DB 조회 성공·기록 없음 | 새 준비 + `CREATE_USER`, 안내 포함 | 401 `SESSION_NOT_FOUND` | 401 `SESSION_NOT_FOUND` |
| 유효한 준비 기록 | 기존 준비 유지 + `CREATE_USER` | 원자적으로 사용자 생성·연결 + JWT | 409 `AUTHENTICATION_NOT_READY` |
| 만료된 준비 기록 | 새 준비 + `CREATE_USER` | 401 `PREPARATION_EXPIRED` | 401 `PREPARATION_EXPIRED` |
| 유효한 정식 기록 | 기존 정식 유지 + `ISSUE_TOKEN` | 같은 사용자 복구 + JWT | 같은 사용자 JWT |
| 만료된 정식 기록 | 새 준비 + `CREATE_USER`, 안내 포함 | 401 `SESSION_EXPIRED` | 401 `SESSION_EXPIRED` |
| 명시적 종료 기록 | 401 `SESSION_REVOKED`, 쿠키 교체 없음 | 401 `SESSION_REVOKED` | 401 `SESSION_REVOKED` |
| 정식 기록의 연결 사용자가 없거나 이용 불가 | 401 `SESSION_UNAVAILABLE`, 쿠키 교체 없음 | 401 `SESSION_UNAVAILABLE` | 401 `SESSION_UNAVAILABLE` |

- 기록 부재·미사용 준비 만료·정식 기록 만료 시 준비 API에서 새 준비로 전환한다. 기존 인증을 연장하거나 이전 사용자로 복구하는 것이 아니다.
- 잘못된 쿠키 형식의 정확한 길이·문자 제한은 비밀값 인코딩 계약과 함께 정의한다. `INVALID_AUTH_COOKIE`는 조작을 단정하는 코드가 아니며 자동 재시도하지 않는다. 이 오류에서 무조건 쿠키를 지우면 다른 탭의 새 쿠키를 덮을 수 있으므로 실패 응답은 쿠키를 임의 교체·삭제하지 않는다.
- 명시적 종료 기록은 자동 새 준비 대상이 아니다. 계정 전환 결과 복구와 종료 쿠키를 새 준비로 바꾸는 명시적 흐름은 전환·동시성 설계에서 구체화한다. 기록이 이미 정리됐다면 이전 종료 사유를 알아낼 수 없으며 기존 기록 부재 정책을 따른다.
- 사용자 FK 불일치·이용 불가는 준비로 취급하지 않고 접근을 거절한다. 실제 FK 무결성 손상과 예기치 않은 내부 오류는 500 및 운영 확인 대상으로 분리하고 오류 상세를 노출하지 않는다.

## 오류 응답과 프론트 처리

형태는 기존 합의의 `{"detail":{"code":"...","message":"..."}}`를 유지한다. 아래 고정 코드와 프론트 처리 방향을 새 인증 경계의 구현 기준으로 사용한다.

| HTTP | 코드 | 프론트 행동 |
| --- | --- | --- |
| 401 | `ACCESS_TOKEN_MISSING` | 초기 복원 상태를 확인하고 쿠키 기반 시작 절차 사용. 원래 변경 요청을 무조건 재실행하지 않음 |
| 401 | `ACCESS_TOKEN_INVALID` | 해당 JWT 사용 중단. 만료 갱신 루프로 처리하지 않음 |
| 401 | `ACCESS_TOKEN_EXPIRED` | 기존 합의대로 갱신 합치기 후 원래 요청 한 번 재시도 |
| 401 | `REAUTHENTICATION_REQUIRED` | 검증된 이전 형식 토큰이면 기존 합의대로 카카오 재로그인 |
| 401 | `AUTH_COOKIE_MISSING` | 최초 시작이면 준비 API 사용. 방금 준비 후 생성에서도 쿠키가 없으면 반복을 중단하고 쿠키 전달 확인 안내 |
| 400 | `INVALID_AUTH_COOKIE` | 자동 반복 중단, 쿠키 처리 설정 확인·사용자 재시작 안내 |
| 401 | `SESSION_NOT_FOUND` | 준비 API로 이동. 그 API만 새 준비를 발급하며 원래 변경 요청은 재실행하지 않음 |
| 409 | `AUTHENTICATION_NOT_READY` | 준비된 쿠키의 사용자 생성 API로 이동. 무한 재발급 금지 |
| 401 | `PREPARATION_EXPIRED` | 새 준비 후 사용자 생성. 이전 준비 부활 금지 |
| 401 | `SESSION_EXPIRED` | 기존 사용자 JWT·화면 상태를 정리하고 새 준비·UUID 시작 흐름 사용 |
| 401 | `SESSION_REVOKED` | 이전 인증 사용 중단. 진행 중 계정 전환 상태 확인, 새 사용자 무조건 생성 금지 |
| 401 | `SESSION_UNAVAILABLE` | 인증 사용 중단, 계정 복구·전환 안내. 자동 생성·갱신 반복 금지 |
| 403 | `CSRF_REJECTED` | 기존 합의대로 자동 재시도 없이 Origin·헤더 설정 확인 |
| 429 | `AUTH_RATE_LIMITED` | `Retry-After` 대기 안내. 기존 총 3회·전체 10초 예산을 넘는 자동 대기·반복 금지 |
| 503 | `AUTH_TEMPORARILY_UNAVAILABLE` | 인증 유지. 안전하게 반복할 수 있는 요청만 기존 예산 내 재시도 |
| 500 | `AUTH_INTERNAL_ERROR` | 인증 유지, 오류 안내. 새 UUID 생성이나 자동 반복의 근거로 사용하지 않음 |

- Bearer 보호 API의 401에는 `WWW-Authenticate: Bearer`를 사용하며 만료·변조 등 무효 토큰에는 `error="invalid_token"`을 함께 사용할 수 있다. 쿠키 API의 오류를 Bearer 인증 실패와 같은 것으로 해석하지 않는다.
- JWT의 서명과 허용 알고리즘 검증 없이 만료·이전 형식이라고 분류하지 않는다. 서명이 유효한 인식 가능한 구형 형식만 재로그인 대상으로 구분한다. 새 형식의 필수 클레임·타입·발급자·대상 불일치와 `sub`·연결 사용자 불일치는 `ACCESS_TOKEN_INVALID`다. 만료와 다른 결함이 함께 있으면 무조건 갱신 가능한 만료로 분류하지 않는다.
- 유효 JWT의 `sid`로 찾은 기록이 없으면 `SESSION_NOT_FOUND`, 만료·종료는 해당 코드로 거절한다. DB 조회 장애는 인증 실패로 바꾸지 않는다. DB 정리 후에는 과거 만료·종료 구분을 보장하지 않는다.
- 오류에서는 원래 추천·식사 저장 등 비즈니스 처리를 시작하지 않는다. 인증 실패 뒤 새 사용자가 생겨도 이전 사용자의 변경 요청을 새 사용자에게 자동 재생하지 않는다.
- 응답 없는 네트워크 장애는 커밋 여부 미확정이다. 사용자 생성은 브라우저가 이미 가진 동일 쿠키로만 안전하게 재시도하며 새 준비 쿠키부터 다시 발급해 재시도하지 않는다. 기존 총 시도·시간 예산을 유지한다.
- 속도 제한 임계값·위치와 `Retry-After` 계산은 운영 제한 묶음에서 정한다. 기존 일반 API의 422 등 프레임워크 오류를 이번 문서만으로 전부 변경하지 않는다.

## 선택의 trade-off

- 사용자 신규 생성 201·기존 복구 200은 동작을 구분하지만 프론트가 두 성공 상태를 지원해야 한다. 모두 200으로 통일하면 분기는 작아지지만 HTTP 상태만으로 신규 생성 여부를 구분하지 못한다. 이번에는 201/200 분리를 채택한다.
- 쿠키 부재·잘못된 상태·기록 부재·DB 장애를 구분하면 사용자 데이터를 잃은 것처럼 처리하거나 중복 생성하는 오류를 줄이지만 코드와 분기 테스트가 늘어난다. 고정 코드로 프론트 행동을 제한하고 메시지로 분기하지 않는다.
- 준비 응답의 선택적 안내 필드는 새 사용자 전환을 알릴 수 있지만 응답 스키마가 추가된다. 기본 `next_action` 두 값은 유지한다.
- 오류에서 쿠키 자동 삭제를 하지 않으면 다른 탭의 최신 인증을 덮을 위험을 줄이지만 종료·잘못된 쿠키의 명시적 재시작 절차가 필요하다. 이 절차는 전환 설계에 남겨 두며 모든 무효 쿠키를 무조건 새 사용자로 바꾸지 않는다.

## 구현 후 검증할 항목

- 상태 표의 각 조합과 만료 경계, 명시적 종료 우선, DB 실패·저장 실패의 쿠키 유지, 오류 시 사용자·JWT 미생성.
- 신규 생성 201과 같은 쿠키 복구 200의 사용자 일치, 새로고침 복원, 토큰 API에서 사용자 미생성, `is_new_user` 의미.
- 준비 안내 후 쿠키 미전달 시 중단, 알 수 없는 코드·행동에서 미생성, 오류 후 이전 사용자 변경 요청의 자동 재생 금지.
- 서명 변조·구형 토큰·필수 클레임 오류·사용자 불일치·JWT 만료 및 DB 인증 만료/종료의 구분과 인증 실패 이전 비즈니스 처리 미실행.
- no-store 헤더, 민감값 비노출, 새 DTO·오류 형식의 기존 카카오·프론트 호환. CORS·쿠키 수용 여부는 실제 브라우저 검증을 별도로 수행한다.

애플리케이션 테스트는 아직 실행하지 않았다. 위 항목은 구현 후 검증 계획이다.

## 공개 근거

- [RFC 9110 HTTP 상태 의미](https://www.rfc-editor.org/rfc/rfc9110.html#name-status-codes): 200·201·400·401·409·500·503의 의미. 세 API에 어떤 코드를 적용할지는 우리 계약의 선택이다.
- [RFC 6750 Bearer 인증](https://www.rfc-editor.org/rfc/rfc6750.html#section-3): Bearer 오류 헤더, 토큰 응답 캐시 제어 예시. 이 문서는 자체 익명 인증을 완전한 OAuth 서버 구현이라고 주장하지 않는다.
- [RFC 6585 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4): 요청 제한과 선택적 Retry-After. 구체적인 제한값은 별도 정책이다.

이 문서는 공개 프로토콜과 현재 코드에 기반한 WhatBap 설계이며 특정 빅테크의 비공개 내부 설계를 재현했다고 주장하지 않는다.

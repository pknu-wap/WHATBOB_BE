# #36 T05 최종 설계 확인안

- 상태: 2026-11-17 사용자 확인 완료 (`T05-D01`, `T05-D02` 전체 확정).
- 범위: 주문서 작성 중 일반 참여자 퇴장 확정 시 라운드 일시 정지(`PAUSED`), 퇴장자 소프트 삭제(`Soft Delete & Status Marking`) 상태 추적, 결정 번호표(`decision_version`) 기반 방장 계속/취소 결정 검증, 2명 미만 시 자동 취소 복귀.
- 선행 조건: `T01` (퇴장 정리 공통화), `T01N` (상태 버전 및 Outbox 알림), `T03` (개인 주문서 제출 및 후보 병합).
- 관련 티켓: [T05 티켓](36-tickets/T05-answering-departure-decision.md).

## 1. 확정된 핵심 아키텍처 결정 요약 (`T05-D01` ~ `T05-D02`)

| 결정 ID | 주제 | 사용자 확정 선택 | 핵심 설계 계약 |
| :--- | :--- | :--- | :--- |
| **T05-D01** | 일시 정지 중 연속 퇴장 및 방장의 결정 동시성 제어 | **1번 확정 (일시정지 결정 번호표 `decision_version` 숫자 비교 `Optimistic Version Token`)** | 주문서 작성 중 참여자의 퇴장이 확정되어 라운드가 일시 정지(`PAUSED`)되거나, 이미 일시 정지된 상태에서 추가 퇴장이 확정될 때마다 `room_rounds.decision_version`을 `+1`씩 올린다. 방장이 '계속 진행(예)' 또는 '라운드 취소(아니요)'를 요청할 때 현재 화면의 `decision_version`을 함께 보내며, 서버 DB의 최신 `decision_version`과 다르면 옛날 화면 기준 결정으로 간주해 거절(`409 Conflict`)하고 최신 퇴장 명단을 다시 확인하게 한다. |
| **T05-D02** | 중도 퇴장한 참여자의 `room_round_members` 행 관리 | **1번 확정 (소프트 삭제 및 상태 도장 `Soft Delete & Status Marking`)** | 중도 퇴장한 참여자의 `room_round_members` 행을 삭제(`DELETE`)하지 않고 보존하되, `member_status` 컬럼으로 상태를 관리한다(`ACTIVE` → 퇴장 확정 시 `LEFT_PENDING` → 방장 계속 진행 승인 시 `LEFT_CONFIRMED`). 별도의 임시 퇴장자 컬럼 없이 `member_status = 'LEFT_PENDING'` 조회만으로 방장 확인 팝업의 퇴장자 명단을 구성하며, 라운드 초기 참여 이력과 `T06`(투표 중 퇴장) 후보 기여자 추적을 단일 구조로 통일한다. |

## 2. 확정된 상세 처리 흐름 및 잠금 규칙

1. **연결 단절 유예와 실제 퇴장 확정의 경계**:
   - 단순 WebSocket 연결 단절 시에는 즉시 라운드를 멈추지 않고 기존의 **60초 재접속 유예(`grace period`)**를 먼저 적용한다. 유예 시간 내 재접속하면 기존 작성·제출 상태를 그대로 유지한다.
   - 명시적 방 나가기 요청 또는 60초 유예 만료로 `T01`의 공통 퇴장 정리가 실행될 때:
     - **방장이 퇴장하거나 방장 유예가 만료된 경우**: 기존 방 종료 정책에 따라 방을 즉시 종료한다.
     - **일반 참여자가 퇴장 확정된 경우**:
       - 대상 `Room` 및 활성 `RoomRound` 행을 잠근다(`with_for_update()`).
       - 해당 참여자의 `room_round_members.member_status`를 `LEFT_PENDING`으로 변경하고 퇴장 시각(`left_at`)을 기록한다(`T05-D02`).
       - **남은 활성 인원(`member_status = 'ACTIVE'`)이 2명 미만(방장 혼자 남은 경우)**:
         - 방장에게 계속 진행 여부를 묻지 않고, 즉시 라운드를 취소(`CANCELLED`, 취소 사유: 최소 인원 미달)하고 방을 대기실 상태(`WAITING`)로 복귀시킨다.
       - **남은 활성 인원이 2명 이상인 경우**:
         - 라운드 상태를 `ANSWERING_PAUSED`(또는 이전 단계 기록 + `PAUSED`)로 전환하고 `room_rounds.decision_version`을 `+1` 증가시킨다(`T05-D01`).
         - 이미 제출을 완료했던 남은 참여자들의 답변과 개인 1순위 메뉴 기록(`submitted_at`, `top_menu_id`), 그리고 시작 시점의 공통 제외 조건 스냅샷은 그대로 보존한다.
2. **일시 정지(`PAUSED`) 중 제출 및 단계 전환 차단**:
   - 라운드가 일시 정지된 동안에는 남은 참여자의 추가 주문서 제출 요청을 거절하며, 방장 외 일반 참여자에게는 "방장의 진행 여부 결정을 기다리는 중" 상태를 안내한다.
3. **방장의 계속 진행(`CONTINUE`) / 라운드 취소(`CANCEL`) 결정 처리 (`T05-D01`, `T05-D02`)**:
   - 방장 권한인지, 라운드가 현재 결정 대기(`PAUSED`) 상태인지 검증한다.
   - 요청에 포함된 `decision_version`이 현재 `room_rounds.decision_version`과 일치하는지 검사한다. 불일치 시(방장이 고민하는 사이 또 다른 참여자가 나간 경우) 결정을 거절하고 최신 상태를 반환한다.
   - **방장이 '아니요(라운드 취소)'를 선택한 경우**:
     - 현재 라운드를 취소(`CANCELLED`, 사유: 참여자 퇴장으로 인한 방장 취소)하고 방을 대기실(`WAITING`)로 되돌린다. 이미 나간 참여자는 방에 복귀시키지 않는다.
   - **방장이 '예(퇴장자 제외 후 계속 진행)'를 선택한 경우**:
     - `member_status = 'LEFT_PENDING'`인 행들을 `LEFT_CONFIRMED`로 갱신하여 이번 결정에서 확인 완료 처리한다.
     - 남은 활성 참여자(`member_status = 'ACTIVE'`)의 주문서 제출 여부를 확인한다:
       - **아직 제출하지 않은 활성 참여자가 남아 있으면**: 라운드 상태를 다시 `ANSWERING`으로 재개하여 남은 사람들이 이어서 주문서를 제출할 수 있게 한다.
       - **남은 활성 참여자 전원이 이미 주문서 제출을 마친 상태라면**: 기다릴 사람이 더 없으므로 즉시 `T03`의 공동 후보 병합 로직(`ACTIVE` 참여자들의 `top_menu_id`만 수집)을 실행하여 후보 수에 따라 `VOTING`(2개 이상) 또는 `RESULT`(1개 무투표 당선)로 자동 전환한다.
   - 모든 상태 변경은 `rooms.state_version` 증가 및 `T01N` Outbox 알림 저장과 함께 단일 트랜잭션으로 `commit`한다.

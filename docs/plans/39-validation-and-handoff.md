# #39 T09 검증 설계와 내일 구현 인계

작성: 2026-11-13. **아래는 실행할 검증 계획이다. 오늘 새 앱·DB·브라우저 테스트를 실행한 결과가 아니다.** 기존 T01 검증 이력은 [인계 기록](39-handoff-2026-11-13.md)과 LOG를 따르고, 후속 기능이 이미 구현됐다는 근거로 쓰지 않는다.

설계: [통합 아키텍처](39-implementation-architecture.md), 정책: [공통 선택](39-cross-feature-architecture-checklist.md), 추가 확정 정책: [M1A·M2A·M3A·M4A](39-final-design-choices.md), 원래 범위: [T01~T09](39-uuid-user-tickets.md).

## 1. 실행 전 고정할 기준

- 작업 시작의 git 상태와 기존 사용자 변경을 보존하고 기준선 테스트 결과를 기록한다. 내일 실행 환경을 다시 확인하며 과거 인터프리터 경로·MySQL 프로세스가 살아 있다고 가정하지 않는다.
- 기존 기록상 `.tools/venv/Scripts/python.exe`가 테스트 환경이다. 원래 `.venv`는 Python 경로가 깨진 이력이 있다. 해당 파일 존재와 버전·의존성을 확인한 뒤 사용한다.
- T01 격리 MySQL은 종료된 상태로 인계됐으며 자동으로 운영 DB 대신 사용하지 않는다. 테스트 전용 DSN·임시 파일 폴더·제공자 응답 fake·시각 제어를 사용한다. 운영 데이터로 테스트하지 않는다.
- 기준선 기록의 메뉴 표시명 2건 실패는 내일 다시 확인해 기존/신규를 구분한다. 모든 실패를 기존 문제로 간주하지 않는다. 새 관련 실패는 수정하고, 남는 기존 실패는 정확한 테스트명·기대/실제와 함께 보고한다.
- 테스트 함수 구현을 그대로 반복하는 검사보다 HTTP/WS·Service Interface를 통해 실제 소유권·저장·복원 결과를 확인한다. 시간 대기는 가짜 시계/제어된 시각으로 대체한다.

R5A 테스트는 인증 없는 사진 GET이 가능함을 기대한다. 반면 업로드·교체·삭제는 본인만 가능해야 한다. R5C 제안을 거절했는데 사진 GET에 방 인가를 요구하는 테스트를 만들지 않는다.

M1의 제한 가중 추첨을 선택하면 같은 기본 점수·개인 예측이 다른 근접 후보의 선택 분포를 검증한다. 고정 난수·충분한 반복/허용 오차 또는 실제 계산한 가중치/선택 경계 검증으로 균등 상태와 변화가 구분돼야 한다. 개인 모델이 없으면 기존 균등 추첨, 같은 종류의 메뉴 수만 늘려도 그 종류의 가중치가 부풀지 않는 결과를 확인한다. 실제 통계 검증은 구현 후 실행하며 점수 단위 테스트만으로 추천 분포 개선을 주장하지 않는다.

## 3. 반드시 실제 MySQL에서 확인할 경쟁 상황

1. 같은 준비 쿠키로 동시 사용자 생성/갱신: 기존 T01 원자성 유지.
2. 닉네임 같은 값 동시 저장: 하나 성공·다른 하나 충돌, 프로필/닉네임 키 일치.
3. 제외 전체 교체 두 개: 성공 순서의 마지막 목록, 타인·다른 타입 불변.
4. 같은 메뉴 평가 수정 두 개: 이력 2개라도 유효 상태 1표, 파생 집계 일치. 같은 키면 1개.
5. 방 참여와 계정 전환: 먼저 확정한 쪽에 맞춰 다른 쪽 거절/보류, 원본 삭제 후 늦은 참여 불가.
6. 원본 개인 기록 저장과 이관: 먼저 저장된 기록 포함 또는 종료 인증 거절, 고아 FK 없음.
7. 서로 다른 UUID가 같은 신규 카카오 subject로 동시 이관: 대상 1개·모든 원본 기록 보존·이관 반복 없음.
8. 대상 카카오 방 참여와 다른 기기 이관: 최종 잠금 아래 다시 확인해 정책 우회 없음.
9. 원본 닉네임 키의 대상 이전과 타인 이름 변경: 중간 해제가 외부에 보이지 않고 유일성 유지.
10. 마지막 연결 종료·재접속·정리 작업 경합: 재접속 전에 실제 마감이 지난 경우와 마감 전 경우 구분, 중복 퇴장/종료 없음.
11. 토큰 갱신·인증 정리와 이관: RESTRICT 참조·원본 세션 갱신·원본 삭제 후 새 쓰기 경합 확인.

SQLite 정상 테스트는 위 잠금·collation·유일성·FK의 MySQL 검증을 대신하지 않는다. 강제로 중간 실패를 주입해 commit 전 원본이 그대로인지 확인한다.

| 사진 파일 이동 후 DB 실패 | 이전 참조 유지, 새 고아 파일 정리 |
| 사진 DB commit 직후 프로세스 중단 | 현재 사진 유지, 이전 미참조 파일만 후속 정리 |
| WS 전송 실패·재시작 | DB 상태 유지, REST 재확인으로 화면 복구 |
| 다른 탭 늦은 응답/쿠키 | 이전 응답으로 새 화면 덮지 않음, 현재 인증 문맥 충돌 시 중단 |

## 5. 마이그레이션 검증

- 기존 카카오·UUID·모든 자식 이력과 메뉴 삭제/소유자 없는 legacy 행을 가진 사전 fixture를 만든다. 원본 행 수·PK·FK·시각·프로필·payload manifest를 저장한다.
- check는 읽기만 수행하고 충돌/미대응/스키마 불일치를 보고한다. apply는 유지보수 확인을 요구하고 단계별 완료를 기록한다. verify는 manifest와 실제 FK/보존 데이터를 대조한다.
- 적용 전·부분 적용 중단·재실행·이미 적용됨·유일 키 충돌·변환 불가 기존값의 각 경우를 검증한다. 데이터 정리와 무관한 원본을 임의 수정하지 않는다.
- 원본 User 삭제 이관은 DML 트랜잭션으로 검증하고, DDL 단계는 부분 적용 후 복구/재실행 경로를 따로 검증한다.
- 실제 운영 버전·데이터에서 실행 전 별도 check/백업·복원 준비가 필요하다. 격리 DB 통과를 운영 적용 완료로 보고하지 않는다.

## 6. 브라우저·1GB 환경 검증

- 허용 Origin과 credentials·Secure/HttpOnly/SameSite·준비/정식 쿠키 Path·JWT 갱신·새 헤더 CORS를 실제 브라우저에서 확인한다. HTTP 테스트만으로 쿠키 동작 통과라고 하지 않는다.
- 두 탭의 계정 변경·알림 누락·지연 응답·방 참여 결과 불명·현재 사용자 재확인과 이전 요청 자동 재전송 금지를 확인한다. 네이티브 앱 플랫폼 결정은 이 검증에 포함되지 않는다.
- 사진은 본인 화면·방 참여자 목록에 표시하고 클릭/확대/공유 동작이 없음을 확인한다. 프론트 전체 구현은 범위 밖이며 연동 화면이 준비되지 않으면 브라우저 검증 미실행으로 기록한다.
- 실제 운영과 같은 1GB·MySQL 동시 실행 환경에서 idle/대표 동시 연결/추천/사진 처리의 메모리 RSS·시스템 가용 메모리·스왑·OOM·CPU·DB 연결·API p50/p95·WS 지연을 측정한다. 1GB로 제한되지 않은 개발 PC 테스트를 대신 쓰지 않는다.
- 무부하 모델/사진 처리의 최대 메모리를 먼저 측정하고, 사용자 수를 단계적으로 늘려 용량·응답 기준을 정한다. 측정 없이 100명·1,000명 지원을 약속하지 않는다. 자원 부족이면 학습/동시 처리 제한·DB 배치/풀을 조정하고 필요한 경우 증설을 별도 검토한다.

## 7. 내일 구현·완료 순서

1. 선택/초안·기준선 확인. T02의 actor/쓰기 트랜잭션·작업 키·확장 스키마를 작은 수직 기능 단위로 구현한다.
2. T02 개인 인증·제외·평가·스냅샷/학습·대체 경로, T03 방, T04 닉네임, T05 파일을 각각 API+저장+관련 검증까지 완료한다. 병렬 구현은 당시 사용자 지시와 공용 파일 소유권을 확인한 경우에만 진행한다.
3. T06 원본→새 대상 이관·복구, T07 기존/다중 UUID 병합·프로필, T08 로그아웃 왕복을 순서대로 통합한다. T06에서 미구현 T07 경로는 원본 보존 후 거절한다.
4. 기능별 테스트 후 해당 MySQL 경합을 실행한다. T09에서 전체 여정·마이그레이션·회귀를 실행하고 새 실패를 해결한다. 실제 브라우저와 1GB 환경이 없으면 해당 검증은 남은 작업으로 구분한다.
5. 요청/응답 예시·오류·인증/사진/WS 호출 순서를 연동 문서와 맞추고 LOG에 실제 결과를 기록한다. 설계 초안·미실행 테스트·미활성 모델을 완료로 표시하지 않는다.

완료 보고는 `설계 정책 선택 / 기술 초안 / 구현 / 격리 테스트 / MySQL / 브라우저 / 1GB 용량 / 운영 적용`을 구분한다. GitHub 이슈 게시·커밋·배포·운영 DB 변경은 이번 설계 단계에 포함하지 않는다.

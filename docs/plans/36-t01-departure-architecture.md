## 확인한 현재 사실

- 일반 참여자의 실제 제거 경로는 명시적 퇴장, 요청 중 지연 정리, 개별 유예 만료 예약, 주기 정리, 늦은 재접속, 계정 전환 전 정리로 분산되어 있다.
- 경로별로 권한·시간·처리 목적이 다르지만 참여자 및 완료 정보 제거와 인원 집계는 공통이다.
- 명시적 퇴장은 사용자·인증 세션 확인 후 방·참여자를 잠그고 정리·집계를 커밋한다.
- 계정 전환 전 정리는 더 큰 계정 전환 트랜잭션 안에서 flush하며, 동일 위치에서 독립적으로 커밋하는 것과 같지 않다.
- WebSocket·주기 정리 경로는 DB 처리 뒤 알림을 보내지만 일부 지연 정리 경로에는 동일한 알림 전파가 없다. 상태 조회가 DB의 사실을 복원할 수 있어야 한다.
- 기존 단일 API 프로세스, 60초 재접속 유예, 방장 종료 및 계정 전환 제한은 제품 제약으로 유지한다.

## T01-D01: 퇴장 대상 판정과 실제 정리의 책임 배치 — A 확정

### A. 각 진입 경로에서 대상을 판정하고 공통 모듈에서 정리

- 명시적 요청은 본인 퇴장 권한을, 만료 경로는 60초 경과를, 계정 전환 경로는 해당 문맥의 조건을 판정한다.
- 공통 모듈은 확정된 퇴장 대상의 참여·완료 상태 제거와 인원 재계산을 맡는다.
- 이점: 기존 문맥·트랜잭션을 보존하면서 중복 정리 로직을 모을 수 있고 변경 범위가 비교적 작다.
- 비용: 호출자가 대상 판정·잠금 등 계약을 지켜야 한다. 어떤 조건을 공통 인터페이스가 보장하고 어떤 조건을 호출자가 보장할지 후속 결정이 필요하다.
- 영향: T05·T06의 퇴장 후 라운드 전환을 실제 정리 경계에 추가할 수 있다. 공통 모듈의 후속 확장 지점은 별도 결정한다.

### B. 판정부터 실제 정리까지 공통 모듈로 이동

- 각 경로가 퇴장 사유와 필요한 문맥을 전달하면 공통 모듈이 권한·유예·대상 판정과 정리를 함께 담당한다.
- 이점: 호출자가 같은 판정 규칙을 반복하지 않고 공통 모듈이 더 많은 불변 조건을 보장할 수 있다.
- 비용: 서로 다른 문맥의 입력·실패·잠금·트랜잭션 계약을 포괄해야 하고 기존 호출 경로를 더 넓게 변경할 수 있다.
- 영향: 방 정책의 유지보수가 한곳에 집중될 수 있으나, 계정 전환 등 큰 작업과의 조합 방식을 함께 설계해야 한다.

### 추천과 결정 상태

- 추천: A. 이번 T01의 동작 보존 목적에 맞춰 실제 정리 중복부터 모으고, 진입 문맥을 광범위하게 바꾸는 위험을 줄인다.
- 사용자 선택: 2026-11-16 “A로 진행해주고 다음”. 각 진입 경로가 퇴장 대상을 판정하고 공통 모듈이 실제 정리를 담당한다.
- 이 결정으로 트랜잭션·잠금·알림 등 후속 계약까지 승인된 것은 아니다.

## T01-D02: 공통 정리의 커밋·롤백 책임 — A 확정

- 전제: D01 A안. 기존 계정 전환 전 정리는 상위 트랜잭션에 속하므로 공통 정리가 항상 독립 커밋하면 기존 원자성을 깨뜨린다.
- A: 공통 정리는 전달받은 세션으로 변경하고 필요한 flush만 수행한다. commit·rollback은 전체 작업을 소유하는 상위 호출자가 담당한다. 이점은 계정 전환과의 조합 및 일괄 취소가 명확하다는 것, 비용은 각 호출 경로가 트랜잭션 종료를 빠뜨리지 않도록 확인해야 한다는 것이다.
- B: 공통 정리가 커밋 여부 옵션을 받아 직접 확정할 수 있다. 일반 퇴장은 내부 커밋, 계정 전환처럼 큰 작업에 속한 경로는 내부 커밋을 끈다. 이점은 독립 호출의 확정 코드가 줄어든다는 것, 비용은 호출마다 옵션을 올바르게 지정해야 하고 같은 세션의 다른 변경까지 조기 확정할 수 있다는 것이다. 자체 rollback도 상위 작업에 영향을 주므로 오류 시 책임을 추가로 정해야 한다.
- 추천: A. 현재처럼 독립 작업과 큰 트랜잭션 안의 정리가 공존하는 구조에 적합하다.
- 사용자 선택: 2026-11-16 “A로 해줘”. 공통 정리는 commit·rollback하지 않고, 전체 작업을 소유하는 상위 호출자가 확정·취소한다. 세션 생성·잠금 획득 순서·알림 발행 책임까지 확정한 것은 아니다.

## T01-D03: 퇴장 판단 전 잠금·조회의 책임 — A 확정

- 전제: D01 A안과 D02 A안. 유예 만료 처리와 재접속이 겹쳐도 잠근 최신 상태로 각 경로가 대상을 판단해야 한다. 잠금은 같은 트랜잭션의 commit·rollback까지 유지하며 실제 행 범위·순서 계약은 별도로 구체화한다.
- A: 각 호출 경로가 방·참여자를 잠금 조회하고 해당 조건을 판단한 뒤, 잠근 대상을 공통 정리 함수에 전달한다. 기존 코드의 조회와 문맥을 보존하기 쉽지만 6개 경로가 올바른 잠금과 조회 계약을 각각 유지해야 한다.
- B: 공통 잠금·조회 함수를 별도로 제공한다. 호출 경로는 이 함수를 먼저 호출하고 잠긴 상태에서 퇴장 조건을 직접 판단한 다음, 같은 세션으로 공통 정리를 호출한다. 잠금 조회 규칙을 모을 수 있지만 단건·묶음 및 이미 잠근 방 등 문맥을 지원하는 인터페이스와 호출 변경이 필요하다. 사용자·인증 세션 검사는 기존 상위 경로에 남으며 D01의 판정 책임을 옮기지 않는다.
- 두 안 모두 잠그기 전에 읽은 오래된 대상 판정만 믿고 삭제해서는 안 된다. B에서도 실제 삭제 시점에 처음 잠그는 방식은 후보로 제시하지 않는다.
- 추천: A. 기존 잠금 문맥을 보존하는 T01 범위에 적합하다. B는 잠금 조회 중복을 줄이는 대신 공통 인터페이스 범위가 커지는 대안이다.
- 사용자 선택: 2026-11-16 “A안으로 해줘 다음”. 각 호출 경로가 방·참여자를 잠금 조회하고 퇴장 여부를 판단한 뒤 잠긴 대상을 공통 정리에 전달한다. 공통 잠금·조회 함수는 이번 결정으로 도입하지 않는다.

## T01-D04: 여러 퇴장자를 받는 공통 정리 인터페이스 — A 확정

- 전제: D01~D03 A안. 기존 주기 정리는 같은 방에서 여러 명을 제거한 뒤 최종 인원·완료 수를 한 번 계산해 각 퇴장 결과에 담는다. 이 최종 집계 동작과 단일 트랜잭션은 두 대안 모두 유지한다.
- A: 공통 정리가 같은 방의 잠긴 퇴장 대상 목록을 받아 전체 참여·완료 기록을 제거하고 한 번 집계해 결과를 반환한다. 단독 퇴장은 길이 1 목록으로 호출한다. 이점은 삭제·집계가 한 인터페이스 안에 묶여 호출 경로의 반복과 집계 누락을 줄이는 것, 비용은 단독 호출에도 목록 입력이 필요하고 여러 방의 대상을 섞지 않는 계약이 필요하다는 것이다.
- B: 한 명의 참여·완료 기록만 지우는 공통 함수와 방의 최종 집계 함수를 분리한다. 호출자가 대상별 삭제를 반복한 뒤 최종 집계를 한 번 수행해 결과를 구성한다. 이점은 단건 삭제를 다른 흐름에 조합하기 쉽다는 것, 비용은 호출 경로가 반복·최종 집계·결과 조합 순서를 지켜야 한다는 것이다.
- 예시: 5명 중 2명이 같은 정리 실행에서 만료되면 두 대안 모두 최종 3명을 반환한다. B에서도 사용자별 커밋이나 중간 4명 상태의 알림을 전제로 하지 않는다. 차이는 내부 호출 인터페이스와 집계 책임에 있다.
- 추천: A. 기존에 실제 묶음 정리가 존재하며 퇴장자 정보와 최종 집계를 함께 전달하려는 T01 목적에 맞는다.
- 사용자 선택: 2026-11-16 “A로 추천해줘”. 직전 A안 채택 질문에 대한 응답으로 A안을 선택한 것으로 기록한다. 공통 정리는 같은 방의 잠긴 퇴장 대상 목록을 받아 삭제와 최종 집계를 수행한다. 알림·방장 결정 UI의 묶음 방식이나 서로 다른 시점의 퇴장까지 묶는 정책은 이 질문으로 정하지 않는다.

## T01-D05: 공통 정리 결과의 구조 — A 확정

- 전제: D04 A안. 기존 LeftRoomMember는 방·사용자 식별자와 최종 인원·완료 수를 담으며 기존 호출 경계는 이 단건 결과 목록을 사용한다. 두 대안 모두 DB 상태를 같은 트랜잭션 안에서 집계하고 외부 REST·WebSocket 형식을 유지한다.
- A: 내부 공통 정리는 방 식별자, 실제 퇴장자 목록, 최종 인원·완료 상태를 한 번씩 담는 방 단위 결과를 반환한다. 기존 경계에서 필요하면 LeftRoomMember 목록으로 변환한다. 이점은 D04의 방 단위 처리와 결과 구조가 일치하고 후속 라운드 판단에 전체 퇴장자를 한 번에 넘길 수 있다는 것, 비용은 내부 결과형과 기존 형식 변환이 추가된다는 것이다.
- B: 내부 공통 정리도 기존 LeftRoomMember 목록을 그대로 반환한다. 이점은 기존 결과형을 재사용하고 변환을 줄이는 것, 비용은 같은 최종 집계가 퇴장자마다 반복되며 방 단위 후속 처리에서는 목록을 다시 묶고 일괄 처리 규칙을 관리해야 한다는 것이다. 중복 집계 필드가 곧 DB 재조회나 큰 성능 문제를 뜻하지는 않는다.
- 예시: 철수·영희 퇴장 후 3명이 남으면 A는 퇴장자 [철수, 영희]와 최종 3명을 한 결과에 담고, B는 철수 결과와 영희 결과 각각에 최종 3명을 담는다. A를 택해도 기존 알림이 곧바로 묶음 알림으로 바뀌지는 않는다.
- 추천: A. 기존 외부 형식은 유지하면서 T05·T06에 필요한 방 단위 판단의 입력을 명확히 할 수 있다. 현재 존재하지 않는 라운드 전환 필드를 미리 추가하지는 않는다.

## T01-D06: 커밋 이후 알림 연결 방식 — A 확정

## T01-D08: 알림 전달 완료 기준과 프론트 계약 — 1번(A) 확정

## T01-D14: 공통 정리에 잘못된 대상이 섞였을 때 — 1번(A) 확정

- 2번(B): 잘못된 대상은 건너뛰고 올바른 대상만 정리한다. 건너뛴 이유와 실제 제거 대상을 구분해 반환·관측해야 한다. 이점은 일부 호출 오류가 있어도 유효한 정리를 진행하는 것, 비용은 부분 성공 결과·로그·원인 추적이 복잡하고 호출 오류가 조용히 지속되지 않도록 관리해야 한다는 것이다. 다른 방 기록 삭제나 방장 일반 퇴장은 어느 대안에서도 허용하지 않는다.

- 비교 축: 정상 입력의 프론트 기능·알림 지연·DB 결과는 동일하다. 차이는 잘못된 입력에서 전체 원자성과 오류 가시성을 우선할지, 유효 대상 처리의 연속성을 우선할지다. 구체적인 성능 차이는 측정하지 않았다.
- 추천: 1번(A). 사용자 요청의 개별 실패 정책이 아니라 내부 함수 계약 검증이므로 부분 성공으로 호출 오류를 가리기보다 원인을 드러내는 쪽을 우선한다.

## T01-D15: 일시적인 DB 잠금 충돌의 서버 재시도 — 1번(A) 확정

- 사실: 현재 방 퇴장·주기 만료 정리는 예외 시 rollback 후 오류를 전파하며 해당 함수 안에 DB 충돌 재시도가 없다. 기존 계정 전환은 MySQL 1205(잠금 대기 만료)·1213(교착 상태)에 최대 2회 추가 시도한다. 기존 계정 전환 정책은 이 질문으로 취소하지 않는다.
- 예시: 명시적 퇴장과 주기 만료 정리가 겹치거나 여러 행의 잠금 순서가 충돌해 DB가 한 작업을 실패시킨다. 정상적인 잠금 대기는 실패가 아니며, 이 질문은 실제 DB 충돌 오류가 발생한 이후의 복구 정책이다. 방·참여자 잠금 순서 통일과 최신 상태 확인은 별도로 필요하다.
- 1번(A): 방 정리의 최상위 트랜잭션 경계에서 위 두 오류만 최대 2회 즉시 추가 시도한다(최초 포함 최대 3회). 매 실패 후 전체 rollback하고 권한·세션·최신 참여 상태·유예 조건을 재조회·재판정한다. 공통 정리 함수 안에서 재시도하거나 계정 전환의 재시도 안에 중첩하지 않는다. 계정 전환 소속 정리는 기존 상위 작업 전체 재시도에 포함된다. 모두 실패하면 오류를 반환하거나 백그라운드 실패를 관측한다.
- 2번(B): 새 방 정리 재시도를 추가하지 않는다. 실패한 작업 전체를 rollback하고 HTTP 호출자는 실패를 받으며, 백그라운드는 실패를 기록하고 다음 정상 실행 기회를 기다린다. 개별 유예 예약에 다음 시도가 자동 보장되는 것으로 간주하지 않는다. 기존 계정 전환의 재시도는 보존한다.
- 비교 축: 1번은 순간 충돌을 서버에서 복구할 기회가 있어 사용자 재요청을 줄이지만 실패 시 응답 대기와 DB 작업이 늘고 전체 작업 재실행의 안전성 검증이 필요하다. 2번은 충돌 시 자원 사용과 실행 경로가 적지만 사용자 실패 노출·정리 지연이 늘 수 있다. 정상 무충돌 요청의 프론트 기능·네트워크 횟수·화면 상태는 같으며 실측 성능 차이는 아직 없다. 둘 다 데이터 원자성·재접속 유예·커밋 이후 알림 규칙을 지켜야 한다.
- 범위 제외: D14 호출 계약 위반, 권한·도메인 오류, 결과를 알 수 없는 커밋·연결 실패, 일반 네트워크 장애는 자동 재시도 대상으로 넓히지 않는다. T01N 알림 재전송의 1·3·5·10·30초 및 전체 60초 기한과는 별개다.
- 추천: 1번(A). 짧은 DB 충돌의 서버 복구와 사용자 실패 감소를 우선하되 재시도 횟수를 제한한다. 빠른 실패와 DB 추가 작업 억제를 더 중시하면 2번(B)이 맞다.
- 사용자 선택: 2026-11-16 “1번”. MySQL 1205·1213에 한해 최상위 작업을 전체 rollback한 뒤 최대 2회 즉시 추가 시도한다. 매 시도 권한·세션·최신 참여 상태·시간 조건을 다시 검증하고 공통 정리 내부 또는 계정 전환 재시도 안에 중첩하지 않는다. 호출 계약 위반·도메인 오류·결과 불명 커밋 및 일반 연결 장애는 이 재시도에 포함하지 않는다. 구체적인 최종 오류 응답 계약과 경로별 재시도 소유 경계는 최종 설계에 정리한다.

## T01-D16: 공통 정리의 빈 목록·동일 대상 중복 입력 — 1번(A) 확정

- 범위: 다른 방·방장 등 D14의 금지 대상과, 올바른 동일 참여자가 여러 번 등장하는 입력을 구분한다. 이미 제거된 참여자는 호출자가 최신 잠금 조회에서 확인하며, 내부 공통 정리의 무처리 선택이 기존 명시적 퇴장의 없는 참여자 404를 바꾸지는 않는다. 이전에 읽은 ORM 객체를 잠금 재확인 없이 넘겨도 된다는 계약이 아니다.
- 1번(A): 같은 방의 정상 대상은 참여 기록 식별자로 중복을 제거해 한 번만 정리한다. 빈 목록이면 삭제·불필요한 집계·퇴장 알림 없이 변경 없음 결과를 반환한다. 금지 대상이 섞이면 중복 제거로 숨기지 않고 D14에 따라 전체 거절한다. 반환 구조는 D05의 방 단위 결과를 유지하되 변경 유무와 실제 제거자 목록으로 무처리를 구분한다. 구체 필드명은 구현 시 정한다.
- 2번(B): 공통 정리는 비어 있지 않고 중복이 없는 목록만 받는다. 빈 목록·중복은 호출 계약 위반으로 전체 거절한다. 각 호출 경로가 빈 목록 호출을 건너뛰고 중복을 미리 제거해야 정상 재시도·동시 퇴장을 처리할 수 있다. 재실행 시 대상이 사라진 상황의 허용 여부와 외부 응답은 각 경로의 기존 정책을 유지한다.
- 예시: 한 정리 작업이 먼저 철수를 제거한 뒤 다른 만료 작업이 최신 조회를 했더니 대상이 없으면, 1번은 공통 정리까지 빈 목록을 넘겨도 무처리로 종료하고 2번은 호출자가 빈 목록을 감지해 호출을 생략한다. 같은 참여 기록이 목록에 두 번 들어오면 1번은 한 번만 처리하고 2번은 오류로 중단한다.
- 비교 축: 양쪽을 올바르게 구현하면 DB 최종 인원·프론트 기능·인증·유예 정책은 같다. 실제 차이는 동일 대상 중복 입력 시 정리를 계속할지 실패시킬지다. 1번은 처리를 계속하며 중복 경고를 남길 수 있으나, 경고를 조사하지 않으면 호출 코드의 중복 생성이 남을 수 있다. 2번은 입력 계약 위반을 실패로 드러내지만 처리 가능한 퇴장도 지연시킨다. 어느 대안도 삭제·집계 코드 자체의 버그까지 자동 탐지하지 않으며 서비스 전체 중단을 뜻하지 않는다. 두 안 모두 이중 인원 차감·가짜 퇴장 알림을 허용하지 않으며 성능 우열은 측정하지 않았다.
- 추천 경과: 최초 1번을 추천했고, 사용자가 엄격한 오류 발견을 중시하는지 논의하며 2번으로 추천을 바꿨다가 차이를 과장했음을 바로잡았다. 최종 추천은 1번에 중복 발견 경고 기록을 더하는 방식이다. 작은 중복 입력 오류가 실제 정리 실패로 번지는 것을 막으면서 원인을 관측하는 가치를 우선한다.
- 사용자 선택: 2026-11-16 “1번으로 해줘 오류 발생을 하게되면 실사용에서 멈춘다는 의미지? 1번은 진행할 수 있다는건데”. 같은 참여 기록의 중복은 한 번으로 합쳐 정리를 계속하고 중복 발견은 경고로 기록한다. 빈 목록은 변경 없이 종료한다. 오류로 중단되는 것은 해당 정리 작업이며 서비스 전체 중단이 아니다. 다른 방·방장 등 D14 금지 대상은 계속 전체 거절하며, DB 작업 자체의 실패까지 성공으로 간주하지 않는다.

## T01-D17: 주기 자동 정리의 여러 방 저장·실패 범위 — 2번(B) 확정

- 현재 사실: 주기 실행이 사용하는 일반 참여자 유예 만료 정리는 여러 방의 대상을 하나의 트랜잭션에서 변경한 뒤 한 번 commit한다. 예외 시 전체 rollback하고 주기 루프는 오류를 기록한 뒤 다음 실행을 기다린다. 같은 서비스 함수는 재시작 복구에서도 사용하므로 주기 실행의 실패 격리 정책을 다른 문맥에 무조건 전파하지 않는다.
- 범위: 일반 참여자의 주기 유예 만료 정리. 명시적 퇴장·계정 전환의 트랜잭션 소유권과 방장 종료·방 만료 정책은 그대로 유지한다. 한 방 안의 참여·완료 기록 제거·집계는 어느 안에서도 원자적이다. 여러 방을 동시에 실행할지에 대한 질문은 아니며 순차 처리 기준으로 비교한다.
- 예시: 이번 실행에서 A·B·C방을 정리해야 하는데 B방 처리에 실패한다. D15 대상 DB 충돌은 확정한 최대 2회 추가 시도 후에도 실패한 상황을 비교한다.
- 1번(A): 기존처럼 모든 대상 방을 한 트랜잭션에 묶는다. B방 실패 시 A방 변경도 취소되고 C방도 해당 실행에서 완료되지 않는다. D15 대상 오류라면 전체 묶음을 다시 조회·검증해 재시도한다. 저장 확정 횟수가 적고 기존 실행 흐름을 보존하지만, 서로 독립된 방의 정리가 함께 지연되고 앞선 방 잠금을 더 오래 보유할 수 있다.
- 2번(B): 주기 실행의 상위 경계가 방마다 별도 트랜잭션을 소유한다. 방별로 최신 잠금 조회·조건 판정·공통 정리·commit을 수행한다. B방의 롤백 가능한 개별 처리 실패는 기록하고 A방 성공은 유지하며 C방을 계속 처리한다. D15는 실패한 방의 전체 작업에만 적용한다. 공통 함수는 계속 commit·rollback하지 않는다. 방마다 저장·재조회가 늘고 성공/실패가 섞인 실행 결과와 오류 관측을 관리해야 한다. 한 실패 방의 대기·재시도 때문에 뒤의 방이 잠시 기다릴 수는 있지만 성공한 방을 되돌리지 않는다.
- 복구·관측: 2번은 저장된 방의 결과를 나중 방 실패로 잃지 않도록 상위 실행이 성공 결과와 실패를 분리해 보존하고 기존 알림도 실제 commit한 방에만 보낸다. T01N의 내구 발송은 별도 선행 설계대로 후속 구현한다. DB 연결 전체 불능·진행 불가능 상태·프로세스 종료까지 무시하고 다음 방이 반드시 처리된다고 보장하지 않는다. 취소 신호와 전역 장애를 개별 방 오류로 삼켜서는 안 된다.
- 비교 축: 정상 처리의 최종 데이터와 프론트 작업은 같다. 1번은 commit 횟수·새 관리 코드가 적으나 실패·재시도 범위와 잠금 보유 범위가 넓다. 2번은 방 간 실패 전파와 재시도 작업 범위를 줄이고 저장된 방의 잠금을 먼저 해제하지만 commit·조회 횟수가 늘어 전체 처리 시간이 더 길 수 있다. 많은 방에서의 순성능 우열은 측정 전이며 2번이 병렬 처리나 항상 빠른 처리를 뜻하지 않는다.
- 추천: 2번(B). 서로 독립적인 방의 정리를 한 방의 실패로 되돌리지 않는 가치를 우선한다. 기존 처리 구조 보존과 저장 확정 횟수 절감을 더 중시하면 1번(A)이 맞다. 2번은 기존 장애 동작을 바꾸므로 사용자 선택 없이 T01의 단순 구조 정리로 포함하지 않는다.
- 사용자 선택: 2026-11-16 자동 정리는 방 삭제가 아닌 일반 참여자의 유예 만료 퇴장임을 확인한 뒤 “2번으로 해줘”. 주기 실행은 방별로 최신 조회·판정·정리·집계를 한 트랜잭션으로 확정한다. 개별 방 실패는 기록하고 이미 확정한 방은 유지하며 다음 방을 처리한다. D15의 DB 충돌 재시도는 실패한 방의 전체 작업 단위에 적용한다. 전역 DB 장애·취소 신호를 개별 방 오류로 삼키거나 방장 종료·계정 전환의 경계를 바꾸지 않는다. 재시작 복구는 별도 상위 문맥이며 주기 실행의 실패 무시 정책을 자동 적용하지 않는다.

## T01-D18: DB 충돌 재시도 소진 시 HTTP 응답 — 1번(A) 확정

- 범위: D15의 MySQL 1205·1213으로 최초 포함 최대 3회 시도해도 실패해 전체 rollback이 끝난 HTTP 작업. 주기 실행은 HTTP 응답 대신 D17의 방별 실패를 기록한다. 이미 존재하는 인증·계정 전환의 오류 코드는 보존하고 새 방 작업 경계의 오류 계약을 정한다.
- 1번(A): HTTP 503과 구조화된 오류를 반환한다. 제안 형식은 기존 인증 오류와 같은 `detail.code`·`detail.message`이며 코드는 `ROOM_TEMPORARILY_UNAVAILABLE`, 메시지는 “일시적으로 방 요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.”로 한다. 프론트가 일시적인 방 처리 실패를 구분할 수 있고 운영에서도 일반 내부 오류와 나눌 수 있다. 구체 오류 계약 문서·응답 검증을 추가하고 프론트가 세분화한 안내를 원하면 분기 처리가 필요하다. 기존 공통 오류 안내를 계속 쓰는 것도 가능하다.
- 2번(B): 새 방 전용 일시 오류 응답을 추가하지 않고 DB 예외를 기존 일반 서버 오류 흐름으로 전파한다. 새 오류 코드를 도입할 계약 작업이 적지만 프론트는 이 응답만으로 일시 잠금 충돌과 다른 내부 실패를 구분하기 어렵다. 서버 내부 로그로 원인을 조사할 수는 있다.
- 공통점: 성공 데이터·최대 재시도 횟수·DB 부하·자동 퇴장 정책은 같다. 503은 성공이나 자동 재실행 지시가 아니다. 새 프론트 자동 재전송을 요구하지 않으며, 결과 불명 커밋·일반 연결 장애를 재시도 소진 오류로 오분류하지 않는다. D14 내부 계약 위반 및 실제 코드 버그를 이 503으로 숨기지 않는다.
- 추천: 1번(A). 재시도를 도입한 경계에서 최종 일시 실패를 구분 가능한 계약으로 제공하는 가치를 우선한다. 정상 처리 속도 향상을 위한 선택은 아니다.
- 사용자 선택: 2026-11-16 “1번”. MySQL 1205·1213에 대한 최초 포함 최대 3회 시도가 모두 실패한 방 HTTP 작업은 전체 rollback 후 503과 `detail.code=ROOM_TEMPORARILY_UNAVAILABLE`, `detail.message=일시적으로 방 요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.`를 반환한다. 프론트 자동 재전송을 새로 요구하지 않는다. 기존 인증·계정 전환 오류 및 도메인 오류·내부 코드 버그·결과 불명 커밋의 분류는 이 계약으로 바꾸지 않는다.

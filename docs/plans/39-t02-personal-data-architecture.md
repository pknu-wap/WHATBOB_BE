## D01. 메뉴 추천 전에 사용자 인증을 필수로 한다 — 승인

- 사용자 선택: B. 카카오 로그인 없이 UUID 사용자로 이용할 수 있지만, 메뉴 추천 요청에는 유효한 Bearer JWT가 필요하다.
- JWT를 과거에 발급받았다는 사실만으로 충분하지 않다. 해당 요청에 JWT를 전달하고 T01의 서명·클레임·만료·사용자·DB 인증 세션 검증을 통과해야 한다.
- 랜덤 추천 `POST /api/recommendations/random`과 주문서 추천 `POST /api/recommendations/order-sheet`에 적용한다. 기존 카카오 사용자도 동일한 유효한 서비스 인증을 사용한다.
- JWT 누락·무효·만료는 인증 오류로 거절한다. 인증 없는 추천으로 자동 전환하거나, 요청 본문의 임의 사용자 번호로 본인 확인을 대신하지 않는다. 인증 검증 중 DB 장애는 T01의 서버 오류 계약을 따르며 비인증 추천으로 우회하지 않는다.
- 기존 JWT 없는 추천 호출은 더 이상 성공하지 않으므로 프론트의 호출 순서와 기존 테스트를 함께 변경해야 한다. 현재 실행 코드는 여전히 선택적 인증이며 이 결정은 아직 적용하지 않았다.

## 사용자 흐름과 이유

1. 최초 방문은 T01의 준비 → 사용자 생성 → JWT 발급 흐름을 거친다. 카카오 로그인 화면이나 비밀번호 입력은 필요하지 않다.
2. 재방문은 유효한 복원 쿠키로 같은 사용자의 JWT를 발급받는다. JWT 만료만으로 새 UUID를 만들지 않는다.
3. 프론트가 JWT를 붙여 주문서 질문을 요청하고 본인 질문 선택 이력을 참고한 질문을 받는다. 답변 후 같은 유효한 JWT로 주문서 추천을 요청한다. 랜덤 추천은 질문 단계를 거치지 않는다. 서버가 확인한 사용자에게 저장된 제외 조건과 요청의 추가 제외 조건을 적용한다.
4. 제외 후 후보가 없으면 기존 도메인 규칙대로 결과 없음을 처리한다. 제외 조건을 임의로 풀지 않는다.
5. 사용자 생성·복원·인증 검증이 실패하면 원인을 구분해 처리한다. 통신·DB 장애를 새 사용자 생성이나 비인증 추천으로 숨기지 않는다.

선택 이유는 개인 설정·추천 기록을 확인된 사용자 기준으로 연결하는 것이다. 대가는 인증 준비 성공이 추천의 선행 조건이 되고 기존 비인증 호출과의 호환성이 바뀐다는 점이다. A(인증 없는 추천도 허용)는 기존 호출 유지에 유리하지만 개인 데이터 사용 여부에 따라 두 흐름을 유지·검증해야 하므로 선택하지 않았다.

## D02. 주문서 질문도 JWT 인증 후 제공한다 — 승인

- 사용자 선택: ①. `GET /api/recommendations/order-sheet/questions`도 T01의 서비스 JWT·DB 인증 세션 검증을 통과해야 한다. D01의 메뉴 추천 인증 필수 정책을 유지한다.
- 최초 생성·재방문 복원 후 발급받은 유효한 JWT를 질문 요청과 메뉴 추천 요청에 재사용한다. 질문을 요청할 때마다 JWT를 새로 발급받는 방식은 아니다.
- 서버가 확인한 사용자 번호로 질문 선택 이력을 읽고 저장한다. 신규 질문 요청은 기존 비인증 `question_session` 쿠키를 본인 확인이나 별도 질문 이력의 기준으로 사용하지 않으며, JWT 누락·무효·만료 시 해당 경로로 우회하지 않는다.
- 이유: 질문 선택 이력과 이후 메뉴 추천 기록의 주체를 처음부터 같은 사용자로 유지한다. 비용: 인증 준비가 완료되기 전에는 주문서 질문도 받을 수 없으며, 기존 비인증 질문 호출·프론트 순서·관련 테스트를 수정해야 한다.
- 질문 선택 알고리즘은 변경하지 않는다. 현재 기본 상위 질문 7개는 주제 중복 없이 중요도순으로 선택하고, 탐색 질문 2개는 가능한 경우 직전 탐색 주제를 뒤로 미룬 뒤 사용자별 누적 선택 횟수가 적은 주제를 우선한다. 남은 후보 안에서 질문 중요도와 전체 노출 횟수에 따른 가중 추첨을 한다. 활성 주제가 부족하면 실제 개수는 줄어든다.
- 모든 질문의 중요도를 매번 낮추거나 반복을 완전히 금지하는 구조가 아니다. 서버가 선택·반환한 질문을 기록하며 실제 화면 열람을 확인하는 별도 이벤트는 현재 없다.
- 기존 `guest:` 질문 이력의 삭제·사용자 귀속 이관·보관 기한, 공개 알레르기 목록의 인증 변경, 피드백 세부 계약은 이번 선택에 포함하지 않는다.
- 현재 실행 코드에는 선택적 인증과 비인증 질문 경로가 남아 있다. D02는 승인된 설계이며 아직 코드에 적용하지 않았다.

## D03. 피드백은 JWT 인증 후 현재 본인 소유 추천에만 허용한다 — 승인

- 사용자 승인: `POST /api/recommendations/{recommendation_id}/feedback`도 T01의 서비스 JWT·DB 인증 세션 검증을 필수로 한다. 인증된 사용자와 해당 추천 기록의 현재 소유자가 일치해야 한다.
- 처리 순서: JWT·세션 검증 → 서버가 확인한 사용자와 추천 소유자 대조 → 평가 메뉴의 해당 추천 포함 여부 확인 → 피드백 저장과 기존 통계 반영. 요청 본문에 적힌 사용자 번호나 추천 번호만으로 권한을 부여하지 않는다.
- 추천 당시 JWT 문자열과 동일할 필요는 없다. 갱신된 유효 JWT로 같은 사용자임을 확인하면 본인 소유 추천을 평가할 수 있다. 사용자 번호 입력 필드의 제거·호환 처리와 오류 응답의 세부 계약은 후속 정리 대상이다.
- JWT 없는 요청, 다른 사용자의 추천, 추천 결과에 포함되지 않은 메뉴의 평가는 거절한다. 거절된 요청은 피드백과 통계를 변경하지 않아야 한다.
- 사용자 없이 생성된 기존 추천은 보존하되 일반 사용자 피드백은 받지 않는다. 추천 번호를 안다는 이유로 새 사용자의 소유로 간주하거나 기록의 귀속을 바꾸지 않는다.
- 장점은 개인 기록의 귀속·수정 권한을 일관되게 유지하고 권한 없는 피드백의 통계 반영을 차단하는 것이다. 비용은 인증 없는 기존 피드백 호출·테스트의 변경과, 소유자를 확인할 수 없는 과거 추천에 대한 일반 사용자 피드백 제한이다.
- 평가를 여러 번 남기거나 수정하는 정책, 중복 전송 처리, 저장·통계 갱신의 트랜잭션 경계와 관리자용 기능은 이번 결정에 포함하지 않는다. 기존 개인 선호 반영·공통 질문 중요도 계산을 새 알고리즘으로 대체하는 결정도 아니다.
- 현재 실행 코드에는 선택적 인증과 사용자 번호 부재 시 소유자 비교를 생략하는 경로가 남아 있다. D03은 승인된 설계이며 아직 코드에 적용하지 않았다.

## D04. 평가 변경을 허용하고 변경 이력을 보존한다 — 승인

- 사용자가 평가 변경 허용·이력 보존 방향을 선택했다. 새 평가나 수정 때문에 기존 평가의 원래 ID·일시·순서를 임의 삭제하거나 덮어쓰지 않는다.
- 평가 변경과 통신 재전송은 서로 다른 의미다. 사용자가 D05 누적 단위를 승인하면서 통신 재전송을 새 평가로 추가하지 않는 원칙도 승인했다. 작업 식별·보관·원자성·동시 수정 순서 등 세부 계약은 아직 미결정이며 특정 구현을 확정하지 않는다.

## D05. 개인 메뉴 선호에 평가를 누적 반영한다 — 누적 단위 승인·계산 세부 미결정

- 사용자가 최신 평가만 참고하는 개인 메뉴 선호를 누적 방식으로 바꾸겠다고 요청했다. 기존 T02의 알고리즘 유지 범위에 이 사용자 요청에 따른 변경을 추가한다. 이후 한도 방식은 D10으로 승인했지만 실제 수식·가중치·한도 수치·시간 감쇠·적용 메뉴 단위와 랜덤 추천 적용 여부는 아직 미결정이다.
- 현재 주문서 추천의 `select_diverse_menus`는 사용자·메뉴별 최신 평가만 선택한다. 최신 불만족이면 고정 비율의 감점을 적용하고 최신 만족이면 그 불만족 감점을 해제한다. 이 효과를 다음 한 번의 추천 뒤 소비·삭제하는 코드는 없으며 이후 추천에도 해당 최신 평가를 참고한다.
- 최근 추천 3건에 따른 메뉴 종류 반복 감점은 별도 로직이다. 랜덤 추천은 현재 위 개인 평가 감점을 사용하지 않는다. 공통 질문 중요도 계산은 이미 누적 피드백을 사용하므로 개인 메뉴 선호 누적과 구분한다.
- 사용자 승인: 같은 사용자·같은 추천·같은 메뉴의 수정 이력은 모두 보존하되 개인 선호 집계에는 그 평가의 최신 상태만 기여시키고, 서로 다른 추천에서 받은 유효 평가를 누적한다. 한 평가의 수정 횟수가 여러 표가 되는 것을 피할 수 있지만 수정 전 기여를 빼고 수정 후 기여를 반영하는 처리가 필요하다.
- 예: 같은 메뉴에 100번 추천에서 만족 → 불만족으로 수정하고 200번 추천에서 다시 불만족으로 평가했다면, 변경 이력은 3건 보존하고 개인 집계에는 불만족 2건이 기여한다. 이는 집계 단위 설명이며 실제 점수 공식이 아니다.
- 실제 수치가 정해지기 전에는 만족 +1·불만족 -1 등의 설명 예제를 구현 수식으로 기록하지 않는다. 기존 공통 질문 중요도 계산·알레르기 등 강제 제외 규칙을 이 지시만으로 변경하지 않는다. 공통 통계에서 수정 이력을 어떻게 집계할지도 후속 확인 대상이다.
- 이번에는 요구와 현재 코드의 차이를 기록했다. 실행 코드·DB·통계 재계산은 변경하지 않았다.

## D06. 제외 조건 목록은 전체 교체·마지막 저장 우선으로 처리한다 — 승인

- 사용자 선택: 마지막 저장 우선. 알레르기·섭취 불가·비선호의 유형별 목록 저장은 최종 전체 목록을 보내 교체하는 기존 비선호 방식을 따른다. 요청에서 빠진 해당 유형의 기존 항목은 해제되고, 다른 유형이나 다른 사용자의 목록은 변경하지 않는다.
- 같은 사용자의 목록 저장·개별 삭제는 기존 사용자 행 잠금으로 직렬화한다. 충돌하는 유효 요청은 DB에서 실제 저장·커밋되는 순서로 처리하고 나중에 성공한 전체 저장이 해당 유형의 최종 목록을 결정한다. 클라이언트 클릭 시각·요청 발송 시각·응답 도착 시각이 이 순서를 보장하는 것은 아니다.
- 목록 버전·ETag 일치를 필수로 요구하는 충돌 거절 방식은 채택하지 않는다. 오래된 화면에서 보낸 전체 목록도 입력·인증 검증을 통과하면 저장한다. 서로 다른 화면의 목록을 자동으로 합치지 않는다.
- 비용을 설명한 뒤 선택했다. 예: A가 [땅콩, 우유]를 저장하고 오래된 B가 나중에 [땅콩, 새우]를 저장하면 최종 목록은 [땅콩, 새우]이며 우유는 해제된다. 이후의 전체 저장이 앞선 개별 삭제 항목을 다시 포함하면 재등록될 수 있다.
- 마지막 저장 우선은 유효 요청 사이의 정책이다. 인증 실패·입력 오류·저장 실패 요청은 이전의 성공한 목록을 변경하지 않으며, 저장 도중 실패하면 해당 변경 전체를 롤백한다.
- 현재 비선호 서비스는 이미 사용자 행 잠금·전체 교체·롤백을 사용한다. 알레르기·섭취 불가 API 확장과 통합 검증은 아직 수행하지 않았다. 요청 개수·정규화·조회·편집의 나머지 계약은 후속 정리 대상이다.

## D07. 알레르기 신규 등록은 서버의 선택 목록으로 제한한다 — 승인

- 사용자 선택: ①. 알레르기는 서버가 제공하는 선택 목록에서만 고르며 목록 밖 항목의 자유 입력 등록은 제공하지 않는다. 목록 밖 항목을 등록할 수 없다는 제약을 설명한 뒤 선택했다.
- 기존 알레르기 목록 조회가 제공하는 고정 코드(예: `milk`, `peanut`)와 표시 이름을 구분하여 서버가 허용 항목을 판정하고 실제 제외 조건에 연결한다. 표시 문구 변경이나 프론트 검사만으로 항목의 유효성을 결정하지 않는다.
- 화면을 우회한 API 요청도 같은 검증을 적용한다. 알 수 없는 코드나 임의 항목이 포함된 신규 저장 요청은 거절하며, 해당 항목만 조용히 버리고 성공으로 처리하거나 기존 목록을 일부 변경하지 않는다.
- D06의 유형별 전체 교체·마지막 저장 우선은 유지한다. 등록 가능한 알레르기 항목의 제한이며 목록 버전 검사를 추가하는 결정은 아니다.
- 기존 DB에 목록 밖 알레르기 키워드가 있을 수 있다. 이번 선택만으로 해당 데이터를 삭제·자동 변환·타 유형으로 이동하지 않는다. 실제 사전 점검 결과를 바탕으로 조회·편집·기존 값의 호환 처리 계약을 기록·기존 데이터 묶음에서 정리한다.
- D07만으로 섭취 불가·비선호의 입력 범위를 같은 목록으로 제한하지 않았다. 이후 섭취 불가에 대해서는 D08의 별도 선택 목록 방식을 추가 승인했다. 기존 비선호 키워드 계약은 유지 대상이다.
- 현재 추천 제외는 메뉴명·분류·주재료·알레르기 태그의 키워드 비교다. 고정 코드를 기존 필터에 연결해야 하며 코드 문자열 자체를 메뉴명과 그대로 비교하지 않는다. 선택 목록을 쓴다는 사실만으로 실제 재료 정보의 완전성을 보장하지 않는다. 매핑·DB 저장 형식의 세부와 실제 API 구현은 아직 수행하지 않았다.

## D08. 섭취 불가 신규 등록도 서버의 선택 목록으로 제한한다 — 승인

- 사용자 선택: ①. 섭취 불가는 서버가 제공하는 음식·재료 선택 목록에서만 고르며, 목록 밖 자유 입력 등록은 제공하지 않는다. 사용자는 서비스가 준비한 항목 안에서만 등록할 수 있다.
- 섭취 불가 선택 목록은 알레르기 목록과 목적을 구분한다. 알레르기 목록을 그대로 재사용하거나 특정 항목 구성을 채택한 결정은 아니다. 초기 항목·범위·고정 코드와 실제 제외 조건의 매핑은 다음에 검토한다. 현재 섭취 불가 전용 선택 목록 API는 없다.
- 서버가 허용 항목을 검증하며 프론트 검사만 신뢰하지 않는다. 알 수 없는 항목이 포함된 신규 저장 요청은 거절하고 기존 목록을 일부 변경하거나 모르는 항목만 버린 성공으로 처리하지 않는다.
- D06의 유형별 전체 교체·마지막 저장 우선을 유지하며 다른 제외 유형과 다른 사용자의 설정은 변경하지 않는다.
- 기존 섭취 불가 키워드가 새 목록 밖에 있다고 해서 임의 삭제·변환·타 유형 이동을 하지 않는다. 사전 점검과 기존 값의 조회·편집 호환은 기록·기존 데이터 묶음에서 정리한다.
- 기존 비선호의 자유 키워드 입력까지 선택 목록으로 바꾸는 결정은 아니다. 새 목록을 유지·관리해야 하는 비용과 목록 밖 항목을 등록하지 못하는 제약을 설명한 뒤 선택했다.
- 아직 코드·DB·기존 목록·추천 필터를 변경하지 않았다. 고정 항목을 제공한다는 사실만으로 실제 메뉴 재료 데이터가 완전해지는 것은 아니다.

## D09. 섭취 불가 선택 단위는 재료 중심으로 한다 — 승인

- 사용자가 메뉴 중심 대신 재료 중심 방식을 선택했다. 돈가스·제육볶음 같은 메뉴를 각각 지정하기보다 돼지고기 같은 재료를 선택하고, 해당 재료에 연결되는 메뉴를 제외하는 구조로 설계한다. D08의 서버 선택 목록 제한과 D06의 전체 교체·마지막 저장 우선을 유지한다.
- 재료 선택은 서버의 고정 코드로 식별하고 메뉴의 분류·태그·키워드와 연결한다. 표시 이름 하나를 그대로 검색하는 것만으로 모든 관련 메뉴가 식별된다고 가정하지 않는다.
- 에이전트의 초기 목록 초안은 돼지고기, 소고기, 가금류, 해산물, 달걀, 유제품, 밀, 대두·콩 8개다. 이번 답변은 재료 중심 단위의 선택으로 기록하며 이 초안의 모든 항목·범위·매핑이 검증·확정된 것으로 처리하지 않는다. 실제 메뉴 데이터와 매핑을 점검해 최종 연동 계약에 구체화한다.
- 재료 중심은 한 항목으로 여러 관련 메뉴를 제외하기 쉽지만 해산물 같은 넓은 항목은 특정 음식만 제외하는 것보다 후보를 많이 줄일 수 있다. 세부 재료 분할과 전체 목록 확대까지 자동 승인한 것은 아니다.
- 현재 대표 주재료 값은 메뉴당 하나이며 전체 재료 명세가 아니다. 태그도 이름·분류에서 추정하므로 선택 목록과 실제 재료 정보의 완전성은 구분한다. 새 메뉴도 연결 정보가 있어야 기존 설정으로 제외할 수 있다.
- 기존 사용자 제외 키워드나 메뉴 데이터를 이번 선택으로 재분류·삭제하지 않는다. 개별 메뉴 단위의 비선호 입력 계약도 이번 결정으로 변경하지 않는다. 실제 선택 목록·매핑·추천 필터 코드는 아직 변경하지 않았다.

## D10. 누적 개인 선호의 점수 영향에 한도를 둔다 — 방식 승인·강도 미결정

- 사용자 선택: ②. 오늘 주문서 답변으로 계산한 점수를 기본으로 두고 누적 개인 선호를 보조 점수로 반영한다. 만족·불만족의 유효 평가 건수와 비율을 함께 참고하고, 평가가 적으면 약하게 반영하며, 보정 영향은 무한히 커지지 않도록 제한한다.
- 만족은 가산, 불만족은 감점하는 방향의 유한한 보정을 설계한다. 평가 이력·유효 평가 건수의 보존에 상한을 두거나 오래된 평가를 삭제하는 결정이 아니다.
- 오늘 답변과의 적합도 차이가 충분히 크면 제한된 개인 보정으로 순위가 뒤집히지 않게 하는 방향이다. 적합도가 비슷한 후보는 누적 선호로 순서가 바뀔 수 있다. 오늘 답변이 언제나 우선하는 사전식 순위나 오늘 90%·과거 10% 같은 고정 비율을 승인한 것은 아니다.
- 설명용 예시는 100점 기준·최대 ±10점·기준 건수 4와 `10 * (만족 수 - 불만족 수) / (전체 유효 평가 수 + 4)`였다. 이 수치·정규화·수식은 이해를 위한 예시이고 실제 구현값으로 승인하지 않았다.
- 실제 계산식·보정 상한·적은 평가를 완화하는 기준과 기존 주문서 점수 스케일의 연결은 같은 T02 설계 안에서 구현 전에 구체적인 초안·예시로 정한다. 테스트에서 후보 순위 변화·평가 없음·소수/다수 평가·평가 수정·상한과 제외 조건 보존을 확인할 계획이며 현재는 미실행이다.
- 알레르기·섭취 불가·비선호 등 강제 제외를 먼저 적용한다. 개인 만족 점수로 제외된 후보를 되살리지 않는다. 기존 최근 추천 감점·종류 다양성·추첨, 공통 질문 가중치 집계·랜덤 추천에 대한 별도 변경은 이번 선택으로 확정하지 않는다.
- 실제 반영 강도를 정하기 전에 임의 수치로 실행 코드를 적용하지 않는다. 이번에는 방식 승인과 남은 설계만 기록했다.

## D11. 여러 신호를 학습하는 추천 모델과 피드백 기반 조정 — 방향 승인

- 사용자가 여러 신호를 학습하는 추천 모델을 사용하고 실제 사용자 피드백을 받으면 조정하는 방향을 선택했다. 수동 누적 가산식의 계수만 선택하는 설계에서 학습 데이터·모델 학습·검증·예측 연결을 포함하는 범위로 확장한다.
- D11 당시 모델 종류·예측 목표·운영 세부는 미결정이었다. 이후 D13으로 체크리스트 1~8번의 방향을 승인했으며 구체적 특징·학습 주기·교체·검증 계약은 후속 정리 대상이다. 딥러닝이나 외부 유료 추천 서비스를 선택한 것으로 간주하지 않는다.
- 과거 평가·오늘 답변·메뉴 특성을 입력으로 활용하는 것은 검토 후보이며 어떤 항목을 학습 정답으로 볼지는 체크리스트에서 정한다. 여러 입력 신호를 쓰는 모델과 여러 목표를 동시에 학습하는 모델은 구분한다.
- D10의 영향 한도를 자동 폐기하거나 학습 모델에도 같은 수동 수식을 강제하지 않는다. 기존 답변 점수에 제한된 학습 보정을 할지, 결합 학습으로 최종 순위를 낼지는 체크리스트 1번에서 비교한다. 5%·10%·20%와 기준 건수 4는 여전히 미승인이다.
- D01~D09의 인증·소유권·수정 이력·유효 평가 단위·마지막 저장·선택 목록 정책과 강제 제외는 유지한다. 새 방향만으로 질문 선택 알고리즘·랜덤 추천·공통 질문 통계·계정 이관을 함께 변경하지 않는다.
- 기존 코드의 통계 기반 질문 중요도 조정을 새 학습형 추천 모델이 이미 구현된 것으로 안내하지 않는다. 라이브러리·학습 기록·모델 파일·서버·실제 사용자 데이터는 이번에 추가·변경하지 않았다.

## D12. 비교 체크리스트와 선택·보류·질의응답 방식 — 승인

- 사용자가 한 번에 하나씩 질문하는 방식을 중단하고, 선택 목록과 trade-off를 한 번에 제시하는 체크 응답 방식으로 바꾸도록 요청했다.
- 사용자는 아는 번호만 답하고 모르는 항목은 건너뛰거나 `보류`로 남겨 질문한 뒤 선택한다. 미응답·보류·추천 표시는 승인으로 간주하지 않는다. 새 사용자 지시가 과거의 한 번에 하나 질문 규칙보다 우선한다.
- [아키텍처 체크리스트](39-t02-architecture-checklist.md)는 사용자 응답만 선택으로 표시한다. 현재 선택은 D13·D14의 10항목을 따른다. 추천 자체는 성능 검증 결과나 사용자 선택이 아니며, 선택한 구현 세부를 묶어 구체적인 계약과 검증 계획으로 검토한다.
- 설계와 코드 적용을 구분한다. D11·D12 선택만으로 미결정 설계를 확정하거나 코드 구현·배포·외부 서비스 연결·원격 이슈 게시를 시작하지 않는다.

## D13. 체크리스트 1~8번의 학습형 추천 구조 선택 — 승인

| 선택 | 승인한 설계 |
| --- | --- |
| 1A | 오늘 주문서 점수를 기본으로 학습 모델이 제한적으로 재정렬한다. D10의 영향 한도를 유지하되 실제 스케일·상한은 후속 설계한다. |
| 2A | 첫 모델은 로지스틱 회귀로 한다. 여러 특징에서 명시적 만족 가능성을 학습하며 복잡한 입력 조합·정규화·규제·모델 검증 세부는 구현 계약에서 정리한다. |
| 3A | 첫 학습 정답은 명시적 만족·불만족이다. 오늘 답변·메뉴 특성·추천 시점까지의 이력은 입력 후보이며, 노출·선택·식사 기록은 구분한다. 미평가·미선택을 자동 불만족으로 보지 않는다. |
| 4A | 공용 모델 하나에 사용자별 이력·취향을 입력한다. 다른 사용자의 원본 기록을 응답에 노출하지 않는다. |
| 5B | 모델은 주기적으로 학습하고 개인 이력 입력은 새 평가에 따라 갱신해 다음 예측에 활용한다. 매 평가마다 모델 전체를 온라인 학습하는 방식은 아니다. |
| 6A | 현재 백엔드에서 학습된 모델을 읽어 예측하며 학습은 요청 밖의 별도 작업으로 실행한다. 별도 추천 서버·외부 유료 서비스를 도입하지 않았다. |
| 7A | 데이터나 모델이 준비되지 않거나 모델 예측에 문제가 있으면 인증·제외 조건 검증 후 기존 추천을 대체 경로로 쓴다. 인증·DB 제외 조건 확인 실패는 우회하지 않는다. |
| 8B | 최근 평가를 더 중요하게 반영한다. 이력을 삭제하지 않으며 시간 특징·가중 방식·기간은 후속 설계한다. |

- 9번과 10번은 사용자가 의미를 질문했으므로 보류다. 기존 목록 밖 값을 유지·삭제만 허용하는 9A나 본문 사용자 번호 호환을 허용하는 10B를 선택한 것으로 처리하지 않는다.
- 정확한 학습 주기·최소 유효 데이터·시간 가중·모델 입출력·실제 점수 한도·검증/버전 교체와 저장 계약은 선택한 구조에 맞춘 구체적 초안으로 검토한다. 특정 라이브러리 버전·운영 배포·성능까지 승인한 것은 아니다.
- 실행 코드·DB·학습 모델·사용자 기록은 이번에 변경하지 않았다.

## D14. 기존 값 정식 대응·요청 사용자 번호 제거와 일정 정정 — 승인

- 사용자 선택 9B: 기존 알레르기·섭취 불가 값은 새 정식 선택 항목과 정확히 대응시킨 뒤 편집을 허용한다. 대응이 확인되지 않은 값은 원본과 제외 효과를 보존하며 임의 삭제·다른 재료로 추측 변환하지 않는다. 실제 운영 데이터의 해당 값 존재 여부와 대응표는 아직 확인하지 않았다.
- 사용자 선택 10A: 주문서 추천·피드백의 요청 본문에서 `user_id`를 제거하고 보내면 입력 오류로 거절한다. 사용자는 T01 JWT 검증 결과로만 확인한다. 기존 프론트·테스트 계약 변경을 문서화한다.
- 사용자의 일정 정정: 오늘의 2시간 제한 대상은 T02~T09 아키텍처 설계이며 구현·테스트는 내일(2026-11-14) 진행한다. 코드 구현을 오늘 2시간 내 완료하라는 지시가 아니다.
- 에이전트가 앞선 시간 제한을 오해해 추가한 User 필드 4개·의존성 2줄·임시 파일 경로 ignore 1줄은 해당 추가 부분만 제거했다. 기존 T01 구현·사용자 변경은 유지했다. 병렬 구현 에이전트 2개는 중단했고 둘 다 파일 수정·테스트 실행이 없었음을 확인했다. 의존성 설치도 실행 도구 경로를 찾지 못해 설치를 시작하지 않았다.
- 9·10번 선택은 설계 문서에만 반영했다. 코드·DB·학습 모델의 새 적용이나 운영 배포는 수행하지 않는다.

## D15. 마지막 반영 강도·재료 범위·학습 자원 선택 — 승인

- 사용자가 M1A·M2A·M3A를 선택했다. M4A 사진 정책은 T05에 해당한다. [선택 기록](39-final-design-choices.md)과 [통합 기술 계약](39-implementation-architecture.md)을 따른다.
- M1A: 오늘 답변 점수 100점 환산 최대 ±5점, 유효 평가 최근성 반감기 90일, 증거 완화 k=5, 개인화 근접 추첨 가중치 최대 비율 1.5:1(beta=0.5)을 초기값으로 한다. 평가가 적으면 영향은 더 작다. 기존 메뉴별 최신 불만족 0.35 감점은 새 보정으로 교체하고 중복 적용하지 않는다. 모델 불가 시 개인 보정 없이 기존 답변/다양성/최근 노출 기준을 사용하며 누적 평가를 보존한다.
- M2A: 첫 섭취 불가 목록은 돼지고기·소고기·가금류·해산물·달걀·유제품·밀·대두/콩 8개 재료군이다. 실제 메뉴 매핑과 커버리지 검증은 남아 있다. 알레르기 catalog와 동일시하지 않는다.
- M3A: 개발 PC 등 별도 기존 환경에서 주 1회 점검/수동 학습하고 검증된 작은 모델을 기존 API에서 예측한다. 사용자의 환경·자료 경로 확인과 실제 학습/반영은 구현 단계에서 수행한다. 새 유료 자원·데이터 외부 공개를 도입하지 않는다.
- 구체화한 핵심은 이력과 집계의 분리, 추천 당시 입력 보존, 새 평가 입력 갱신과 모델 재학습의 구분, 계정 이관의 원자성과 응답 유실 복구다. 기술 용어만으로 완료라고 설명하지 않고 사용자 시나리오로 확인한다. 새 실행 코드나 모델 학습은 수행하지 않았다.

## 현재 코드 확인

- 비선호·식사 기록의 본인 API와 사용자별 추천·피드백·질문 순환 저장 구조는 존재한다.
- 알레르기·섭취 불가 저장 구조와 추천 제외 로직은 있지만 목록 관리 API는 없다. 이전 T02 로그와 달리 관련 신규 문서·테스트 파일은 비어 있다.
- 추천 라우터의 `_bind_user`는 비인증 요청의 본문 `user_id`를 그대로 전달한다. 피드백은 요청 사용자 번호가 없는 경우 소유자 비교를 건너뛴다. 후속 설계와 구현에서 보완해야 하며 이번에는 수정하지 않았다.
- 위 관찰은 정적 코드 확인이다. 이번 설계 기록 작업에서 앱 테스트를 실행하지 않았다.

## 다음 검토 범위

- 최신 구체 초안은 [통합 구현 아키텍처 §4~5](39-implementation-architecture.md), 검증은 [T09 계획](39-validation-and-handoff.md)이다. 초기 강도·최근성, 재료 범위, 학습 자원은 [M1A·M2A·M3A](39-final-design-choices.md)와 D15로 선택했다. 아래 기존 진행표는 기술 초안 작성 전 분류이며 사용자 승인 정책의 원본 D01~D14는 유지한다.
- D11 학습형 추천의 모델·학습·예측·피드백 계약을 기존 2번 묶음에서 구체화한다. D10과의 연결, 실제 강도·적용 범위와 중복 처리도 체크리스트와 최종 구현 계약에서 검토한다. 학습 데이터 수집·학습·평가·모델 제공이 추가되어 이 묶음의 작업량은 이전보다 늘었다.
- 제외 조건 목록의 전체 교체·마지막 저장 우선은 D06, 선택 목록 제한은 D07·D08, 섭취 불가의 재료 중심 단위는 D09로 확정했다. 재료 목록·매핑과 나머지 관리 계약, 기존 목록 밖 값의 호환 처리, 식사·추천·피드백의 저장 경계와 UUID 생성·복원부터 이어지는 검증을 기존 묶음 안에서 정리한다.
- D12에 따라 선택·보류·질문을 한 번에 받는다. 정책 변경 선택과 채택한 정책 안의 구현 세부를 구분하며, 설계 선택을 T02 전체 구현 지시로 해석하지 않는다.

## T02 진행표 — 남은 범위 관리

사용자가 남은 분량을 확인할 수 있도록 기존 T02 범위를 아래 5묶음으로 정리한다. 묶음 수는 구현 완료율이나 동일한 작업량을 뜻하지 않는다. 새로운 기능을 추가하는 계획이나 미결정 정책의 승인이 아니다.

| 묶음 | 포함 범위 | 설계 상태 |
| --- | --- | --- |
| 1. 인증·소유권 | 메뉴 추천·질문·피드백의 JWT 필수, 피드백 소유자·메뉴 검증 | D01~D03 승인 |
| 2. 피드백·학습형 추천 | 평가 이력·집계, 학습 신호·모델·학습·검증·예측과 중복·동시 요청 | D13/D14와 통합 §4~5 초안. M1A/M3A 선택·실제 품질 검증 남음 |
| 3. 제외 조건 관리 | 알레르기·섭취 불가·비선호의 조회·편집, 정규화·제한, 동시 저장과 기존 제외 규칙 | D06~D09와 통합 §4 초안. M2A 선택·실제 데이터 대응/매핑 검증 남음 |
| 4. 기록·기존 데이터 | 식사 스냅샷·추천·질문 상태의 저장 경계, 실패 원자성, 기존 비인증 질문 이력·소유자 없는 기록의 취급 | 통합 §2~5/8 초안 작성. 실제 보존 검증은 구현 후 |
| 5. 연동 계약·검증 계획 | 요청 사용자 번호의 호환 처리, 오류·응답·호출 순서, UUID 생성·복원·사용자 격리·회귀·필요한 MySQL 검증 | 통합 §4와 T09 계획 작성. 실제 연동/테스트 미실행 |

- 5묶음 모두 통합 문서에 기술 초안을 작성했다. M1A·M2A·M3A는 D15로 선택했으며 세부 검토와 실제 구현/검증은 남아 있다. T02의 새 실행 코드 변경·통합 검증은 아직 시작하지 않았다. 문서 초안을 구현 완료율로 계산하지 않는다.
- D12의 체크리스트로 여러 결정을 한 번에 비교하고 사용자 선택·보류를 기록한다. 선택한 정책 안의 세부 필드·쿼리·검증 사례를 모두 별개의 사용자 결정으로 늘리지 않는다. 묶음 수가 동일해도 D11로 작업량이 늘었으므로 개수로 완료율을 계산하지 않는다.
- 사용자가 추가한 D05·D11 개인 선호 누적·여러 신호 학습 외의 추천 알고리즘 개선, T03 방, T06~T08 계정 이관과 운영 배포를 T02의 새 필수 기능으로 추가하지 않는다. 학습형 추천은 기존 2번 묶음에서 다루며 구체적인 구현 작업 분할은 설계와 데이터 조건을 정리한 뒤 제시한다.

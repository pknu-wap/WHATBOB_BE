# #39 여러 탭·계정 전환 경계 설계

작성: 2026-11-13. 상태: 사용자가 R2A 준비·확정 두 단계 전환, R3A 이관 후 원본 사용자 행 물리 삭제, R4A 탭 알림과 인증 재확인을 선택했다. 이 정책을 충족하는 기술 설계안이며 요청 경로·작업 표·수명·잠금 등 세부 계약은 구체화 중이다. 실행 API·DB 구현 완료를 뜻하지 않는다. [고정 진행표](39-architecture-status.md), [HTTP 계약](39-t01-http-contract-proposal.md), [DB 계약](39-t01-database-contract.md), [방 ADR](../adr/0002-room-reconnect-and-account-switching.md)을 따른다.

## 적용 환경과 검토 순서

- 2026-11-13 사용자 재확인: 앱 형태는 아직 정하지 않았다. 이는 플랫폼 선택을 뒤로 미루거나 웹 우선으로 진행하라는 승인이 아니다. 플랫폼 선택 시점·진행 방향도 에이전트가 임의로 확정하지 않는다.
- 현재 웹 프론트의 쿠키·여러 탭 검토안과 향후 앱의 인증 보관·전달 방식을 구분한다. 웹의 공유 쿠키·BroadcastChannel을 모든 앱의 필수 구조로 일반화하지 않는다. 웹 경로를 유지하는 동안에는 관련 검토를 삭제하거나 완료로 처리하지 않는다.
- 서버의 공통 인증 처리와 클라이언트별 보관·전달 분리는 에이전트의 제안이다. 기존 승인된 사용자 식별·해시·JWT·만료·폐기·방 참여 제한과, 새로 검토하는 구조·진행 순서의 채택을 구분한다. 앱 전용 인증 경로는 미승인·미구현이다.
- 유효한 동일 인증으로 기존 사용자를 복원하는 기존 계약은 유지한다. 새 탭·추가 실행 환경에서 어떤 인증·사용자를 사용할지, 모든 탭의 사용자 일치 보장이나 탭별 신규 사용자 정책은 미결정이다. 앞선 에이전트의 ‘새 UUID를 만드는 방향으로 바꾸지 않겠다’는 설명은 사용자 선택으로 기록하지 않는다.
- 최신 D12 사용자 요청에 따라 여러 선택지와 trade-off·근거를 [공통 체크리스트](39-cross-feature-architecture-checklist.md)로 함께 제시한다. 사용자는 선택·보류·질문할 수 있으며 과거의 한 번에 하나 질문 방식은 대체했다. 보호 요청 보류·현재 사용자 확인과 전환 준비·확정 방식은 R4A·R2A로 선택됐으며, R1·R5의 미선택과 구분한다.
- 아키텍처의 채택·변경·유보는 사용자가 선택한다. 에이전트는 추천 이유와 영향을 설명하고 사용자 응답 전에는 제안을 확정 설계·완료 상태로 전환하지 않는다. 이미 승인된 개별 정책은 새 선택과 혼동해 해제하지 않는다.

## 문제와 유지할 정책

- 같은 이름·Domain·Path의 쿠키는 브라우저 탭들이 공유하지만 JWT는 각 탭의 메모리에 있다. A 탭의 JWT·화면이 이전 사용자이고 쿠키만 B 탭의 새 인증으로 바뀔 수 있다.
- 쿠키가 바뀌었다는 이유로 이전 사용자의 식사 저장·피드백 요청을 새 사용자로 자동 실행하지 않는다. UUID·공개 사용자 번호·작업 번호만으로 인증하지 않는다.
- 최초 여러 탭에서 서로 다른 준비 비밀값으로 별도 UUID가 생기는 기존 허용은 유지한다. 탭 대표 선출·최초 생성 Web Locks·브라우저당 한 사용자 보장·별도 UUID 자동 병합은 추가하지 않는다.
- 방 참여 요청 시작·응답 대기·참여·60초 재접속 유예 중 로그인·로그아웃·계정 전환을 막는다. 대상 카카오 계정이 다른 기기에서 참여·유예 중인 경우도 전환을 막는다.

## 1. 탭 간 알림과 화면 상태

1. 프론트는 동일 출처의 `BroadcastChannel`에 `AUTH_CHANGE_STARTED`, `AUTH_CHANGE_COMPLETED`, `AUTH_CHANGE_CANCELLED` 힌트를 보낸다. JWT·비밀 쿠키·해시·사용자 프로필은 보내지 않는다. 메시지에는 중복 구분용 임의 이벤트 번호만 포함한다.
2. 전환 시작을 인지한 탭은 보호된 새 쓰기 요청을 보류한다. 진행 요청 취소는 최선 노력이며 서버 롤백으로 해석하지 않는다.
3. 탭마다 인증 세대 번호를 증가시키고, 각 요청은 시작 당시 세대·사용자·인증 기록 문맥을 기억한다. 응답 시 문맥이 달라졌으면 이전 응답으로 현재 화면·JWT·캐시를 덮어쓰지 않는다.
4. 전환 완료 힌트는 성공 증거가 아니다. 새 쿠키의 토큰 API와 사용자 DTO로 현재 사용자를 확인하고 메모리 JWT·캐시·화면을 함께 교체한다. 전환이 확인된 이전 사용자의 변경 요청을 자동 재생하지 않는다.
5. 기존 방 참여·요청 결과 불명 상태가 있다면 다른 사용자로 조용히 바꾸지 않는다. 해당 사용자·참여의 결과 확인을 우선하고 계정 전환 차단 안내를 유지한다. 최초 별도 UUID 생성에 따른 쿠키 경합이 방 이용과 겹친 경우도 서버 인증 문맥 불일치로 처리하며 기존 방을 다른 사용자로 승계하지 않는다.
6. 알림이 오지 않거나 브라우저가 지원하지 않아도 서버 검증은 유지한다. 탭 복귀·초기 복원·401·전환 결과 확인 시 현재 인증을 재검증한다. 이미 다른 사용자가 된 것이 확인되면 이전 화면을 비우고 계정 변경 안내를 표시한다.

선택의 trade-off: 탭 알림은 다른 탭이 빨리 화면을 정리하게 돕지만 잠든 탭·닫힌 탭·지원 차이 때문에 안전성 근거가 될 수 없다. 서버 검증과 응답 세대 검사를 함께 쓰면 구현이 늘지만 오래된 사용자 데이터와 새 사용자 쓰기의 혼합을 막는다. [MDN Broadcast Channel API](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API)는 동일 출처의 탭·창 사이 통신을 설명하며 인증이나 서버 트랜잭션을 대신하지 않는다.

## 2. JWT 갱신에서 다른 사용자 쿠키가 온 경우

- 토큰 API의 최초 복원은 현재 쿠키로 사용자를 확인한다. 이미 사용자·인증 문맥을 가진 화면의 갱신은 `X-Whatbob-Auth-Context` 헤더에 기대하는 `sid`의 십진 문자열을 보낼 수 있도록 계약을 확장하는 안을 둔다. 이 헤더는 전제 비교용이며 인증 근거가 아니다.
- 서버는 먼저 보호 쿠키와 DB 기록을 검증하고 실제 `sid`와 기대 문맥을 비교한다. 다르면 `409 AUTH_CONTEXT_CHANGED`로 응답하며 JWT 발급·쿠키 교체·30일 연장을 하지 않는다. 임의의 헤더를 안다고 다른 인증으로 접근하지 못한다.
- 프론트는 이를 JWT 시간 만료로 바꾸지 않고 자동 반복을 중단한다. 이전 사용자 변경 요청은 폐기·결과 확인 대상으로 남기고, 현재 쿠키를 확인하는 명시적 복원 흐름에서 사용자 DTO와 화면을 함께 바꾼다. 방 참여 상태가 남았다면 전환 차단 원칙을 우선한다.
- 이 선택 헤더의 CORS 허용은 운영 설정 4번에 포함한다. 기존 세 API의 JSON 무본문 원칙과 쿠키·Origin·`X-Whatbob-Request: 1` 검사는 유지한다. 헤더 없는 최초 방문 복원과 문맥 있는 재발급을 클라이언트에서 구분한다.
- 여러 탭의 최초 쿠키 경합까지 기존 사용자 복원을 보장하는 새 정책은 아니다. 브라우저가 서버 응답의 `Set-Cookie`를 늦게 적용하는 상황은 JavaScript가 이전 응답을 무시하는 것만으로 막을 수 없다. 다음 인증 문맥 확인에서 불일치를 감지하고 안전하게 멈추는 한계를 명시한다.

## 3. 서버에서 방 참여·계정 전환을 같은 문으로 통과시키기

1. 프론트는 방 생성·참여 요청 직전에 전환을 차단한다. 응답 대기·실패 불명 동안 차단을 유지한다.
2. 서버의 보호된 상태 변경은 관련 기존 사용자 행을 ID 오름차순으로 잠근 뒤 인증 행을 ID 오름차순으로 검증·잠근다. 방 관련 행은 그 뒤 일정한 순서로 잠근다. 인증 의존성의 과거 조회 결과만으로 쓰기를 커밋하지 않는다.
3. 방 생성·참여는 최신 인증과 전환 진행 여부를 확인하고 같은 트랜잭션에서 참여를 확정한다. 계정 전환은 같은 사용자 잠금 아래 실제 참여·60초 유예를 확인한다.
4. 방 참여가 먼저 확정됐다면 전환은 `409 ROOM_PARTICIPATION_ACTIVE`다. 계정 전환이 먼저 확정됐다면 이전 인증의 참여 요청은 종료된 인증으로 거절한다. UI의 금지 정책을 직접 요청·다른 탭에서도 유지하기 위한 서버 방어이며 방 이용 중 전환을 허용하는 새 흐름이 아니다.
5. 카카오 외부 인증·이미지 처리 등 느린 외부 통신 중 DB 행 잠금을 계속 보유하지 않는다. 외부 결과를 받은 뒤 원본·대상 사용자와 인증·참여 상태를 잠금 아래 다시 검증하고 변경을 확정한다. 외부 호출 전 한 번의 미참여 확인만으로 전환을 허용하지 않는다.
6. 현재 사용자 쓰기와 이관이 겹치면 먼저 커밋된 원본 기록까지 이관에 포함하거나, 전환 후 이전 인증 쓰기를 거절한다. 원본 사용자 이관 뒤 이전 사용자 FK로 새 기록을 만들지 않는다. 이 경계는 해당 T02·T03·T06~T08 구현에서 함께 검증한다.

잠금은 같은 사용자의 작업을 잠깐 줄 세우는 방법이다. 사용자가 다른 작업을 하는 동안 그 사람의 행만 기다리게 하는 대신, 잠금 범위·순서·교착 재시도 검증이 필요하다. [MySQL locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)는 트랜잭션 안의 `SELECT ... FOR UPDATE`를 설명한다. 실제 MySQL에서 확인하며 SQLite 테스트만으로 경합 통과를 주장하지 않는다.

## 4. 참여 응답 유실과 늦은 성공

아래는 T03 구현에 포함할 작업 결과 확인 인터페이스 설계안이다. 공개된 기존 방 API를 이미 변경한 것으로 기록하지 않는다.

- 새 프론트의 방 생성·참여에는 UUIDv4 `Idempotency-Key`를 붙인다. 기존 본문·정상 상태·중복 참여의 도메인 의미를 일괄 교체하지 않고 같은 작업 번호의 재전송만 같은 작업으로 구분한다.
- 작업 기록은 인증으로 확인한 사용자·원본 인증·작업 종류·키와 정규화한 요청 지문을 묶는다. 요청 번호 자체는 인증 수단이 아니며 다른 사용자 결과를 조회·취소하지 못한다.
- 응답이 유실되면 같은 작업 번호의 서버 결과를 확인한다. `SUCCEEDED`는 해당 방·참여 상태 재조회, `FAILED`·`CANCELLED`는 해당 요청의 차단 해제 가능, `PENDING`·`UNKNOWN`·DB 장애는 확인 중 상태다. 단순 미참여 한 번 조회나 기록 없음은 실패 확정이 아니다.
- 늦게 도착할 원래 요청까지 차단하려면 명시적 취소·종결 요청이 필요하다. 서버는 같은 사용자 잠금·작업 키 유일 제약 아래 기존 작업이 없더라도 취소 표식을 먼저 저장할 수 있다. 나중의 원래 요청은 표식을 보고 참여를 만들지 않는다.
- 이미 참여가 성공했다면 취소가 성공한 것처럼 위장하지 않는다. 현재 참여를 반환하고 기존 퇴장 흐름을 사용한다. 단순 네트워크 오류만으로 방장 방을 종료하거나 참여자 주문서를 삭제하지 않는다.
- 작업 결과·종결 조회 경로의 구체 명칭은 T03 구현 PR에 고정한다. 예시 역할은 사용자에게 귀속된 `GET .../{operation_id}` 조회와 `POST .../{operation_id}/cancellation` 종결이다. 둘 다 인증과 상태 변경 권한이 필요하다.
- 작업 기록 보관·종결 표식이 유효한 기간은 운영 설정에서 정의하고 프론트의 재전송 허용 기간과 함께 검증한다. 보관 기한이 지난 불명 작업은 단순히 같은 키로 재실행하지 않는다. 이 설계안에서는 기간을 임의로 사용자 정책으로 확정하지 않는다.

## 5. 카카오 연결·로그아웃 응답 유실의 복원

T01의 쿠키 준비 → 사용자 생성 구조를 계정 전환에서도 활용하는 설계안이다. 후속 T06~T08의 트랜잭션·작업 결과 보관과 함께 구현한다.

1. 현재 사용자·인증·방 상태를 검증한 뒤 전환 작업 번호를 만든다. 이후 결과 확인과 재요청은 같은 작업을 가리킨다.
2. 이전 인증을 종료하기 **전에** 다음 인증용 비밀값을 별도의 HttpOnly 준비 쿠키로 브라우저에 전달한다. 원본 인증 쿠키와 구분해 준비만으로 원본 사용자를 바꾸지 않는다. 준비 해시는 전환 전용 작업 기록에서 관리하고 일반 `auth_sessions` 준비 행으로 노출하지 않는다. 원본 인증·작업에 연결해 세 기존 쿠키 API나 일반 API에서 전환 준비를 익명 생성·인증으로 오인하지 않게 한다. 확정 시에만 해당 해시의 대상 정식 인증을 만들고 연결한다.
3. 후속 확정 요청은 서버가 준비 쿠키를 실제 받았음을 증명한다. 작업 번호만으로 새 인증을 발급하지 않는다. 준비 응답이 유실됐으면 원본 인증·기록은 아직 바뀌지 않았으므로 확인·준비 복구를 할 수 있다.
4. 서버는 방·원본·대상 사용자 제한을 다시 검사하고, 이관 또는 새 UUID 생성·대상 인증 연결·이전 인증 종료·작업 성공을 한 트랜잭션으로 확정한다. 카카오 외부 인증 실패·저장 실패 시 원본 상태를 보존한다.
5. 확정 응답에 대상 정식 쿠키·JWT·사용자 DTO를 내려준다. 브라우저가 응답을 못 받아도 이미 가진 준비 비밀 쿠키로 같은 성공 작업을 증명하고 같은 대상 인증을 복구할 수 있다. 대상 비밀 원문을 DB에 저장하거나 작업 번호만으로 임의 재발급하지 않는다.
6. 복구는 이미 성공한 대상 인증을 확인하는 역할이며 기록을 다시 이관하거나 새 UUID를 추가 생성하지 않는다. 종료된 원본 쿠키만 받은 일반 준비·토큰 API는 기존 `SESSION_REVOKED` 정책을 유지한다.
7. 현재 쿠키·작업·기대 원본 문맥이 다르면 다른 탭의 최신 전환을 덮지 않고 충돌로 중단한다. 초기 준비 쿠키 경합을 전부 직렬화하거나 브라우저가 지운 비밀값을 서버에서 복원하는 보장은 추가하지 않는다.
8. 정리 작업에서 원본 인증 행을 삭제해도 성공 작업과 대상 인증의 복구 연결을 잃지 않도록 작업 기록과 수명을 따로 설계한다. 원본 사용자 삭제 시 참조는 작업 시작 때 검증한 최소 비민감 문맥을 보존하는 방식으로 T06 마이그레이션에서 명시한다. 비밀 준비 쿠키가 없거나 복구 보관 기한이 지나면 작업 번호만으로 인증하지 않는다.

이 방식은 응답 유실 뒤 중복 사용자·중복 이관을 막을 복원 근거를 만들지만, 보호 쿠키와 서버 준비 기록·정리·추가 왕복이 늘어난다. 별도 준비 없이 바로 전환하면 요청 수는 적지만 서버에 해시만 저장하는 정책에서 유실된 새 비밀 쿠키를 같은 값으로 다시 보내기 어렵다. [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)는 같은 작업 키로 중복 실행을 막는 실제 서비스 사례다. Stripe의 응답 보관 방식·기간을 그대로 채택하거나 작업 키를 인증 수단으로 쓰는 것은 아니다.

## T01과 후속 구현 범위

- T01은 인증 문맥·현재 사용자 확인·DB 원자성·프론트 응답 세대·기존 사용자 보존의 기반을 갖춘다. 방 참여 요청 작업 기록은 T03, 카카오 전환 준비·복구 작업 기록은 T06~T08에서 함께 구현·테스트한다.
- T01 DB 계약의 기본 사용자·인증 표가 이 후속 작업의 결과 보관 표까지 이미 구현·승인했다는 의미는 아니다. 작업 표의 물리 자료형·인덱스·FK와 보관 기한은 해당 기능 PR·운영 계약에 포함한다. 이를 T01 완료 조건에 계속 추가하지 않는다.
- 사용자 경험에 영향을 주는 ‘다른 탭에서 계정이 바뀌면 보호된 요청을 보류하고 현재 사용자 확인’과 ‘전환 준비·확정 두 요청’은 R4A·R2A로 선택됐다. 원본 사용자는 R3A에 따라 이관 트랜잭션에서 참조·인증 정리 후 물리 삭제한다. 성공 작업의 복구 연결은 원본 행 삭제 뒤에도 유지하도록 설계한다. 기술 세부 전체나 실행 API가 승인·구현됐다는 뜻은 아니다.

## 구현 후 검증

- 두 탭의 같은 사용자·다른 인증·다른 UUID, 알림 유실·탭 복귀·서버 문맥 불일치와 이전 화면 응답 비적용.
- 다른 사용자 쿠키가 온 갱신에서 JWT·쿠키·만료 비변경, 새 사용자로 이전 식사·피드백 자동 재생 금지.
- 방 참여·로그아웃·원본/대상 카카오 참여·유예의 경합과 서버 잠금, 외부 인증 뒤 상태 재검증.
- 참여 응답 유실·늦은 원래 요청·기록 부재·취소 표식·이미 성공한 참여와 정확한 차단 해제.
- 전환 준비 응답·확정 응답 각각의 유실, 동일 작업 복원·중복 생성/이관 방지, 원본 종료 및 정리 후 복구 근거, 비밀값 없이 작업 번호만 아는 요청 차단.
- 실제 MySQL의 유일성·잠금·롤백, 브라우저 쿠키 전달·늦은 Set-Cookie·BroadcastChannel 미지원과 민감값 비노출.

위는 설계안과 검증 계획이다. 실행 코드·새 API·DB 표·프론트·운영 데이터 변경 및 동작 테스트는 수행하지 않았다.

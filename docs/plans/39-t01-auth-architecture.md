# T01 UUID 사용자 생성·재방문 복원 아키텍처

상태: 2026-11-12 단일 인증 기록의 준비 → 정식 인증 전환 및 최소 JWT 구성 합의. 실행 코드는 미구현이며 HTTP·쿠키·DB 상세 계약은 아래 후속 설계 대상이다.

기준: [구현 명세](../specs/39-uuid-users-and-kakao-migration.md), [T01 작업 범위](39-uuid-user-tickets.md), [사용자·이관 ADR](../adr/0001-uuid-users-with-optional-kakao-linking.md).

## 합의한 인증 방식

- 서버가 Python `secrets.token_urlsafe(32)`로 32바이트 무작위 데이터를 기반으로 한 비밀값을 생성한다. SHA-256은 난수 생성기가 아니라 받은 비밀값을 해시로 계산하는 함수다.
- 원본 비밀값은 브라우저의 보호된 쿠키에 보관하고 DB에는 SHA-256 해시만 저장한다. 원본을 로그에 남기지 않는다.
- SHA-256 결과는 32바이트이며 16진수 문자열로 표현하면 64글자다. 사용자 결정에 따라 DB에는 64글자 문자열 대신 원래의 32바이트를 MySQL `BINARY(32)`로 저장한다. Python에서는 `hashlib.sha256(...).digest()`의 바이트 결과를 저장·조회하며 `hexdigest()` 문자열을 저장하지 않는다.
- 브라우저는 복원 요청에 비밀값 쿠키를 전송한다. 서버는 해시를 계산하고 해당 해시의 인증 세션을 인덱스로 조회한다.
- 인증 세션이 유효하고 만료·폐기되지 않았을 때만 연결된 사용자로 복원한다. 사용자 UUID만으로 인증하지 않는다.
- 쿠키에 별도의 공개 세션 식별자를 포함하는 방식은 현재 채택하지 않는다. 세션 내부 PK를 두는 것과 브라우저가 세션 식별자를 보내는 것은 별개다.
- SHA-256 선택은 서버가 충분히 긴 무작위 토큰을 생성한다는 전제다. 사람이 정하는 비밀번호 저장에 그대로 적용하는 결정이 아니다. Argon2id·HMAC 비밀키는 이번 토큰 저장 방식에 추가하지 않는다.

## 접근 JWT 유효 시간

- 사용자 결정에 따라 접근 JWT는 발급 시점부터 1시간(60분, 3,600초) 동안 유효하도록 구현한다.
- 접근 JWT 만료는 사용자 삭제나 UUID 재생성을 의미하지 않는다. 유효한 복원 인증 세션으로 같은 사용자의 새 JWT를 발급할 수 있도록 설계한다.
- 사용자 최종 결정에 따라 복원 쿠키·인증 세션은 최초 사용자 생성 성공 시점부터 30일 동안 유효하며, 만료 전에 이용하면 연장 시점부터 다시 30일 유효하도록 한다. 기존 14일 고정 정책을 대체한다.
- 설계상 이용 시 연장은 유효한 정식 쿠키로 JWT 발급·재발급에 성공할 때 수행한다. 서버 만료를 현재 시각 + 30일로 갱신하고 응답 쿠키 만료를 이에 맞춘다. 일반 API 요청마다 만료일을 쓰거나 준비 API만 호출하여 연장하지 않는다. 먼저 서버에서 만료·폐기를 검증한다.
- 생성 시각과 갱신 가능한 만료 시각을 분리해 관리한다. 별도 최장 수명은 현재 두지 않으며 유효 기간 내 이용을 이어가면 반복 연장할 수 있다. 이미 만료된 인증은 연장·복구하지 않으며 사용자 데이터 자체를 삭제하는 결정은 아니다.
- 이관·로그아웃 후 기존 인증을 즉시 폐기하는 요구는 유지한다. JWT 만료까지 기다리는 것으로 대체하지 않는다.
- 이번 결정은 설계 문서에 반영했으며 현재 실행 코드의 JWT 기본 설정은 변경하지 않았다.

## 접근 JWT 내용

- 사용자 결정에 따라 ① 인증에 필요한 식별자와 시간·발급자·대상 정보만 담는 구성을 채택한다. 닉네임·이미지·카카오 ID·로그인 종류·역할·권한 등 프로필·권한 스냅샷은 포함하지 않고 필요한 정보는 DB에서 확인한다.
- 필수 클레임은 `sub`(내부 사용자 PK의 십진 문자열), `sid`(인증 기록 PK의 십진 문자열), `iat`(발급 시각의 UTC Unix 초 정수), `exp`(발급 시각 + 3,600초), `iss`(WhatBap 인증 발급자), `aud`(WhatBap API 대상)로 한다. `sid`는 우리 접근 JWT에서 인증 기록을 가리키는 계약이며 JWT별 고유 번호가 아니다. 재발급 시 같은 인증 기록을 유지한다.
- 발급·검증은 같은 고정 `iss`·`aud` 값을 사용하고 불일치를 거절한다. 실제 문자열과 환경별 분리는 설정 상세 설계에서 확정한다. 서명·허용 알고리즘·필수 클레임과 타입·만료·발급 시각 검증 후 DB 인증 기록의 유효성 및 `sub`와 연결 사용자의 일치를 확인한다. 미래 발급 시각의 허용 오차는 구현 설정에서 구체화한다.
- 비밀 쿠키 원본과 SHA-256 해시는 JWT에 포함하지 않는다. 서명된 JWT 내용은 암호화된 비밀 저장소로 취급하지 않는다.
- `sub` 없이도 `sid`로 조회한 인증 기록의 사용자 FK에서 사용자를 찾는 별도 설계는 가능하지만 이번에는 두 값을 담고 일치를 검증한다. `sid` 없이 사용자 번호만 담으면 해당 인증의 만료·종료를 확인할 연결이 없어지므로 이번 즉시 폐기 구조를 만족하지 못한다. 두 값이 모두 없는 JWT는 별도 연결 수단 없이는 사용자를 식별하지 못하며 거절한다.
- 근거: [JWT 표준](https://www.rfc-editor.org/rfc/rfc7519.html), [Auth0 최소 클레임 지침](https://auth0.com/docs/secure/tokens/token-best-practices). 이는 공개 표준·지침에 기반한 우리 설계이며 특정 기업의 내부 구현을 단정하지 않는다.

## 접근 JWT 갱신 방식

- 사용자 결정에 따라 API가 접근 JWT 만료를 응답하면 복원 쿠키로 새 JWT를 발급받고 원래 요청을 한 번 재시도한다. 만료 전 타이머에 의한 주기적 갱신은 채택하지 않는다.
- 이유: 현재 이용자가 적은 단계에서는 실제 요청 시 갱신하는 단순한 흐름으로 시작한다. 활동·만료 시점을 추적하는 사전 갱신 관리가 필요 없고, 이용을 중단한 브라우저의 불필요한 예약 갱신도 피할 수 있다. 메모리 1GB만으로 이 방식이 필수이거나 큰 자원 절감 효과가 있다고 판단한 것은 아니다.
- 만료 전 갱신도 사용자 활동에 따라 제한할 수 있으므로 모든 사전 갱신 구현보다 자원을 덜 쓴다고 단정하지 않는다. 계속 이용하는 사용자에게는 만료 응답과 재시도 비용이 추가된다.
- 추후 사용자 수만을 기준으로 전환하지 않는다. 만료 응답 후 갱신·재시도로 발생하는 지연과 활동 기반 사전 갱신의 요청량·집중도·서버 부하를 측정해 비교한다. 사전 갱신을 추가하더라도 만료 응답 후 복구 처리는 유지한다.
- 모든 401을 갱신 대상으로 삼지 않는다. JWT 만료와 변조·세션 폐기 등 다른 인증 실패를 구분하는 오류 계약을 구현 전에 정한다.
- 프론트는 동시 만료 요청의 갱신을 하나로 모으고, 갱신 실패·재시도 실패 시 무한 반복하지 않는다. 백엔드는 인증 만료 요청의 비즈니스 처리를 시작하기 전에 거절한다.
- 유효한 정식 쿠키로 JWT를 새로 발급하면 복원 인증과 쿠키의 만료일도 발급 시점부터 30일로 연장한다. 접근 JWT 자체의 유효 기간은 계속 1시간이다. 재방문 때 JWT가 없는 경우도 토큰 API에서 복원한다.

## 웹 프론트의 접근 JWT 보관

- 사용자 결정에 따라 ① 접근 JWT는 실행 중인 프론트의 메모리에만 보관한다. `localStorage`, `sessionStorage`, IndexedDB 등 지속 저장소나 JWT 쿠키로 복제하지 않는다. 영속화 기능이 있는 상태 관리 도구를 사용하더라도 JWT는 영속화 대상에서 제외한다. 구체적인 프론트 모듈·프레임워크는 호출부 확인 후 정한다.
- 일반 API 요청은 메모리의 JWT를 `Authorization: Bearer`로 전달한다. 30일 복원 비밀값은 기존 HttpOnly 쿠키 정책을 유지하며 프론트 JavaScript가 읽어 메모리로 옮기거나 저장소에 복제하지 않는다.
- 페이지 새로고침·완전한 페이지 이동·새 탭 진입 등 메모리 상태가 새로 시작할 때 JWT는 없어진다. 유효한 정식 쿠키가 있으면 토큰 API로 같은 사용자·같은 인증 기록의 JWT를 재발급받아 메모리에 보관한다. 처음 방문처럼 쿠키가 없는 경우와 준비 쿠키만 있는 경우는 기존 준비·생성 분기로 처리하며 JWT 부재만으로 사용자를 생성하지 않는다.
- 시작 시 복원이 끝날 때까지 보호 API 요청을 보류하고, 같은 프론트 실행 컨텍스트 내 동시 복원·재발급은 하나로 합친다. 탭마다 메모리는 독립적이며 JWT를 탭 간 공유하거나 최초 사용자 생성을 직렬화하는 기능을 이번 결정으로 추가하지 않는다. 계정 전환 시 탭 동기화·진행 중 응답 경합은 별도 후속 설계 대상이다.
- 로그아웃·인증 종료 시 메모리의 JWT와 이전 사용자 화면 상태를 정리한다. 브라우저 메모리에서 JWT를 지우는 것만으로 서버 인증이 종료되는 것은 아니므로 기존 DB 인증 종료 정책을 함께 적용한다. 일시적 DB·네트워크 장애는 새 UUID 생성으로 바꾸지 않고 복원 오류를 처리한다.
- 메모리 보관은 페이지 종료 후 JWT가 저장소에 남는 노출을 줄이는 선택이다. 실행 중 악성 JavaScript의 토큰 탈취·사용자 대신 요청을 차단한다고 보장하지 않는다. 새로고침·새 탭마다 재발급과 DB 조회·대기 비용이 추가되며 재발급 성공 시 기존 30일 연장 정책을 적용한다. 타사 쿠키 차단으로 복원 쿠키가 전달되지 않는 배포 한계도 유지된다.
- 근거: [Auth0 Token Storage](https://auth0.com/docs/secure/security-guidance/data-security/token-storage)의 브라우저 메모리 보관 권장과 페이지 새로고침·탭 간 비영속성 설명. Auth0 SDK 도입이나 Web Worker 사용을 이번에 확정하는 것은 아니다. 네이티브 앱 저장 방식은 앱 형태 확정 후 별도로 설계한다.
- 후속 검증: JWT의 지속 저장소 미기록, 새로고침·새 탭에서 같은 사용자 복원, JWT 부재만으로 사용자 미생성, 동시 복원 합치기, DB 장애 시 인증 보존, 로그아웃 후 이전 화면·JWT 정리를 실제 프론트·브라우저에서 확인한다. 아직 실행하지 않았다.

## 요청별 JWT와 세션 검증

- 사용자 결정에 따라 JWT의 서명·만료 검증 후 연결된 DB 인증 세션의 유효성을 확인하는 방식을 채택한다. JWT만 확인하거나 차단 목록·사용자 인증 버전으로 대체하지 않는다.
- JWT의 `sid`로 내부 인증 기록을 조회하고, 연결된 사용자와 `sub`의 내부 사용자 번호가 일치하는지 확인한다. 클레임 계약은 위 접근 JWT 내용 절을 따르며 비밀값 원문은 JWT에 넣지 않는다.
- 세션과 사용자가 모두 필요한 인증 경로는 기본키 기반 JOIN으로 함께 조회하여 DB 왕복 1회를 목표로 한다. 이는 두 테이블 조회 비용이 사라지거나 처리량이 보장된다는 뜻이 아니다. 매 요청 접속 시각 갱신은 추가하지 않는다.
- UUID에서 카카오로 이관하거나 카카오에서 로그아웃해 새 UUID로 전환할 때 기존 세션을 종료한다. 종료 후 인증 확인부터 기존 JWT를 거절하며 이미 진행 중인 요청의 취소는 별도 동시성 문제로 다룬다.
- 즉시 폐기를 지연시키는 세션 상태 캐시는 현재 추가하지 않는다. DB 장애 시 인증을 우회하지 않는다. 기존 WebSocket 연결의 폐기 반영 방식은 별도 설계한다.
- 처리량은 미측정이다. JWT만 확인하는 방식에는 없는 저장소 조회가 추가되며, 다른 상태 조회 방식과의 성능 차이는 쿼리·인덱스·연결·캐시 구성에 따라 달라진다. 기존 사용자 조회와 JOIN을 구성하면 현재 대비 DB 왕복 증가를 피할 수 있지만 DB 작업량은 증가한다.

## 기존 JWT의 새 인증 구조 전환

사용자 결정에 따라 ① 새 인증 구조 배포 후 기존 카카오 사용자는 한 번 다시 로그인하는 방식을 채택한다. 인증 세션 내부 번호가 없는 기존 JWT는 남은 유효 기간과 무관하게 새 인증 경계에서 거절한다. 기존 JWT를 잠시 허용하는 우회 경로나 자동으로 새 인증에 교환하는 API는 추가하지 않는다.

- 새 JWT는 위 필수 클레임 계약을 따르고, 인증 기록의 사용자와 `sub`가 일치하는지 검증한다. 세션 번호 없이 사용자 조회만으로 인증을 완료하는 기존 방식으로 되돌아가지 않는다.
- 재로그인이 필요한 이전 형식 JWT는 HTTP 401과 `REAUTHENTICATION_REQUIRED`로 안내한다. 프론트는 이전 토큰을 사용 중단하고 카카오 재로그인으로 연결하며, 이 응답을 JWT 만료 재발급 루프로 처리하지 않는다. 변조 토큰을 이전 형식이라고 신뢰하거나 서명 검증 없이 새 인증을 발급하지 않는다.
- 재로그인은 기존 카카오 사용자와 기록을 유지하고 새 인증 기록·쿠키·JWT를 발급하는 절차다. 기존 계정을 삭제하거나 새로운 카카오 계정을 만드는 결정이 아니다. 자동 새 UUID 생성으로 기존 카카오 계정이 복원된 것처럼 처리하지 않는다.
- 새 검증 적용 시점까지 카카오 발급 경로와 프론트 재로그인·쿠키 처리도 새 구조를 지원해야 한다. 오래된 발급 코드가 세션 없는 JWT를 계속 발급하는 상태로 배포하지 않는다. 기존 사용자 프로필·기록 보존 원칙을 지키며 프론트·발급·검증 배포 순서를 구현 계획에 포함한다. 실행 코드는 아직 변경하지 않았다.

## 인증 오류 구분과 복구 방향

- 사용자 결정에 따라 프론트의 다음 행동이 달라지는 기준으로 인증 오류를 구분하고, 아래 고정 오류 코드를 사용한다. 프론트는 설명 문구가 아니라 코드로 분기한다. 나머지 오류와 성공 응답 DTO 계약은 후속 설계에서 정한다.
- 접근 JWT 만료는 유효한 복원 세션으로 갱신한 뒤 원래 요청을 한 번 재시도한다. 변조된 JWT와 다른 인증 실패를 동일하게 갱신하지 않는다.
- 쿠키가 없으면 새 익명 사용자 시작 절차로 이동한다. 쿠키에 대응하는 세션이 없거나 만료·폐기되었다면 기존 인증을 종료하고 새 시작 또는 카카오 로그인 흐름으로 연결한다. 세션 부재가 사용자·기록 삭제를 의미하지 않는다.
- DB의 일시적인 연결·조회 장애는 인증 실패나 세션 부재로 바꾸지 않는다. 인증 정보는 유지하고 접근을 허용하지 않은 채 일시 장애를 반환한다. 예기치 않은 내부 오류도 새 사용자 생성의 근거로 사용하지 않는다.
- 응답 없는 네트워크 오류는 저장 성공 여부를 알 수 없는 상태다. 사용자 생성처럼 부작용이 있는 요청은 중복 방지와 안전한 자격 증명 복구 계약을 정하기 전에 자동 반복하지 않는다.
- 사용자 결정에 따라 안전하게 반복할 수 있는 일시 장애 요청은 최초 요청을 포함해 총 3회까지만 시도한다. 자동 재시도는 최대 2회이며 지수 백오프를 적용한다. 인증 무효나 안전한 중복 방지가 없는 사용자 생성 요청에는 이 정책을 일괄 적용하지 않는다.
- 사용자 결정에 따라 재시도 기준 대기는 1초·2초(배수 2)로 하고 각 기준의 ±50% 범위에서 균등 무작위 지터를 적용한다. 첫 재시도는 0.5~1.5초, 두 번째는 1~3초를 기다린다. 각 재시도마다 새 값을 뽑으며 사용자별 고정 대기 시간을 배정하지 않는다. 총 3회 시도이므로 4초 기준의 세 번째 재시도는 하지 않는다.
- 사용자 정정에 따라 최초 요청 시작부터 요청·지터 대기·자동 재시도를 모두 합친 전체 시간 제한을 10초로 한다. 요청마다 10초를 부여하는 설정이 아니다. 앞서 제안한 전체 15초·20초와 최대 34.5초 흐름은 채택하지 않는다.
- 사용자 결정에 따라 요청 한 번의 대기는 최대 3초로 제한한다. 각 시도의 실제 제한은 3초와 전체 10초 중 남은 시간의 최솟값이다. 이 수치는 운영 인증 API를 측정해 검증한 값이 아니므로 구현 후 재검토한다.
- 총 3회는 최대 시도 횟수다. 전체 10초가 먼저 소진되면 남은 재시도를 하지 않는다. 진행 중인 요청도 전체 제한 시 대기를 중단하며, 요청과 지터 대기는 남은 시간 예산을 넘겨 계속하지 않는다. 세 번 모두 실행할 것을 보장하지 않는다. 적용 위치와 JWT 갱신 흐름과의 구체적인 시간 예산 결합은 후속 설계 대상이다.
- 클라이언트가 대기를 중단해도 서버 작업이 자동으로 취소되거나 DB 트랜잭션이 롤백되었다고 판단하지 않는다. 서버의 DB 연결·쿼리 제한은 별도 설계한다. JWT 갱신 후 원래 요청 1회 재시도와 장애 재시도 예산을 중첩해 무한 반복하지 않는다.

## 사용자와 인증 세션의 역할

| 정보 | 역할 |
| --- | --- |
| `users.id` | 기존 내부 정수 PK. 식사 기록 등 기존 FK 연결을 유지한다. |
| 사용자 UUID | 카카오 연결 전 사용자 식별자. 인증 자격 증명이 아니다. 이관 후 원본 UUID를 폐기하는 정책을 따른다. |
| 인증 세션 내부 PK | DB 안에서 개별 인증 세션을 관리하는 번호. 쿠키로 노출할 필요는 없다. |
| 인증 세션 `user_id` | `users.id`를 참조하는 FK. 인증 세션의 주인을 나타낸다. |
| 인증 세션 비밀값 해시 | 요청으로 받은 비밀값을 검증하고 세션을 찾는 값. 유일 인덱스를 둔다. |
| 인증 세션 만료·폐기 정보 | 해시가 일치해도 이용을 거절해야 하는 상태를 나타낸다. |

사용자 테이블은 아래 합의에 따라 기존 구조를 확장하고, 인증 기록은 별도 테이블로 추가한다. 비밀값 해시의 저장 형식은 `BINARY(32)`로 확정했으며 인증 테이블의 실제 이름·나머지 컬럼 자료형·인덱스 구성은 DB 상세 설계에서 구체화한다. 인증 기록 삭제는 아래 서버 내부 10분 주기 정리 결정을 따른다. 별도 Redis 없이 기존 DB에 저장하는 구성을 우선 제안한다. 서버 메모리 1GB는 설계 제약이며 실제 처리 용량을 측정한 것은 아니다.

## 사용자 테이블 확장과 해시 저장

- 사용자 결정에 따라 기존 `users` 테이블을 유지하면서 UUID 컬럼을 추가하고, 기존 `kakao_id`의 유일성을 유지한 채 NULL을 허용하여 카카오 연결 없는 사용자를 저장한다. 기존 내부 정수 PK `users.id`와 이용 기록의 FK 연결은 유지한다. 닉네임·사진·이메일·생성/수정 시각 등 기존 데이터는 보존하며 사용자 테이블을 새로 만들거나 번호를 재부여하지 않는다.
- 인증 기록은 사용자 표의 해시 컬럼으로 합치지 않고 별도 표로 추가한다. 제안한 기본 항목은 인증 기록 번호, nullable 사용자 FK, 비밀값 해시, 생성 시각, 만료 시각, nullable 종료 시각이다. 준비와 정식 상태는 기존 합의대로 사용자 FK 유무로 구분한다. 표 이름·나머지 자료형·FK 삭제 정책은 후속 상세 설계 대상이다.
- 비밀값 해시는 정확히 32바이트인 SHA-256 결과를 `BINARY(32)`에 저장하고 유일 인덱스로 중복을 막는다. 저장·조회 모두 같은 비밀값 문자열 인코딩으로 해시를 계산하고 바이너리 파라미터를 사용한다. 길이 32바이트 검증으로 DB의 짧은 값 패딩·초과 길이 변환에 의존하지 않는다. 비교는 바이트 기준이며 문자열의 문자셋·대소문자 정렬 규칙에 의존하지 않는다.
- 64글자 16진수 표현보다 해시 데이터 표현이 작지만 실제 행·인덱스·메모리 비용은 별도 오버헤드가 있으므로 DB 전체 사용량이 절반으로 줄거나 1GB 서버의 처리량이 보장된다고 해석하지 않는다. 사람이 바로 읽기 불편한 trade-off를 받아들이며 해시도 로그·API 본문에 출력하지 않는다.
- 기존 데이터의 닉네임 충돌·길이·NULL 등을 사전 점검하고 해결되지 않은 충돌은 보고한다. 기존 카카오 프로필을 임의 변경하거나 중복 사용자를 삭제하지 않는다. UUID 채움 대상·형식과 인덱스·프로필 출처 정보·기본 이미지 및 마이그레이션 적용 순서는 후속 상세 설계에서 확정한다. `create_all()`만으로 기존 테이블을 수정하지 않는다.
- 구현 후 검증 계획: 카카오 번호 없는 사용자 생성, 기존 PK·관련 기록·프로필 보존, 서로 다른 사용자 분리, SHA-256의 32바이트 저장·정확 조회, 중복 해시 거절, 같은 쿠키 동시 생성 수렴과 FK 연결 원자성을 격리 DB에서 확인한다. 아직 실행하지 않았다.

근거: [MySQL 바이너리 자료형](https://dev.mysql.com/doc/refman/8.4/en/binary-varbinary.html). 운영 DB 버전·엔진·기존 스키마는 실제 마이그레이션 전에 확인한다.

## 생성과 복원 흐름

사용자 결정에 따라 첫 이용은 ② 서버가 비밀 쿠키를 먼저 전달하는 방식을 채택한다. 준비 요청에서 서버가 비밀값을 생성하여 HttpOnly 쿠키로 전달하고, 브라우저가 그 쿠키를 보내는 후속 생성 요청에서 사용자와 인증 세션을 생성한다. 준비 단계만으로 사용자 UUID나 접근 JWT를 발급하지 않는다.

생성 요청은 준비 쿠키의 발급 근거·상태·유효성을 검증한 후 비밀값의 SHA-256 해시를 기준으로 처리한다. 해당 비밀값으로 이미 생성된 유효한 인증 세션이 있으면 같은 사용자의 JWT를 발급하며 새 UUID를 만들지 않는다. 생성 응답이 유실되어도 브라우저가 이미 가진 쿠키로 재요청할 수 있고, DB에서 비밀값 원문을 복구할 필요가 없다.

같은 비밀값의 동시 생성 요청은 DB 고유 제약과 트랜잭션으로 하나의 사용자·세션에 수렴하도록 설계한다. 사용자와 세션의 DB 저장은 하나의 트랜잭션으로 처리하며, 충돌한 요청의 사용자만 별도로 남기지 않는다. 단순 조회 후 삽입만으로 동시성 문제를 해결했다고 판단하지 않는다.

준비 쿠키는 기존 사용자의 인증 수단과 구분한다. 만료·폐기된 기존 인증을 준비 쿠키처럼 취급해 재활성화하거나 새 사용자를 생성하지 않는다. 추가 준비 요청의 응답이 유실되어도 아직 사용자 생성이 없다는 순서를 유지한다.

사용자 결정에 따라 준비 쿠키의 생성 요청 허용 기간은 발급 후 5분 고정으로 한다. 브라우저는 수신 즉시 후속 생성 요청을 보낼 수 있으며 5분 동안 기다리는 의미가 아니다. 서버에서도 준비 만료를 확인한다. 사용자·인증 세션 생성 성공 시점부터 정식 인증의 최초 30일 수명을 계산한다. 이미 생성된 유효한 정식 세션이 있다면 준비 5분이 지났다는 이유로 새 UUID를 생성하지 않는다. 생성이 완료되지 않은 채 준비 기간이 만료되면 새 준비 절차가 필요하다.

사용자 결정에 따라 준비 쿠키는 DB에 준비 기록을 저장하여 검증한다. 서버 발급 비밀값의 SHA-256 해시, 준비 상태와 발급·만료 시각을 저장하고 원본 비밀값은 저장하지 않는다. 준비 상태에는 아직 연결된 사용자가 없으며 정식 사용자로 인증하지 않는다. 서명만으로 준비 발급을 검증하는 방식은 채택하지 않는다.

사용자 결정에 따라 준비 기록과 정식 인증 세션은 하나의 인증 기록으로 관리한다. 준비 시 만든 기록의 내부 PK를 유지하고, 사용자 생성 성공 시 같은 기록에 `users.id`를 연결하여 정식 인증으로 전환한다. 별도 준비 테이블에서 새 정식 세션으로 옮기는 방식은 채택하지 않는다. ‘사용 중’은 사용자가 현재 접속 중이라는 뜻이 아니라 사용자와 연결되어 인증에 사용할 수 있다는 뜻이다.

사용자 결정에 따라 ② 사용자 FK 유무로 준비·정식 단계를 구분하고 별도 `PENDING`/`ACTIVE` 상태 컬럼은 추가하지 않는다. `user_id IS NULL`이면 사용자 생성 전 준비 단계이고, 사용자 생성 트랜잭션에서 `users.id`를 연결하면 정식 단계다. `users.id`는 내부 정수 사용자 번호이며 사용자 UUID와 별개다. 인증 기록의 `user_id`는 이 내부 번호를 참조한다. 사용자 번호가 있다는 사실만으로 인증을 허용하지 않으며, 종료 여부와 만료 시각을 먼저 확인하고 연결된 사용자의 존재·이용 가능 여부도 검증한다.

만료·종료는 준비·정식 구분과 별개로 관리한다. 만료 시각이 현재 시각 이하이면 만료이며 종료 시각이 있으면 명시적 종료다. 만료 사실을 표현하려고 주기적으로 상태 컬럼을 갱신하지 않는다. 사용자 FK를 비워 정식 인증을 준비 단계로 되돌리거나, 사용자 삭제 시 FK를 자동으로 NULL 처리하여 재사용 가능한 준비 기록처럼 만들지 않는다. 사용자 삭제·이관 시 FK 참조 처리의 구체적 방식은 후속 DB·이관 설계에서 정하되 종료된 인증의 재사용을 금지한다.

생성 요청에서는 해당 인증 기록을 잠그고 준비 상태·만료·폐기를 확인한 뒤, 사용자 생성과 동일 인증 기록의 사용자 FK 연결·정식 만료 시각 설정을 하나의 트랜잭션으로 처리한다. 실패하면 사용자 생성과 기록 변경을 함께 롤백한다. 비밀값 해시의 유일 제약과 기록 잠금으로 같은 비밀값의 동시 요청이 한 사용자로 수렴하도록 한다. 준비 단계에서는 정식 사용자로 인증하지 않으며, 이미 연결된 유효 세션이면 새 사용자를 만들지 않고 같은 사용자의 JWT를 발급한다. 만료·폐기된 정식 인증은 재활성화하지 않는다. 정확한 테이블·컬럼·제약과 만료 기록 정리 정책은 DB 상세 설계에서 정한다.

정식 인증의 30일 변경에 맞춰 첫 준비 쿠키는 처음부터 30일 + 5분(2,592,300초) 동안 브라우저에 보관하도록 설정한다. 이는 준비 상태로 생성할 수 있는 기간을 늘리는 결정이 아니다. 서버는 준비 발급 후 5분 고정 제한을 유지하고, 준비 상태로 만료된 쿠키는 브라우저에 남아 있어도 사용자 생성·인증에 사용하지 못하게 한다. 사용자 생성에 성공하면 같은 비밀값과 인증 기록으로 정식 인증을 이어가며 생성 성공 시점부터 최초 30일 만료를 적용한다. 최초 보관 기간의 추가 5분은 준비 기간 끝 무렵에 생성해도 정식 인증 30일보다 쿠키가 먼저 삭제되지 않게 하는 여유다.

생성 성공 응답에서는 쿠키의 삭제 시각을 서버에 저장한 정식 인증 만료 시각에 맞춘다. 이 응답이 유실되어도 최초 쿠키가 남아 있으면, 같은 쿠키의 재요청은 이미 연결된 유효 사용자를 찾아 JWT를 발급하고 새 UUID를 생성하지 않는다. 유효한 정식 쿠키로 생성 결과 복구·복원·JWT 갱신에 성공하면 서버 만료와 쿠키를 그 시점부터 30일로 연장한다. 연장 응답이 유실되면 서버 만료는 연장되어도 브라우저 쿠키는 이전 삭제 시각을 유지할 수 있다. 다음 유효한 복원 응답으로 맞출 수 있지만 그 전에 쿠키가 삭제되면 서버 기록만으로 비밀값을 복구할 수 없다. 브라우저에 쿠키가 남아 있어도 서버 만료·폐기를 검증한다. 쿠키가 삭제·차단·덮어쓰기된 경우까지 기존 사용자 복구를 보장하지 않는다.

사용자 생성 없이 만료된 준비 기록도 아래 주기적 정리 대상에 포함한다. 발급 요청 속도 제한은 별도 정책으로 정한다. 브라우저 보관 기간 때문에 만료된 준비 기록을 30일간 유지할 필요는 없다. 같은 만료 쿠키로 반복 요청하는 것만으로 새 인증 기록이나 사용자를 생성하지 않는다. DB에 저장하는 것은 인증 상태와 비밀값 해시이며 JWT 원문 저장을 의미하지 않는다.

## 만료·종료 인증 기록 정리

사용자 결정에 따라 ② 서버 내부 주기적 정리를 채택하고 실행 간격은 10분(600초)으로 한다. 만료된 준비 기록, 만료된 정식 인증 기록, 명시적으로 종료된 인증 기록을 정리 대상으로 삼는다. 별도 보관 유예를 추가하지 않으며 삭제 실행 시점에 대상 여부를 확인한다. 사용자·UUID 자체나 취향·식사·추천·방 기록은 이 정리 작업에서 삭제하지 않는다.

- 인증 거절 시점과 물리 삭제 시점은 다르다. 만료 시각 또는 명시적 종료 시점부터 인증을 거절하고 정리 작업 실행을 기다리지 않는다. 기록이 남아 있다는 이유로 인증을 허용하지 않는다.
- 유효한 정식 인증의 30일 연장이 반영된 최신 만료 시각을 기준으로 삭제를 판정한다. 후보를 미리 조회했다는 이유만으로 ID만 이용해 나중에 삭제하지 않고, 삭제 시에도 만료·종료 조건을 확인하여 연장·생성 전환과의 경합을 처리한다.
- 사용자 결정에 따라 정리 작업 한 번의 실행에서 삭제하는 인증 기록은 전체 대상 종류를 합쳐 최대 100건으로 제한한다. 100건씩 반복하여 같은 실행에서 상한을 넘겨 삭제하지 않는다. 남은 대상은 다음 10분 주기에 처리한다. 대상이 100건보다 적으면 있는 대상만 삭제한다. 오래된 정리 대상이 계속 밀리지 않도록 삭제 대상 순서를 DB 상세 설계에서 정한다. DB 작업 시간 제한도 구현 전에 구체화한다. 10분마다 모든 대상이 삭제 완료되거나 만료 후 반드시 10분 내 삭제됨을 보장하지 않는다.
- 10분마다 최대 100건은 정상 실행 기준 시간당 최대 600건의 삭제 상한이다. 서버의 측정된 처리 용량을 뜻하지 않으며 장애·중단 시 실제 정리량은 더 적을 수 있다. 삭제 건수·남은 정리 대상 수로 누적 여부를 확인하고 추후 한도 조정을 판단한다. 여러 실행 주체가 각각 100건을 삭제하는 방식으로 전체 상한을 늘리지 않도록 실행 주체를 정한다.
- 기존 방 정리 루프의 실행 패턴을 참고하되 인증 정리 로직과 DB 세션은 분리한다. DB 오류 시 인증 검증을 우회하거나 사용자 데이터를 정리하지 않으며, 실패를 기록하고 다음 실행에서 다시 처리한다. 서버 중단·재시작 시 정리도 지연될 수 있다. 여러 워커·서버에서 중복 실행되지 않게 하는 실행 주체는 배포 구성 확인 후 정한다.
- 삭제된 인증은 해시 조회 결과가 없으므로 과거 만료·종료 원인을 항상 구별할 수 없다. 기록이 있을 때는 기존 만료·종료 오류 코드를 사용하고, 삭제 후 기록 부재 오류와 프론트 복구 동작은 후속 계약에서 정한다. DB 장애를 기록 부재로 처리하지 않는 원칙은 유지한다.

사용자 결정에 따라 여러 탭이 최초 접속 때 서로 다른 준비 쿠키를 발급받아 각각 별도 UUID 사용자가 생성되는 상황은 허용한다. 이를 막기 위한 Web Locks, 탭 대표 선출, 브라우저 공통 초기 요청 번호는 추가하지 않는다. 같은 비밀값의 재시도·동시 생성은 기존 DB 잠금·유일 제약으로 한 사용자에 수렴시키는 결정을 유지한다. 서로 다른 비밀값으로 생성된 사용자를 자동 병합하지 않는다.

이 선택은 구현을 단순하게 유지하는 대신 추가 사용자·인증 기록 저장과 쿠키 덮어쓰기로 인한 사용자 전환 가능성을 받아들이는 것이다. 동일한 이름·범위의 쿠키는 탭 간 공유되므로 각 탭의 JWT와 이후 복원 쿠키가 서로 다른 사용자를 가리킬 수 있고, 쿠키를 잃은 사용자는 해당 쿠키로 복원할 수 없다. 이 경합에서 브라우저당 사용자 한 명이나 동일 사용자 복원을 보장하지 않는다. 단, 요청별 JWT·세션의 사용자 일치 검증은 유지하며 서로 다른 사용자의 데이터를 임의로 합치지 않는다. 카카오 전환·로그아웃 시 탭 간 인증 전환 처리는 별도 후속 설계 대상이다.

재방문은 비밀값 쿠키 수신 → SHA-256 계산 → 해시로 세션 조회 → 만료·폐기 확인 → `user_id`로 기존 사용자 확인 순서다. UUID를 요청에서 받아 세션을 고르는 구조가 아니다.

다른 브라우저에서 카카오 연결 없이 시작하면 별도 UUID 사용자다. 여러 기기의 UUID를 자동으로 같은 사용자로 묶거나 기기 관리 화면을 추가하지 않는다.

사용자 재확인에 따라 카카오 계정 연결은 이관이 성공적으로 완료되면 이전 UUID와 해당 인증을 종료하고 카카오 사용자 인증으로 전환한다. 카카오 로그아웃은 해당 브라우저의 기존 카카오 인증을 종료하고 새 UUID 사용자로 시작하며 카카오 계정의 기록은 보존한다. 로그아웃·이관으로 종료한 인증은 기간 만료와 구분하며 자동 30일 연장·복원 대상으로 삼지 않는다. 이 동작은 후속 T06~T08에서 구현하지만 T01의 인증 구조가 이를 지원해야 한다. 방 참여 중 전환 제한 등 기존 ADR 정책은 유지한다.

## 고정 인증 오류 코드

사용자 결정에 따라 새 인증 계약은 `{"detail":{"code":"PREPARATION_EXPIRED","message":"준비 시간이 만료되었습니다."}}` 형태로 오류를 전달한다. `message`는 설명용이며 문구 변경이 프론트의 동작을 바꾸지 않게 한다. 기존 카카오·일반 API의 문자열 detail을 일괄 변경한 것으로 취급하지 않으며, JWT 인증 의존성의 적용 범위와 기존 호출부 호환은 구현 전에 확인한다.

| 상황 | HTTP 상태 설계 | 고정 코드 | 프론트 처리 |
| --- | --- | --- | --- |
| 접근 JWT 만료 | 401 | `ACCESS_TOKEN_EXPIRED` | 쿠키로 토큰 발급 후 원래 요청을 한 번 재시도. 동시 갱신은 합친다. |
| 새 구조에서 사용할 수 없는 이전 형식 JWT | 401 | `REAUTHENTICATION_REQUIRED` | 이전 토큰 사용을 중단하고 카카오에 다시 로그인한다. 자동 교환·쿠키 갱신 반복으로 처리하지 않는다. |
| 준비 5분 만료 | 401 | `PREPARATION_EXPIRED` | 준비 API에서 새 준비 쿠키를 받은 후 생성 요청. 이전 준비를 되살리지 않는다. |
| 정식 인증 30일 만료 | 401 | `SESSION_EXPIRED` | 이전 세션을 연장하지 않고 새 준비·UUID 시작 흐름으로 이동한다. 토큰 API 자체는 사용자를 만들지 않는다. |
| 명시적 인증 종료 | 401 | `SESSION_REVOKED` | 이전 인증을 중단하고 계정 전환 완료 상태를 확인한다. 재발급 반복·이관 재실행·무조건 새 UUID 생성으로 처리하지 않는다. |
| 출처 또는 필수 헤더 검사 실패 | 403 | `CSRF_REJECTED` | 자동 반복하지 않는다. 허용된 프론트는 요청 설정을 확인한다. 미허용 출처의 스크립트는 CORS 때문에 응답 본문을 읽지 못할 수 있다. |
| 일시적 DB 연결·조회 장애 | 503 | `AUTH_TEMPORARILY_UNAVAILABLE` | 인증을 보존하고 안전하게 반복할 수 있는 요청만 기존 총 3회·전체 10초 제한 내에서 재시도한다. |

이 HTTP 상태는 구현 계약의 기본 설계다. 변조 JWT·쿠키 부재·불일치·잘못된 상태·예기치 않은 500·속도 제한 등의 나머지 오류는 별도로 정하며, 고정 코드를 채택했다고 모든 오류 계약이 완료된 것은 아니다. 삭제된 준비 기록은 만료 여부를 판별할 근거가 없어질 수 있으므로 위 만료 코드는 기록을 확인할 수 있을 때 적용한다. DB 오류를 세션 없음이나 만료로 바꾸지 않는다. 실제 프론트 재시도와 오류 분기는 별도 작업이며 아직 구현하지 않았다.

## 준비·사용자 생성·토큰 발급 API 분리

사용자 결정에 따라 세 역할을 별도 API로 분리한다. 아래 메서드·경로를 설계에 채택하며, 실행 코드에는 아직 추가하지 않았다. 요청·응답 DTO, HTTP 상태와 오류 코드의 상세 계약은 후속 설계에서 확정한다.

| 메서드·경로 | 역할 | 사용자 생성 | JWT 발급 |
| --- | --- | --- | --- |
| `POST /api/auth/preparations` | 서버에서 비밀값 생성, 해시와 준비 인증 기록 저장, HttpOnly 쿠키 전달 | 하지 않음 | 하지 않음 |
| `POST /api/auth/anonymous-users` | 준비 쿠키 검증 후 사용자·UUID 생성과 기존 인증 기록의 정식 전환. 이미 연결된 유효 세션이면 기존 생성 결과 복구 | 최초 유효 준비 인증에 한 번 | 생성·복구 응답에서 바로 발급 |
| `POST /api/auth/tokens` | 유효한 정식 쿠키로 기존 사용자 복원 및 JWT 재발급 | 하지 않음 | 발급 |

첫 방문은 준비 요청 → 쿠키 수신 → 사용자 생성 요청 → 사용자 정보와 JWT 수신의 두 번의 순차 요청으로 완료한다. 첫 이용을 위해 토큰 API를 추가 호출할 필요는 없다. 재방문 시 JWT가 없거나 API에서 JWT 만료를 응답하면 토큰 API를 사용한다. 브라우저는 쿠키를 서버에 보내고 서버가 DB를 조회·저장하며, 프론트 JavaScript가 HttpOnly 비밀값을 읽어 JSON에 넣거나 DB로 직접 전달하지 않는다.

토큰 API는 준비 상태·쿠키 부재·만료·폐기를 새 사용자 생성으로 처리하지 않는다. 생성 API의 같은 쿠키 재요청은 기존 유효 사용자로 수렴하며, 유효한 정식 쿠키로 JWT 발급·재발급 시 정식 인증과 쿠키의 만료를 현재 시각부터 30일로 연장한다. 기존 `/api/auth/kakao` 경로와의 공존·호환은 후속 HTTP 계약에서 정한다.

사용자 결정에 따라 준비 API는 요청에 유효한 쿠키가 있으면 같은 비밀값과 인증 기록을 유지한다. 유효한 준비 상태면 사용자 생성 단계로, 유효한 정식 인증이면 토큰 발급 단계로 안내하며, 이때 새 준비 기록·비밀값을 만들거나 쿠키를 교체하지 않는다. 준비 API에서 JWT를 발급하거나 사용자를 생성하지 않는다. 반복 준비 요청은 준비 만료·정식 만료를 연장하지 않는다. HttpOnly 비밀값을 응답 본문에 노출하지 않고 다음 행동만 프론트에 알려준다. DB 장애 시 기존 쿠키를 유지하고 새 준비 기록을 만들지 않는다.

이 결정은 쿠키 없이 동시에 온 서로 다른 준비 요청의 중복 허용을 변경하지 않는다. 쿠키 부재 시 최초 준비 기록·쿠키를 발급한다. 사용자 결정에 따라 사용자 생성 없이 준비 5분이 만료된 쿠키로 준비 API를 호출하면 새 비밀값과 준비 기록을 발급한다. 이전 기록의 만료를 연장하거나 재활성화하지 않으며, 준비 API에서 사용자를 생성하지 않는다. 정확한 응답 DTO·HTTP 상태·오류 코드와 나머지 무효 쿠키의 처리는 후속 설계에서 정한다.

사용자 최종 결정은 정식 인증 30일과 만료 전 이용 시 30일 연장이다. 만료 후 복구를 위한 28일 쿠키 보관·추가 14일 유예 제안은 채택하지 않는다. 기간 만료 또는 로그아웃·카카오 이관으로 종료한 인증은 모두 연장·복원 대상에서 제외한다. 연장은 매 API 요청의 쓰기 대신 위 JWT 발급·재발급 지점에서 처리하며, 동시 연장·폐기 시 폐기가 덮어써지지 않도록 원자적 조건부 변경 또는 행 잠금을 DB 상세 설계에 포함한다. 실행 코드는 아직 변경하지 않았다.

## 준비 API의 다음 행동 응답

- 사용자 결정에 따라 ① 준비 API는 현재 상태를 프론트가 해석하게 하는 대신 `next_action`으로 다음 호출을 직접 안내한다. 다음 요청 URL을 응답하는 방식은 채택하지 않는다.
- 쿠키가 없어 새 준비 인증을 발급했거나 기존 유효한 준비 인증을 확인한 경우 `{"next_action":"CREATE_USER"}`를 반환한다. 프론트는 쿠키를 포함해 `POST /api/auth/anonymous-users`를 호출한다. 만료된 미사용 준비를 새 준비로 교체한 경우도 같은 응답을 사용한다.
- 기존 유효한 정식 인증을 확인하면 `{"next_action":"ISSUE_TOKEN"}`을 반환한다. 프론트는 쿠키를 포함해 `POST /api/auth/tokens`를 호출한다. 기존 쿠키·인증 기록은 유지하며 준비 API 자체는 JWT를 발급하거나 정식 인증을 연장하지 않는다.
- 두 값은 성공 응답의 고정 열거값이다. 프론트는 설명 문구로 분기하지 않으며 알 수 없는 값이나 실패 응답을 사용자 생성으로 추정하지 않는다. 이 안내는 다음 API의 쿠키·만료·종료 검증을 대체하지 않으며 요청 사이에 준비가 만료되거나 정식 인증이 종료되면 다음 API에서 거절한다.
- 비밀값 원본·해시·JWT는 준비 응답 본문에 포함하지 않는다. 새 비밀값은 HttpOnly 쿠키로만 전달한다. DB 장애는 다음 행동 성공 응답으로 바꾸지 않으며 기존 오류 계약을 적용한다. 나머지 무효 쿠키의 재준비 정책과 성공 HTTP 상태는 후속 상세 계약에서 확정한다.

## 쿠키에 대응하는 인증 기록이 없는 경우

- 사용자 결정에 따라 ① 준비 API에서 DB 조회가 정상 완료됐으나 쿠키 해시와 일치하는 인증 기록이 없으면 자동으로 새 준비를 시작한다. 서버가 새 비밀값을 생성하고 해시를 새 준비 인증 기록으로 저장한 뒤 HttpOnly 쿠키를 교체하고 `{"next_action":"CREATE_USER"}`를 반환한다. 준비 유효 시간은 새 발급 시점부터 5분이며 최초 쿠키 보관 기간은 기존 30일 + 5분 정책을 따른다.
- 준비 API에서는 사용자나 JWT를 생성하지 않는다. 이후 프론트가 새 쿠키로 사용자 생성 API를 호출하면 새 UUID 사용자를 만든다. 이전 비밀값을 새 인증의 비밀값으로 재사용하거나 기존 사용자 번호·UUID만으로 원래 사용자에게 재연결하지 않는다. 기존 사용자와 이용 기록은 삭제·병합하지 않는다.
- 적용 조건은 DB 조회 성공과 인증 기록 부재다. DB 연결·조회 실패, 시간 초과, 예기치 않은 내부 오류를 기록 부재로 취급하지 않는다. 새 준비 저장이 실패하면 성공 응답이나 쿠키 교체를 하지 않는다. 기존 유효한 쿠키 유지 정책과 확인 가능한 명시적 종료 인증의 전환 처리는 바꾸지 않는다.
- 사용자 생성·토큰 API·일반 JWT 인증 경로는 인증 기록이 없다고 즉시 새 준비·사용자를 만드는 경로로 확장하지 않는다. 기존 인증을 거절한 뒤 준비 API를 통한 새 시작 흐름을 사용한다. 삭제된 기록의 과거 만료·종료 사유나 카카오 연결 여부를 현재 쿠키만으로 알아낼 수 있다고 가정하지 않는다.
- 선택의 trade-off는 기존 사용자 복원이 불가능한 경우에도 새 이용을 이어갈 수 있지만 새 사용자로 바뀌는 점을 놓칠 수 있다는 것이다. 프론트의 새 사용자 시작 안내와 이를 위한 응답 구분 필드·쿠키 부재/기록 부재 오류 코드의 상세 계약은 후속 설계 대상으로 남긴다. 준비·생성 반복은 무한 재시도하지 않는 기존 정책을 유지한다.
- 검증 계획: 조회 성공·기록 부재 시 새 준비 한 건과 새 쿠키·`CREATE_USER` 응답, 준비 단계 사용자·JWT 미생성, 후속 생성 시 새 UUID, 기존 사용자 데이터 보존, DB 장애·새 준비 저장 실패 시 쿠키 유지, 유효·명시적 종료 인증 처리 보존을 확인한다. 아직 실행하지 않았다.

## JWT 발급 성공 응답

- 사용자 결정에 따라 ① JWT와 사용자 정보를 같은 응답 본문에 함께 반환한다. 사용자 생성·생성 결과 복구·기존 사용자 복원·JWT 재발급은 공통 응답 형식을 사용한다. 준비 API는 JWT·사용자 발급 응답 대상이 아니며 다음 행동을 알리는 별도 응답을 사용한다.
- 공통 최상위 필드는 `access_token`(발급 JWT), `token_type`(`bearer`), `expires_in`(초 단위 유효 시간, 3,600), `user`(사용자 DTO), `is_new_user`(이번 요청에서 사용자를 신규 생성했는지)로 설계한다. 최초 생성은 `true`, 같은 쿠키의 생성 결과 복구와 복원·재발급은 `false`다. 응답 유실 전후에 이 값이 달라질 수 있으므로 동일 사용자의 신규 생성 여부를 영구적으로 판별하는 값이나 부작용 재실행 기준으로 사용하지 않는다.
- `user`의 기본 정보는 내부 사용자 번호 `id`, 사용자 식별자 `uuid`, 표시 닉네임 `nickname`, 프로필 사진 `profile_image`다. 이는 응답에서 JWT와 나란히 전달하는 DTO이며 JWT 내부 클레임에 프로필을 추가하는 결정이 아니다. 실제 UUID 형식·기본 사진 표현 및 기존 `kakao_id`·`email` 필드 호환은 사용자 DTO·마이그레이션 상세 계약에서 구체화한다. Entity를 직접 반환하지 않는다.
- 프론트는 발급 응답의 사용자 정보로 초기 화면을 표시하며 직후 별도 사용자 조회 요청을 필수로 하지 않는다. 이 정보는 응답 시점의 정보로, 이후 프로필 변경에 대한 동기화는 별도다. 비밀 쿠키 원본과 해시는 응답 본문에 포함하지 않는다.
- 현재 `TokenResponse`의 `access_token`, `token_type`, `user`, `is_new_user` 구조를 확장하는 방향이며 실행 코드는 변경하지 않았다. 기존 카카오 응답과 프론트 호출부 호환, HTTP 상태·나머지 오류 계약은 후속 설계에서 정한다.

## 웹 배포 관계와 쿠키 전달

사용자 결정에 따라 ③ 프론트와 API가 서로 다른 사이트인 현재 구성을 유지한다. 프론트 코드는 `https://whatbobfe-app.vercel.app`을 기준으로 하고, API는 사용자가 제공한 `https://whatbob.kro.kr`을 설계 기준으로 삼는다. 운영 환경의 실제 설정은 배포 시 확인하며, 이번 선택으로 프록시·도메인 이전을 추가하지 않는다.

- 운영 웹 쿠키의 기본 설계는 `HttpOnly; Secure; SameSite=None`이다. `Domain`은 지정하지 않아 API 호스트에 한정하고 `Path=/api/auth`로 인증 요청에 전달 범위를 제한한다. 이는 경로를 보안 경계로 신뢰한다는 뜻은 아니다. 쿠키 이름과 개발 환경 설정은 상세 계약에서 정한다.
- 프론트는 준비·생성·토큰 등 쿠키를 사용하는 요청에 `credentials: "include"` 또는 Axios `withCredentials: true`를 설정한다. 서버는 정확한 프론트 Origin 허용 목록과 `allow_credentials=True`를 사용한다. 자격 증명 요청에 와일드카드 Origin을 허용하지 않는다. 현재 `app/main.py`에 명시적 Origin 목록과 자격 증명 허용이 있으며 새 인증 쿠키 구현은 아직 없다.
- 쿠키 수명은 앞의 준비 5분·최초 보관 30일 + 5분·정식 인증 30일 연장 계약을 따른다. `SameSite=None`이나 CORS 설정이 브라우저의 타사 쿠키 차단을 해제하지 않는다. 따라서 이 배포 관계에서 모든 브라우저의 UUID 인증 유지 성공을 보장하지 않는다.
- 준비 응답 후 후속 요청에 쿠키가 없으면 사용자 생성이 진행되지 않아야 한다. 쿠키가 차단된 상황에서 준비·생성을 무한 반복하거나 실패할 때마다 사용자를 만들지 않으며, 쿠키 확인 실패를 프론트에 전달하는 오류 계약과 실제 브라우저 검증을 후속 작업으로 둔다. 서버만으로 쿠키 차단·사용자 삭제·전송 설정 누락의 원인을 항상 구분할 수 있다고 가정하지 않는다.
- 사용자 결정에 따라 웹 쿠키 인증 명령의 CSRF 방어는 ② 정확한 Origin 허용 목록 검사 + 필수 추가 헤더 `X-Whatbob-Request: 1`을 채택한다. 두 검사를 쿠키 발급·DB 변경·JWT 발급 등 실제 처리 전에 수행한다. 웹 보호 경로에서 Origin 누락·`null`·미허용 출처 또는 헤더 누락·잘못된 값은 403으로 거절하며, 쿠키 교체·사용자 생성·세션 연장을 하지 않는다. 이 검사는 사용자 인증을 대체하지 않는다.
- 보호 대상은 세 POST API(준비·사용자 생성·토큰 발급)와 후속 쿠키 기반 로그아웃·계정 전환 명령이다. UUID 생성은 유효한 준비 쿠키까지 필요하고 토큰 발급은 유효한 정식 쿠키까지 필요하다. 일반 API가 명시적 Authorization Bearer JWT만 인증 수단으로 사용하고 쿠키 인증으로 대체하지 않는 경우 별도 CSRF 헤더를 일괄 요구하지 않는다. 공개 조회와 사전 확인 OPTIONS에도 요구하지 않는다. OAuth 리다이렉트 콜백의 state 등 별도 방어 계약은 후속 카카오 전환 설계에서 다루며 이 헤더 규칙을 무조건 적용하지 않는다.
- 브라우저는 필요할 때 OPTIONS로 Origin·요청 방식·추가 헤더 사용을 사전 확인한다. 사전 확인에는 비밀값 쿠키나 필수 헤더의 실제 값을 요구하지 않으며 상태를 변경하지 않는다. CORS 허용 헤더에는 구현 시 `X-Whatbob-Request`를 추가한다(현재 코드에는 없음). 실제 요청에서도 Origin과 필수 헤더를 독립적으로 검증하며 OPTIONS 통과 이력을 서버에 저장하거나 의존하지 않는다. 브라우저의 사전 확인 캐시가 있으면 OPTIONS가 생략될 수 있다.
- 추가 헤더 이름·값은 공개된 고정 표시이며 비밀 토큰이 아니다. 악성 웹페이지의 추가 헤더 요청은 정확한 CORS 허용 목록으로 제한하며, 추가 헤더 없는 요청은 서버에서 거절한다. 비브라우저 프로그램의 헤더 위조·쿠키 탈취·허용된 프론트의 XSS·대량 호출을 이 방식으로 차단한다고 간주하지 않는다. 별도 CSRF 토큰 저장은 추가하지 않는다. 웹 Origin 누락을 앱 지원 명목으로 허용하지 않으며 앱 전달 계약은 앱 형태 확정 후 별도로 설계한다.
- 앱 형태는 미정이다. WebView와 네이티브·React Native·Flutter를 같은 쿠키 동작으로 가정하지 않는다. 서버의 해시 검증·세션 수명·폐기·JWT 발급 로직과 웹 쿠키 입출력을 분리할 수 있도록 구현하되, 앱 전용 비밀값 응답·전송 경로는 아직 추가하거나 확정하지 않는다. 웹에서 비밀값을 JSON으로 노출하지 않는 결정도 유지한다.

근거: [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [타사 쿠키 제한](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies), [OWASP CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). 이들은 공개 동작·보안 지침이며 특정 기업의 비공개 내부 아키텍처를 뜻하지 않는다.

## 인증·쿠키의 배포 환경 검증

- 사용자 결정에 따라 별도 테스트용 Vercel 배포·API 서버·DB를 추가하지 않고 현재 서비스에 배포한 뒤 그 환경에서 실제 브라우저의 인증·쿠키 동작을 검증한다. 프론트는 현재 Vercel 서비스 주소, API는 `https://whatbob.kro.kr`을 대상으로 하며 배포 시 실제 프론트 Origin과 설정 일치를 확인한다.
- 이번 합의는 검증 환경의 선택이다. 현재 진행 단계에서는 설계 문서만 변경하며, 실제 배포·운영 DB 마이그레이션·테스트 사용자 생성은 수행하지 않았다. 구현과 검증을 마친 뒤 운영 배포·검증 절차를 구체화한다.
- 운영 쿠키는 기존 `HttpOnly; Secure; SameSite=None`, Domain 생략, `Path=/api/auth` 정책을 유지한다. 운영에서 확인하기 위해 HTTP용 개발 설정으로 완화하지 않는다. 앞서 제안했던 로컬 HTTP용 별도 쿠키 설정이나 로컬 HTTPS 인증서 구성을 이번 합의의 필수 작업으로 추가하지 않는다. 운영 쿠키 이름은 구현 설정 상세에서 정한다.
- 배포된 코드는 다른 이용자에게도 적용되고 검증으로 생성한 사용자·기록은 운영 DB에 저장된다. 테스트 과정에서 기존 이용자의 데이터·프로필·인증을 임의 변경하거나 전체 인증 정리·일괄 삭제를 수행하지 않는다. 필요한 검증 데이터는 작업 중 생성한 대상만 구분해 기록하며 정리 절차는 실제 데이터 생성 시 구체화한다.
- 서버·로컬 격리 DB의 자동 테스트와 실제 브라우저 검증은 역할이 다르다. 현재 환경 선택은 단위·통합 테스트를 운영 DB에서 실행하겠다는 뜻이 아니다. 기존 명세의 격리 테스트 원칙을 유지한다.
- 실제 브라우저에서 준비 쿠키 수용·후속 전송, 사용자 생성·복구, 새로고침 후 같은 사용자 JWT 복원, Origin·추가 헤더·CORS, 만료·종료 거절을 확인한다. 테스트 브라우저·버전·쿠키 차단 설정과 결과를 기록하며 타사 쿠키 차단 실패를 성공으로 보고하지 않는다. 장기간 만료 경계는 운영 전체 설정을 임의로 줄이지 않고 격리 테스트에서 검증한다.
- 준비 직후 쿠키가 오지 않으면 합의된 `AUTH_COOKIE_MISSING` 처리로 생성·자동 반복을 중단한다. 현재 서로 다른 사이트 구성에서 브라우저의 타사 쿠키 제한은 남으며, 실제 검증 전 모든 브라우저의 동작을 보장하지 않는다.

## 점검 중 DB 변경과 배포

- 사용자 결정에 따라 ① 점검 중 서비스 이용을 잠시 중단하고 DB 구조 변경·새 코드 배포·검증을 마친 후 이용을 재개한다. 무중단 다단계 전환이나 별도 온라인 변경 도구 도입은 이번 방식에 포함하지 않는다. 중단 시간은 실제 DB 크기·변경 명령·배포 절차 확인 전 임의로 보장하지 않는다.
- 사전 단계에서 실제 DB 버전·엔진·스키마·테이블 크기와 기존 데이터의 닉네임 충돌·제약 위반을 읽기 전용으로 점검한다. 해결되지 않은 데이터 충돌은 보고하고 적용 전에 멈추며 기존 닉네임·프로필·기록을 임의 변경하지 않는다. 격리 DB에서 변경 스크립트와 새 발급·검증 동작을 먼저 확인한다.
- 실행 순서는 점검 진입과 신규 요청 차단 → 진행 중 HTTP 요청·WebSocket·주기적 쓰기 작업 정리 → 일관된 DB 백업 및 복구 방법 확인 → 기존 `users` 확장·인증 표 추가 → 새 백엔드·프론트 배포 → 제한된 점검 접근으로 기존 데이터·인증·쿠키 검증 → 서비스 재개로 한다. 단순히 프론트 안내 화면만 표시하고 외부 API 쓰기를 계속 허용하는 상태를 점검 완료로 취급하지 않는다.
- 새 세션 번호 없는 기존 JWT의 한 번 재로그인 정책을 유지한다. 새 검증을 적용하면서 구형 발급 경로가 남지 않도록 카카오 발급 경로와 프론트의 오류·쿠키 처리를 함께 전환한다. 기존 사용자 번호·카카오 계정·프로필·연관 기록을 보존하며 새 UUID 기능을 위해 기존 계정을 재생성하지 않는다.
- DB 구조 변경의 여러 명령을 일반 데이터 트랜잭션처럼 전부 롤백할 수 있다고 가정하지 않는다. 단계별 적용 결과·실패 지점·재실행 조건을 확인할 수 있게 준비하고, 실패 시 서비스 재개를 보류한 채 원인을 확인한다. 이전 코드가 변경 스키마와 호환되는지 확인하지 않고 코드만 되돌려 재개하지 않는다. 새 쓰기 재개 후 과거 백업 복원은 이후 데이터를 잃을 수 있으므로 별도 복구 판단이 필요하다.
- 점검 차단 위치·제한된 검증 접근·정확한 명령·백업/복구 점검·서비스 재개 기준·진행 중 방 처리와 공지는 운영·배포 상세에서 구체화한다. 이번 합의는 설계 선택이며 실제 점검 모드·배포·운영 DB 변경은 아직 실행하지 않았다.

근거: [MySQL 암묵적 커밋](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html). 현재 프로젝트의 `scripts/migrate_room_lifecycle.py`는 명시적 DB 변경 스크립트의 선례이며 실행 환경의 DB 버전에 맞춰 검증한다.

## 기존 코드와 연결할 지점

- `app/users/models.py`: 현재 `kakao_id`는 필수이고 UUID·닉네임 유일 제약은 없다. 정수 PK·기존 FK를 보존하며 필요한 컬럼과 제약을 확장한다.
- `app/auth/service.py`, `router.py`, `schemas.py`: UUID 생성·복원·갱신의 서비스 처리, HTTP 쿠키 설정 및 DTO를 추가할 지점이다. 현재는 카카오 로그인 경로만 있다.
- `app/core/security.py`, `app/auth/dependencies.py`: 현재 JWT의 `sub`로 내부 사용자 번호를 확인한다. 인증 세션과 JWT를 연결하고 폐기된 인증으로 접근하지 못하게 할 계약이 필요하다.
- `app/rooms/websocket.py`: 기존 최초 인증 메시지 흐름과 일관된 현재 사용자 판정을 유지해야 한다.
- `scripts/migrate_room_lifecycle.py`: 기존 스키마 변경 스크립트의 선례다. `create_all()`이 기존 테이블을 변경한다고 가정하지 않는다.
- `tests/test_auth.py`, `tests/test_user_profile.py`: 기존 카카오 인증 회귀와 실제 앱 테스트의 출발점이다. 명세의 격리 DB 테스트 방식을 따른다.

## 구현 전에 이어서 설계할 항목

API 상세 묶음은 사용자 승인된 [T01 HTTP 계약](39-t01-http-contract-proposal.md)을 구현 기준으로 사용한다. 성공 상태·쿠키 상태별 분기·고정 오류 코드·응답 안내 필드는 설계상 확정됐으며 실행 코드는 미구현이다. 앞 절에서 후속으로 남겼던 HTTP 상태·오류 계약은 이 문서의 상세 계약을 따른다. 남은 묶음은 쿠키·개발 환경, DB·마이그레이션, 계정 전환·동시성·WebSocket, 운영 제한·배포다.

1. 접근 JWT 유효 시간은 1시간, 복원 쿠키·인증 세션은 30일이며 만료 전 이용 시 JWT 발급·재발급 지점에서 30일 연장한다. JWT 갱신은 만료 응답 후 수행하며 요청마다 JWT와 DB 세션을 확인한다. 기존 세션 번호 없는 JWT는 거절하고 카카오 재로그인으로 전환한다. 정확한 JWT 클레임, 발급·검증·프론트 배포 순서, 전환 동시 요청과 기존 WebSocket 연결의 폐기 반영을 이어서 정한다.
2. 준비·사용자 생성·토큰 발급은 위 세 POST API로 분리하고 준비 요청의 기존 유효 쿠키는 유지하기로 확정했다. 요청·응답 DTO·HTTP 상태·오류 및 무효 쿠키의 새 준비 절차를 정한다. 쿠키 없음, 잘못된 쿠키, 만료된 쿠키와 서버 장애를 구분하고 접근 JWT 만료만으로 새 UUID를 만들지 않는다.
3. 프론트·API는 서로 다른 사이트 구성을 유지하며 위 쿠키·CORS·Origin 및 필수 추가 헤더 CSRF 설계를 따른다. 쿠키 이름·개발 환경 설정과 쿠키 보관 실패 오류 계약·실제 브라우저 검증을 구체화한다. 여러 탭의 서로 다른 준비 쿠키로 인한 별도 사용자 생성은 허용하며 탭 간 최초 생성 직렬화는 추가하지 않는다.
4. DB 컬럼·인덱스·닉네임 충돌 처리·기본 이미지 및 기존 카카오 데이터 사전 점검·마이그레이션을 구체화한다. 기존 중복 닉네임을 임의 변경하지 않는다.
5. 요청 속도 제한의 적용 위치와 기준을 정한다. UUID나 세션을 타인이 임의로 잠글 수 있는 실패 횟수 차단은 피한다.

위 계약을 구체화한 후 T01을 생성·복원·갱신·사용자 격리·원본 인증 폐기 기반·카카오 회귀의 실제 앱 테스트와 함께 구현한다. 이후 개인 기능과 방 기능 확장은 T02·T03 범위다.

## 검증 계획과 현재 상태

- 실제 FastAPI 요청으로 준비 쿠키 발급 후 생성, 생성 응답 유실 후 같은 쿠키 재요청, 같은 비밀값의 동시 생성 중복 방지, 서로 다른 준비 비밀값의 별도 사용자 생성·데이터 격리, 같은 쿠키 복원, 별도 브라우저 독립성, JWT 갱신, 타인 접근 차단, 만료·폐기 거절을 검증한다.
- 최초 쿠키 보관 기간 30일 + 5분, 생성 없이 준비 5분 경과 시 거절, 생성 성공 응답 유실 후 준비 5분이 지나도 동일 사용자 복원, 정식 만료 후 쿠키가 남아 있어도 거절을 검증한다. 유효한 정식 쿠키로 JWT 발급·재발급 시 30일 연장, 일반 API·준비 요청만으로는 비연장, 만료 경계와 연장·폐기 경합 시 종료 인증 비복원, 연장 응답 유실 시 기존 쿠키 삭제 시각의 한계를 검증한다.
- 기존 카카오 사용자와 관련 기록·참조 보존 및 닉네임 생성 충돌을 확인한다.
- 아직 만료되지 않은 기존 세션 번호 없는 JWT 거절과 재로그인 안내, 새 구조 JWT의 유효 세션·사용자 일치 확인, 종료 인증 거절을 검증한다. 카카오 재로그인 후 기존 계정·프로필·기록이 보존되고 새 구조 토큰이 발급되는지 확인한다. 프론트가 재로그인 필요 응답을 무한 갱신하지 않는지도 별도 연동 검증한다.
- 600초 정리 간격 설정, 만료·종료 인증만 삭제, 유효한 인증 및 사용자·연관 데이터 보존, 연장·생성 전환과의 경합, DB 실패 후 다음 실행 복구를 검증한다. 대상 0건·100건 미만·정확히 100건·100건 초과 및 대상 종류 혼합 시에도 실행당 총 100건 상한을 지키고 나머지를 다음 실행에 남기는지 확인한다. 복수 프로세스 실행 주체가 확정되면 중복 실행 방지 검증도 추가한다.
- 사용자 FK가 없는 준비 기록의 정식 인증 거절, 생성 성공 시 같은 기록의 FK 연결·30일 만료 설정, 생성 실패 시 사용자·FK 변경의 함께 롤백, FK가 있어도 만료·종료된 기록의 인증 거절을 검증한다. FK 제거로 준비 단계가 재생성되는 경로가 없어야 한다.
- CSRF 보호 경로에서 허용 Origin + 필수 헤더 조합의 통과, 잘못된 출처·누락·null 및 헤더 누락·오류의 403과 상태 비변경을 검증한다. OPTIONS에 쿠키·실제 추가 헤더가 없어도 올바른 사전 확인을 처리하고 상태를 변경하지 않는지 확인한다. 실제 요청의 독립 검증, 일반 Bearer API와 OAuth 콜백의 계약 보존도 확인한다. 브라우저의 사전 확인·쿠키 정책은 서버 단위 테스트만으로 검증 완료라고 보고하지 않는다.

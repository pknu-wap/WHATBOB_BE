# T01 WebSocket JWT 재인증 계약

작성·합의: 2026-11-13. 상태: 재인증 흐름·갱신·복구 한도는 사용자 승인, 통신 세부는 해당 정책 안에서 에이전트가 정리한 구현 계약이다. T01 서버 재인증·만료 처리를 구현하고 격리 테스트했다. 프론트 갱신·재시도 한도와 실제 브라우저 검증은 남았다. 현재 상태는 [연동 문서](../UUID_AUTH_API.md)와 LOG 최신 기록을 따르며 아래 미구현 서술은 설계 작성 시점이다. [인증 아키텍처](39-t01-auth-architecture.md), [HTTP 인증 계약](39-t01-http-contract-proposal.md), [설계 진행표](39-architecture-status.md)를 함께 따른다.

## 적용 범위

- 활성 방 WebSocket은 JWT 만료 2분 전에 브라우저가 토큰 API로 새 JWT를 발급받고, 현재 연결에서 재인증한다. JWT 수명은 1시간이다.
- 방 참여 요청 시작·응답 대기·참여 중·60초 재접속 유예 동안 로그인·로그아웃·계정 전환을 차단하는 기존 정책을 유지한다.
- 이번 계약은 연결 중 재인증이다. 최초 연결의 기존 `auth`·`connection.ready` 메시지를 이 문서만으로 변경하지 않는다.

## 정상 처리

1. 브라우저가 비밀 쿠키로 `POST /api/auth/tokens`를 호출해 새 JWT를 받는다. 토큰 발급 성공은 WebSocket 재인증 성공이 아니다.
2. 브라우저는 현재 연결에 아래 `auth.refresh` 메시지를 보낸다.
3. 서버는 JWT 서명·필수 클레임·만료와 DB 인증 기록을 검증하고, 기존 연결과 같은 사용자·같은 인증 기록인지 확인한다. `request_id`만으로 인증하지 않는다.
4. 통과하면 연결의 인증 정보와 만료 기준을 교체한다. 이전 만료 예약이 이후 새 인증 연결을 잘못 종료하지 않도록 한다.
5. 교체 완료 후 서버가 같은 요청 번호의 `auth.refreshed`를 보낸다. 브라우저는 일치하는 성공 응답을 받아야 해당 연결의 갱신 완료로 판단한다.
6. 연결과 방 참여·주문서 상태는 유지한다. 브라우저는 확인된 새 만료 시각을 기준으로 다음 갱신을 예약한다.

요청:

```json
{
  "type": "auth.refresh",
  "request_id": "refresh-17",
  "access_token": "새 JWT"
}
```

성공 응답:

```json
{
  "type": "auth.refreshed",
  "request_id": "refresh-17",
  "expires_at": "2026-11-13T04:58:00Z"
}
```

- `request_id`는 요청·응답 연결과 같은 요청의 재전송을 구분하는 번호다. 비밀값이나 사용자·인증 기록의 대체 식별자가 아니다. 1~64자의 ASCII 영문·숫자·`-`·`_`를 허용하며 새 요청에는 새 번호를 쓴다. 재전송만 같은 번호와 JWT를 사용한다. 형식·길이는 정책을 바꾸지 않는 구현 세부로 정리했다.
- `expires_at`은 서버가 검증한 JWT `exp`를 UTC RFC 3339 문자열로 변환한 값이며 초 단위·`Z` 접미사를 사용한다. 예시는 형식 설명이며 실제 만료는 적용된 JWT와 일치해야 한다. 날짜 인코딩은 내부 JWT의 Unix 초 정수 표현을 변경하지 않는다.
- JWT·복원 비밀 쿠키·해시를 URL이나 메시지 로그에 기록하지 않는다. 성공 응답에 JWT를 다시 포함하지 않는다.

## 성공 확인 유실과 중복 재전송

1. 서버가 교체했더라도 성공 응답을 브라우저가 확인하지 못할 수 있다. 확인 실패만으로 서버 교체 실패를 단정하지 않는다.
2. 연결이 살아 있으면 브라우저는 **같은 JWT·같은 `request_id`**로 제한적으로 재전송한다. 성공 확인 유실만을 이유로 토큰 API를 반복 호출해 새 JWT를 계속 만들지 않는다.
3. 서버는 이미 적용한 동일 JWT의 중복 요청을 그것만으로 실패시키지 않는다. 현재 인증의 유효성을 확인하고 같은 요청 번호로 성공을 다시 알린다. 과거 성공 응답만으로 종료·만료된 인증을 통과시키지 않는다.
4. 늦은 이전 요청으로 연결의 인증 상태나 만료 시각을 과거로 되돌리지 않는다. 브라우저도 늦은 응답으로 더 최신의 확인된 상태를 덮어쓰지 않는다. 서로 다른 갱신 요청의 처리는 아래 동시 갱신·순서 규칙을 따른다.
5. 제한 내에 확인하지 못하면 해당 연결을 정리하고 보유한 유효 JWT로 재연결한다. 이미 끊긴 연결에서는 재전송하지 않는다. 재연결 후 방 상태를 다시 조회해 단절 중 놓친 변경을 확인한다.
6. 재연결도 기존 방 참여 권한·재접속 유예·방 종료 정책을 따른다. JWT를 보유했다는 이유만으로 삭제된 방이나 종료된 참여를 복구하지 않는다.

## 확인 대기·재전송·공유 시간 한도

2026-11-13 사용자 승인에 따라 아래 한도를 적용한다. 120초는 사전 갱신 시작 여유이며 120초 동안 반복하라는 의미가 아니다.

| 항목 | 한도 |
| --- | --- |
| 갱신 전체 | 토큰 API 최초 요청 시작부터 WebSocket 성공 확인까지 최대 10초 |
| 토큰 API | 기존 정책대로 최초 포함 최대 3회, 각 응답 대기는 최대 3초 |
| WebSocket 재인증 메시지 | 최초 포함 최대 3회, 즉 재전송 최대 2회 |
| WebSocket 각 성공 확인 | 최대 3초와 전체 남은 시간 중 작은 값 |
| 첫 재전송 전 대기 | 기준 1초의 ±50%, 즉 0.5~1.5초 균등 무작위 |
| 두 번째 재전송 전 대기 | 기준 2초의 ±50%, 즉 1~3초 균등 무작위 |

- 두 단계의 횟수 한도는 각각 적용하되 **하나의 10초 시간 한도**를 공유한다. 토큰 API와 WebSocket에 각각 10초를 부여하거나, WebSocket 재전송 때 토큰 API를 다시 실행하지 않는다. 토큰 API에서 7초를 썼다면 WebSocket에는 최대 3초만 남는다.
- 3회는 상한이며 모두 전송할 것을 보장하지 않는다. 전체 10초가 소진되면 응답 대기·재전송 전 대기를 중단하고 남은 시도를 하지 않는다. 서버에 적용된 JWT가 먼저 만료되거나 연결이 끊기면 그 제한을 우선한다.
- 대기 중 현재 요청에 일치하는 성공 응답이 도착하면 예약된 재전송을 취소하고 완료한다. 지터 값은 재전송마다 새로 뽑는다. 재전송은 확인 유실 등 안전하게 반복 가능한 상황에만 적용하며 무효 인증에 일괄 적용하지 않는다.
- 전체 한도 종료는 서버 실패·롤백의 증거가 아니다. 새 JWT가 실제 적용됐지만 성공 확인만 유실될 수 있다. 한도 내 확인 실패 시 기존 합의대로 연결을 정리하고 보유한 유효 JWT로 재연결·방 상태 재조회를 수행한다.
- 재연결은 아래의 별도 최대 3회·전체 10초 한도를 적용하며 실패한 갱신의 시계를 초기화해 토큰 발급·재인증 루프를 반복하는 수단으로 사용하지 않는다. 토큰을 얻지 못했거나 이미 만료됐다면 유효 JWT가 있는 재연결과 구분한다.
- 이 정책은 기존 시간 제한을 재사용해 동작을 일관되게 하지만, 느린 정상 응답을 실패로 판단하고 재연결할 가능성이 있다. 3초·10초는 응답 시간 측정으로 검증된 최적값이 아니며 구현 후 재검토한다.
- 현업 근거: [AWS의 시간 제한·재시도·백오프·지터 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)은 제한된 재시도와 지터, 여러 계층의 재시도 증폭 위험을 설명한다. 위 숫자는 WhatBap 정책이며 AWS의 공통 표준값으로 주장하지 않는다.

## 재연결 한도와 60초 재접속 유예

2026-11-13 사용자 결정에 따라 방 재접속 유예를 기존 설계의 30초에서 **60초**로 변경하고, 자동 재연결은 최초 포함 최대 3회·전체 최대 10초로 제한한다.

1. 갱신 성공 확인에 실패했거나 연결이 끊겼다면 실패한 연결을 정리하고 보유한 유효 JWT로 재연결한다. 토큰을 반복 발급하며 갱신 절차 전체를 자동 재시작하지 않는다.
2. 첫 자동 재연결 시도 시작부터 하나의 10초 한도를 계산한다. 연결 열기와 최초 인증 및 `connection.ready` 성공 확인을 한 시도로 묶는다. WebSocket 열림만으로 복구 성공으로 판단하지 않는다.
3. 각 시도는 최대 3초와 전체 남은 시간 중 작은 값만 기다린다. 실패한 시도의 연결을 정리한 뒤 재시도하며 동시에 여러 복구 연결을 남기지 않는다.
4. 첫 재시도 전 0.5~1.5초, 두 번째 재시도 전 1~3초의 균등 무작위 지터를 적용한다. 최초 포함 최대 3회이므로 자동 재시도는 최대 2회다. 시간이 먼저 끝나면 남은 시도를 하지 않는다.
5. 연결 준비가 완료되면 예약된 재시도를 취소하고 방 상태를 다시 조회한다. 방 상태 조회의 실패가 새 연결 생성 루프를 무제한 재시작하는 근거가 되지 않는다.
6. 방 종료·참여 권한 없음 등 서버에서 확정한 복구 불가 사유는 즉시 중단한다. 인증 무효를 단순 통신 장애로 처리하지 않는다. 상세 오류 코드는 후속 계약에서 정한다.
7. 한도 내 복구에 실패하면 자동 시도를 멈추고 연결 복구 실패 안내와 수동 재시도를 제공한다. 수동 재시도도 서버의 현재 방·참여·인증 상태를 확인하며 이미 종료된 방이나 삭제된 참여를 되살리지 않는다.

- 60초는 서버가 사용자의 **마지막 WebSocket 연결 종료를 확인한 시각**부터 계산한다. 다른 탭의 유효 연결이 남아 있으면 유예를 시작하지 않는다. JWT 갱신이 기존 연결에서 성공하면 단절이 없으므로 유예를 시작하지 않는다.
- 유예 안에 재접속하면 기존 참여·주문서 상태를 유지한다. 유예가 끝나면 일반 참여자는 자동 퇴장, 방장은 방 종료라는 설계 정책을 유지한다. 유예 중 계정 전환은 계속 금지한다.
- 10초 재연결 시도를 시작하거나 실패했다고 60초 유예를 새로 부여하지 않는다. 복구를 완료하지 못한 임시 연결의 반복 개폐로 기존 유예 기한을 연장하지 않는 세부 처리는 구현 시 검증한다. 유예의 최종 판정은 서버 기준이다.
- 갱신의 최대 10초와 재연결의 최대 10초는 서로 다른 단계의 한도다. 재연결 실패 뒤 갱신부터 다시 시작하는 자동 순환은 금지한다. 서버의 단절 감지·브라우저 실행 지연 등이 있으므로 두 한도를 더한 값만으로 유예 내 복귀를 보장하지 않는다.
- 60초는 짧은 네트워크 장애에서 복귀할 여유를 늘리는 대신 떠난 참여자와 방장 부재 상태를 더 오래 유지한다. 자동 복구를 10초로 제한하면 무한 대기·요청을 줄이지만 느린 환경에서는 수동 재시도가 필요할 수 있다.
- 현재 코드의 방장·일반 참여자 유예 기본 설정은 이미 60초다. 다만 일반 참여자는 유예 후 오프라인으로 남는 기존 구현이므로, 위 자동 퇴장 정책이 구현 완료됐다고 해석하지 않는다. 이번 변경은 설계 문서만 반영했다.

## 만료와 인증 실패

- 서버에서 현재 적용된 JWT의 만료까지 재인증을 완료하지 못하면 연결을 종료한다. 재전송이나 대기 중이라는 이유로 만료를 연장하지 않는다.
- 서버 교체가 성공하고 확인 응답만 유실된 경우 서버 만료 기준은 이미 새 JWT다. 브라우저는 성공 확인 전까지 완료를 추정하지 않고 위 복구 흐름을 따른다.
- 변조·다른 사용자·다른 인증 기록·종료된 인증을 새 인증으로 채택하지 않는다. 이러한 실패를 모두 토큰 만료로 바꿔 무한 재발급하지 않는다. 오류별 동작은 아래 표를 따른다.
- DB 장애는 인증 부재나 사용자 생성의 근거로 바꾸지 않는다. 실패한 재인증으로 연결 인증을 교체하지 않으며 기존 JWT의 만료를 늘리지 않는다.
- 정상적인 같은 사용자 갱신은 계정 전환이 아니다. WebSocket 재인증 메시지가 복원 쿠키를 대신하거나 인증 기록의 30일 수명을 별도로 연장하지 않는다.

## 선택의 trade-off와 현업 근거

- 성공 확인과 같은 메시지의 제한적 재전송은 일시적 확인 실패마다 연결을 끊거나 토큰을 추가 발급하는 일을 줄인다. 대신 요청 번호 관리·중복 처리·만료 예약 교체와 경합 검증이 필요하다.
- 확인 실패 시 즉시 재연결만 하는 방식은 상태 처리가 단순하지만 연결 공백과 방 상태 재조회가 늘어난다. 이번에는 재전송 후 필요 시 재연결하는 방식을 선택했다.
- [Python websockets 공식 인증 문서](https://websockets.readthedocs.io/en/stable/topics/authentication.html)는 HTTP에서 얻은 토큰을 WebSocket 메시지로 전달하는 인증을 설명한다. URL에 토큰을 넣으면 로그에 노출될 수 있다는 한계도 제시한다.
- 메시지 이름과 성공 확인·재전송 계약은 WhatBap의 선택이며 업계 공통 표준으로 주장하지 않는다.

## 동시 갱신과 늦은 응답

에이전트 정리: 아래는 기존 동시 갱신 합치기·동일 인증 유지·비퇴행 원칙을 구체화한 구현 계약이며 별도 사용자 정책 승인으로 기록하지 않는다.

1. 프론트 실행 컨텍스트마다 진행 중인 토큰 발급 작업을 하나만 둔다. 방 갱신과 HTTP 만료 처리가 겹치면 같은 작업 결과를 기다리고 토큰 API를 중복 호출하지 않는다. 다른 탭의 인증 상태 동기화는 진행표의 별도 3번 범위다.
2. 합쳐진 작업은 최초 시작의 10초 기한을 유지한다. 뒤늦게 합류한 요청이 기한을 새로 시작하지 않는다. 방 갱신의 성공 확인도 해당 남은 시간 안에서 수행한다. 실패한 작업 뒤 자동으로 새 갱신 작업을 연속 생성하지 않는다.
3. HTTP 요청은 자신이 사용한 토큰의 로컬 버전을 기억한다. 만료 응답이 늦게 왔는데 더 새 토큰이 이미 있으면 추가 발급 없이 그 토큰으로 원래 요청을 한 번 재시도한다. 해당 재시도도 실패하면 다시 갱신 루프를 돌리지 않는다.
4. 새 토큰을 받은 시점과 각 WebSocket에서 적용을 확인한 시점을 따로 관리한다. HTTP는 발급받은 새 토큰을 사용할 수 있지만 WebSocket은 각 연결의 성공 확인 전까지 갱신 완료로 표시하지 않는다. 같은 화면에 여러 연결이 있으면 토큰 발급은 공유하고 성공 확인은 연결별로 한다.
5. 각 연결의 재인증 처리와 만료 종료는 하나의 직렬화 경계에서 현재 상태를 다시 확인한다. 검증 도중 기존 토큰이 만료됐고 새 토큰 적용은 아직 완료되지 않았다면 연결을 종료한다. 성공 응답은 인증 정보·만료 기준 교체 후에만 보낸다.
6. 현재 적용된 JWT와 동일한 JWT는 현재 유효성 검증 후 중복 성공을 반환한다. 다른 JWT는 동일한 `sub`·`sid`이고 `exp`가 더 클 때만 교체한다. 그 외 서명과 클레임은 정상이나 `exp`가 같거나 작은 다른 JWT는 `AUTH_REFRESH_SUPERSEDED`로 응답하고 현재 상태를 유지한다. 동일 초의 발급을 전역 순번으로 간주하지 않는다.
7. `AUTH_REFRESH_SUPERSEDED`는 새 요청을 계속 발급할 근거가 아니다. 현재 요청에 대한 응답이면 더 최신의 확인된 연결 만료를 사용하고, 오래된 요청에 대한 응답이면 무시한다. 연결의 적용 만료를 응답의 `expires_at`으로 안내하되 토큰을 노출하지 않는다.
8. 서버는 연결별로 처리 중 요청과 마지막 성공 요청의 번호·토큰 지문만 관리한다. 마지막 성공 정보는 10초의 중복 확인 창 또는 연결 종료 중 먼저 도달한 시점까지 보관한다. 창이 지났어도 JWT 자체가 현재 적용 토큰과 동일하면 검증 후 중복 성공할 수 있다. 무제한 요청 이력·JWT 원문 저장소를 만들지 않는다.
9. 보관 중인 같은 요청 번호에 다른 JWT가 오면 `INVALID_AUTH_MESSAGE`로 거절한다. 토큰 지문은 내용 동일성 비교용이며 DB의 복원 비밀값 해시와 역할이 다르다. 서버·클라이언트 모두 JWT·지문을 로그에 남기지 않는다.
10. 클라이언트는 연결 세대와 현재 요청 번호가 모두 일치하는 응답만 현재 상태에 적용한다. 이전 연결에서 뒤늦게 도착한 이벤트와 취소한 요청의 성공이 새 연결 상태를 덮어쓰지 못하게 한다.

## 오류 메시지와 종료 처리

재인증 오류는 아래 형태로 보내며 HTTP 상태 코드와 WebSocket 종료 코드는 구분한다. `request_id`는 형식이 유효한 입력만 반영하고 나머지는 `null`이다. `message`는 사용자용 고정 설명이며 예외·쿼리·JWT를 넣지 않는다.

```json
{
  "type": "auth.error",
  "request_id": "refresh-17",
  "code": "AUTH_TEMPORARILY_UNAVAILABLE",
  "message": "일시적으로 인증을 확인할 수 없습니다."
}
```

| 상황 | 오류 코드 | 서버 연결 처리 | 프론트 처리 |
| --- | --- | --- | --- |
| 현재 연결 JWT가 만료됨 | `ACCESS_TOKEN_EXPIRED` | `4408` 종료 | 이미 발급받은 유효 JWT가 있으면 정해진 재연결 한도 적용. 없으면 HTTP 인증 오류 흐름 사용, 갱신·재연결 자동 순환 금지 |
| 재인증 메시지의 JWT만 만료됨 | `ACCESS_TOKEN_EXPIRED` | 기존 연결 JWT가 아직 유효하면 교체 없이 유지 | 같은 만료 JWT 재전송 중단, 현재 갱신 실패로 처리. 새 토큰 발급 자동 반복 금지 |
| JWT 누락·변조·필수 클레임 오류 | `ACCESS_TOKEN_MISSING` / `ACCESS_TOKEN_INVALID` | `4401` 종료 | 같은 토큰의 자동 재시도 중단 |
| 인식 가능한 구형 JWT | `REAUTHENTICATION_REQUIRED` | `4401` 종료 | 기존 HTTP 계약의 재로그인 안내 적용 |
| 다른 사용자 또는 다른 인증 기록 | `AUTH_CONTEXT_MISMATCH` | `4401` 종료 | 이전 사용자 데이터 유지·전송 중단, 자동 사용자 생성·계정 교체 금지 |
| DB 인증 부재·만료·종료·사용 불가 | 기존 `SESSION_NOT_FOUND` / `SESSION_EXPIRED` / `SESSION_REVOKED` / `SESSION_UNAVAILABLE` | `4401` 종료 | HTTP 계약과 같은 원인별 안내. 해당 방 복구 중 자동 새 사용자 생성 금지 |
| 메시지 형식 오류·요청 번호 충돌 | `INVALID_AUTH_MESSAGE` | `4400` 종료 | 같은 잘못된 메시지 자동 재전송 중단 |
| 이미 더 최신 JWT가 적용됨 | `AUTH_REFRESH_SUPERSEDED` | 교체 없이 유지 | 위 순서 규칙 적용. 오류 응답에 현재 `expires_at` 추가 |
| 재인증 DB 조회의 일시 장애 | `AUTH_TEMPORARILY_UNAVAILABLE` | 기존 적용 JWT가 유효한 동안 유지, 실패한 토큰으로 교체·만료 연장 없음 | 기존 공유 10초·횟수 한도 안에서만 같은 메시지 재시도. 장애를 새 사용자 생성으로 처리하지 않음 |
| 예상하지 못한 내부 오류 | `AUTH_INTERNAL_ERROR` | `1011` 종료 | JWT·사용자 기록을 임의 삭제하지 않고 오류 안내, 자동 반복 중단 |
| 방 참여 권한 없음 | `ROOM_MEMBERSHIP_REQUIRED` | 기존 `4403` 종료 | 복구 중단·현재 참여 상태 안내 |
| 방 없음 | `ROOM_NOT_FOUND` | 기존 `4404` 종료 | 방 복구 중단 |
| 방 종료·만료 | 기존 `room.closed` 또는 조회 결과 | 기존 `4000` 종료 | 방 복구 중단 |

- 오류 메시지 전송은 최선 노력이며 끊긴 연결에 전달을 보장하지 않는다. `4401`만으로 상세 원인을 추측해 재발급하지 않는다. 상세 오류를 받지 못했다면 인증 상태 확인·안내로 이동하고 새 사용자 자동 생성·무한 재연결을 하지 않는다.
- 알려진 JWT 만료 `4408`과 비정상 네트워크 종료는 기존 제한 안에서 복구할 수 있다. 브라우저에 관찰되는 `1006`은 서버가 직접 전송하는 종료 코드로 쓰지 않는다.
- `4400`·`4401`·`4403`·`4404`·`4408`·`4000`은 WhatBap용 애플리케이션 계약이다. HTTP 400·401·403·404와 같은 프로토콜 코드로 주장하지 않는다. [RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455#section-7.4.2)의 4000~4999 사적 사용 범위와 기존 코드 관례를 따른다.
- 실제 종료 프레임의 reason은 짧은 고정 문자열을 쓰며 상세 오류는 위 JSON에 둔다. reason의 UTF-8 123바이트 한도를 준수한다. [브라우저 close API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/close)도 해당 제한을 설명한다.

## 연결의 Origin·데이터 전송 경계

- 웹 클라이언트의 Origin은 구성된 프론트·허용 개발 Origin의 정확한 값과 비교한다. 와일드카드·부분 문자열·`null`·누락 Origin으로 브라우저용 경계를 우회하지 않는다. 네이티브 앱의 별도 인증 전송 방식은 현재 범위 밖이다.
- Origin 거부는 연결 수락 전 처리하며 브라우저가 거부 원인을 특정 종료 코드로 관찰할 것이라고 보장하지 않는다. HTTP 쿠키 명령의 `X-Whatbob-Request` 헤더를 브라우저 WebSocket에 요구하지 않는다.
- 최초 인증 성공 전에는 보호된 방 데이터를 보내지 않는다. 현재 연결 JWT가 만료되거나 연결 종료가 확정되면 추가 보호 데이터 전송을 차단하고 연결 목록에서 제거한다. 전송과 타이머는 같은 연결 세대·현재 만료 기준을 사용한다.
- 현재 사용자 판단은 연결 당시 및 재인증 때 JWT와 DB를 함께 검증한 결과를 사용한다. 모든 방 데이터 전송 전 DB 인증 조회·정기 조회·Redis 도입을 이번 계약으로 추가하지 않는다. 방 참여·전환의 서버 상태 직렬화와 예외적인 운영 강제 폐기는 각각 진행표의 3번·4번 범위다.
- 서버 JWT 만료 기준은 UTC 시각이며 클라이언트의 남은 대기 예산은 단조 증가 시계로 계산한다. 화면 복귀 시 남은 시간을 다시 판단하고 예약 콜백 지연을 만료 연장의 근거로 삼지 않는다.

## 통신 설계 완료 경계

- 이 문서로 T01의 인증 통신 묶음은 메시지·필드·동시 발급 합치기·갱신 순서·오류·종료·복구 한도까지 정리했다. 이는 구현·테스트 통과나 운영 적용 완료가 아니다.
- 다른 탭의 계정 전환·응답 유실 복구는 3번, 쿠키·JWT의 실제 설정·요청 제한·프로세스 수는 4번, 배포와 강제 폐기 절차는 5번을 포함한 운영 설계 범위에서 다룬다. 해당 작업을 새로운 인증 통신 하위 항목으로 계속 추가하지 않는다.

## 구현 후 검증

- 동일 연결의 정상 갱신, 요청 번호가 일치하는 성공 응답, 만료 예약 교체와 방·주문서 유지.
- 서버 교체 후 응답 확인 실패, 동일 JWT·요청 번호 재전송, 중복 성공 확인, 오래된 요청·응답의 상태 비퇴행.
- 토큰 API와 WebSocket의 각 최대 3회·응답 대기 최대 3초 및 공유 10초 제한, 지터 범위, 남은 시간에 따른 조기 중단, 대기 중 성공 확인 시 재전송 취소, 재전송에서 토큰 API 비반복.
- 변조·만료·다른 사용자·다른 인증 기록·종료 인증과 DB 장애, 중복 처리 시 현재 유효성 재검증.
- 만료와 재인증 경합, 확인 실패 후 연결 정리·재연결·방 상태 재조회, 유예 초과 및 이미 종료된 방.
- 재연결 최초 포함 최대 3회·각 최대 3초·전체 10초, 지터와 성공 시 취소, 복구 불가 오류의 즉시 중단, 실패 후 수동 재시도와 자동 순환 금지.
- 마지막 연결 종료 기준 60초 경계, 다른 탭 연결 유지, 유예 안 상태 보존과 종료 후 일반 참여자 퇴장·방장 종료, 실패한 임시 연결 반복으로 기존 유예 기한을 연장하지 않기.
- 브라우저 백그라운드 지연·복귀와 로그의 민감값 비노출.
- HTTP·WebSocket 동시 발급의 하나의 작업 공유·기한 비초기화, 늦은 401의 새 토큰 재사용, 여러 연결의 개별 성공 확인.
- 요청 번호 충돌·마지막 성공 보관 창·같은 JWT 중복 성공·같은 초의 다른 JWT 비퇴행, 이전 연결 세대 응답 무시.
- 오류 표의 연결 유지·종료와 자동 반복 금지, Origin 정확 비교·누락 거절, 초기 인증 전 및 연결 만료 후 보호 데이터 차단.

위 항목은 검증 계획이며 애플리케이션·DB·브라우저 테스트를 아직 실행하지 않았다.

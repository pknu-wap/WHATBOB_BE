## 이미 확정된 방향

- 상태 변경·상태 버전 증가·해당 알림의 발송 대기를 같은 DB 트랜잭션에 저장한다. 최종 commit 후 상위 경계가 전송을 명시적으로 호출한다.
- 프론트 ACK는 추가하지 않는다. 서버 소켓 전송 결과로 시도 성공을 판단하고 일부 실패 시 방 전체의 현재 유효한 연결에 같은 내용을 재전송한다.
- 실패 후 대기는 1·3·5·10·30초이며 전체 기한은 최초 전송 실패부터 60초다. 재시도·재시작으로 기한을 연장하지 않는다.
- 60초 기한이 되면 진행 중인 미완료 전송의 기다림도 중단한다. 기한이 있는 전송은 기존 연결별 2초와 전체 남은 시간 중 짧은 범위에서 기다리고 기한에 취소를 요청한다. 이미 나간 데이터의 회수나 기한 이후 앱 도착 방지, DB 결과 정리까지 정확히 60초 이내 완료를 보장하는 규칙은 아니다.
- 현재 유효한 접속자가 없으면 수신자 없음으로 종료한다. 알림 실패만으로 연결 중인 참여자를 퇴장시키지 않는다.
- 방 상태에는 증가 버전을 두고 같은 버전·내용으로 재전송한다. 프론트는 더 높은 버전의 상태만 적용하며 동일·과거 버전은 무시한다. 최초 입장·재접속은 최신 조회로 복구한다.
- 각 상태 알림은 해당 버전의 전체 공통 방 상태를 담는다. 더 최신 알림 하나로 공통 상태를 교체할 수 있도록 하고 같은 버전의 필수 상태를 여러 부분 알림으로 분할하지 않는다. 정확한 필드와 방 외부 데이터 범위는 후속 결정이다.
- 조회자별 비공개 정보와 타인의 답변·선호·투표를 공통 알림에 노출하지 않는다. 외부인의 방 조회 범위도 유지한다.
- 기존 앱 규칙에 따라 방 참여 중에는 닉네임·프로필 사진을 변경할 수 없다. 따라서 참여 중 프로필 변경의 실시간 방 전파나 별도 프로필 갱신 규칙을 도입하지 않는다. 서버도 같은 제한을 검사해야 하며 현재 구현 누락은 별도 검증 대상으로 기록한다.
- 최초 전송과 매 재시도 직전에 현재 방 참여 자격을 DB에서 방 단위로 일괄 확인한다. DB 확인 실패를 수신자 없음으로 취급하지 않으며 실제 전송 중 DB 잠금을 유지하지 않는다.
- 최초 전송과 재시도는 같은 공통 발송 진입점과 발송 기록 ID별 메모리 잠금을 사용한다. 같은 기록만 실행을 조정하며 다른 기록·여러 방의 발송을 전역 잠금으로 직렬화하지 않는다. 결과·재시도 시각·기한은 DB에 남겨 재시작 후 복구한다. 현재 단일 API 프로세스에 DB 처리 권한 임대를 추가하지 않는다.
- D06 2번(B): 최초 전송의 시작 기록은 있으나 확정 결과·최초 실패 기한이 없는 기록은 재시작 복구 시 재전송하지 않고 결과 불명 종료한다. 성공·실패·수신자 없음으로 오인하지 않으며 저장된 업무 상태를 되돌리지 않는다. 아직 최초 전송을 시작하지 않은 대기와 최초 실패 시각·기한이 저장된 재시도 대기는 이 예외로 종료하지 않는다. 서버 중단으로 끊긴 앱 연결은 재접속 후 최신 상태·버전 조회로 화면을 복구한다.
- D07 2번(B): 발송 종료 확정 시 원문을 제거하고 처리 요약만 종료 시각부터 3일 보관한다. 진행 중 원문은 재시도에 필요하므로 유지한다. 보관 기간이 지난 종료 요약은 주기 정리 대상으로 삼으며 재전송하지 않는다. DB 장애·정리 주기에 따른 삭제 지연과 백업·다른 로그의 별도 수명은 구분한다.
- D08 1번(A): 실제 방 연결은 비울 수 있는 외래 키로 DB가 존재를 검사하고 ON DELETE SET NULL로 방 삭제 시 연결만 비운다. 별도의 변하지 않는 이력용 방 식별 정보와 종료 요약은 보존하며 원래 종료 시각부터 3일 보관한다. 방 삭제로 요약을 연쇄 삭제하거나 보관 기한을 초기화하지 않는다. FK가 방 활성 상태·원문 제거·미완료 발송 종료를 대신 보장하지는 않는다.
- D09 2번(B): 같은 API 프로세스의 별도 요약 정리 작업을 시작 후 한 번 실행하고 매 실행 완료 후 1시간 기다린다. 만료한 종료 요약만 최대 100건씩 확정하며 한 번에 최대 10묶음·1,000건으로 제한한다. 실패한 묶음은 취소하고 이미 확정된 묶음은 유지하며 다음 실행에서 남은 대상을 다시 찾는다. 확인 횟수를 줄이는 대신 삭제 지연·누적 가능성을 받아들이며 정확한 삭제 시각이나 처리량을 보장하지 않는다. 주기·한도는 실측 후 조정 가능한 초기 운영값이다.
- D10 1번(A): 방 참여·주문서 완료 등 적용 가능한 변경 요청의 성공 HTTP 응답에 명령 결과와 최종 저장 버전의 전체 공통 상태를 함께 반환한다. 같은 버전의 발송 대기 snapshot과 일치시키고 최종 commit 이후 응답한다. 앱은 전체 공통 상태를 적용했을 때만 적용 버전을 올리며 같은 버전·과거 상태가 뒤늦게 와도 화면을 되돌리지 않는다. 최초 입장·재접속 최신 조회는 유지하고 본인 퇴장·방 삭제 응답의 정보 범위를 확대하지 않는다.
- D11: 접속 기록의 변화도 같은 방 상태 버전에 포함한다. 마지막 연결 끊김 감지·유예 내 복귀 등으로 실제 DB 값이 바뀌면 변경·버전·snapshot을 함께 저장하고 최종 commit 후 전달한다. 연결 끊김은 즉시 퇴장이 아니며 기존 60초 유예 후 일반 참여자 퇴장·방장 종료를 유지한다. 단순 heartbeat·같은 값·추가 연결 하나의 종료만으로 새 버전을 만들지 않으며 실제 사용자 연결과 DB 값의 변화를 기준으로 판단한다. 끊김 시각이 실제로 지워지는 복귀는 is_online의 변경 여부만으로 누락하지 않는다.

## 남은 설계 지도

1. 실행·복구 규칙: D04 기록별 공통 잠금·D05 기한에 전송 대기 중단·D06 미확인 최초 결과의 결과 불명 종료는 확정. 시작·결과 저장 실패, 저장된 기한의 복구, 잠금 수명·취소·방 종료와 늦은 결과의 조정을 한 안으로 정리한다.
2. 최종 검토: D11 접속 변화의 버전 포함과 나머지 확정 방향에 맞춰 공통 필드·개인별 정보 분리·일관된 조회·저장 구조·인덱스·명시적 마이그레이션·실패 관측을 정리한다. 전체 흐름·권한·프론트 계약·실제 REST/WebSocket 및 격리 MySQL 검증 계획을 함께 확인하며 아직 제안 단계인 필드를 승인 완료라고 표시하지 않는다.

세부 질문은 선행 선택에 따라 달라진다. 이 지도는 미정 설계를 미리 승인하거나 알림 보장 범위를 확대하는 문서가 아니다.

## 확인한 코드 사실

- 현재 room.updated는 참여·퇴장·완료·연결 복귀 사유에 따라 서로 다른 일부 필드를 담는다. 같은 실행의 여러 퇴장자는 사용자별 알림으로 나누어 전송하는 경로가 있다.
- 방 조회는 방 상태·인원·완료 수와 참여자 목록을 반환하지만 is_member/my_role은 조회자에 따라 달라지고, 참여자 목록도 비참여자에게는 비운다. 이 응답 전체를 같은 내용으로 방송할 수 없다.
- 닉네임·사진은 User 데이터에서 조회한다. 사용자가 방 참여 중 변경 금지 규칙을 확인했으므로 참여 중 실시간 프로필 변경을 지원하는 설계는 제외한다. 현재 백엔드 프로필 변경 경로에는 이 참여 제한 검사가 없어 서버 코드와 앱 규칙을 맞춰야 한다.
- T01N 이전에는 방 상태 버전과 DB 발송 대기가 없다. 기존 일부 필드 알림에 숫자 버전만 붙이면 모든 필요한 상태를 복구할 수 있는 것은 아니다.
- 입장 요청 안의 지연 퇴장과 새 입장처럼 한 트랜잭션이 여러 변경을 만들 수 있고 HTTP 명령 응답도 부분 상태다. 필요한 변경 전체를 담기 전에 같은 버전을 적용 완료로 표시하지 않도록 HTTP 응답과 알림의 적용 범위를 맞춰야 한다.
- 연결 끊김·재접속에 따라 DB 값은 바뀌지만 즉시 상태 알림이 항상 나가는 것은 아니다. 버전 범위에 넣을 필드는 해당 변경 경로 전체를 검토한다. 현재 broadcast는 토큰 만료는 검사하지만 DB 참여 자격을 매 전송 재검증하지 않으므로 재시도 시 수신 권한도 후속 구현 계약이다.

## T01N-D01: 상태 알림에 전체 공통 상태를 담을지 변경분만 담을지 — 1번(A) 확정

### 왜 필요한가

20번 상태의 화면에서 21번 변경은 철수 퇴장이고 22번 변경은 영희 주문서 완료라고 하자. 변경분 알림의 22번이 먼저 도착했을 때 숫자가 크다는 이유만으로 적용하고 21번을 버리면, 완료 표시만 바뀌고 철수가 화면에 남을 수 있다. 버전 비교만으로 부분 정보 누락을 해결하지 못한다.

### 1번(A): 알림마다 해당 버전의 전체 공통 방 상태

- 비용: 프론트의 변경분 적용·기준 버전 검사·누락 시 재조회·복구 중 동시 알림 처리가 필요하다. 누락·역순 때 HTTP 왕복과 DB 조회가 추가될 수 있다. 서버도 기준 버전과 변경분의 일관성을 보장해야 한다.

## T01N-D02: 방 참여 중 닉네임·사진 변경 금지 — 기존 앱 규칙 확인, 비교 철회

## T01N-D03: 전송 대상의 현재 방 참여 자격을 확인하는 근거 — 1번(A) 확정

### 상황과 코드 사실

- 철수가 DB에서 퇴장 처리됐지만 연결 종료가 완료되기 전에 같은 방 알림 또는 이전 알림의 재시도가 실행될 수 있다. 메모리에 소켓이 남았다는 이유만으로 전체 공통 상태 수신 자격이 있다고 판단하면 안 된다.
- 현재 broadcast는 메모리 소켓 목록을 순회하고 전송 시 토큰 만료를 확인한다. 매 전송 시 DB의 RoomMember를 확인하지 않으며 명시적 퇴장 경로는 방송 뒤 사용자 연결을 닫는다. 기존 소켓 목록을 그대로 권위 있는 현재 참여자 명단이라고 가정할 수 없다.
- 두 대안 모두 최초 연결 인증·기존 토큰 만료 검사와 퇴장자 연결 정리를 유지한다. 이 질문으로 인증·계정 전환 정책이나 프론트 ACK를 새로 설계하지 않는다.

### 1번(A): 알림 전송 시도마다 DB에서 현재 참여자 일괄 확인

- 최초 전송과 각 재시도 직전, 해당 방과 현재 연결된 사용자들의 참여 자격을 DB에서 함께 확인한다. 연결 하나마다 별도 조회하는 방식은 아니며 자격이 확인된 연결만 전송 후보로 삼는다.
- 권위는 현재 DB 참여 기록이다. 예전 payload에 참여자로 등장하더라도 이미 나간 사용자를 허용하지 않는다. 현재 조회 실패는 자격 없음·수신자 없음으로 단정하지 않고 전송을 보류하거나 실패로 관측한다. DB 작업은 전송 전에 끝내고 네트워크 전송 중 DB 잠금을 유지하지 않는다.
- 이점: 여섯 정리 경로 중 연결 정리 호출이 누락돼도 다음 전송 자격 조회에서 이미 제거된 참여자를 걸러낼 수 있다. 재시도·재시작 복구에서 같은 판정 근거를 쓴다.
- 비용: 매 전송 시도에 DB 조회와 왕복 지연이 추가된다. DB에서 자격 확인이 불가능하면 연결 자체가 살아 있어도 해당 보호 상태를 보내지 않는다. 실제 지연·부하는 측정 전이다.

### 2번(B): 단일 프로세스의 현재 참여 자격 명단을 유지

- 단순 연결 목록과 별개로 검증된 방 참여 자격 명단을 메모리에 유지한다. 최초 연결·참여·모든 퇴장/만료 경로의 commit 결과로 명단을 갱신하고, 각 전송은 이 명단과 토큰 만료 검사로 허용 여부를 판단한다.
- 기존 소켓 목록을 그대로 재사용하는 선택이 아니다. 상태 commit·명단 갱신·전송 자격 판정의 순서를 방별로 조정하고, 같은 사용자의 퇴장·재참여 세대를 구분해야 한다. 재시작·불명확한 캐시 상태에서는 새 연결 자격을 DB로 확인해 복원하며 모르는 상태로 허용하지 않는다.
- 이점: 정상 전송마다 참여자 확인 DB 조회를 반복하지 않아 왕복과 조회 부하를 줄일 수 있다. 기존 단일 API 프로세스 운영 조건에서 구현 가능한 대안이다.
- 비용: 모든 참여·삭제 경로와 예외 처리에서 명단 갱신을 빠뜨리지 않는 계약·순서 조정·테스트·복원 관리가 필요하다. 빠뜨리면 이미 퇴장한 연결을 허용할 수 있다. 별도 DB 수정이나 향후 다중 API 프로세스 운영에는 추가 무효화·동기화가 필요하다. 실제 처리량 우위는 미검증이다.

## T01N-D04: 같은 발송 기록을 동시에 처리하지 않도록 조정하는 위치 — 1번(A) 확정

### 상황과 전제

- 상태 변경의 commit 직후 즉시 발송 경로와, DB 대기를 찾는 재시도 실행기가 같은 기록을 동시에 발견할 수 있다. 두 경로 모두 같은 전송 진입점을 거쳐 한 번에 하나의 시도만 진행하도록 조정한다.
- 현재는 내구 발송·재시도 실행기가 없으므로 아래는 새 구현 대안이다. DB 발송 대기·원본 버전/payload·재시작 복구·D03 수신 자격 조회는 어느 선택에서도 유지한다.
- 기존 ADR은 API 프로세스 하나를 운영 전제로 한다. 이 질문은 그 전제를 다중 프로세스로 바꾸거나 Redis·브로커를 추가하는 선택이 아니다.
- 현재 요구사항에서 여러 API 프로세스나 별도 발송 프로세스가 필요한 근거는 없다. 여러 방·동접자 수와 프로세스 수는 별개이며, 처리 한계나 확장 시점은 실제 부하 측정 없이 인원 숫자로 정하지 않는다. 2번은 여러 프로세스가 같은 대기를 처리해야 할 때 검토할 확장 대안이다.

### 1번(A): 단일 API 프로세스 안의 공통 발송 잠금

- 최초 전송·재시도 모두 발송 기록 ID별 공통 메모리 잠금을 거친다. 잠금을 얻은 뒤 DB의 기록 상태·다음 시각·기한을 다시 확인하고, 다른 시도가 이미 완료했거나 아직 재시도 시각이 아니면 보내지 않는다.
- 공통 발송 코드는 한 곳에 두되 잠금은 기록별로 적용한다. A방 알림 101번을 처리하는 동안 B방 알림 202번도 실행할 수 있다. 같은 방의 서로 다른 기록까지 이 잠금으로 순서를 보장하는 것은 아니며 기존 상태 버전 규칙을 유지한다.
- 전송 결과·다음 시각·전체 기한·완료 여부는 계속 DB에 남긴다. 프로세스가 끝나 잠금이 사라져도 발송 대기는 남아 새 프로세스가 복구한다. D03에서 비교한 참여자 명단 캐시와는 다른 목적의 잠금이다.
- 이점: 처리 담당자를 DB에서 선점·만료시키는 추가 상태가 필요하지 않고 단일 프로세스 안의 중복 실행을 적은 DB 조정 작업으로 막을 수 있다. 기동 시 이전 프로세스의 잠금 임대 만료를 기다릴 필요가 없다.
- 비용: 모든 전송 경로가 같은 잠금 관리자·실행 경계를 사용해야 하고 사용이 끝난 잠금 정리가 필요하다. 다른 프로세스가 같은 대기를 처리하면 이 잠금은 공유되지 않아 별도 대책이 필요하다. 처리 중 상태의 관측은 로그 등 별도 수단으로 보완한다.

### 2번(B): DB에 기한 있는 처리 권한을 기록

- 전송 전에 짧은 DB 트랜잭션으로 해당 기록의 처리 담당자·고유 시도 식별자·권한 유효 기한을 선점한다. 다른 실행자는 권한이 살아 있으면 같은 기록을 처리하지 않는다. DB 잠금은 선점 후 바로 해제하고 소켓 전송 중에는 유지하지 않는다.
- 결과 저장은 현재 선점 식별자와 일치할 때만 허용해 오래된 실행이 새 시도의 결과를 덮지 않게 한다. 실행이 중단되면 권한 기한이 지난 뒤 다른 실행이 인계한다. 권한 기한·전송 시간 제한·재시작 복구·갱신 관계는 선택 시 후속 전송 기한 계약과 함께 정한다.
- 이점: 처리 담당 상태를 DB에서 관측하고 프로세스가 여러 개여도 같은 조정 근거를 사용할 수 있다. 모든 발송자가 DB 선점 계약을 따르는 경우에 한한다.
- 비용: 선점·완료/해제 DB 작업과 상태·식별자·인덱스, 임대 만료와 오래된 실행의 결과 검증이 늘어난다. 임대가 너무 짧으면 겹친 시도, 너무 길면 중단 후 복구 지연이 생길 수 있다. 재시작 직후에도 유효 임대가 남으면 인계가 지연될 수 있다.

## T01N-D05: 60초 기한에 이미 진행 중인 전송을 어떻게 다룰지 — 1번(A) 확정

- 이점: 기한 직전에 시작한 전송도 정상적으로 끝날 기회를 주고 전체 기한을 이유로 한 추가 중단 경계를 줄인다.

- T01이 참여 상태를 정리하고, T01N이 상태·버전·발송 대기를 함께 저장한 다음 실제 소켓 전송과 결과 저장을 수행한다. 이번 결정은 전송과 결과 저장 사이에서 프로세스가 중단된 경우다. 주문서·투표 규칙이나 재접속 유예를 바꾸는 질문이 아니다.
- 소켓 전송과 MySQL 결과 저장은 하나의 DB 트랜잭션으로 함께 확정할 수 없다. 실패를 관찰했어도 그 시각을 저장하기 전에 꺼지면 재시작한 프로세스에는 정확한 실패 시각이 없다. 성공 직후 결과 저장 전 중단도 같은 미확인 상태가 된다. 결과 기록 부재를 실패 확정 또는 미전송 확정으로 해석하지 않는다.
- 실패 결과·최초 실패 시각·고정 기한이 저장된 경우는 기존대로 그 기한을 복구한다. 이번 선택은 최초 시도의 결과가 아직 내구 기록으로 남지 않은 경우만 대상으로 한다. 이미 정한 60초 상한을 재시작 시 새로 계산하지 않는다.

### 두 안을 비교하기 위한 공통 기술 초안

- 실제 최초 소켓 전송 전에 발송 기록에 최초 시도 시작 기준 시각을 저장 확정한다. 그 저장을 확인하지 못하면 소켓 전송을 시작하지 않으며, 커밋 결과 불명은 DB 재조회로 확인한다. 이는 발송 기록별 메모리 잠금을 대체하거나 다중 프로세스용 DB 임대를 추가하는 제안이 아니다.
- 최초 시도 결과를 정상적으로 기록할 수 있으면 성공 종료 또는 관찰한 최초 실패 시각과 그 시각부터 60초인 기한, 다음 시도 정보를 저장한다. 실패 시각은 DB 저장이 끝난 시각으로 늦춰 잡지 않는다. 전체 전송 시도의 실패 판정 경계 등은 최종 실행 계약에서 구체화한다.
- 결과를 DB에 저장하지 못한 동안 같은 프로세스에서 결과·기한을 잊고 새 전송을 진행하지 않는다. 재시작 뒤에는 DB에 확인되는 기록을 근거로 아래 미확인 결과 정책을 적용한다.
- 저장된 시각 비교에는 일관된 UTC 시각·서버 시계 관리가 필요하다. 실행 중 대기 취소에는 경과 시간 기준 타이머를 사용한다. 프로세스 중단·DB 장애·시계 변동까지 포함한 정확한 물리 시각 보장을 주장하지 않으며 시계 이상 대응은 운영 계약에 연결한다.

### 1번(A): 미확인 결과는 최초 시도 시작 기준의 보수적 기한으로 복구

- 시작 기록은 있으나 최초 시도의 확정 결과가 없으면, 저장된 시작 기준 시각 + 60초를 복구 기한으로 사용한다. 실제 실패가 있었다면 그보다 앞선 기준이므로 실패 이후 새 60초를 부여하지 않는다. 실제 전송까지 지연된 경우 재시도 시간이 더 짧아질 수 있다.
- 예: 12:00:00 시작 기록, 12:00:01 실패, 결과 저장 전 중단, 12:00:20 복구라면 정확한 실패 기한 12:01:01을 추정하지 않고 12:01:00까지만 허용한다. 복구 시각 12:00:20부터 60초를 다시 주지 않는다.
- 복구 기한을 저장·확인한 뒤 전송하며 이후 실패나 또 다른 재시작으로 기준을 늦추지 않는다. 기존의 재시도 횟수·간격 상태를 복구하고, 미확인 최초 결과를 어떻게 첫 재시도에 대응시킬지는 후속 실행 계약에서 정한다. 재시작 자체로 즉시 재전송이나 횟수 초기화를 반복하지 않는다.
- 이미 기한이 지났거나 방이 종료됐으면 전송하지 않는다. 유효한 현재 연결이 실제로 없으면 D12대로 수신자 없음 종료이며 재접속자를 기다리는 새 대기를 추가하지 않는다. DB 자격 확인 실패는 수신자 없음과 구분한다.
- 이점: 미확인 결과에도 제한된 복구 기회를 남기고, 재시작으로 기한이 늘어나는 문제를 피한다.
- 비용: 최초 전송 전 DB 저장과 왕복이 추가되고, 미확인 상태·복구 기한 고정·재시도 상태를 구현·검증해야 한다. 실제 실패부터 60초를 전부 쓰지 못할 수 있고 이미 성공한 알림을 중복 전송할 수도 있다. 기존 버전 검사로 같은 상태의 중복 적용을 막지만 전송 비용 자체는 남는다. 현재 연결별 2초 설정만으로 손실 시간이 항상 최대 2초라고 단정하지 않는다.
- 정책상 의미: 알려진 최초 실패는 기존 기한을 유지하고, 정확한 시각을 복구할 수 없는 경우에 한해 더 이른 기한을 사용하는 예외를 추가하는 비교안이다. 사용자는 2번을 선택했으므로 이 복구 기한 대체는 채택하지 않는다.

### 2번(B): 미확인 최초 결과는 재전송하지 않고 별도 사유로 종료

- 시작 기록은 있지만 최초 시도의 확정 결과가 없으면 결과 불명 종료로 기록한다. 확정된 실패 시각·기한이 저장된 일반 미완료 기록의 복구는 계속 수행한다. 알림 종료가 이미 저장된 퇴장·방 상태를 되돌리지는 않는다.
- 이점: 미확인 최초 시도의 중복 전송과 해당 복구 전송의 수신 자격 조회·네트워크 작업을 줄이고, 추정 기한으로 전송할지 판단하는 경로가 줄어든다.
- 비용: 재전송하면 전달할 수 있었던 알림도 포기한다. 해당 최신 알림을 못 받은 연결은 후속 최신 전체 상태 알림이나 기존 최초 입장·재접속 조회 전까지 오래된 화면을 유지할 수 있다. 기존 설계에 없는 주기 조회나 강제 재접속으로 이 비용을 숨기지 않는다.
- 정책상 의미: 기존의 재시작 후 미완료 알림 복구 계약을 이 미확인 결과에 한해 축소한다. 동등한 내부 구현 대안이 아니라 복구 보장에 예외를 두는 변경이므로 선택 시 그 범위를 명시한다. 시작 기록 등 공통 저장 비용이 전부 없어지는 방식도 아니다.

### 확정한 재접속 흐름과 검증 경계

- 서버 프로세스가 중단되면 기존 WebSocket 연결도 끊긴다. 앱이 단절을 감지하는 시점에는 지연이 있을 수 있다. 서버 재시작과 앱 재접속 이후 현재 상태·버전 조회로 화면을 복구하는 기존 계약을 유지한다. 이전 알림이 재전송돼야만 조회 결과를 적용할 수 있는 구조가 아니다. 실제 프론트 구현·브라우저 검증 완료를 뜻하지 않는다.
- 결과 불명 종료는 전송 성공으로 표시하지 않는다. 방 상태·이미 저장된 제출·결과를 되돌리거나 참여자를 퇴장시키지 않는다. 서버 중단 없이 결과 저장만 실패한 경우는 임의로 새 시도를 시작하지 않으며 보존된 결과와 DB 확인을 사용하는 후속 저장 실패 계약에서 구체화한다.
- DB 상태가 미시작이면 일반 최초 발송 경로로 복구하고, 시작만 확인되면 결과 불명 종료, 최초 실패 시각·기한이 확인되면 기존 남은 기한·시도 상태를 복구한다. 모든 미완료 알림을 폐기하는 정책으로 확대하지 않는다. 후속 재시도 결과가 불명확해도 저장된 최초 실패 기한을 초기화하지 않는다.
- 검증: 시작 저장 직후 전송 전 중단도 결과 불명으로 종료하고, 전송 성공/실패 후 결과 저장 전 중단도 같은 종료를 확인한다. 미시작 대기 복구, 최초 실패 기한을 저장한 대기의 복구, 결과 불명 종료 후 재전송 없음, 재접속 조회와 지연 과거 알림의 버전 검사, 결과 불명 종료 저장의 재실행을 확인한다. 조회 실패를 복구 성공으로 표시하거나 새로운 주기 조회·강제 재접속을 추가하지 않는다.

### 채택 대상으로 제안하지 않는 방법

- 결과가 없으니 재시작 시각을 최초 실패로 간주하고 새 60초를 주는 방식은 실제 실패 이후 기한을 연장할 수 있어 기존 결정과 충돌한다.
- 결과를 전송 후 DB에 저장하는 것만으로 중단 직전의 정확한 실패 시각을 항상 복원할 수 있다고 설명하지 않는다. 전송과 DB 저장을 묶기 위해 네트워크 전송 내내 방 DB 잠금을 유지하는 방법도 이 간격을 없애지 못하며 기존 경계에 맞지 않는다.

### 현업 근거와 추천

- [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)는 업무 변경과 발송 대기를 같은 저장 작업으로 묶고 중복 메시지 소비를 안전하게 처리하도록 설명한다.
- [Amazon의 안전한 재시도](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)는 응답이 없더라도 실제 작업은 끝났을 수 있다는 불확실성과, 같은 작업 식별자를 이용해 재시도의 추가 부작용을 막는 기법을 설명한다. 우리 방 버전 검사는 같은 공통 상태의 중복·역순 적용을 막는 역할이며 EC2 자원 생성 API와 동일한 기능이라는 뜻은 아니다.
- 이 자료가 우리 서비스의 정확한 60초 또는 시작 시각 대체 규칙을 채택했다는 근거는 아니다. 1번의 복구 기한은 기존 요구사항에 맞춘 기술 제안이다. 새 큐·별도 서버를 도입하는 제안도 아니다.
- 최초 추천은 1번(A)이었다. 추가 설명에서 서버 중단 시 기존 연결도 끊기고, 1번도 복구 시 현재 수신자가 없으면 종료하므로 항상 추가 복구 효과가 생기지는 않는다는 제한을 확인했다. 사용자는 재접속 조회로 현재 상태를 복구하는 흐름을 이해하고 2번(B)을 선택했다. 시작 시각을 대체 기한으로 삼는 1번은 채택하지 않으며 D06 2번의 제한된 예외만 확정한다. T01N 전체 승인·실행 코드 구현은 아니다.

## T01N-D07: 종료한 발송 기록의 내용과 보관 기간 — 2번(B)·3일 확정

- 사용자 선택: 2026-11-17 “2번 3일로 하자”. 원문 제거·요약만 보관하는 2번을 선택하고 제안 기간 7일을 3일로 조정했다. 적용 기준은 종료 시각부터 3일이다. 아래 1번·3번은 비교 이력이며 채택하지 않는다. 정리 주기·묶음 크기·방 삭제 참조·스키마의 세부까지 확정하거나 실행 코드 구현을 시작한 뜻은 아니다.

### 전체 흐름과 이번 선택의 범위

- 방 상태 변경 → 상태·버전·발송 대기 저장 → 실제 전송·제한된 재시도 → 종료 확정 → 보관·정리 중 마지막 부분이다. 진행 중인 알림을 지우거나 최신 방 상태·개인 기록을 지우는 결정이 아니다.
- 알림은 성공뿐 아니라 수신자 없음, 방 종료·만료, 기한 초과, D06 결과 불명으로도 종료한다. 성공은 서버 전송 기준이며 앱의 수신·화면 반영 증명이 아니다. 보관 중인 종료 기록을 발송 대기로 되살리지 않는다.
- 발송 기록은 전송할 당시의 전체 공통 상태(payload)와 발송 처리 요약으로 나눠 생각한다. 요약 예시는 기록 ID, 방 식별 참조, 상태 버전, 생성·첫 시도·최초 실패·종료 시각, 시도 횟수, 종료 사유와 제한된 오류 분류다. 없는 시각을 추정해 채우지 않으며, 전체 연결별 전달 이력을 새로 만드는 제안이 아니다.
- 공통 상태에는 참여자 닉네임·사진 URL 등 표시 정보가 포함될 수 있다. 비공개 답변·선호·개인별 표는 기존대로 공통 알림에 담지 않는다. 요약에는 닉네임·사진·인증 비밀값·원문 요청이나 원문 예외를 복사하지 않는다.

### 1번(A): 종료 확정 시 발송 기록 삭제

- 작업이 더 이상 실행되지 않게 종료를 확정하고 같은 DB 정리 경계에서 해당 발송 기록을 삭제하는 방향이다. 정확한 트랜잭션·진행 중 작업 조정은 최종 실행 계약에 따른다. 저장 실패를 종료 성공으로 취급하지 않는다.
- 이점: 종료 기록이 쌓이지 않고 보관 만료를 위한 별도 DB 청소 범위가 작다. 재시도에 필요한 진행 중 원본은 그대로 보존한다.
- 비용: 나중에 특정 알림의 시도 횟수·종료 이유·내용을 DB에서 조사할 수 없다. 따로 수집한 서버 로그가 실제로 남아 있으면 보완할 수 있지만 현재 로그 수집·보관을 검증하지 않았으므로 대체 보장으로 약속하지 않는다. 종료 기록 없이도 이미 잡힌 작업이 재생성·재전송하지 않도록 없는 기록의 처리도 검증해야 한다.

### 2번(B): 종료 시 원문 제거, 요약만 3일 보관 — 사용자 확정

- 종료와 함께 재전송용 원문을 제거하고 같은 발송 기록에 종료 요약만 남기는 방향이다. 별도 기록 저장 서비스나 별도 DB를 도입하는 제안이 아니다. 종료 시각부터 3일이 지난 요약을 주기 정리에서 나눠 삭제한다.
- 이점: D06 결과 불명, 기한 초과, 반복 실패 등 운영 단서를 종료 후 3일 범위에서 기록별로 조회할 수 있다. 전체 방 상태를 중복 보관하는 양과 표시 정보 보존을 줄인다.
- 비용: 당시 정확한 알림 본문은 복원할 수 없다. 참여자 누락·필드 구성 오류 등의 본문 문제를 이 요약만으로 재현하지 못한다. 요약 행·검색용 인덱스·백업과 만료 조회·삭제 작업은 남고 원문 제거의 갱신 작업도 필요하다.

### 3번(C): 종료 원문과 요약 모두 7일 보관

- 종료 시각부터 7일 동안 발송 당시 전체 공통 상태와 요약을 함께 보관한다. 이후 주기 정리에서 삭제하며, 보관 목적은 조사이지 종료한 알림의 재전송이 아니다.

### 세 안에 공통인 정리·운영 경계

- 원래 payload는 발송이 끝나기 전까지 보존한다. 생성된 지 3일이라는 이유만으로 아직 진행 중인 작업을 보관 정리 대상으로 삭제하지 않는다. 오래된 미완료 작업은 발송 실행 계약으로 종료 사유를 먼저 판단한다.
- 확정한 보관 기간은 DB의 종료 시각을 기준으로 한다. 3일이 지나면 삭제 대상이며 주기 실행·DB 장애에 따라 실제 삭제는 늦어질 수 있다. 보관 정책만으로 정확한 시각 삭제나 과거 백업·다른 로그까지 즉시 삭제를 약속하지 않는다.
- 정리 작업은 종료 기록만 제한된 묶음과 짧은 DB 작업으로 처리하는 방향이다. 만료된 항목을 한꺼번에 대량 삭제해 방 요청을 오래 기다리게 하지 않도록 크기·주기·인덱스는 최종 운영 계약과 실측에서 정한다. API 프로세스 하나라는 기존 전제를 유지한다.
- RAM 1GB와 디스크 저장 공간은 다르다. 보관 데이터가 전부 RAM에 상주한다고 설명하지 않는다. 다만 DB 읽기 캐시·조회·정리·백업은 같은 서버 자원을 사용할 수 있다. 측정 없이 비용·지연·수용 인원을 확정하지 않는다.
- 현재 방 종료 경로는 알림 후 연결 종료와 방 물리 삭제를 수행한다. 보관 기간 때문에 실제 방을 유지하거나 삭제를 막는 정책을 자동 추가하지 않는다. 방 삭제 후 기록 참조의 생존·개인정보 범위·미완료 알림 종료는 다음 참조 계약에서 설계한다.

### 현업 근거와 사용자에게 물을 선택

- [Google Cloud Pub/Sub 보관 정책](https://docs.cloud.google.com/pubsub/docs/subscription-message-retention)은 기본적으로 확인된 메시지를 버리고, 별도 설정하면 확인된 메시지도 보관해 다시 읽을 수 있으며 보관 비용이 발생한다고 설명한다. 처리 이후 보관의 가치와 비용을 목적에 맞게 선택하는 사례다. 우리 서버 전송 성공과 Pub/Sub 소비자 ACK를 동일시하지 않으며 현재 프론트 ACK 없음 결정을 유지한다.
- [AWS CloudWatch Logs 보관 설정](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html)은 로그 보관 기간과 기간이 지난 기록의 삭제를 설정하는 기능을 제공한다. 업무용 발송 대기와 조사용 기록은 목적·보관 수명을 구분할 수 있다. 이 서비스 도입이나 우리 기록 3일 보관의 근거로 오해하지 않는다.
- 최초 추천은 2번(B)·7일이었고 사용자는 2번(B)·3일을 확정했다. 운영 초기의 종료 사유 조사 단서를 남기되 전체 공통 상태의 중복 보관은 줄인다. 종료 상태·시각·요약 보존과 원문 제거의 저장 실패, 3일 전후의 삭제 경계, 진행 중 기록 보호·정리 재실행을 후속 검증에 포함한다. T01N 전체 설계·구체 스키마·구현 완료는 아니다.

## T01N-D08: 방 물리 삭제와 보관 요약의 연결 — 1번(A) 확정

- 사용자 선택: 2026-11-17 “1번으로 해줘”. 실제 방 연결은 nullable 외래 키와 ON DELETE SET NULL로 관리하고 변하지 않는 이력용 방 식별 정보를 별도로 보존한다. 아래 2번은 비교 이력이며 채택하지 않는다. 구체 컬럼명·마이그레이션·잠금 순서·종료와 삭제의 상세 실행 계약까지 확정하거나 구현을 시작한 뜻은 아니다.

### 전체 위치·기존 선택·현재 코드

- 방장 퇴장·유예 만료·방 만료 → 방 종료 → 기존 종료 알림·연결 정리 → 방 물리 삭제와 이어지는 발송 기록 정리가 이번 위치다. 일반 참여자 퇴장만으로 방을 삭제하는 질문이 아니다.
- 기존 코드의 방장 종료는 방을 CLOSED로 저장하고, 호출 경계가 room.closed 방송·연결 종료 뒤 방을 삭제한다. 만료·방장 연결 유예 종료 경로도 물리 삭제를 수행한다. delete_closed_room은 참여자 주문서·참여 기록·방을 지우며 현재 내구 발송 테이블은 없다.
- D07에 따라 종료 요약은 3일 보관한다. 방 삭제에 발송 요약까지 연쇄 삭제하거나 요약 보관 때문에 방을 3일 유지하면 이 선택 또는 기존 물리 삭제 방향을 바꾸게 된다. 이번에는 이 둘을 동등한 신규 선택지로 다시 제안하지 않는다.
- 방이 살아 있을 때의 실제 연결과, 삭제 후에도 같은 방의 이력을 묶어 조사하는 식별 정보는 목적이 다르다. 전자는 존재하는 방을 가리켜야 하고 후자는 삭제된 방의 과거 기록을 식별할 수 있어야 한다.

### 두 안에 공통인 처리 초안

1. 방 종료를 처리하는 DB 경계에서 새 참여·제출·일반 상태 발송을 더 진행하지 않는 종료 상태를 확정한다. 같은 방의 발송 대기 변경도 관련 잠금 순서에 맞춘다.
2. 미완료 일반 상태 알림은 방 종료 사유로 종료하고 원문을 제거한다. 이전에 이미 종료된 요약의 사유·종료 시각은 바꾸지 않는다. 새로 종료된 요약만 그 종료 시각부터 3일 보관하며 삭제 요청 재실행으로 수명을 늘리지 않는다.
3. DB 저장 성공 뒤 기존 방 종료 알림·연결 종료·물리 삭제 흐름에 연결한다. room.closed 자체를 60초 내구 재시도 대상으로 확장하는 선택은 아니다. 소켓 전송·취소 대기를 하면서 방 DB 잠금을 유지하지 않는다.
4. 방을 물리 삭제해도 종료 요약은 남는다. 이후 요약은 자신의 원래 종료 시각부터 3일이 지나면 기존 정리 대상이 된다. 삭제된 방은 현재 상태 조회로 되살리지 않으며 기존 종료/없음 계약을 따른다. 구체 응답 형식은 최종 계약에서 정리한다.
5. 발송 처리와 종료가 겹치면 종료된 기록에 새 시도를 시작하지 않는다. 이미 자격 확인을 통과해 전송 중이거나 네트워크로 나간 데이터는 회수할 수 없다. 진행 중 작업의 취소와 늦은 결과의 조건부 저장으로 종료 상태가 대기·성공 상태로 되돌아가지 않도록 최종 실행 계약에서 검증한다.

### 1번(A): 살아 있는 방 연결은 DB 외래 키로 검사, 삭제하면 연결만 비움 — 사용자 확정

- 발송 기록에 실제 방 연결과 변하지 않는 이력용 방 식별 정보를 별도로 둔다. 실제 연결에는 nullable 외래 키와 ON DELETE SET NULL을 사용한다. 방 삭제 때 실제 연결은 비우고 기록과 이력 식별 정보는 보존한다. 구체 컬럼명·식별자 형태는 스키마 초안에서 정한다.
- 외래 키는 살아 있는 방 연결을 넣거나 바꿀 때 그 대상 방이 존재하는지 DB가 확인하는 장치다. SET NULL은 방 삭제 때 발송 기록을 지우지 않고 그 연결 칸만 비우는 규칙이다. 연결 칸은 비울 수 있어야 한다.
- 이점: 존재하지 않는 방을 현재 방으로 연결하는 저장 실수를 DB가 거절한다. 방 삭제 시 연결 비우기도 DB가 처리하므로 별도 삭제 경로에서 이 동작만 빠뜨리는 오류를 줄인다. 요약은 같은 발송 기록에 남겨 별도 이력 이동 테이블을 도입하지 않는다.
- 비용: 살아 있는 방 연결과 이력 식별 정보의 두 값, FK용 인덱스와 제약을 관리한다. 저장 시 FK 검사와 방 삭제 시 연관 행의 연결 갱신·잠금 비용이 든다. 연관 요약이 많으면 실제 삭제 비용이 커질 수 있으므로 격리 MySQL 경합·삭제량을 검증한다.
- 한계: FK는 대상 방의 존재를 검사할 뿐 방이 진행 가능한 상태인지, 실제 연결과 이력 식별 정보가 올바른 쌍인지, 대기 알림이 종료됐는지까지 보장하지 않는다. 이 규칙은 서버 코드와 테스트가 담당한다. SET NULL 자체를 원문 제거·발송 취소로 설명하지 않는다.

### 2번(B): 발송 기록에는 이력용 방 식별 정보만 저장, 외래 키 없이 코드로 확인

- 방이 삭제돼도 의미가 있는 방 식별 정보를 발송 기록에 두고 DB 외래 키는 설정하지 않는다. 생성·전송·정리 시 서버가 실제 방의 존재·상태를 확인하고 같은 방의 변경과 조정한다. 식별 정보는 기록 조사용이며 방이 살아 있다는 증거가 아니다.
- 이점: 이 관계를 위한 DB FK 검사와 방 삭제 때 연결 비우기 작업이 없다. 과거 기록은 방 생명주기와 DB 제약으로 연결되지 않는다. 조회·정리를 위한 검색 인덱스는 여전히 필요할 수 있다.
- 비용: 잘못된 방 식별 정보의 저장이나 누락된 종료 처리를 DB가 거절해 주지 않는다. 모든 생성·삭제·복구 경로에서 코드 검증과 경합 처리를 유지해야 한다. 미완료 고아 기록은 정리·관측 계약에서 다뤄야 한다. 이미 필요한 방 조회를 활용할 수 있으므로 추가 조회가 항상 더 든다고 단정하지 않는다.
- 사용자 화면·3일 보관·미완료 종료 정책은 1번과 같다. FK가 없다고 방 확인·권한 확인을 생략하거나 무조건 빠르다고 보장하지 않는다.

### 장애 경계와 비교 범위

- 요약 종료 저장에 실패하면 결과 저장 성공으로 표시하지 않으며 해당 DB 작업은 취소한다. 방 종료가 이미 별도 단계에서 저장된 경우까지 되돌렸다고 설명하지 않는다. 이미 CLOSED인 방의 재실행·물리 삭제 재시도는 남은 정리를 이어가고 요약 수명을 초기화하지 않아야 한다.
- 종료와 물리 삭제가 다른 DB 단계이므로 중간 중단 뒤 닫힌 방이 일시 남을 수 있다. 이를 다시 사용 가능한 방으로 취급하지 않는다. 단계별 복구와 FK 경합은 최종 실행 계약·MySQL 검증에서 구체화한다.
- 작은 내부 일관성 장치의 차이다. 이번 선택을 새 실시간 전달 보장이나 대규모 분산 시스템 선택으로 과장하지 않는다. 다중 프로세스·새 큐·별도 로그 서비스를 추가하는 안은 없다.

### 현업 근거와 추천

- [MySQL 외래 키 공식 문서](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html)는 CASCADE, RESTRICT, SET NULL 등의 삭제 규칙을 설명한다. 1번은 이 중 연결만 비우는 기능을 사용하는 우리 서비스 제안이다. 현재 프로젝트의 참여 기록은 CASCADE를 사용하지만 보관 요약에 그대로 복사하면 요약도 삭제되므로 목적을 구분한다.
- [Google Cloud Spanner의 외래 키](https://docs.cloud.google.com/spanner/docs/foreign-keys/overview)는 실제 존재 관계를 검사하는 enforced 외래 키와 검사하지 않는 informational 외래 키를 구분한다. 후자는 쓰기 검사 부담을 줄이는 대신 데이터 관계의 정확성을 외부에서 관리해야 한다. Google이 제공하는 DB 기능에서 확인되는 trade-off이며 Google 내부의 모든 서비스가 특정 안을 사용한다는 근거는 아니다. Spanner의 구체 삭제 문법을 MySQL의 SET NULL과 동일시하지 않는다.
- 최초 추천은 1번(A)이었고 사용자가 같은 안을 확정했다. 같은 MySQL 안에 방과 발송 기록이 있고, 기존 코드도 FK를 사용하므로 존재 관계에 DB 검사를 활용한다. FK 검사·인덱스와 방 삭제 시 연결 갱신·잠금 비용을 받아들이는 선택이다. FK 없이 코드가 관계를 관리하는 2번은 채택하지 않는다.
- 방 물리 삭제 후 실제 연결은 NULL이지만 이력 식별 정보와 종료 요약은 남고 원래 종료 시각부터 3일이 지나면 정리 대상이 된다. 이미 종료된 요약의 사유·종료 시각을 덮어쓰지 않는다. 검증에는 없는 방 연결 거절, 방 삭제 후 연결만 비움·요약 보존, 이력 식별 정보 불변, 3일 기한 보존과 실제 MySQL 삭제 경합을 포함한다. 방 활성 상태 검사·미완료 발송 종료·원문 제거는 별도 코드 책임으로 유지한다.
- 다음은 정리 운영과 최종 실행·상태 계약이다. 위 공통 처리 초안의 상세 순서·취소·중간 중단 복구는 후속 계약에서 구체화하며 T01N 전체 승인·구현 완료로 표시하지 않는다.

## T01N-D09: 만료한 종료 요약의 정리 주기와 작업량 — 2번(B)·1시간 확정

- 사용자 선택: 2026-11-17 “2번으로 해줘”. 실행 완료 후 1시간 간격을 선택했다. 함께 설명한 시작 후 첫 실행, 같은 API 프로세스의 별도 작업, 100건씩 최대 10묶음·1,000건, 묶음별 저장·실패 복구 방식을 초기 운영 설계에 반영한다. 아래 1번은 비교 이력이며 채택하지 않는다. 구체 인덱스·관측 수집·전체 실행 계약까지 확정하거나 구현을 시작한 뜻은 아니다.

### 전체 위치와 공통 전제

- 상태 변경 → 발송 대기 저장 → 전송·재시도 → 종료 시 원문 제거 → 종료 요약 3일 보관 → 만료 요약 정리 중 마지막 부분이다. 방장 시작·추천·투표 기능이나 실시간 알림 재시도 주기를 바꾸는 질문이 아니다.
- D07의 보관 기준은 종료 시각부터 3일이다. 만료 시점과 실제 삭제 완료 시점은 다르며 작업 실행 지연·DB 장애·밀린 기록 때문에 삭제가 늦어질 수 있다. D08의 실제 방 연결 유무와 관계없이 만료한 종료 요약을 정리한다. 방이 없어졌다는 이유만으로 3일 전에 지우지 않는다.
- 현재 API는 lifespan에서 방 정리용 asyncio 작업을 시작하고 종료 시 취소한다. 이를 근거로 같은 API 프로세스 안에 별도의 요약 정리 작업을 두는 안을 제안한다. 기존 방 만료·재접속 유예 정리 주기는 변경하지 않고 새 서버·외부 스케줄러·메시지 큐를 추가하지 않는다. 서버가 꺼진 동안은 실행되지 않는다.

### 두 안에 공통으로 설명했고 채택한 실행 방향

1. 시작 후 첫 정리를 실행하고, 그 실행이 끝난 뒤 선택한 간격을 기다린다. 같은 정리 작업을 겹쳐 시작하지 않는다. 따라서 벽시계에 정확히 맞춰 실행되거나 삭제 지연이 간격 이내라는 보장은 아니다.
2. DB 기준 시각으로 종료 후 3일이 지난 종료 요약만 대상으로 삼는다. 진행 중 원문·실제 방·참여자·답변·투표는 대상이 아니다. 종료 시각과 기록 ID 순으로 오래된 것부터 제한해서 삭제하는 방향이다.
3. 한 DB 작업은 최대 100건을 삭제·확정하고 연결을 반환한다. 한 번 실행은 최대 10묶음, 총 1,000건까지만 처리한다. 묶음 사이 다른 작업이 실행될 수 있게 하고, 동기 DB 호출로 이벤트 루프를 막지 않는다. 100건·10묶음은 실측 전 초기 설정이며 성능 보장 수치가 아니다.
4. 한 묶음 저장에 실패하면 해당 묶음은 취소하고 오류를 기록한 뒤 이번 실행을 끝낸다. 이미 확정된 앞선 묶음은 유지한다. 다음 실행이나 서버 재시작 때 남은 만료 기록을 다시 대상으로 삼는다. 빠른 무한 재시도·전체 기록 메모리 적재는 하지 않는다.
5. 만료 대상을 찾는 검색 인덱스를 마련한다. 인덱스는 오래된 기록을 찾는 목차이며 조회에 도움이 되지만 저장 공간과 쓰기 유지 비용이 있다. 정확한 컬럼·실행 계획은 스키마와 MySQL 검증에서 정한다. 작은 묶음도 한 번의 DB 잠금 시간을 보장하지는 않으므로 실제 지연을 측정한다.
6. 삭제 건수·실행 시간·오류와 만료 기록 누적을 관측한다. 구체 지표 수집 방식은 후속 계약이다. 매번 한도까지 삭제하고도 만료 기록이 계속 늘면 주기·한도·인덱스를 조정할 근거로 삼는다. 초기 한도가 모든 발생량을 처리한다고 약속하지 않는다.

### 1번(A): 매 실행 완료 후 10분 간격 — 미채택 비교 이력

- 정상이고 밀린 기록이 적다면 3일이 지난 뒤 다음 실행에서 정리할 수 있다. 10분 간격은 목표 실행 빈도이며 추가 삭제 지연의 상한은 아니다.
- 이점: 만료 기록이 쌓이는 시간을 줄이고, 같은 실행당 한도에서 더 자주 밀린 기록을 처리할 기회를 얻는다.
- 비용: 대상이 없어도 정상 지속 실행 기준 하루 약 144회 확인한다. DB 조회·연결 사용·실행 관리의 고정 비용이 2번보다 자주 발생한다. 같은 기록을 삭제하는 본래 비용이 없어지는 것은 아니다.
- 실행 시간이 거의 없다는 가정에서 시간당 최대 6,000건의 처리 기회가 있지만 실제 처리량 보장은 아니다. 발생량·경합·장애가 이를 넘으면 계속 밀릴 수 있다.

### 2번(B): 매 실행 완료 후 1시간 간격 — 사용자 확정

- 이점: 정상 지속 실행 기준 하루 약 24회로 대상 확인 횟수를 줄인다. 초기 발생량이 적고 만료 이후 추가 지연을 허용한다면 선택할 수 있다.
- 비용: 다음 정리까지 기다리는 시간이 더 길고 만료 기록이 더 많이 남을 수 있다. 같은 실행당 최대 1,000건이므로 실행 시간이 거의 없다는 가정에서도 시간당 처리 기회가 1번보다 작다. 더 오래 쌓이면 조회·저장 공간·방 삭제 시 SET NULL 대상량에 영향을 줄 수 있다.
- 한 번의 삭제 묶음 크기는 1번과 같으므로 한 시간마다 무조건 대량 삭제하거나 잠금 시간이 반드시 더 길다는 뜻은 아니다. 동일한 기록량을 결국 지우는 비용도 남는다. 프론트 화면·전송 보장·3일 기준은 1번과 같다.

### 현업 근거와 추천의 범위

- [MySQL DELETE 공식 문서](https://dev.mysql.com/doc/refman/8.0/en/delete.html)는 LIMIT으로 한 DELETE의 행 수를 제한하고 필요하면 반복하는 방식을 설명한다. 한 번에 처리하는 양을 제한하는 근거이며 100건·10묶음·10분을 권장한다는 뜻은 아니다.
- [AWS DynamoDB TTL](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html)은 기록별 만료 시각과 실제 백그라운드 삭제를 구분하며 삭제는 보통 만료 후 수일 안에 이루어진다고 설명한다. 빅테크가 제공하는 서비스에서도 만료와 물리 삭제 시점을 분리하는 사례다. 우리 MySQL에 같은 자동 기능이 있거나 수일 지연을 채택한다는 뜻은 아니다.
- 최초 추천은 1번(A)이었고 사용자는 2번(B)을 확정했다. 빈 확인 횟수를 줄이는 대신 만료 이후 추가 삭제 지연과 같은 실행당 한도에서 더 적은 처리 기회를 받아들이는 선택이다. 1시간 간격과 작업 한도는 부하 측정 뒤 조정 가능한 초기 운영값이다. 서버 중단·DB 장애·누적으로 삭제가 1시간보다 더 늦어질 수 있음을 유지한다.
- 검증에는 3일 전후 대상 구분, 시작 후 첫 실행, 실행 완료부터 1시간 대기, 동일 작업 중첩 방지, 100건·10묶음 상한, 일부 묶음 실패 후 재실행, 진행 중 기록 보호를 포함한다. 구체 스키마·인덱스·관측 수집 방식과 최종 발송 실행·조회 및 알림 상태 계약은 후속 설계다. T01N 전체 설계·구현 완료는 아니다.

## T01N-D10: 변경 요청의 HTTP 응답과 전체 공통 상태 적용 — 1번(A) 확정

- 사용자 선택: 2026-11-17 응답 크기 설명을 확인한 뒤 “1번으로 해줘”를 선택했다. 적용 가능한 변경 요청의 성공 응답에 명령 결과와 전체 공통 상태·버전을 함께 반환한다. 아래 2번은 비교 이력이며 채택하지 않는다. 정확한 필드·응답 구조·접속 표시 범위·전체 티켓 설계까지 확정하거나 실행 코드 구현을 시작한 뜻은 아니다.

### 전체 위치와 이미 정한 경계

- 참여·주문서 완료 같은 요청 → 상태·버전·발송 대기의 최종 DB 저장 → 요청자에게 HTTP 응답과 참여자들에게 WebSocket 알림 → 앱 화면 적용 중 응답·알림이 만나는 부분이다. HTTP는 버튼 요청에 대한 답이고 WebSocket은 서버가 연결된 앱에 보내는 알림이다. 도착 순서는 보장하지 않는다.
- D01의 알림마다 전체 공통 상태, 동일·과거 버전 무시, 최초 입장·재접속 최신 조회는 유지한다. 이번에는 전체 알림과 변경분 알림을 다시 선택하지 않는다. 요청이 성공한 본인 화면이 최신 공통 상태를 얻는 경로를 정한다.
- 현재 RoomJoinResponse·RoomOrderSheetCompleteResponse 등은 일부 결과만 반환하고 RoomDetailResponse에는 is_member·my_role 같은 조회자별 값도 섞여 있다. 같은 방 조회 응답 전체를 공통 방송으로 복사할 수 없다.
- 공통 상태의 예시는 방 식별자·상태·방장·참여자 명단·인원·주문서 완료 여부다. 정확한 필드와 접속 표시의 버전 범위는 후속 계약이며 이 비교에서 확정하지 않는다. 본인 역할 같은 조회자별 정보는 공통 상태 밖에 두고 개인 답변·선호·표를 방송하지 않는다. 비참여자의 현재 조회 범위도 확대하지 않는다.

### 두 안에 공통인 안전 규칙

1. 앱은 해당 방의 전체 공통 상태를 실제로 교체했을 때만 그 버전을 적용 완료로 표시한다. 일부 명령 결과나 큰 숫자만 받아서는 적용 버전을 올리지 않는다. 이 규칙 없이 같은 버전의 알림을 무시하면 부분 누락이 생긴다.
2. 전체 공통 상태와 그 버전은 서로 일관된 묶음이어야 한다. 늦게 도착한 이전 HTTP 응답·조회가 더 최신 알림 상태를 되돌리지 못하게 한다. 명령의 성공 여부와 화면 동기화 여부를 구분한다.
3. 성공 응답은 최종 commit 이후에만 보낸다. 같은 상위 작업에서 지연 정리와 새 참여 등 여러 변경이 있으면 중간 버전·부분 상태를 전체 상태라고 반환하지 않는다. 새로운 DB 잠금을 소켓 전송 내내 유지하지 않는다.
4. 전체 참여자 상태는 조회·발송 권한이 있는 현재 참여자에게만 제공한다. 본인 퇴장·방 삭제의 응답을 전체 상태 반환 대상으로 확대하지 않으며 기존 종료·탈퇴 결과를 따른다. 권한이나 상태가 이미 바뀐 경우의 응답·클라이언트 처리도 구현에서 검증한다. 요청 결과 불명일 때 명령을 무조건 반복하는 정책은 추가하지 않는다.

### 1번(A): 성공 응답에 명령 결과와 전체 공통 상태·버전을 함께 반환 — 사용자 확정

- 방 참여 성공·주문서 완료 등 적용 가능한 변경 요청에는 기존 명령 결과와 그 최종 저장 상태의 전체 공통 상태·버전을 함께 반환한다. 공통 부분은 같은 버전의 발송 대기에 저장한 snapshot과 일치해야 한다. 구체 응답 필드명·하위 객체 구조와 기존 필드 호환은 API 계약에서 정한다.
- 앱은 HTTP 응답으로도 전체 상태를 교체하고 적용 버전을 올릴 수 있다. 뒤늦게 같은 버전의 알림이 오면 무시하고 더 최신 알림이 먼저 왔다면 이전 HTTP 상태를 무시한다. 알림이 먼저 도착해도 명령 자체의 성공 결과는 별도로 처리한다.
- 이점: 요청자의 화면 갱신이 알림 도착에만 의존하지 않고 정상 응답 이후 별도 GET 왕복을 줄일 수 있다. outbox용으로 이미 만든 공통 snapshot을 활용할 수 있다.
- 비용: HTTP 응답이 커지고 요청자에게 응답과 알림으로 같은 상태가 중복 전달될 수 있다. 공통 snapshot을 명령 응답 경계까지 전달하고 기존 프론트 계약을 수정해야 한다. 이것만으로 DB 조회가 반드시 추가되는 것은 아니며 실제 구성·직렬화·전송 비용은 측정한다. 응답 상태는 해당 저장 버전이며 도착 시점의 전역 최신 상태를 보장하지 않는다.
- 최종 저장 뒤 새 조회로 더 최신 상태를 읽었다면 이전 명령 버전을 붙여서는 안 된다. 원래 snapshot 반환과 별도 최신 조회를 섞지 않도록 검증한다. HTTP 응답 자체 유실·마지막 후속 알림 유실을 모두 없애는 보장은 아니다.

### 2번(B): 성공 응답은 명령 결과만, 이후 최신 방 상태를 GET으로 조회 — 미채택 비교 이력

- 현재처럼 변경 요청의 결과를 반환하고 성공을 확인한 앱이 별도 최신 방 조회를 수행한다. 조회에서 현재 전체 공통 상태·버전을 얻고 같은 버전 검사로 적용한다. 비교를 명확히 하기 위해 정상 경로도 한 번 GET하는 기본안을 제안하며 알림 수신 여부에 따른 조회 생략 최적화는 포함하지 않는다.
- 이점: 명령 응답을 작게 유지하고 전체 상태를 얻는 HTTP 경로를 조회로 모을 수 있다. 명령 처리 결과를 공통 snapshot과 함께 응답으로 전달하는 작업이 줄 수 있다. 기존 알림 snapshot 생성·저장 비용은 그대로다.
- 비용: 성공한 변경 요청마다 추가 HTTP 왕복과 서버·DB 조회가 생긴다. 조회 실패·지연 중에는 요청 성공과 화면 갱신을 따로 다뤄야 한다. 이때 같은 명령을 재실행하지 않고 동기화 실패로 구분한다. 조회 실패 때의 상세 재시도·표시는 최종 프론트 계약에서 정한다.
- 최신 알림이 먼저 도착하면 화면은 먼저 갱신될 수 있다. 별도 조회가 반드시 그 알림보다 새롭거나 반환 순간에도 전역 최신이라는 보장은 없으므로 응답·알림의 버전 비교는 여전히 필요하다. 최초 입장 직후 WebSocket이 아직 없어도 GET으로 복구할 수 있다.

### 사례·현업 근거·추천

- 현재 화면 20에서 철수 퇴장과 영희 완료가 반영된 21을 얻는 상황에서, 영희 완료 표시와 버전 21만 먼저 적용하면 참여자 명단이 20에 머물 수 있다. 1번은 응답의 전체 21을 적용하고, 2번은 부분 결과로 적용 버전을 올리지 않고 GET 또는 전체 알림으로 전체 21 이상을 적용한다.
- [Microsoft Azure REST API Guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)는 변경 작업 이후 리소스 상태를 응답으로 반환하는 방향을 제시한다. [Microsoft Graph plannerTask 수정](https://learn.microsoft.com/en-us/graph/api/plannertask-update?view=graph-rest-1.0)은 Prefer: return=representation으로 수정한 객체를 반환하는 기능을 제공한다. 변경 후 상태를 응답으로 받는 실제 제품의 기법이며 우리 API에 해당 헤더를 도입한다는 제안은 아니다.
- [Microsoft Graph 권장 사항](https://learn.microsoft.com/en-us/graph/best-practices-concept)은 응답 데이터가 필요 없는 경우 지원되는 작업에서 최소 응답을 요청할 수 있다고 설명한다. 작은 명령 응답의 가치는 있지만 우리 화면은 공통 상태가 필요하므로 2번은 별도 조회 비용을 함께 고려해야 한다. 특정 기업이 우리 두 안 중 하나를 모든 서비스에 사용한다는 뜻은 아니다.
- 최초 추천은 1번(A)이었고 응답 크기를 확인한 사용자가 같은 안을 확정했다. 이미 전체 알림 snapshot을 만들고 요청자 화면도 갱신해야 하므로 같은 공통 상태를 응답에도 활용하고 정상 성공 뒤 별도 조회를 줄인다. 응답 크기와 기존 명령 응답·프론트 변경을 받아들이며 명령 결과만 받고 매번 별도 GET하는 2번은 채택하지 않는다.
- 검증에는 같은 버전 응답·알림의 양방향 도착 순서, 더 최신 알림 이후 과거 HTTP 상태 무시, 전체 적용 전 버전 확정 금지, 같은 상위 트랜잭션의 최종 snapshot 일치, commit 실패 시 성공 응답 없음, 비공개 정보·퇴장자 접근 범위 보존을 포함한다. 요청 성공 결과는 공통 상태의 중복 무시와 별도로 처리한다. 정확한 API 구조·필드와 최종 발송·조회 계약은 후속 설계다.

### D10 추가 설명: 응답 크기의 예시 계산 — 선택 전 설명 이력

- 사용자가 1번의 메시지 크기를 질문했을 때는 선택으로 해석하지 않았다. 이후 설명을 확인한 사용자가 1번을 확정했다. 현재 RoomDetailResponse·RoomMemberResponse·RoomOrderSheetCompleteResponse 항목을 참고해 합성 JSON을 구성하고 Python json.dumps(ensure_ascii=False, separators=(',', ':')).encode('utf-8')의 바이트 수를 계산했다. 실제 구현·운영 트래픽·처리 시간 측정이 아니다.
- 기본 예시: 36자 방 식별자, 6자리 사용자 ID, 한글 8자 닉네임, 61자 사진 주소, 20자 시각 문자열을 사용했다. 참여자 1명은 완료 시각이 있고 나머지는 미완료, 모두 온라인·끊김 시각 없음으로 구성했다. 방 공통 항목은 현재 방 조회에서 is_member·my_role을 빼고 version을 더한 예시다. 명령 결과에 state 객체를 추가하는 응답 형태를 가정했으며 실제 필드·형식은 미확정이다. 닉네임 문자열은 길이 계산용 합성값이다.
- 긴 항목 예시는 한글 20자 닉네임·500자 사진 주소와 완료·연결 끊김 시각이 모두 있는 상태로 계산했다. 실제 닉네임 수정은 2~20자 검사를 사용하고 사진 주소 DB 컬럼은 500자다. 이 예시는 운영 평균이나 최대 크기 보장이 아니다.

- 표는 압축 전 JSON 본문이며 HTTP 헤더·TLS·WebSocket 프레임·재전송을 포함하지 않는다. KB로 설명할 때는 1KB=1,000바이트로 환산한다. 현재 방 생성의 기본 정원은 8명, 입력 허용 상한은 100명이다. 이는 성능 검증 결과가 아니며 제품 최종 정원 선택도 아니다. 이후 후보·결과 등 새 공통 항목이 추가되면 다시 계산한다.
- 사진 파일 자체는 JSON에 넣지 않고 주소만 넣는다. 이미지 내려받기·캐시의 트래픽은 별도다. URL이 같다고 이미지를 매번 재다운로드한다고 가정하지 않는다.
- 1번 때문에 커지는 대상은 해당 명령의 요청자 HTTP 응답이다. 방 전체 WebSocket 알림의 전체 snapshot은 이미 D01로 정했으므로 D10 선택으로 추가 확대하지 않는다. 여러 연결에 방송하는 기존 총량은 참여자·연결 수와 재시도 횟수에 영향을 받는다.
- 2번도 성공 후 별도 GET으로 비슷한 전체 공통 상태를 받아야 한다. 따라서 정상 경로의 요청자 수신 본문 합계는 대략 1번=명령 결과+공통 상태, 2번=명령 결과+별도 조회 공통 상태로 비슷할 수 있다. 정확한 조회 응답 부가 정보는 최종 API 구조에 달려 있다. 2번은 추가 요청·응답 헤더, 왕복 지연과 서버·DB 조회가 생긴다. 총 전송량이 1번에서 무조건 더 크다고 설명하지 않는다.
- 이 계산만으로 1GB 서버의 처리 가능 인원·처리 지연·안전한 발생량을 보장하지 않는다. 실제 직렬화·동시 요청·DB 및 네트워크 측정은 구현 검증에서 수행한다.

## T01N-D11: 공통 상태 필드·접속 표시·일관된 조회 — 접속 변화의 같은 버전 포함 확정

- 사용자 선택: 2026-11-17 쉬운 상황 설명을 확인한 뒤 “접속 변화도 같은 버전에 포함으로 해줘”라고 선택했다. 끊김·복귀 등 실제 접속 기록 변화도 같은 공통 상태 버전으로 전달하고 저장·전송 비용 증가를 받아들인다. 아래 공통 필드 표·편의 정보 분리·구체 조회 구현까지 일괄 승인한 것으로 취급하지 않으며 세부는 최종 검토에 포함한다. 실행 코드는 변경하지 않았다.

### 위치와 제안 범위

- 남은 3묶음 중 첫 번째다. DB의 한 버전 상태 → 저장할 발송 snapshot → WebSocket 알림·D10 성공 HTTP 응답·참여자 최신 조회 → 같은 버전 검사로 화면 교체에 쓰는 공통 자료의 범위를 정한다. 아래 안은 검토용이며 실행 코드·API 구조를 확정하지 않는다.
- 기존 방의 상태와 참여자·주문서 완료 정보를 대상으로 한다. 라운드·후보·투표·결과의 새 상세 필드는 해당 기능을 설계하는 T02~T06에서 이 공통 계약에 확장한다. 미구현 기능을 빈 값으로 먼저 설계 완료 처리하지 않는다.

### 제안하는 공통 필드 목록

| 묶음 | 공통으로 제공하는 정보 |
| --- | --- |
| 식별·순서 | 공개 방 식별자, 방 상태 버전 |
| 방 | 진행 상태, 방장 식별자, 최대 인원, 생성 시각, 만료 시각 |
| 참여자별 표시·구성 | 기존 공개 API의 사용자 식별자, 표시 닉네임, 프로필 사진 주소, 역할, 참여 시각 |
| 참여자별 접속 기록 | DB에 저장한 is_online, disconnected_at |
| 참여자별 완료 | 주문서 완료 여부, 완료 시각. 답변 내용은 제외 |
| 전체 집계 | 참여 인원, 정원 도달 여부, 완료 인원, 전원 완료 여부 |

- 참여자는 기존 순서인 참여 시각·내부 참여 기록 ID로 안정적으로 정렬한다. 내부 정렬용 ID를 공개할 필요는 없다. 참여 인원은 유예 중 남아 있는 참여자도 포함하고 전원 완료는 현재 참여자가 1명 이상이며 완료 인원이 같은 경우로 계산한다. 관련 필드·집계는 같은 상태 기준이어야 한다.
- is_member·my_role은 조회자별 정보로 공통 상태 밖에 둔다. 방 참여자 각자의 role은 공통 목록에 있어도 본인만의 my_role을 한 값으로 방송하지 않는다. join_url은 조회·생성 응답의 편의 정보로 유지하고 DB 방 버전이 보장하는 공통 필드에서 제외한다. 주소 설정 변경 때문에 업무 상태 버전을 올리는 정책은 추가하지 않는다.
- 개인 답변·음식 선호·개인별 투표·인증 비밀값·이메일·내부 오류·발송 재시도 요약은 공통 상태에 넣지 않는다. 후보·공개 결과를 이후 확장할 때도 개인 답변·개인 표 공개로 해석하지 않는다. 사진은 주소만 제공한다.
- 비참여자의 기존 조회에는 참여자 목록을 노출하지 않는 제한을 유지한다. 제한된 응답을 전체 공통 상태라고 표시해 참여자 앱의 상태 교체에 사용하지 않는다. 본인 퇴장·방 삭제 응답은 D10의 기존 예외를 따른다.

### 접속 표시와 버전의 제안 규칙

1. 접속 표시도 같은 공통 상태 버전으로 관리한다. 연결 객체 자체는 메모리에 있고 DB 접속 기록은 서버가 관측해 저장한 상태다. 실제 기기·네트워크 상태의 즉각적인 증명이나 수신자 권한의 대체물은 아니다. D03 현재 자격 확인·D06 재접속 조회도 유지한다.
2. 마지막 연결 끊김을 감지하면 기존처럼 disconnected_at을 저장하고 60초 참여 유예를 유지한다. 현재 구현은 이때 is_online을 즉시 false로 바꾸지 않으므로, disconnected_at이 있으면 이를 우선해 재접속 대기 상태로 해석한다. 초기 미연결 상태와 구분하며 새로운 60초 후 잔류 오프라인 정책을 도입하지 않는다.
3. 유예 안 재접속은 연결 끊김 시각을 비우고 기존처럼 온라인 상태를 기록한다. 사용자별 여러 연결에서 하나만 끊긴 것을 마지막 연결 종료로 취급하지 않는다. 유예 만료 후 일반 참여자는 퇴장·방장은 방 종료라는 기존 정책을 유지한다. 클라이언트의 시간 경과만으로 DB 퇴장 완료를 단정하지 않는다.
4. 버전 범위의 DB 값이 실제 바뀌는 연결 시작·마지막 단절 감지·유예 내 복귀·서버 재시작 시 유예 시작도 상태·버전·snapshot을 같은 변경 경계로 저장한다. 끊김 시각만 지워진 재접속도 변경이며 현재 became_online 반환값만으로 알림 필요 여부를 판단하지 않는다. 재시작 시 기존 단절 시각을 덮어써 유예를 늘리지 않는다.
5. 같은 값 반복 저장·단순 조회·heartbeat·알림 재시도는 새 업무 버전을 만들지 않는다. 한 상위 트랜잭션의 같은 방 변경은 최종 공통 상태로 묶고 서버 재시작 시 여러 방 전체를 한 트랜잭션으로 바꾸지 않는다. 방 종료 후 일반 발송 종료는 D08과 최종 실행 계약에 따른다.

### 조회·응답·알림의 일관성

- 현재 상태를 조회할 때도 상태·멤버 목록·집계·버전을 같은 DB 상태 기준으로 읽는다. 버전을 먼저 읽은 뒤 독립된 다른 시점의 목록을 붙이지 않는다. 기존 방 단위 변경 조정과 짧은 읽기 경계를 사용하고 정확한 SQL·잠금 순서는 실행 설계와 MySQL 검증에서 결정한다.
- 조회 안에서 지연 퇴장·만료 정리가 발생한다면 그 변경도 같은 버전·발송 대기 규칙을 따른다. 변경 없는 조회 자체는 새 발송 대기를 만들지 않는다. 개인별 조회 정보의 접근 권한도 해당 조회 경계에서 확인한다.
- 응답·조회·알림에 같은 버전이 붙으면 공통 필드는 같아야 한다. 재시도는 저장된 원래 내용을 사용한다. 본인 정보나 편의 URL이 같아야 한다는 뜻은 아니다. D10 전체 공통 상태 적용 후에만 버전 확정 규칙을 유지한다.

### trade-off와 현업 근거

- 접속 기록까지 같은 snapshot에 넣으면 오래된 알림이 새 접속 표시를 되돌리지 않도록 기존 버전 검사로 함께 처리할 수 있고 별도 접속 상태 버전 체계가 필요 없다. 끊김·복귀가 잦으면 전체 상태 구성·DB 발송 기록·전송이 추가되며 방 변경끼리의 경합도 늘 수 있다. 신호가 흔들릴수록 비용이 늘어나는 한계가 있다.
- 참여 인원·완료 집계도 함께 보내면 앱이 같은 계산을 반복할 필요가 줄지만 명단·완료 여부와 집계가 모순되지 않게 서버가 계산·검증해야 하고 본문이 조금 늘어난다. 닉네임·사진 주소를 함께 보내면 별도 프로필 조회가 줄지만 반복 문자열이 생긴다. 기존 참여 중 프로필 변경 금지 때문에 실시간 프로필 수정 전파는 필요 없다.
- 접속 표시를 공통 버전에서 빼고 별도 조회 때만 갱신하면 끊김·복귀만으로 만드는 알림을 줄일 수 있지만 참여 중 접속 표시가 오래되며 앱에 별도 적용 규칙이 필요하다. 이는 접속 표시 갱신 수준을 낮추는 대안이다. 현재 방향을 유지하는 제안은 같은 버전에 포함하는 안이며 별도 Redis·presence 서버를 도입하지 않는다.
- [Google Firebase의 presence 설계](https://firebase.google.com/docs/firestore/solutions/presence)는 연결 상태를 감지해 저장하고 다른 저장소에 반영하는 기법, 연결 대상 차이에 따른 부정확성과 잦은 이벤트를 줄이는 처리를 설명한다. 접속 상태도 관측된 데이터이고 동기화 비용이 있다는 실제 서비스의 사례다. Firebase 도입이나 Google의 모든 서비스가 방 버전에 접속 상태를 넣는다는 근거는 아니다.
- 사용자는 접속 변화도 같은 버전에 포함하는 안을 확정했다. 접속 표시를 별도 조회 때만 갱신하는 대안은 채택하지 않는다. 끊김·복귀가 잦을 때 전체 상태 저장·발송이 늘고 관측 지연이 남는 한계를 유지한다. 별도 presence 서버·Redis는 추가하지 않는다.
- 남은 진행은 실행·복구 규칙과 최종 검토의 2묶음이다. 검증에는 마지막 연결 종료·유예 내 복귀·유예 만료·재시작·같은 값과 heartbeat의 새 버전 없음·지연 과거 접속 상태 무시를 포함한다. 나머지 공통 필드·집계·조회 권한·일관된 조회의 제안은 최종 검토에서 함께 확인하고 세부 컬럼 이름을 별도 사용자 질문으로 늘리지 않는다.

## T01N-D12: 발송 실행·결과 저장 실패·중단 복구 — 1번(A) 확정

- 사용자 선택: 2026-11-17 “1번으로 해줘”. 전송 결과를 DB에 저장하지 못했을 때 살아 있는 프로세스가 메모리에 관찰한 결과·첫 실패 시각(60초 고정 기한)을 유지한 채 결과 저장 복구를 먼저 수행하고, 무작정 새 전송을 다시 시작하지 않는 1번(A)을 확정했다. 이로써 T01N의 핵심 아키텍처 trade-off(D01~D12) 결정이 모두 완료되었다.

### 전체 위치와 제안의 핵심

- 남은 2묶음 중 실행·복구를 정리하는 묶음이다. 업무 상태·버전·발송 대기 저장 → 시작 기록 확인 → 실제 전송 → 전송 결과 저장 → 종료 또는 다음 시도 중 각 경계의 실패를 다룬다. 기존 D01~D11 선택을 재선택하지 않는다.
- 핵심 제안은 전송 결과를 저장하지 못했을 때 같은 프로세스가 관찰한 결과를 보존하고 저장 복구를 먼저 수행하는 것이다. DB가 불확실한 동안 같은 알림을 새로 전송하거나 성공 처리하지 않는다. 업무 변경 전체를 알림 실패 때문에 다시 실행하지 않는다.

### 정상 발송 경계

1. 상위 업무 트랜잭션에서 최종 방 상태·증가 버전·그 버전의 전체 공통 snapshot을 담은 발송 대기를 함께 저장한다. 저장 실패가 확정되면 전체를 취소하고 전송하지 않는다. commit 결과 자체가 불명확하면 실패 확정으로 오인해 업무를 반복하지 않고 새 DB 세션으로 기존 작업·발송 기록의 저장 여부를 확인한다. 기존 계정 전환·참여 작업의 결과 확인 계약을 유지한다.
2. 최종 commit 확인 이후 공통 발송 진입점이 기록을 처리한다. 단일 API 프로세스의 기록별 잠금을 얻고 DB의 종료 여부·실행 가능 시각·기한·방 상태를 재확인한다. DB 연결이나 방 잠금을 잡은 채 메모리 잠금을 기다리거나 네트워크 결과를 기다리지 않는다.
3. 현재 참여 자격과 연결을 확인한다. DB 확인 실패는 수신자 없음이 아니다. 현재 유효한 연결이 실제로 없으면 해당 사유로 종료 저장하며, 방 종료·만료·기한 도달이면 해당 종료 규칙을 먼저 따른다. 중간에 권한이 바뀌는 경쟁과 이미 나간 데이터 회수 불가는 유지한다.
4. 실제 최초 전송의 시작 표시를 저장하고 commit 성공을 확인한 뒤에만 소켓 전송을 시작한다. commit 응답이 불명확하면 DB 재조회로 표시·기록을 확인할 때까지 전송하지 않는다. 아직 소켓 호출을 하지 않았다는 사실과 같은 프로세스의 기록 잠금을 보존하면 확인 후 같은 시도를 이어갈 수 있다. 이 기억이 사라지는 재시작은 D06 경계를 따른다.
5. 현재 대상 연결들에 저장된 원래 snapshot을 전송한다. 연결별 기존 2초 제한을 유지하고 최초 실패 이후에는 남은 전체 기한도 적용한다. 전송은 방 DB 잠금을 해제한 뒤 수행한다. 앱 ACK·개인별 전달 테이블은 추가하지 않는다.
6. 대상 전송이 모두 서버 소켓 기준 성공이면 종료·원문 제거·요약 보관을 저장한다. 하나 이상 실패하면 시도 실패로 보고 처음 관찰한 실패의 UTC 시각과 그 시각+60초의 고정 기한을 보존한다. 최초 실패를 관찰할 때 경과 시간 타이머도 시작하고 결과 취합·저장 지연으로 기한을 늦추지 않는다. 여러 연결 결과를 모은 시각을 기준으로 다음 대기 간격을 계산하되 전체 기한보다 뒤이면 새 전송을 시작하지 않는다.
7. 실패한 차례 이후 대기 간격은 기존 1·3·5·10·30초 순서를 사용한다. 이후 간격은 30초를 상한으로 두되 전체 60초 기한을 우선한다. 저장이 늦어도 다음 실행 시각을 저장 완료 시점부터 새로 계산하지 않는다. 재시도 전 매번 자격·종료·기한을 확인하고 같은 버전·내용을 현재 유효한 방 연결 전체에 전송한다.

### 결과 저장이 실패했을 때의 제안

- 같은 프로세스에서 확인한 결과·시각·기한·다음 시도 정보를 해당 기록 처리 문맥에 유지하고 결과 저장만 복구한다. 같은 기록의 즉시 발송·주기 복구가 새 전송을 시작하지 못하도록 공통 잠금과 처리 문맥을 공유한다. 무제한 작업을 메모리에 쌓지 않도록 전체 실행 수와 탐색 묶음을 제한하는 운영값은 최종 검토에 명시한다.
- DB 오류 후 기존 세션을 정리하고 새 세션으로 기록을 재확인한다. commit은 실제 성공했지만 응답만 잃었을 수 있다. 이미 같은 결과가 저장됐으면 다시 덮어쓰지 않고 확인으로 마치며, 방 종료·기한 종료 등 다른 종료가 먼저 확정됐으면 그 종료를 보존한다. 없는 기록을 다시 만들지 않는다.
- 확정한 최초 실패 시각·기한은 보존하고 최초 시작 표시만 남았다는 이유로 살아 있는 프로세스가 알고 있는 실패를 잊어버리지 않는다. 결과를 모르는 재시작과 구분한다. 최초 실패부터 60초가 지나면 미완료 전송 대기도 취소하고 더 보내지 않으며, DB가 돌아온 뒤 종료 결과를 정리한다.
- 결과 저장이 복구되기 전에 서버가 중단되면 메모리의 결과는 사라진다. 시작 표시만 있고 최초 실패 기한이 DB에 없으면 D06대로 재전송 없이 결과 불명 종료한다. 이미 최초 실패 기한이 DB에 있으면 그 기한을 보존하고 미시작·대기·결과 불명 재시도의 실행 상태를 재확인해 복구한다. 저장된 정보 없이 성공·실패·정확한 실패 시각을 추정하지 않는다.
- DB 장애 중에는 저장 복구에도 대기와 실행 수 제한을 두며 빠른 무한 반복을 하지 않는다. 재시작이 아닌 살아 있는 프로세스의 결과 저장 복구에는 알림 재전송 횟수·간격을 소모하지 않는다. 구체 저장 재확인 주기와 복구 작업량은 최종 운영안에 모은다.

### 재시작·기한·방 종료의 우선 관계

| DB에서 확인한 상태 | 복구 방향 |
| --- | --- |
| 발송 미시작 | 정상 최초 발송 대상으로 확인. 방·수신 자격 재검사 |
| 최초 시작 표시만 있고 최초 결과·실패 기한 없음 | D06 결과 불명 종료. 재전송 없음 |
| 최초 실패 기한·다음 실행 정보가 저장됨 | 기존 기한·시도 단계 유지. 이미 만료면 종료 |
| 성공·수신자 없음·기한·방 종료 등 종료 확정 | 다시 발송하지 않음. 원문 제거·3일 요약 유지 |
| 방이 닫혔거나 실제 방 연결이 사라짐 | 일반 상태 발송 중단·종료 정리. 과거 방을 재생성하지 않음 |

- 재시작 복구는 기존 방 유예·만료 정리와 조정한다. 방 종료 사실이 있으면 알림의 일반 재시도보다 종료를 우선하며 기존 종료 요약의 사유·시각은 바꾸지 않는다. 여러 방 전체를 하나의 원자 트랜잭션으로 재설계하지 않는다.
- 기한은 최초 실패부터 60초이며 재접속 유예 60초와 별개다. 재시작·DB 장애·추가 실패로 기한을 연장하지 않는다. 이미 저장된 최초 실패 기한이 있는 재시도의 결과가 불명확하면 최초 전송 결과 불명 예외로 바꾸지 않는다. 저장된 시도 단계·실행 시각으로 복구하며 새 최초 실패 시각을 만들지 않는다.
- 방 종료 저장과 일반 대기 종료·원문 제거를 관련 DB 경계에서 조정하고 commit 후 기존 room.closed·연결 정리·물리 삭제로 이어간다. room.closed 자체를 새 60초 내구 재시도로 확대하지 않는다. 이미 전송 중인 데이터는 회수할 수 없고 늦은 성공 결과가 방 종료 기록을 대기로 되살리거나 종료 사유를 바꾸지 못하게 조건부 저장한다.
- 종료·원문 제거·요약 저장은 같은 기록의 DB 작업으로 확정한다. 저장 실패를 완료로 표시하지 않으며 재실행해도 최초 종료 시각·3일 수명을 초기화하지 않는다. D08 SET NULL은 이 업무 처리를 대신하지 않는다.

### trade-off·현업 근거·검증 경계

- 이 안은 DB 불확실성 중 근거 없는 중복 전송과 새 기한 부여를 줄이고 살아 있는 프로세스가 관측한 결과를 보존한다. 대신 저장 복구 문맥·종료 경쟁·메모리 잠금 수명 관리가 필요하고, DB 장애 동안 알림이 늦어지거나 기존 기한 안 재전송 기회를 잃을 수 있다. 서버까지 중단되면 D06의 최초 결과 불명 종료로 알림 복구 기회도 포기한다. 업무 상태는 알림 실패만으로 되돌리지 않는다.
- 결과 저장을 기다리지 않고 다시 전송하는 대안은 추가 전달 기회를 얻을 수 있지만 결과·시도 단계가 DB와 어긋나고 이미 성공한 알림도 반복될 수 있다. 최초 실패 시각까지 잊고 다시 시작하면 기존 기한 계약을 위반한다. 이번 추천안은 저장 확인을 먼저 하는 방향이다. 단순한 방 상태 재전송의 중복이 주문서·투표의 재실행으로 번지지 않게 한다.
- [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)는 업무 변경과 발송 대기의 같은 트랜잭션 저장, rollback된 변경의 미전송과 중복 처리 대비를 설명한다. [Amazon 안전한 재시도](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)는 응답 부재와 실제 실패의 차이, 같은 작업 식별자로 중복 부작용을 막는 기법을 설명한다. 우리 저장 확인·버전 검사는 이 원리를 적용한 것이며 AWS 서비스의 전달 보장이나 우리 60초·결과 불명 종료 정책을 동일시하지 않는다.
- 검증에는 최초 업무 저장의 rollback·결과 불명, 시작 표시 저장 실패·응답 유실, 실제 전송 전후 중단, 성공·실패 결과의 저장 오류 및 commit 응답 유실, 살아 있는 프로세스의 결과 보존, 새 기한 금지, 60초 취소, 방 종료와 늦은 결과 경합, 메모리 작업 수 제한과 취소·재실행을 포함한다. 실제 시계 오차·스케줄링·DB 장애를 포함한 정확한 물리 시각 전달 보장은 아니다.

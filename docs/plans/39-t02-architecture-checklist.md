# T02 아키텍처 선택 체크리스트

기준일: 2026-11-13. 사용자 응답 `1A,2A,3A,4A,5B,6A,7A,8B,9B,10A`를 반영해 이 체크리스트 10항목의 선택을 마쳤다. 이는 주요 방향의 선택 완료이며 상세 계약·전체 T02~T09 설계 또는 구현 완료가 아니다. 최신 일정은 오늘 2시간 내 아키텍처 설계, 내일(2026-11-14) 구현·검증이다. 미응답·추천 표시는 승인이 아니며 실제 코드·DB·학습 모델 적용은 아직 진행하지 않는다.

## 이미 선택한 방향

- 여러 신호를 학습하는 추천 모델을 사용하고 실제 사용자 피드백으로 조정한다(D11). 1~8번의 구조·모델·학습 방향은 D13으로 확정했다. 정확한 학습 주기·배포·클라우드 서비스·성능까지 확정한 것은 아니다.
- 질문·메뉴 추천·피드백에는 JWT 인증을 요구하고 본인 추천만 평가한다(D01~D03).
- 평가 수정 이력은 보존하며 사용자·추천·메뉴별 최신 유효 평가만 기여한다. 다른 추천의 평가는 누적하고 재전송은 새 평가로 추가하지 않는다(D04~D05).
- 제외 목록은 유형별 전체 교체·마지막 성공 저장 우선이다(D06). 알레르기와 섭취 불가는 서버 선택 목록만 허용하고 섭취 불가는 재료 중심이다(D07~D09).
- 강제 제외·후보 없음 규칙은 유지한다. 학습 점수가 제외된 메뉴를 되살리지 않는다.
- 1A 선택으로 기존 답변 점수를 기본으로 하고 제한된 학습 재정렬을 적용해 D10의 영향 제한을 유지한다. 실제 한도·스케일과 수동 누적식·5/10/20%·기준 건수 4는 확정값이 아니다.

## 선택 방법

`1A, 2보류, 3A`처럼 답하거나 `2번의 B와 C 차이 설명`처럼 질문한다. 나머지는 보류로 유지한다. 각 번호는 하나의 선택 묶음이며 필요한 항목만 답해도 된다. 추천은 현재 코드와 운영 부담을 고려한 에이전트 제안으로, 실제 성능이 검증된 최적값이 아니다.

## 1. 학습 모델과 오늘 답변의 관계

- [x] **1A — 기존 답변 점수를 기본으로 학습 모델이 제한적으로 재정렬(추천).** 여러 입력으로 배운 예측을 보조 순위에 사용하고 D10의 영향 제한을 유지한다. 장점: 오늘 의도를 통제하고 기존 결과와 비교하기 쉽다. 비용: 한도·스케일 연결 설계가 필요하고 모델이 순위를 바꿀 자유가 제한된다.
- [ ] **1B — 오늘 답변·이력·메뉴 특성을 함께 학습해 모델이 최종 순위 결정.** 장점: 상황과 과거 행동의 복잡한 조합을 학습할 자유가 크다. 비용: 오늘 답변 우선과 D10의 별도 보정 한도는 재검토해야 하며 학습 데이터·목표·설명·평가 부담이 커진다. 강제 제외는 그대로 유지한다.

## 2. 처음 사용할 모델

- [x] **2A — 로지스틱 회귀 같은 단순 학습 모델(추천).** 여러 입력으로 만족 확률 등을 학습한다. 장점: 계수 점검·재현·CPU 추론이 비교적 단순하다. 비용: 복잡한 조건 조합은 특징 설계가 필요하고 좋은 성능은 데이터 검증이 필요하다. 여러 신호 학습은 가능하며 수동 가산식과 다르다.
- [ ] **2B — 부스팅 트리 계열 모델.** 예: LightGBM. 장점: 입력 조건 사이의 비선형 조합을 표현하기 쉽다. 비용: 과적합·파라미터·특징 누출 검증이 늘어난다. 분류와 순위 학습 중 어떤 목표를 쓸지는 라벨·후보 그룹 구조에 맞춰 정한다.
- [ ] **2C — Two-tower 후보 검색과 별도 순위 모델.** 사용자/현재 요청과 메뉴를 벡터로 표현해 후보를 찾는다. 장점: 후보가 매우 많을 때 검색을 효율화할 수 있다. 비용: 임베딩 학습·검색 인덱스·별도 순위 모델의 복잡도가 추가된다. Two-tower만으로 현재 순위 로직을 전부 대체하는 것은 아니다.

공식 근거: [scikit-learn](https://scikit-learn.org/stable/modules/linear_model.html#logistic-regression), [LightGBM 목적함수](https://lightgbm.readthedocs.io/en/stable/Parameters.html), [LightGBM 튜닝](https://lightgbm.readthedocs.io/en/stable/Parameters-Tuning.html), [TensorFlow Recommenders 검색](https://www.tensorflow.org/recommenders/examples/basic_retrieval). 위 장단점은 구조와 운영 부담에 따른 적용 판단이며 WhatBap 성능 비교 결과가 아니다.

## 3. 처음 학습할 정답과 신호

- [x] **3A — 명시적 만족·불만족을 첫 학습 정답으로 사용(추천).** 오늘 답변·메뉴 특성·그 시점까지의 과거 이력은 여러 입력으로 사용한다. 장점: 정답 의미가 명확하고 수정 정책을 연결하기 쉽다. 비용: 평가하는 사람의 데이터만 생겨 표본이 적거나 편향될 수 있다. 노출·선택·식사 기록은 분리 기록해 후속 활용을 검토한다.
- [ ] **3B — 만족·선택·식사 기록을 처음부터 여러 학습 목표로 사용.** 장점: 평가 버튼 외 행동도 학습할 수 있다. 비용: 클릭·선택·식사 기록의 의미와 누락·가중치를 구분해야 한다. 선택을 실제 식사나 만족으로 단정하지 않으며, 미평가·미선택을 자동 불만족으로 만들지 않는다. 학습·평가 체계가 복잡해진다.

입력 신호가 여러 개라는 것과 정답 종류가 여러 개라는 것은 다르다. 3A도 여러 신호를 학습하는 모델이다. 실제 추천 시점의 입력·노출 결과·모델 버전을 재현할 기록을 설계하고, 현재 평가나 미래 행동을 과거 입력으로 섞지 않는다.

## 4. 다른 사용자 데이터와 개인화

- [x] **4A — 공용 모델 하나에 사용자별 이력·취향을 입력(추천).** 장점: 사용자마다 모델을 따로 학습하지 않고 공통 패턴을 활용할 수 있다. 비용: 전체 학습 데이터 관리와 사용자별 검증이 필요하다. 모델을 공유해도 다른 사용자의 원본 개인 기록을 API에 반환하지 않는다.
- [ ] **4B — 사용자별로 별도 모델 학습.** 장점: 모델 자체를 사용자별로 분리할 수 있다. 비용: 새 사용자·평가가 적은 사용자는 학습이 어렵고 모델 개수·학습·운영 부담이 늘어난다. 사용자별 모델만으로 성능이 더 좋다는 보장은 없다.

## 5. 사용자 피드백을 반영하는 속도

- [ ] **5A — 일정 주기로 모델과 개인 특징을 함께 갱신.** 장점: 운영이 단순하고 재현하기 쉽다. 비용: 방금 평가한 내용이 다음 갱신까지 반영되지 않을 수 있다.
- [x] **5B — 모델은 주기적으로 학습하고 개인 이력 입력은 즉시 갱신(추천).** 장점: 새 평가를 다음 예측의 입력에 활용하면서 학습 비용을 제어한다. 비용: 입력 갱신과 모델 버전의 일관성 관리가 필요하다. 매 요청마다 모델 가중치를 재학습하는 방식은 아니다.
- [ ] **5C — 평가마다 모델 파라미터를 온라인 갱신.** 장점: 학습 상태 자체를 빠르게 바꿀 수 있다. 비용: 중복·동시 요청·불안정한 데이터·롤백과 재현을 처리해야 하고 온라인 학습 가능한 모델을 선택해야 한다. 모든 모델이 같은 방식으로 지원하지 않는다.

주기·최소 데이터·품질 기준은 선택 후 하나의 구현 계약으로 정리한다. [AWS도 모델 재학습과 지원 레시피의 실시간 이벤트 반영을 구분한다](https://docs.aws.amazon.com/personalize/latest/dg/how-new-data-influences-recommendations.html). 이 제품 기능을 자체 모델에 자동으로 제공된다고 가정하지 않는다.

## 6. 예측을 실행할 위치

- [x] **6A — 현재 백엔드가 학습된 모델을 읽어 예측하고 학습은 별도 작업으로 실행(추천).** 장점: 새 네트워크 서비스 없이 시작할 수 있다. 비용: API 프로세스의 메모리·CPU와 모델 버전 교체를 관리해야 한다. API 요청 안에서 학습하지 않는다.
- [ ] **6B — 독립 추천 서버로 예측 분리.** 장점: API와 모델을 독립적으로 확장·교체할 수 있다. 비용: 별도 배포·통신 지연·장애·운영 책임이 추가된다. 외부 유료 제품이나 특정 인프라 사용을 함께 선택한 것은 아니다.

## 7. 데이터 부족 또는 모델 장애 시

- [x] **7A — 인증·제외 조건 확인 후 기존 추천을 대체 경로로 사용(추천).** 장점: 학습 자료나 모델이 준비되지 않아도 기본 추천을 제공할 수 있다. 비용: 모델 추천과 대체 추천을 구분해서 기록·검증해야 한다. 새 사용자는 이력이 없더라도 공용 모델의 다른 입력으로 예측 가능한지 먼저 확인한다.
- [ ] **7B — 모델을 사용할 수 없으면 추천을 거절.** 장점: 학습형 추천만 제공한다는 동작이 명확하다. 비용: 데이터 부족·모델 문제로 서비스 이용이 막힐 수 있다.

7A는 인증 없는 추천으로의 우회가 아니다. JWT 인증이나 DB의 제외 조건 조회가 실패하면 오류로 처리한다. 실제 데이터가 없는데 합성 데이터로 학습한 결과를 검증된 개인화 성능으로 표시하지 않는다.

## 8. 오래된 평가의 영향

- [ ] **8A — 모든 시기의 유효 평가를 같은 무게로 사용.** 장점: 단순하고 오래된 취향을 보존한다. 비용: 취향이 바뀌었을 때 오래된 기록의 영향이 오래 남을 수 있다.
- [x] **8B — 최근 평가를 더 중요하게 반영(추천).** 장점: 변하는 취향에 적응할 수 있다. 비용: 시간 특징·가중 방식·기간을 검증해야 하며 최근의 일시적 선택을 과하게 반영할 수 있다. 이력을 삭제하는 정책은 아니다.

추천은 [Netflix의 최근 행동 반영 사례](https://help.netflix.com/en/node/100639)를 참고한 제안이며 특정 감쇠 기간을 승인한 것은 아니다.

## 9. 새 선택 목록에 없는 기존 제외 항목이 발견될 때

- [ ] **9A — 기존 항목으로 표시해 유지·삭제만 허용(추천).** 장점: 기존 제외를 유지하면서 새 등록은 D07·D08의 목록으로 제한할 수 있다. 비용: 기존 항목과 신규 코드 항목의 조회·저장 호환 처리가 필요하다. 기존 키워드의 제외 효과도 유지한다.
- [x] **9B — 기존 값을 정식 항목과 대응시킨 뒤 편집 허용.** 장점: 코드 기반으로 통일할 수 있다. 비용: 대응이 불명확한 항목은 확인 작업이 필요하고 편집 가능 시점이 늦어진다. 확인 전 값은 보존하며 임의 대응·삭제하지 않는다.

실제 운영 데이터에 해당 값이 있는지는 미확인이다. 새 알레르기·섭취 불가 항목을 자유 입력하게 바꾸는 선택은 아니다.

## 10. 기존 요청 본문의 user_id 호환 처리

- [x] **10A — 사용자 번호 필드를 요청에서 제거하고 보내면 거절.** 장점: JWT가 본인 확인의 유일한 입력이라는 계약이 단순하다. 비용: 기존 프론트·테스트를 동시에 수정해야 한다.
- [ ] **10B — 과도기에는 JWT와 같으면 허용하고 다르면 거절(추천).** 장점: 기존 호출 수정 부담을 줄이면서 서버는 JWT에서 확인한 사용자만 사용한다. 비용: 호환 필드와 제거 계획을 관리해야 한다. JWT 없이 사용자 번호만 보내는 요청은 계속 거절한다.

## 선택 후 한 번에 검토할 구현 계약

- 모델 입력·학습 정답·결과·모델 버전·데이터 기준 시점과 사용자 격리를 명시한다. 학습 결과는 과거 데이터의 시간 순서를 지킨 평가와 실제 조건 위반·중복·수정·장애 검증을 거쳐 적용하도록 구체적인 초안을 제시한다.
- 중복 작업 번호·트랜잭션·요청/응답·오류·식사 스냅샷·기존 비인증 질문 상태·재료 코드 매핑은 확정된 정책 안의 구현 계약으로 묶어서 검토한다. 제품 동작·보존 범위를 바꾸는 미결정 항목이 있으면 보류로 표시한다.
- 기존 비선호 자유 입력, 데이터 원본 보존, 강제 제외와 후보 없음, 방·계정 이관 범위는 이번 체크리스트의 추천만으로 바꾸지 않는다.
- 실제 사용자 수·평가 수·트래픽·성능 요구·운영 환경을 아직 검증하지 않았다. 모델 종류별 우열, 학습 시점이나 A/B 시험 가능성을 미리 보장하지 않는다.
- 이 10개를 선택했다고 구현 완료가 되는 것은 아니다. 선택과 보류를 정리한 뒤 구체적인 설계·검증 계획과 작업 범위를 제시한다. 코드 적용·배포·원격 이슈 게시를 자동 승인한 것으로 해석하지 않는다.

응답 양식: `1: A / 2: 보류 / 3: B ...` 또는 원하는 번호만 응답. `질문: 2번 모델 차이`처럼 질문과 선택을 함께 보내도 된다.

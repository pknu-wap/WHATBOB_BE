# 주문서 질문과 메뉴 다양성

## 적용

수정한 코드를 배포한 환경에서 다음 명령을 실행한다. 기존 메뉴·추천·피드백을 삭제하지 않고 식사 후보를 추가·갱신하고 질문에 `any`를 추가한다. 외부 LLM은 호출하지 않는다.

```bash
python -m scripts.seed_menus --meals-only --no-llm
```

이 명령은 기존 프로젝트 방식인 `Base.metadata.create_all`로 신규 `question_selection_states` 테이블도 생성한다. 테이블 생성 권한이 필요하다. 메뉴 ID와 기존 추천·피드백 참조는 유지한다. 이후 백엔드를 재시작한다. DB를 초기화하거나 기존 테이블을 삭제할 필요는 없다.

`--questions-only`는 메뉴를 추가하지 않으므로 햄버거·피자 복구에는 위 명령을 사용한다. `--max-menus`를 주면 전체 식사 후보가 적재되지 않을 수 있으므로 생략한다. 기존 DB에 이미 저장된 음료·디저트는 이 명령으로 삭제하지 않는다.

공유 파일만 재생성할 때는 다음을 사용한다. DB·외부 API에 접근하지 않는다.

```bash
python -m scripts.export_recommend_data
```

## 프론트 연동

- 질문 조회, 추천 요청, 피드백 요청에 서비스 JWT를 `Authorization: Bearer <token>`으로 보낸다. 로그인 사용자의 질문 순환 상태와 최근 추천·싫어요를 연결한다. JWT가 있으면 본문 `user_id`는 생략할 수 있으며 다른 사용자 ID를 함께 보내면 403이다. 유효하지 않은 Bearer 토큰은 401이다.
- 기존 토큰 없는 추천 요청도 유지한다. 기존 `user_id` 연동은 그대로 지원하지만 로그인 연동에는 JWT를 사용한다. 익명 추천은 메뉴 종류 중복 제거·추첨이 적용되며 사용자별 최근 메뉴·싫어요 반영은 사용자 식별이 필요하다.
- `GET /api/recommendations/order-sheet/questions`는 매번 새로 요청한다. 응답은 `Cache-Control: no-store`다. 이전 응답을 프론트 상태에 계속 재사용하면 화면은 바뀌지 않는다.
- 익명 질문 조회는 `question_session` HttpOnly 쿠키로 브라우저별 상태를 구분한다. 다른 출처의 API에 요청할 때 `fetch(..., { credentials: "include" })` 또는 Axios `withCredentials: true`가 필요하다. HTTPS에서는 `Secure; SameSite=None`, HTTP에서는 `SameSite=Lax`다. 쿠키 차단·삭제 또는 전송 생략 시 익명 질문 상태가 새로 시작할 수 있다.
- `options` 전체를 렌더링한다. 두 취향 답변 뒤 세 번째 선택지 `{ "option_id": "any", "label": "상관없어요", "rules": [] }`가 추가됐다. `options.slice(0, 2)`처럼 두 개만 표시하지 않는다. 기존 두 취향 선택지 ID와 질문 ID는 유지한다.
- `any`도 일반 답변처럼 `answers[].option_id`에 전송한다. 메뉴 점수는 0점 추가, 질문 일치 목록과 질문 중요도 학습에서는 제외한다. 전부 `any`인 경우에도 제외 조건을 지킨 후보에서 다양한 종류를 추천한다.
- `recommended_menus`의 실제 개수로 렌더링한다. 같은 기본 메뉴 종류는 한 번에 하나만 반환하므로 종류가 부족하면 `top_k`보다 적게 반환할 수 있다.

## 선택 기준

- 햄버거·버거·피자·피자빵·샌드위치·핫도그·토스트·또띠아와 코드에 정의된 식사용 빵류는 `main_meal`로 포함한다. 케이크·과자·음료를 통째로 복구하지 않는다.
- 알레르기·섭취 불가·명시적 비선호 및 요청 제외 조건은 점수 계산 전에 적용한다. 다양성을 이유로 제외 음식을 복구하지 않는다.
- 상위 7개 질문은 서로 다른 주제의 중요도 상위 질문이다. 탐색 2개는 상위 주제를 제외하고 직전 탐색 주제를 뒤로 미룬 후 덜 나온 주제부터 가중 추첨한다. 남은 주제가 부족하면 필요한 만큼 직전 주제를 재사용하며, 한 요청 안의 주제는 중복시키지 않는다. 질문 조회 시 노출 횟수를 증가시키고 답변 제출 시에는 이중 증가시키지 않는다.
- 메뉴는 기본 이름을 기준으로 종류를 묶는다. 버거/햄버거 등 동의어도 합친다. 피자 상품이 수천 개여도 종류를 먼저 추첨하므로 후보 개수만으로 추천을 독점하지 않는다.
- 답변 일치 점수를 바탕으로 선택하고, 로그인 사용자의 최근 3회 추천 종류에 회당 총 답변 가중치의 10%, 가장 최근 평가가 싫어요인 개별 메뉴에 35%의 순위 패널티를 적용한다. 이후 같은 메뉴에 좋아요를 누르면 싫어요 패널티를 해제한다. 싫어요는 영구 제외 설정과 다르다.
- 조정 점수가 최고점의 일정 범위(총 답변 가중치의 10%) 안인 종류를 추첨하고, 그 종류 안에서도 같은 범위의 메뉴를 추첨한다. 동점에서 작은 ID가 계속 이기는 정렬을 제거한다. 이 비율은 `app/recommend/variety.py` 상수로 관리한다.
- 응답의 `match_score`는 원래 답변 일치 점수다. 최근 노출·피드백 패널티를 뺀 내부 점수와는 다르며, 결과가 `match_score` 내림차순일 필요는 없다. 답변에 맞지 않는 메뉴까지 같은 빈도로 노출하는 방식은 아니다.
- 피드백의 `selected_menu_id`는 해당 추천 결과에 포함된 ID여야 한다. 생략하면 기존처럼 첫 번째 결과를 평가한다. 추천 요청과 피드백의 사용자 ID가 다르면 400이다.

## DB

- 추가 테이블: `question_selection_states`.
- 컬럼: `scope_key`(문자열 기본키), `last_clusters`(직전 탐색 주제 JSON), `topic_counts`(주제별 탐색 횟수 JSON), `updated_at`.
- 기존 메뉴·질문·추천·피드백 테이블 구조 변경과 별도 마이그레이션 파일은 없다. 서버 시작 또는 위 시드 명령의 `create_all`을 사용한다.
- 익명 상태는 무작위 브라우저 식별자이며 프로필·토큰·답변 내용은 저장하지 않는다. 장기간 운영 시 `updated_at`을 기준으로 오래된 익명 상태를 정리할 수 있다.

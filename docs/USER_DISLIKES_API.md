# 로그인 사용자의 비선호 음식 API

## 인증

모든 요청에 카카오 로그인 후 백엔드가 발급한 서비스 JWT를 전달한다.

```http
Authorization: Bearer <서비스 JWT>
```

사용자 ID는 JWT의 `sub`로 확인한다. 요청 본문에 `user_id`를 보내지 않는다. 토큰 누락·무효·만료·사용자 부재는 401이다. 기존 프로필 조회 `GET /api/users/me`의 응답은 변경하지 않는다.

## 목록 조회

```http
GET /api/users/me/dislikes
```

200 응답 예시:

```json
{
  "success": true,
  "data": {
    "items": [
      { "id": 12, "keyword": "피자" },
      { "id": 13, "keyword": "홍어" }
    ],
    "total_count": 2
  },
  "message": null
}
```

아직 설정하지 않았다면 `items: []`, `total_count: 0`이다. 로그인 사용자의 `DISLIKE` 항목만 반환한다. 알레르기·섭취 불가 항목과 다른 사용자의 정보는 포함하지 않는다. 응답은 `Cache-Control: no-store`다.

## 목록 전체 저장·수정

```http
PUT /api/users/me/dislikes
Content-Type: application/json
```

```json
{
  "keywords": ["피자", "홍어"]
}
```

- 화면에서 최종 선택된 **전체 목록**을 전송한다. 기존 목록에 추가만 하는 API가 아니다. 위 요청을 저장하면 기존 비선호 중 피자·홍어 외 항목은 해제된다.
- 응답은 200이며 목록 조회와 같은 형식으로 최종 저장된 목록을 반환한다. 유지된 항목의 ID는 유지하고, 새 항목에는 새 ID를 발급한다.
- `{"keywords": []}`는 비선호 목록 전체 해제다. `keywords` 필드를 생략하면 422다.
- 요청은 최대 100개 항목이며 각 항목은 앞뒤 공백 제거 후 1~100자의 문자열이어야 한다. 공백만 있는 문자열, 숫자, null, 잘못된 필드 등은 422로 거부한다.
- 공백 제거 후 동일한 키워드는 영문 대소문자를 구분하지 않고 한 번만 저장한다. 예: `[" 피자 ", "피자", "ABC", "abc"]`는 `["피자", "ABC"]`가 된다.
- 본인의 `DISLIKE`만 변경한다. 같은 키워드의 `ALLERGY`·`UNABLE` 설정과 다른 사용자의 설정은 유지한다.
- 저장 실패 시 변경 전체를 롤백한다. 같은 사용자에 대한 목록 저장·개별 삭제는 사용자 행 잠금으로 직렬화한다. 나중에 완료된 전체 저장이 최종 목록을 결정한다.

## 항목 하나 삭제

조회 응답의 `items[].id`를 사용한다. 메뉴 ID나 카카오 ID가 아니다.

```http
DELETE /api/users/me/dislikes/12
```

성공하면 본문 없는 204다. 존재하지 않는 항목, 다른 사용자의 항목, 알레르기·섭취 불가 항목은 모두 404다. 양의 정수가 아닌 경로 ID는 422다.

## 추천과의 연결

저장 후 다음 `POST /api/recommendations/order-sheet` 요청에도 같은 서비스 JWT를 전달하면 본인의 비선호가 자동 적용된다. 추천 요청마다 비선호 키워드를 다시 보낼 필요는 없다.

기존 추천 제외 로직은 키워드를 원본 메뉴 이름·기본 이름·분류·주재료·알레르기 태그와 대소문자 구분 없는 부분 문자열로 비교한다. 예를 들어 `피자`를 저장하면 해당 원본 정보에 `피자`가 포함된 후보를 제외한다. 메뉴 ID 목록이나 의미 기반 검색이 아니므로 실제 저장할 키워드는 이 규칙을 고려해 정한다.

비선호를 삭제해도 동일한 음식을 별도의 알레르기·섭취 불가 설정이나 추천 요청의 `exclusions`로 제외했다면 계속 제외된다. 제외 후 후보가 없으면 기존과 같이 404이며 제외 조건을 임의로 해제하지 않는다.

추천 결과의 좋아요·싫어요 피드백은 순위 조정용이다. 이 API로 관리하는 비선호 목록에 자동 등록하거나 삭제하지 않는다.

## 배포와 검증

기존 `user_food_exclusions` 테이블을 재사용한다. 테이블·컬럼 변경, 데이터 재적재, 추가 환경 변수는 없다. 수정한 백엔드를 배포·재시작하면 사용 가능하다. 운영 DB에 기존 테이블이 없다면 프로젝트의 서버 시작 `Base.metadata.create_all`이 필요하다.

`python -m pytest -q tests/test_user_dislikes.py`로 JWT 인증, 본인 데이터 격리, 입력 경계, 전체 저장·개별 삭제, 다른 제외 유형 보존, 실패 시 롤백, 다음 추천 제외 및 해제를 확인한다. 현재 검증은 인메모리 SQLite이며 운영 MySQL·프론트 화면·동시 요청 검증은 별도다.

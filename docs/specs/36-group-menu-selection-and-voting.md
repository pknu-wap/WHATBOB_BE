# 같이 고르기: 개인 추천 후보와 복수 선택 투표 개발 명세

- 기준일: 2026-11-15
- 원본 요청: [#36 같이 고르기 로직 추가](https://github.com/pknu-wap/WHATBOB_BE/issues/36)
- 게시된 개발 명세: [GitHub #43](https://github.com/pknu-wap/WHATBOB_BE/issues/43)
- 상태: 합의된 요구사항의 개발 명세. 2026-11-15 사용자가 제안한 검증 경계를 확인했다. Q19·Q20은 보류 상태다.
- 개발 상태: 명세 작성 단계이며 기능 구현·테스트·배포 완료를 의미하지 않는다.
- 결정 상태: Q19(결과 이후 다시 고르기)·Q20(추가 제외 조건)은 사용자 요청에 따라 계속 보류한다. 지원 또는 미지원으로 간주하지 않는다.

## Problem Statement

여러 사람이 함께 식사 메뉴를 정할 때 각자의 취향과 먹을 수 없는 음식을 고려하면서도, 모두가 받아들일 메뉴를 간단히 결정할 방법이 필요하다. 현재 서비스는 방 생성·참여·완료 여부·퇴장·재접속을 관리하지만, 개인 주문서 답변에서 나온 추천을 방의 후보로 모으거나 투표로 결과를 정하는 흐름은 제공하지 않는다.

참여자는 카카오 로그인 없이도 UUID 사용자로 이용하고, 기존 주문서 경험을 사용해 각자의 후보를 제안한 뒤 복수 선택 투표로 최다 득표 메뉴를 확인하고 싶다. 연결 단절이나 중도 퇴장으로 참여자가 바뀌어도 방장은 계속 진행할지 취소할지 결정할 수 있어야 한다.

## Solution

방장이 최소 두 명의 참여자를 모아 같이 고르기 라운드를 시작한다. 시작 시 참여 인원과 참여자 전원의 저장된 알레르기·섭취 불가·비선호 조건을 고정한다. 각 참여자는 기존 개인 주문서 질문에 답하고, 공통 제외 조건을 적용한 본인 추천의 첫 번째 메뉴 하나를 같이 고르기 후보로 제공한다.

정확히 같은 메뉴는 후보 하나로 합친다. 전원 주문서 제출이 완료되면 자동으로 투표를 시작한다. 각 참여자는 자기 후보를 포함해 하나 이상, 전체 후보까지 복수 선택할 수 있고 선택한 후보마다 한 표를 준다. 전원 투표 전에는 자신의 선택을 수정할 수 있다. 전원이 제출하면 각자의 최신 선택으로 집계하고 메뉴 하나를 확정한다. 최다 득표가 동률이면 해당 메뉴 중 하나를 같은 확률로 뽑는다. 후보가 하나뿐이면 투표 없이 해당 메뉴를 결과로 표시한다.

결과 확정 전 일반 참여자의 퇴장이 확정되면 진행을 멈추고 방장에게 제외 후 계속 진행할지 묻는다. 계속 진행하면 남은 사람의 주문서를 유지하고, 이미 투표 중이었다면 후보를 정리해 새 투표 회차로 다시 투표한다. 취소하면 대기실로 돌아간다. 두 명 미만이면 인원 부족으로 라운드를 취소한다.

## User Stories

1. As a UUID 사용자, I want 카카오 로그인 없이 인증된 사용자로 방에 참여하기, so that 별도 회원가입 절차 없이 친구와 메뉴를 정할 수 있다.
2. As a 방장, I want 기존 방 생성과 초대 링크를 이용하기, so that 참여자를 같은 대기실로 모을 수 있다.
3. As a 방장, I want 두 명 이상일 때 라운드를 시작하기, so that 혼자 진행하는 상황을 방지할 수 있다.
4. As a 참여자, I want 방장만 라운드를 시작할 수 있기, so that 참여 준비 중 다른 사람이 임의로 진행하지 못한다.
5. As a 참여자, I want 시작 시 이번 라운드의 참여 인원이 확정되기, so that 추천과 투표 대상이 일관되게 유지된다.
6. As a 초대받은 사용자, I want 진행 중인 라운드의 신규 참여가 거절됐음을 안내받기, so that 참여하지 못한 이유를 알 수 있다.
7. As a 기존 참여자, I want 연결이 끊겨도 재접속 유예 안에 같은 라운드로 복귀하기, so that 진행 중인 내용을 잃지 않는다.
8. As a 참여자, I want 본인의 질문 선택 이력을 반영한 기존 주문서 질문을 받기, so that 개인 추천과 같은 방식으로 취향을 표현할 수 있다.
9. As a 참여자, I want 다른 사람과 질문이 다를 수 있기, so that 각자의 이력에 맞는 질문으로 답할 수 있다.
10. As a 참여자, I want 제출 전 주문서 답변을 편집하기, so that 실수한 답변을 고칠 수 있다.
11. As a 참여자, I want 제출한 주문서가 확정되기, so that 이후 후보 생성 중 답변이 바뀌지 않는다.
12. As a 참여자, I want 모든 참여자의 저장된 제외 조건을 내 추천에도 적용하기, so that 다른 참여자가 제외한 메뉴를 공동 후보로 제안하지 않는다.

14. As a 참여자, I want 진행 중 변경한 개인 제외 설정은 다음 라운드부터 적용된다는 안내를 받기, so that 이번 추천에 반영된 조건을 이해할 수 있다.

## Implementation Decisions

### 확정된 제품 규칙

- **후보 선정:** 각 참여자의 개인 주문서 추천 응답 첫 메뉴를 사용한다. 현재 첫 메뉴는 단순 최고 점수와 다를 수 있다. 주문서 알고리즘 자체를 이번 요구만으로 변경하지 않는다.
- **공통 제외:** 시작 시 참여자 전원의 저장된 알레르기·섭취 불가·비선호 조건을 합쳐 라운드 기준으로 고정한다. 개인 설정의 후속 변경은 다음 라운드부터 적용한다. 원래 개인 모드에서의 첫 추천과 달라질 수 있다.
- **중복:** 정확히 같은 메뉴를 한 후보로 합치고, 중복 때문에 후보가 줄어도 차순위 메뉴로 채우지 않는다. 이름이 비슷한 서로 다른 메뉴를 음식 종류 단위로 합치는 정책까지 승인된 것은 아니다.
- **질문:** 기존 개인 질문 선택 로직과 사용자별 이력을 활용한다. 참여자별 질문이 달라도 된다.
- **시작과 참여:** 방장만 대기실에서 최소 두 명으로 시작한다. 시작 후 신규 참여는 거절하고 기존 참여자의 유예 내 재접속은 허용한다.
- **투표:** 한 사람은 현재 후보 중 최소 하나부터 전체 후보까지 선택한다. 자기 후보 선택을 허용한다. 한 사람이 같은 후보에 줄 수 있는 표는 하나다. 빈 투표·기권은 허용하지 않는다.
- **제출 확정:** 주문서는 제출 후 수정할 수 없다. 투표는 전원 제출 전까지 같은 제출 API에 새로운 후보 목록을 보내 교체할 수 있다. 현재 저장된 투표와 같은 선택을 다시 보내면 기존 제출 상태를 반환한다. 결과 확정 후 다른 후보 목록을 보내면 `409 VOTE_ALREADY_SUBMITTED`를 반환한다.
- **자동 진행:** 전원 주문서 제출 후 투표를 시작하고 전원 투표 제출 후 결과를 확정한다. 후보가 하나면 투표 없이 결과로 진행한다.
- **결과:** 전원 제출 시 각 참여자의 최신 선택으로 집계한다. 최다 득표 메뉴가 하나면 그 메뉴를 확정하고, 여러 개면 그중 하나를 같은 확률로 뽑아 저장한다. 방 조회와 실시간 알림의 `winners` 배열에 같은 메뉴 하나를 반환한다. 단일 후보 무투표 결과의 득표수는 `null`이다.
- **공개 범위:** 투표 중에는 제출 인원만 공개한다. 확정 후에는 메뉴별 실제 득표수와 최종 메뉴를 공개한다. 개인의 투표 내용은 본인만 확인할 수 있다.
- **후보 없음:** 공통 제외 후 추천 가능한 메뉴가 없으면 사유를 안내하고 라운드를 취소해 대기실로 돌아간다. 제외 조건을 임의로 완화하지 않는다.
- **시간:** 주문서·투표의 별도 제한 시간은 없다. 기존 방 만료와 연결 유예 정책은 유지한다.

### 퇴장과 라운드 일시 정지

- 결과 확정 전 일반 참여자의 명시적 퇴장 또는 60초 유예 만료 시 방장에게 퇴장 사실과 계속 진행 여부를 알린다.
- 방장 결정 대기 중 작성·제출 내용은 보존하고 주문서·투표의 추가 제출 및 자동 단계 전환을 막는다. 다른 참여자는 결정 대기 상태를 확인할 수 있어야 한다.
- **예:** 퇴장자를 제외하고 남은 사람의 주문서를 유지한다. 후보가 생성됐다면 퇴장자만 제안했던 후보를 제거하고 남은 사람도 제안한 동일 후보는 유지한다. 투표 중이었다면 기존 표를 초기화하고 새 투표 회차에서 남은 사람 전원이 다시 투표한다.
- **아니요:** 라운드를 취소하고 남은 참여자와 대기실로 돌아간다. 퇴장자를 복귀시키지 않는다.
- 두 명 미만이 되면 계속 진행 선택 대신 인원 부족을 안내하고 라운드를 취소한다.
- 단순 연결 단절은 바로 퇴장으로 간주하지 않는다. 복수 탭 중 마지막 연결이 끊긴 시점부터 기존 유예를 적용하고, 유예 내 재접속 시 참여·제출 상태를 유지한다.
- 방장의 명시적 퇴장·유예 만료와 방 자체 만료는 기존 방 종료 정책을 따른다.
- 퇴장으로 재투표가 시작되면 회차가 바뀌고 기존 선택을 초기화한다. 투표 수정은 현재 회차의 선택에 적용된다. 이전 회차 요청은 거절한다.

### 모듈 책임과 데이터 요구

- **방·라운드:** 기존 방 생명주기와 라운드 진행 단계를 구분한다. 라운드는 참여자, 공통 제외 조건, 단계, 일시 정지 사유, 퇴장 결정 대기와 투표 회차를 DB에 보존한다.
- **개인 질문·추천:** 기존 질문·점수·개인화·다양성 선택 기능을 활용하면서, 본 라운드의 고정된 공통 제외 조건을 적용할 수 있는 경계를 제공한다. 나중에 사용자의 최신 개인 추천을 임의로 가져오는 방식으로 연결하지 않는다.
- **제출:** 참여자·라운드별 답변과 그 답변으로 생성된 추천을 연결한다. 완료 표시만으로 답변 제출을 대신할 수 없다.
- **후보:** 원본 메뉴와 제안한 참여자들을 연결해 보존한다. 이는 동일 후보 병합과 퇴장 후 후보 유지 판단에 필요하다.
- **투표·결과:** 라운드·회차·사용자 단위로 제출을 구분하고, 확정된 결과와 단일 후보 무투표 여부를 보존한다. 집계는 후보별 실제 유효 표만 사용한다.
- **인증·권한:** 기존 Bearer 인증을 재사용한다. 라운드 명령·상세 상태·후보·결과는 참여자 권한을 확인하고, 시작·퇴장 후 결정은 방장 권한을 확인한다. 요청 본문의 임의 사용자 식별자를 본인 확인 수단으로 사용하지 않는다.
- **일관성:** 기존 사용자·세션·방 잠금 순서를 존중한다. 참여자 변경, 제출 확정, 단계 전환, 후보 갱신, 집계는 서로 충돌해 중복 결과가 생기지 않게 처리한다.
- **복구:** 라운드의 진실은 DB에 두고 기존 단일 API 프로세스 운영 조건을 유지한다. 연결 관리자나 알림 수신 여부만으로 현재 단계를 판단하지 않는다.
- **정리·마이그레이션:** 명시적 퇴장뿐 아니라 지연 만료 처리·예약 작업·주기 정리·늦은 재접속·계정 전환 전 정리에서도 같은 라운드 규칙이 적용돼야 한다. 방 종료·삭제·재시작 복구와 새 데이터의 참조 정리를 함께 검증한다. 기존 데이터 전환은 명시적 마이그레이션으로 수행한다.

### 프론트 연동 요구

- 대기실 시작, 주문서, 후보 복수 선택, 제출 완료 대기, 방장 결정 대기, 결과를 구분해 표시한다.
- 인증 준비를 완료한 후 현재 사용자로 요청하고, 재연결 시 현재 라운드 상태를 조회해 화면을 복원한다.
- 시작 후 신규 참여 거절, 제외 조건 고정, 최소 인원, 후보 없음, 취소와 방 종료 사유를 안내한다.
- 방장에게 퇴장자와 예/아니요 선택을 표시하고, 일반 참여자에게는 결정 대기 상태를 표시한다.
- 새 투표 회차가 시작되면 이전 선택·제출 완료 표시를 초기화한다. 단일 후보 결과에는 투표 화면을 표시하지 않는다.
- 중간 득표수·다른 사람의 개별 표를 화면·응답·알림 어디에서도 노출하지 않는다.
- Q19·Q20에 해당하는 화면·요청의 지원 여부는 보류 결정 후 정한다.

## Testing Decisions

### 검증 경계와 확인 상태

- **사용자 확인 완료:** 2026-11-15 사용자가 인증된 REST API와 방 WebSocket을 외부 동작 경계로 삼아 검증하고, 격리 MySQL 환경에서 동시성·마이그레이션을 보완하는 기준을 확인했다.
- 테스트는 실제 사용자 명령·응답·상태 조회·이벤트로 관찰되는 행동을 검증한다. 내부 함수 호출 순서나 구현을 그대로 복제하는 테스트는 작성하지 않는다.
- 기존 인증된 방 요청, 개인 주문서 요청, WebSocket 연결·유예·방 종료 테스트의 선례를 활용한다. 신규 라운드도 가능한 한 같은 높은 경계에서 검증한다.

### 검증 대상과 시나리오

1. **방·라운드:** 방장만 시작, 최소 두 명, 시작과 동시 참여의 인원 일관성, 시작 후 신규 참여 거절, 상태 재조회.
2. **질문·공통 제외:** 개인별 기존 질문 이용, 시작 시점 설정 고정, 전원 제외 조건 적용, 첫 메뉴 후보, 중복 후보 병합과 제안자 보존.
3. **자동 진행·결과:** 전원 제출 후 단계 전환, 복수 선택·자기 후보·한 후보당 한 표, 최다 득표 동률에서 메뉴 한 개 확정, 단일 후보 무투표, 후보 없음 취소.
4. **권한·비공개:** 비참여자의 신규 상세 정보 접근 차단, 일반 참여자의 방장 명령 거절, 투표 중 득표수·개인별 표 비공개, 결과의 집계 공개.
5. **투표 수정·재전송:** 전원 제출 전 수정 및 최신 선택 집계, 확정 후 변경 요청 거절, 동일 제출 재시도, 중복 표, 지난 라운드·투표 회차 요청 거절, 마지막 제출 재전송 시 결과 유지.
6. **연결·퇴장:** 마지막 연결 종료에만 60초 유예, 유예 내 복귀, 명시적·유예 만료 퇴장, 방장 결정 대기 중 제출·전환 차단과 내용 보존, 예/아니요, 후보 기여자에 따른 유지·제거, 재투표, 최소 인원 취소.
7. **복구·회귀:** 알림 유실 후 상태 재조회, 서버 재시작 후 진행·일시 정지 복원, 기존 유예 연장 방지, 방장 종료·방 만료·삭제 정리, 기존 개인 추천·사용자 설정·방 인증과 계정 전환 제한 유지.

### 보완 검증과 한계

- SQLite 기능 테스트로 실제 MySQL 행 잠금과 동시 커밋의 안전성을 증명하지 않는다. 격리된 MySQL 환경이 있으면 시작과 참여, 마지막 답변·투표와 퇴장, 방장 결정과 추가 퇴장, 유예 만료와 재접속을 독립 세션으로 경합시킨다.
- 기존 방·참여·개인 기록을 보존하는 마이그레이션, 중단 후 재개·재실행, 참조·제약과 삭제 정리를 격리 스키마에서 확인한다.
- 사용할 수 없는 환경의 검증은 미실행으로 명시한다. 실제 프론트 브라우저 연결과 운영 서버 부하를 로컬 테스트만으로 완료했다고 보고하지 않는다.
- Q19·Q20 의존 시나리오는 미정 동작을 기대값으로 만들어 테스트하지 않는다.

## Out of Scope

- 기존 개인 주문서의 점수·학습·다양성 알고리즘 자체를 별도 개선하는 작업.
- 개인 추천 목록의 교집합으로 그룹 결과를 정하는 방식.
- 이름이 비슷한 변형 메뉴를 자동으로 음식 종류 단위까지 병합하거나 중복 후보를 차순위로 보충하는 기능.
- 한 참여자의 표에 더 큰 가중치를 주거나 방장에게 추가 표를 주는 기능.
- 동률 해소용 재투표, 빈 투표·기권, 결과 확정 후 투표 수정, 단계별 강제 제한 시간.
- 일반 참여자의 신규 강퇴 권한, 방장 이전, 기존 60초 유예·방 종료·계정 전환 제한을 바꾸는 작업.
- 그룹 결과를 개인 식사 기록이나 개인 평가로 자동 확정·저장하는 기능. 이는 논의·승인되지 않았으며 기존 개인 기록 흐름을 임의로 호출하지 않는다.
- 프론트 전체 화면 구현, 운영 DB 직접 변경·배포, 다중 API 프로세스·새 메시지 시스템 도입.
- **Q19·Q20은 범위 제외로 확정한 항목이 아니라 사용자 보류 항목이다.** 구현 범위를 정하기 전에 의존성을 명시하고, 독립적인 작업과 구분한다.

### 확정 규칙을 만족하기 위한 기술 제안

다음은 사용자에게 제품 선택으로 승인받은 항목이 아니라 구현 설계에서 구체화할 제안이다. 확정된 제품 규칙을 바꿀 근거로 사용하지 않는다.

- 기존 방 생명주기와 별도 라운드 단계를 두고, 현재 라운드·투표 회차·퇴장 결정 버전을 사용해 지연 요청을 구분한다.
- 시작, 현재 상태 조회, 개인 질문 조회, 주문서 제출, 투표 제출, 퇴장 후 방장 결정의 인터페이스를 제공한다. 구체 경로·필드·오류 코드는 구현 계약에서 정한다.
- 본문 없는 기존 완료 표시가 신규 라운드에서 답변 제출·권한·일시 정지 검증을 우회하지 못하도록 호환 방식을 정한다.
- WebSocket은 상태 변경 알림을 전달하고 REST 조회를 복구 기준으로 삼는다. 알림 실패가 이미 커밋된 제출이나 결과를 되돌리지는 않는다.
- 결정 대기 중 연속 퇴장이 발생하면 최신 퇴장 목록을 기준으로 방장이 결정하게 하고, 예전 목록에 대한 결정으로 추가 퇴장자를 누락하지 않게 한다. 구체적인 버전·재확인 UX는 구현 계약에서 정한다.
- 결과 확정 후 퇴장이 이미 확정된 집계를 소급 변경하지 않도록 결과의 확정 경계를 분명히 한다. 결과 이후 방 재사용과 상세 보존 계약은 Q19 결정에 따른다.
- 일시적인 DB·통신 실패와 정상적으로 확인된 추천 후보 없음을 구분한다. 일시 장애를 후보 없음·새 라운드 생성으로 숨기지 않는다.
- 기존 개발 방향에 적힌 교집합은 이번 사용자가 선택한 개인별 첫 후보·복수 선택 투표로 대체한다. 구현 단계에서 관련 개발 지침·API 문서도 최신 계약과 맞춘다.

### 문서와 게시 상태

- 이 명세의 요구사항은 현재 대화에서 확정한 Q1~Q18·Q21·Q22를 반영한다. Q19·Q20은 계속 보류다.
- 사용자가 확인한 검증 경계를 기준으로 프로젝트 이슈 트래커에 게시하고 준비 라벨을 적용한다. 준비 라벨은 확정된 범위의 작업을 위한 것이며 Q19·Q20 의존 작업의 차단 상태를 해제하지 않는다.
- 명세 작성은 기능 구현·마이그레이션 실행·테스트 성공·배포 완료를 뜻하지 않는다.

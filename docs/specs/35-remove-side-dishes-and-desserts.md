# #35 메뉴 삭제와 추천 점수 정리 명세

2026-11-19 개발 명세. 삭제 메뉴군, 연결 기록과 현재 추천 점수의 처리 범위를 합의했다. [GitHub 이슈 #35](https://github.com/pknu-wap/WHATBOB_BE/issues/35)

## 해결할 문제

메뉴 적재 목록과 DB에 남은 단독 반찬·디저트 및 사용자가 지정한 메뉴군이 식사 후보로 나올 수 있다. 해당 메뉴를 DB와 파일에서 삭제하고, 과거 기록과 현재 추천 점수를 정리하며, 이후 적재에서도 같은 메뉴가 다시 들어오지 않도록 한다.

## 합의한 범위

- 삭제 단위는 식품코드다. 기존 단독 반찬 554개와 디저트 1,948개에 조림 174개, 무침 225개, 겉절이 45개를 추가해 총 2,946개다. 장아찌로 끝나는 항목은 기존 목록에 포함돼 있다. [용어집](../../GLOSSARY.md) · [삭제 식품코드 목록](../../data/removed_side_dishes_and_desserts.csv)
- 원본 메뉴 이름에서 `_` 앞 기본 이름이 `조림`, `무침`, `겉절이`, `장아찌`로 끝나면 식품코드를 삭제 목록에 추가한다(Q9). `고등어조림_무`와 `골뱅이무침_채소_소면`이 해당한다. 닭볶음탕, 김치찌개, 햄버거, 피자, 과일샐러드는 유지한다.
- 메뉴 원본 CSV와 공유 메뉴 CSV·JSON에서 같은 식품코드 행을 제거한다. 이전 CSV로 적재해도 같은 코드를 건너뛴다. 개인 주문서, 완전 랜덤, 같이 고르기에서 해당 메뉴가 새 후보로 나오지 않아야 한다. [메뉴 적재 코드](../../scripts/seed_menus.py)
- 운영 DB에서 목록에 있는 `menus` 행과 해당 메뉴에 연결된 사용자 식사 기록, 추천 피드백 및 메뉴별 추천 기록을 삭제한다. 과거 추천 목록, 투표 선택, 같이 고르기 후보·제안자와 알림에서도 삭제 대상 항목을 제거한다. 삭제된 식사 기록이나 피드백을 돌려줄 수 있는 기존 재시도 응답도 지운다. 같은 기록에 있던 다른 메뉴의 항목은 유지한다. [DB 정리 스크립트](../../scripts/remove_side_dishes_and_desserts.py)
- 첫 메뉴가 삭제된 과거 추천은 남아 있는 메뉴가 명시된 평가만 저장한다(Q6). 사용자가 누른 평가가 다른 메뉴에 붙는 일을 막는다. 메뉴가 모두 삭제된 경우 추천 요청과 답변을 남기고 결과 목록을 비운다.
- 사용자가 같이 고르기 실행이 0회라고 확인했다. 기존 완료 결과를 위한 별도 화면 변경은 범위에서 제외한다(Q7). 실제 적용 시점에 삭제 대상이 포함된 진행 중 라운드가 발견되면 해당 실행을 중단하고 라운드 종료 후 다시 확인한다.
- 삭제 대상 피드백이 현재 추천 점수에 준 영향도 제거한다(Q8). 영향을 받은 질문의 긍정 횟수와 질문 가중치를 남은 유효 평가로 다시 계산한다. 삭제로 평가 근거가 없어진 질문은 초기 점수로 돌아간다. 점수에 반영될 수 있는 기록의 삭제와 활성 개인화 모델 파일이 함께 확인되면 파일을 보관 위치로 옮긴다. 다시 학습한 모델이 배포될 때까지 서비스는 DB에 남은 기록을 사용한다. [질문 가중치 계산](../../app/recommend/order_sheet.py) · [개인화 모델 학습](../../scripts/train_personal_model.py)

## 검증과 운영 반영

1. 확정된 메뉴군을 식품코드 목록과 파일에 반영한다. 삭제 대상 평가가 빠진 자료로 질문 통계와 추천 점수를 계산하고, 남은 평가가 반영되는지 확인한다. 과거 추천의 평가가 다른 메뉴에 저장되지 않는지 검증한다.
2. 로컬에서 원본·공유 메뉴 파일에 대상 코드가 0개이고, 예전 CSV로 적재할 때도 제외되는지 확인한다. 김치찌개·햄버거·과일샐러드 등 유지 대상과 혼합 기록의 다른 메뉴가 남아야 한다.
3. `fix/35-menu-cleanup`의 변경을 커밋하고 푸시한다. SSH 접속 후 서버에서 현재 체크아웃한 배포 브랜치와 백엔드 서비스를 확인한다. 배포 브랜치에 승인된 변경을 반영한 뒤 서버에서 `git pull`한다.
4. 서버 저장소에서 백엔드와 같은 환경 설정으로 `python -m scripts.remove_side_dishes_and_desserts`를 실행해 대상 메뉴·연결 기록 건수와 진행 중 라운드를 확인한다. 실제 DB 대상 수는 사전 조회 결과를 사용한다. 활성 개인화 모델의 유무를 확인한다.
5. 같은 메뉴에 새 요청이 기록되는 일을 막기 위해 백엔드 쓰기를 멈춘 상태에서 같은 명령에 `--apply`를 붙여 적용한다. 오류가 생기면 트랜잭션 전체가 롤백된다. 적용 후 사전 조회 명령을 다시 실행했을 때 `menus`가 `0`이어야 한다.
6. 백엔드를 다시 시작한다. 공개 API 응답, 정상 메뉴 조회, 개인 주문서·완전 랜덤·같이 고르기에서 삭제 대상이 나오지 않는지 확인한다. 적용된 커밋과 삭제 전후 건수를 기록한다.
